# Internationalisation

Every user-facing string goes through a shared key-based catalog. The app is
mid-migration onto it from three older inline patterns, held by a ratchet rather
than a clean line: new hardcoded strings fail, and the existing backlog is
grandfathered. See [D-52](../decisions/D-52.md) for the decision; this file is
the pattern and the playbook for converting a surface.

## Where things live

- **Registry** — `packages/shared/src/i18n/locales.ts`. One row per supported
  language (`tag`, `languageCode`, `label`, Accept-Language `match`). `AppLocale`
  derives from it. **To add a language, add a row here** and follow the compile
  errors.
- **Catalog** — `packages/shared/src/i18n/catalog.ts`: `strings[locale][key]`,
  one block per locale in the registry (today `es-MX`, `en`, `fr`). Web-only
  keys are namespaced `web.*`. The file's completeness assertion means every
  locale must define every key, or `tsc` fails.
- **Runtime** — `packages/shared/src/i18n/translate.ts`: `createT(locale)` →
  `t(key, vars)`, `{var}` interpolation. Framework-free.
- **Web wrappers**:
  - Server Components / route handlers: `getT()` from `@/lib/i18n`
    (`const t = await getT(); t("key")`).
  - Client Components: `useT()` from `@/components/locale-provider`
    (`const t = useT(); t("key")`).
  - Client-safe types/helpers (no `next/headers`): `@/lib/i18n-translate`.

## The three legacy patterns you'll be replacing

1. `translate({ en, "es-MX" }, locale)` — inline dicts (still supported for the
   last few call sites; prefer moving the string into the catalog).
2. `locale === "en" ? "…" : "…"` / `en ? "…" : "…"` ternaries — the common case.
3. Pure hardcoded Spanish with no English branch — auth (done), the admin area,
   and scattered strings.

## Migrating a surface — recipe

1. **Add keys** to `packages/shared/src/i18n/catalog.ts` in EVERY locale block
   (the completeness guard enforces all of them). Namespace web-only copy `web.<area>.*`;
   reuse an existing key when the copy genuinely matches.
2. **Swap the accessor.** Client Component → `const t = useT();`. Server
   Component → `const t = await getT();`. Replace each literal / ternary with
   `t("key")` (or `t("key", { name })` for placeholders).
3. **Attributes too** — `placeholder`, `title`, `alt`, `aria-label` etc. take
   `t("key")`.
4. **Regenerate the ratchet baseline**: `node scripts/i18n-guard.mjs --generate`
   (from `apps/web`). The migrated file should drop to 0 and leave the baseline.
5. **Protect it at edit-time** (optional but encouraged for fully-clean files):
   add the file to the `no-literal-string` glob in `apps/web/eslint.config.mjs`.
6. **Run** `pnpm --filter spiralclass-web typecheck && pnpm --filter spiralclass-web test`.

## The guardrails (why you can't just paste a Spanish string)

- **Ratchet test** — `apps/web/tests/i18n-guard.test.ts` (+ `scripts/i18n-guard.mjs`,
  baseline `scripts/i18n-guard.baseline.json`). Fails when a file adds
  user-facing JSX literals beyond its baseline, or a brand-new file has any. The
  count can only shrink. **Do not** hand-edit the baseline upward to dodge it.
- **ESLint `no-literal-string`** — `apps/web/eslint-rules/no-literal-string.mjs`,
  scoped in `eslint.config.mjs` to already-migrated files. Edit-time backstop.
- **Compile-time completeness** — adding a key to one locale without the other
  fails `tsc` in `packages/shared`.

## Four language fields per teacher, and why they must not be merged

This is the part worth reading even if you never migrate a string.

| Column                | Means                  |
| --------------------- | ---------------------- |
| `target_language`     | What she teaches       |
| `teaching_language`   | What she teaches _in_  |
| `locale`              | What _she_ reads       |
| `booking_page_locale` | What her _buyers_ read |

**All four are allowed to diverge**, and conflating a pair of them has broken
production twice ([D-72](../decisions/D-72.md),
[D-73](../decisions/D-73.md)). Teacher-facing copy resolves the viewer's own
locale — cookie, then Accept-Language, then `DEFAULT_LOCALE` (`en`).

**The public booking funnel (`/b/**`) renders in `booking_page_locale`, never in
the visitor's locale.** `publicFunnelLocaleFor()` resolves it, with
`PUBLIC_FUNNEL_LOCALE` (`en`) when she has not chosen; she sets it in
Settings → Booking page. Three renderings must agree and all three derive from
that one value: the server pages (`getPublicFunnelT`), the client half
(`b/[slug]/layout.tsx`) and the social card (`b/[slug]/opengraph-image.tsx`).

A per-visitor rule cannot work, and this is the concrete reason: **the social
card is generated with no visitor present.** Two wrong answers shipped before
this one — a hardcoded English, and deriving it from her own `locale`. The
second is falsified by the platform's Mexican teacher, who reads Spanish and
sells Spanish lessons to English speakers, so her buyers read English while she
reads Spanish. What her buyers read cannot be inferred from anything else on her
row.

## Where the remaining work is

Deliberately **not** listed here. A prose list of migrated files is a changelog
that rots; the authoritative, always-current list is
`apps/web/scripts/i18n-guard.baseline.json` — every file with a non-zero count
still has literals, and the count is what may only shrink.

Three things are worth knowing about the shape of that backlog:

1. **Files still hardcoded Spanish with no English branch are the only real
   user-facing gaps**, because an English-preferring user sees Spanish. Find them
   by scanning for Spanish diacritics with no `t(` or `translate(` nearby. This
   has already caught two live bugs — the "no online payment" branch on the buy
   page, and the invalid-link screen behind a notification-settings token.
2. **The `en ? … : …` ternary files are already bilingual**, so converting them
   is future-language readiness rather than a visible fix. Do them
   opportunistically, highest-traffic first.
3. **The admin area is low priority.** It is internal staff tooling and is
   already hardcoded _English_, not Spanish — converting it mostly adds Spanish
   for staff-only screens. Do it for consistency, not for launch value.

Nav labels already come from `packages/shared/src/nav.ts` (bilingual) — reuse
`navLabel()` rather than re-adding those strings to the catalog.
