# Internationalisation

Every user-facing string goes through a shared key-based catalog, and a literal
anywhere else fails the build. [D-72](../decisions/D-72.md) is the decision;
this file is the pattern.

## Where things live

- **Registry** — the rows are in `packages/shared/src/i18n/locale-registry.ts`,
  and everything derived from them in `locales.ts`. One row per supported
  language (`tag`, `languageCode`, `label`, `englishName`, Accept-Language
  `match`, the `intl` formatting tag, the `og` Open Graph locale, the writing
  direction `dir`, how a funnel shows the seller's own currency, and
  `launched`). `AppLocale` derives from it. **To add a language, add a row with
  `launched: false`** and follow the compile errors; flip it once a native
  speaker has read it and its legal translations exist (D-72). Until then it is
  in no picker, detector, URL or hreflang set. Reader-facing code lists
  `LAUNCHED_LOCALES`, never `LOCALES`
  (`apps/web/tests/i18n/launched-locales-usage.test.ts`). Anything that is one
  value per language belongs on the row, not in a dictionary beside its
  consumer.
- **A regional locale is a delta.** A second locale of one language (`es-ES`
  beside `es`) holds only the keys whose wording differs and falls back to its
  base, then `DEFAULT_LOCALE`, never to another language. `es` is written as
  Latin American Spanish and formatted as `es-419`. The delta type does not
  exist yet; build it before registering one.
- **Glossary** — `packages/shared/src/i18n/glossary.ts`. Per language: how the
  reader is addressed (`vous` in French, `tú` in Spanish), the one word for
  each thing (teacher, student, class, package, booking, availability), and
  the words that must never appear. `glossary.test.ts` fails a catalog that
  uses a forbidden word, or a glossary term the catalog does not use. Read it
  before translating anything, help guides included.
- **Catalog** — one file per locale, `packages/shared/src/i18n/catalog.<locale>.ts`
  (today `es`, `en`, `fr`), composed into `strings[locale][key]` by
  `catalog.ts`. `es` is the source key set. Web-only keys are namespaced
  `web.*`. The completeness assertion in `catalog.ts` means every locale must
  define every key, or `tsc` fails.
- **Country and language names** — `packages/shared/src/country-names.ts` and
  `languages.data.ts`, one column per locale. Both are typed by `AppLocale`, so
  a new locale does not compile until `node scripts/generate-locale-names.mjs`
  has added its column from CLDR. The names are static rather than asked of
  `Intl.DisplayNames` at render, because the server and the browser each carry
  their own CLDR and a name rendered on both could otherwise differ. The
  generator only adds a missing column; it never rewrites a shipped name.
- **Runtime** — `packages/shared/src/i18n/translate.ts`: `createT(locale)` →
  `t(key, vars)`, `{var}` interpolation. It imports every language, so it is
  **server-only in practice**; the catalog-free half (`createTFrom`,
  interpolation, plurals) is `translate-core.ts`.
- **Web wrappers**:
  - Server Components / route handlers: `getT()` from `@/lib/i18n`
    (`const t = await getT(); t("key")`).
  - Client Components: `useT()` from `@/components/locale-provider`
    (`const t = useT(); t("key")`).
  - Client-safe types/helpers (no `next/headers`): `@/lib/i18n-translate`.
- **Navigation labels** — `packages/shared/src/nav.ts` carries each item's
  label per locale; use `navLabel()` rather than adding those strings to the
  catalog.

### A browser loads one language

`<LocaleProvider>` (`@/components/locale-catalog`) loads the reader's catalog
behind its own `import()`, one module per language, so a French page downloads
French — about 125 kB gzipped instead of all three languages at 400 kB. Two
things undo that while still type-checking:

- **Client code reaching the full catalog.** `createT`, `strings`,
  `isStringKey` and `issueMessage` put every language back into a shared
  chunk, wherever they are called from, including a shared helper a form
  imports. A function a Client Component calls takes the reader's `t`, not a
  locale: `signInSchemaWith(useT())`, `planReasonText(reason, t)`. Words in a
  _second_ language (the booking-page preview speaks the buyers') are worded
  on the server and passed down as props.
- **Importing the per-language modules statically.** The bundler groups a
  layout's client components into one chunk whatever the page renders, so
  only `import()` separates them. A new language adds its module to
  `locale-catalog/` and a line to `loader.tsx`; the `Record<AppLocale, …>`
  there fails the typecheck until it does.

`apps/web/scripts/catalog-chunks.mjs` checks the built chunks after the
integration suite's production build: at most one language per chunk, and
every language in one.

## Adding copy

1. **Add the key** to every `catalog.<locale>.ts` (the completeness guard
   enforces all of them). Namespace web-only copy `web.<area>.*`; reuse an
   existing key when the copy genuinely matches.
2. **Read it through the accessor** — `const t = useT();` in a Client
   Component, `const t = await getT();` in a Server Component — and write
   `t("key")`, or `t("key", { name })` for placeholders. Attributes
   (`placeholder`, `title`, `alt`, `aria-label`) take `t("key")` too.
3. **Check**: `node scripts/i18n-guard.mjs` (from `apps/web`) lists every
   literal outside the catalog and should list none; then
   `pnpm --filter spiralclass-web typecheck && pnpm --filter spiralclass-web test`.

## Server actions and schemas

A server action answers in words, so it resolves a translator once and returns
`t("web.action.<area>.<name>")`. Three rules keep that honest:

- **A whole sentence is one key.** Never assemble one from pieces — a noun plus
  an `"s"`, a verb picked by a ternary. That works for the two languages it was
  written in and no others. Use a plural key (`<key>_one` beside `<key>`, chosen
  by passing `count`) and let the catalog hold each language's own sentence.
- **A schema's message is a catalog key, not a sentence.** A schema is a module
  constant: it is built once, with no request and so no reader, and a sentence
  written into one is in a single language for everybody. Write
  `z.string().min(3, "web.action.reasonTooShort")` and turn the first issue into
  words with `issueMessage(parsed.error, t, "web.action.invalidData")` from
  `@spiralclass/shared`. `apps/web/tests/i18n/schema-message-keys.test.ts`
  checks that every key-shaped string really is a key; it cannot see a
  sentence written where a key belongs.
- **On the public funnel the language is the page's**, never the request's.
  Checkout resolves it from the slug (`funnelLocaleForSlug`); the lead form
  sends it as a field, because a lookup there would put a database read ahead
  of the rate limiter.

`packages/shared/src/i18n/action-copy.test.ts` fails when a locale's
`web.action.*` string is a copy of the default locale's: the completeness guard
proves a key exists in a language, never that anyone translated it.

## The guardrails

- **No hardcoded copy** — `apps/web/tests/i18n-guard.test.ts` (+
  `apps/web/scripts/i18n-guard.mjs`). Fails on any user-facing literal in a
  `.tsx` file: JSX text, a user-facing attribute, or a string inside a `{…}`
  child, ternaries included. A name that never translates is a constant
  (`BRAND_NAME`); an identifier goes in `<code>`; only an `EXEMPT` entry with a
  stated reason excuses a file.
- **No two-armed copy** — `apps/web/tests/i18n/two-armed-copy.test.ts` (+
  `apps/web/scripts/two-armed-copy.mjs`). Fails on any comparison against `"es"`
  in `apps/web/src` or `packages/shared/src`: copy chosen between an English and
  a Spanish string reads English to every other language, and the catalog's
  completeness guard never sees it. A comparison that is not about copy (a
  speech vendor's regional code) is a data table keyed by language.
- **No English branch** — `apps/web/tests/i18n/english-branch.test.ts`. The
  other half of the same shape: no locale compared to `"en"` to choose what a
  reader sees.
- **ESLint `i18n/no-literal-string`** — `apps/web/eslint-rules/no-literal-string.mjs`,
  scoped in `apps/web/eslint.config.mjs` to a list of files. An edit-time
  backstop; the test above covers every file.
- **Compile-time completeness** — adding a key to one locale without the others
  fails `tsc` in `packages/shared`.

## Four language fields per teacher, and why they must not be merged

| Column                | Means                  |
| --------------------- | ---------------------- |
| `target_language`     | What she teaches       |
| `teaching_language`   | What she teaches _in_  |
| `locale`              | What _she_ reads       |
| `booking_page_locale` | What her _buyers_ read |

**All four are allowed to diverge**, and conflating a pair of them has broken
production twice ([D-72](../decisions/D-72.md)). Teacher-facing copy resolves
the viewer's own locale — cookie, then Accept-Language, then `DEFAULT_LOCALE`
(`en`) — except on a public page whose URL names a language, which wins
(below).

**The public booking funnel (`/b/**`) renders in `booking_page_locale`, never in
the visitor's locale.** `publicFunnelLocaleFor()` resolves it, with
`PUBLIC_FUNNEL_LOCALE` (`en`) when she has not chosen; she sets it in
Settings → Booking page. Three renderings must agree and all three derive from
that one value: the server pages (`getPublicFunnelT`), the client half
(`b/[slug]/layout.tsx`) and the social card (`b/[slug]/opengraph-image.tsx`).

A per-visitor rule cannot work, because **the social card is generated with no
visitor present.** Deriving it from her own `locale` is wrong too: a teacher
who reads Spanish can sell Spanish lessons to English speakers. What her buyers
read cannot be inferred from anything else on her row.

## Public pages have a URL per language

The marketing, help and legal pages ([D-72](../decisions/D-72.md)) live at
`/pricing` (English, `DEFAULT_LOCALE`), `/es/pricing`, `/fr/pricing`. The
allowlist and every path helper are in
`packages/shared/src/i18n/localized-paths.ts`; the middleware rewrites a prefixed
URL to its route and hands the URL's language on as `x-locale`, which
`getPreferredLocale` reads before the cookie.

- **Link to a public page with `useLocalizedHref()`** (client) **or
  `getLocalizedHref()`** (server), never a bare `"/pricing"`. A link that stays
  in its own language is what keeps a client-side navigation safe: the root
  layout carries the language too, and a client-side navigation keeps the layout
  it already has.
- **A link that changes language is a plain `<a>`**, a full load, for the same
  reason. That includes a public page's links into sign-in and sign-up, which
  follow the reader's own language rather than the URL's.
- **The bare URL redirects** a reader arriving from outside the site whose
  cookie or browser prefers another launched language. A link followed from
  inside the site never does: it was localized on purpose.
- **A page is advertised only in the languages its content exists in**
  (`pageLanguages` in `apps/web/src/lib/seo/localized-alternates.ts`). The
  terms exist in English and Spanish, the privacy policy in English; at any
  other language's URL they render the English text with
  `web.legal.englishOnly` above it, and canonicalise to the English URL
  ([D-72](../decisions/D-72.md)).

## Prices follow the reader's number format

A price keeps its own currency, but its digits are written the reader's way
([D-153](../decisions/D-153.md)): `1 500,00 $ MXN` for a French reader,
`$1,500.00 MXN` for an English or Spanish one. Format with `useFormatMoney()`
(client) or `getFormatMoney()` (server), or pass the reader's locale as
`formatMinorUnits`'s third argument. That means the funnel's locale under
`/b/**`, and the recipient's in a notification. Omitting it means English, and
`apps/web/tests/i18n/money-locale.test.ts` fails on that anywhere outside the
admin console.
