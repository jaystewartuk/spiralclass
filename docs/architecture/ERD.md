# Database ERD (`/admin/database`)

An interactive Entity-Relationship Diagram of the production database, rendered
inside the admin panel. It stays in sync with the schema automatically because
it is generated **from the schema**, not hand-drawn and not parsed from
migration history.

- **Page:** `apps/web/src/app/admin/database/page.tsx` — superadmin (or the
  `engineer` capability `schema:view`, D-55).
- **Stack:** [React Flow](https://reactflow.dev) (`@xyflow/react`) for the
  interactive canvas, [ELK.js](https://github.com/kieler/elkjs) (`layered`
  algorithm) for automatic layout.

## The pipeline

```
prisma/schema.prisma            ← the single source of truth for the schema
      │  prisma generate  (postinstall — runs the prisma-dbml-generator block)
      ▼
apps/web/dbml/schema.dbml        ← canonical DBML, gitignored (fully derived)
      │  scripts/generate-erd-schema.mjs   (@dbml/core parse → clean graph)
      ▼
apps/web/src/lib/erd/schema.generated.json   ← committed; the ERD's only input
      │  import (static, build-time)
      ▼
/admin/database  →  React Flow + ELK  →  interactive diagram
```

Two derivation steps, each with a maintained tool:

1. **Schema → DBML.** The `generator dbml` block in `prisma/schema.prisma`
   (the [`prisma-dbml-generator`](https://github.com/notiz-dev/prisma-dbml-generator))
   emits `apps/web/dbml/schema.dbml` on every `prisma generate`, which already
   runs in the web app's `postinstall`. The DBML is **gitignored** — it is
   fully derived and would only drift if committed. It is the canonical
   current-state representation of the schema (migrations are deliberately
   _not_ used — they describe change over time, not the present state).

2. **DBML → JSON graph.** `apps/web/scripts/generate-erd-schema.mjs` parses the
   DBML with [`@dbml/core`](https://www.npmjs.com/package/@dbml/core) and writes
   a clean, flattened graph to `apps/web/src/lib/erd/schema.generated.json`:
   tables, columns (types, PK/FK/unique/not-null/enum flags, defaults),
   indexes, relationships (with cardinality and referential actions), enums,
   and schemas. The shape is typed in `src/lib/erd/types.ts`. The **frontend
   consumes this JSON only** — it never parses DBML in the browser.

The page statically imports the committed JSON, so it always shows the latest
generated schema with zero runtime database or DBML dependency.

## How schema changes flow into the ERD

The DBML regenerates on its own (any `prisma generate`), but the committed JSON
is regenerated by an explicit step so it is reviewable in the PR diff alongside
the schema change. You get it for free through the normal migration command:

```bash
# The usual way — migrating already regenerates the ERD JSON:
pnpm --filter spiralclass-web prisma:migrate

# Or regenerate just the JSON (after any schema/DBML change):
pnpm --filter spiralclass-web erd:generate
```

`erd:generate` runs `node scripts/generate-erd-schema.mjs` against the current
`dbml/schema.dbml`. Commit the resulting `schema.generated.json` with your
schema change.

### The drift guard (why you can't forget)

`apps/web/tests/erd-schema.test.ts` regenerates the graph from the _current_
DBML and asserts it byte-for-byte matches the committed
`schema.generated.json`. If you change the Prisma schema and don't regenerate
the JSON, this test fails in the fast CI tier (`checks.yml`, required before
merge) with:

```
committed JSON matches what the generator produces from the current DBML
```

The fix is always the same: `pnpm --filter spiralclass-web erd:generate`, then
commit. The same test also asserts structural invariants (every relationship
endpoint resolves to a real table/column, FK columns are flagged, cardinalities
are known).

> Note the split of responsibilities: `postinstall` regenerates only the
> **DBML** (never the JSON), so in CI the guard compares your committed JSON
> against a freshly-derived schema — catching staleness — rather than silently
> overwriting it.

## How future database changes should be handled

1. Edit `prisma/schema.prisma` and create the migration as normal
   (`pnpm --filter spiralclass-web prisma:migrate`). This already refreshes the
   ERD JSON.
2. If you edited the schema without migrating (e.g. `prisma db push`), run
   `pnpm --filter spiralclass-web erd:generate`.
3. Commit `src/lib/erd/schema.generated.json` alongside the schema/migration.
4. If you added an admin management surface for a table, add it to
   `src/lib/erd/admin-routes.ts` so the ERD's "Open in admin" deep-link
   appears for that table. Keep that map to routes that actually exist.

No hand-editing of `schema.generated.json` or `schema.dbml` — both are
generated. `schema.dbml` isn't even committed.

## Features

- Zoom / pan / fit-to-screen, minimap, automatic ELK layout.
- Search tables (Enter zooms to matches); selecting a table highlights it and
  its foreign-key neighbours and dims the rest.
- Expand/collapse a table's columns (per-table and all-at-once), with primary-
  key, foreign-key, unique and not-null indicators plus data types.
- Click a table for full metadata (columns, indexes, incoming/outgoing
  relationships, and a deep-link to its admin page when one exists).
- Click a relationship (edge) for the foreign-key details — endpoints,
  cardinality, and `ON DELETE` / `ON UPDATE` actions.
- Light/dark aware (React Flow `colorMode` follows the app theme).
