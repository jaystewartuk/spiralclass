# D-168. Two migrations, split by who writes them — the generated schema, and the invariants Prisma cannot express

**What changed.** `apps/web/prisma/migrations/` goes from 46 directories to
two:

| Migration                            | Written by | Contains                                                                                                                                               |
| ------------------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `20260906120000_schema_baseline`     | Prisma     | Every table, enum, index, foreign key and default `schema.prisma` expresses                                                                            |
| `20260906120100_database_invariants` | A person   | `btree_gist`, 10 partial indexes, 33 CHECK constraints, 2 GiST exclusion constraints, `NOT NULL` on 4 list columns, 2 plpgsql functions and 3 triggers |

The baseline is generated, not transcribed:

```bash
prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script
```

reproduces it byte for byte. Nothing was carried across from the old files.

**Why it changed.** The repository is being published as a portfolio piece with
no git history ([D-163](./D-163.md)), and 46 migrations dated across eight weeks
are archaeology of a private repo nobody cloning this one can read. They also
were not, by then, an accurate account of anything: the history contained a
`bank_account` payout kind created and removed, three transfer/commission
columns created and removed, a `device_tokens` table created and dropped, a
`discipline` enum replaced by a BCP-47 code, `centavos` renamed to
`minor_units` across seventeen columns, and a `wise_*` block on `teachers`
moved wholesale onto a new table. A reader reconstructing the current schema
from those files is reconstructing five schemas that no longer exist first.

**What the collapse is NOT.** It is not a concatenation of the old SQL, and it
is deliberately not a fabricated "meaningful evolution" — `001_core`,
`002_booking`, `003_payments` — of a schema that never evolved that way. Two
files, split along a boundary that is real.

## The boundary, and why it is the whole decision

A single squashed baseline is the obvious answer and it is the one this
repository already tried. [D-70](./D-70.md) squashed 125 migrations into one
file on 2026-07-13, and mixed the hand-authored raw SQL into the bottom of it.
Eight weeks later, two things had gone wrong quietly:

- The CHECK constraints in that file still read `price_centavos`,
  `amount_centavos`, `wise_price_centavos`. Postgres rewrites a constraint
  expression when a column is renamed, so the live constraints were fine — but
  the file that claimed to be the schema had been describing columns that no
  longer existed since 2026-09-02.
- It still created `device_tokens_active_idx`, an index on a table a later
  migration dropped.

Neither broke a deploy, because the file was applied once and never re-read.
That is exactly the hazard: **a baseline that mixes generated and hand-authored
SQL cannot be regenerated**, so the moment it drifts, the only options are
hand-editing it (which Prisma's checksum forbids on an applied migration) or
leaving it wrong.

Separating them makes regeneration a two-step procedure instead of a decision:
regenerate the first file, hand-review the second. It also puts the SQL that
_needs_ a human reader in a file a human will actually open — 363 annotated
lines rather than page 1,800 of a 2,440-line generated dump.

The invariants are the half nothing automated protected. `prisma migrate dev`
will never write a partial index or an exclusion constraint, and the
migration-drift check in `scripts/ci/integration.sh` diffs **models** — drop
the entire invariants migration and it still reports "no model drift
detected". That was survivable while the raw SQL sat inside a baseline nobody
regenerated. It is not survivable now that regenerating the baseline is the
documented way to change it: the whole point of the split is that step two is
a hand-review, and a hand-review with no assertion behind it is a hope.

So `tests/migrations/invariants.integration.test.ts` inventories the real
catalog of a really-migrated database — every partial index (and that it still
carries a predicate), all 33 CHECKs and both exclusion constraints as exact
sets, the three triggers and the tables they sit on, and the four list columns'
nullability. It was verified to fail: dropping one CHECK from the test database
turns it red naming that constraint. What each rule _does_ stays covered where
the behaviour lives — the append-only trigger in `tests/seed/cleanup`, booking
overlap in the booking suites; what this adds is that the rule is still there.

Adding an invariant means adding it to that list in the same change. That cost
is the intended one: an invariant nobody listed is an invariant nobody notices
going missing.

## Verified against the old history, not just against itself

The claim that matters is that the two new files produce the schema 46 old ones
produced. Both were built on a throwaway `postgres:16`:

1. `prisma migrate diff` between the two databases, **in both directions** —
   both empty.
2. A catalog inventory (`pg_extension`, `pg_indexes`, `pg_constraint`,
   `pg_trigger`, `pg_proc`, `pg_enum`, `information_schema.columns`) — **1,648
   objects each, identical** but for eight column defaults rendered `now()`
   against `CURRENT_TIMESTAMP`, which are the same function.
3. Behaviour, not just DDL: on a database built from the two new files alone,
   an overlapping booking is refused, one inside the previous class's buffer is
   refused, a cancelled booking may reuse the slot, a second pending payment on
   one package is refused while a paid one is accepted, the buffer trigger
   derives `buffered_end`, an UPDATE and a DELETE on `overrides` both raise, a
   list column rejects NULL and defaults to `{}`, and the money, ISO-format and
   testimonial-shape CHECKs all fire.
4. The project's own gate: `pnpm gate` green, and `scripts/ci/integration.sh`
   with `GATE_FRESH_DB=1` — a real `next build`, the drift check on a
   from-scratch database, and the integration suite.

## What the rebuild fixed on the way past

`schema.prisma` declared `@default(dbgenerated("pg_catalog.gen_random_uuid()"))`
on the five better-auth tables. The databases held `gen_random_uuid()` — the
same function, and the same default; only the rendering differed. Prisma
compares the strings, so `migrate diff` emitted five no-op `SET DEFAULT`
statements on every run, and applying them would not have silenced it. The
`20260831181335_add_seeded_at_marker` migration recorded the symptom and left
it: _"That drift is real and still unaddressed — it belongs in its own
migration by whoever understands why it is there."_

It was not drift. Dropping the `pg_catalog.` prefix from those five lines makes
the drift check print `-- This is an empty migration.` for the first time.

**Worth keeping:** a permanently-noisy check trains you to skim it, and a check
you skim is a check you do not have. The five phantom lines had been printed on
every integration run for a week and read as background.

## What is preserved that a naive regeneration loses

`prisma migrate diff --from-empty` is not sufficient on its own, and one case
proves it. Prisma models a scalar list as always-present and never writes NULL
to one, but it emits the column **nullable**. The old hand-written migrations
had declared `NOT NULL` on `teacher_marketing_profiles.{audiences,
learner_locations, levels}` and `teacher_share_groups.promo_weekdays`.

Prisma's own diff considers the two equivalent, so **the drift check would not
have caught the loss** — and the columns are read with array operators whose
result on NULL is NULL rather than the empty-list answer their callers assume.
The four `SET NOT NULL` statements are in the invariants file.

## The cost, stated

**Every existing database must be baselined once**, because its
`_prisma_migrations` names 46 migrations this repository no longer contains and
a `migrate deploy` would try to `CREATE TABLE` over live tables:

```sh
prisma migrate resolve --applied 20260906120000_schema_baseline
prisma migrate resolve --applied 20260906120100_database_invariants
```

That is production Neon, preview Neon, the `spiralclass-dev-db` container and
any long-lived checkout's test database. `migrate resolve` writes rows and runs
no SQL. A mis-sequenced adoption fails loudly rather than corrupting anything —
but not through P3005, which only guards a database with no
`_prisma_migrations` table. With the old history's table present, `migrate
deploy` stops at the baseline's first `CREATE TYPE` (P3018), applies nothing,
and records the baseline as failed until the adoption is run. The
procedure and the verification that must precede it are in
`apps/web/prisma/migrations/README.md`. This is the same adoption D-70 required
and documented in 2026-07, for the same reason.

**Per-migration history is gone**, and with it the ability to `git log` a
column back to the change that introduced it. That was already true of anything
before 2026-07-13, and the public repository has no history to log against
anyway. Where the reasoning was load-bearing it is in the decision log — D-113
for the manual rail's generalisation, [D-143](./D-143.md) for the transfer
columns, [D-145](./D-145.md) for `bank_account`, [D-151](./D-151.md) for
verified testimonials — which is where
a reader would look for _why_, rather than in a `.sql` file that can only show
_what_.
