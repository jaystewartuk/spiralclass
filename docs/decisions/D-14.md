# D-14. Teacher-private student notes live in their own table, never in the audit trail

**What changed.** Teachers can now keep private notes on a student from the
student detail page — free-form jottings such as "focus on the past subjunctive
next class". The notes are stored in a new `student_notes` table (one row per
note, many per `(teacher, student)` pairing, newest-first), created/edited/deleted
by `src/app/actions/student-notes.ts` and rendered by `student-notes-form.tsx`.
They are scoped to a single student and visible **only to the teacher** — there
is no student-facing surface and no student-side RLS policy.

We chose a dedicated table over a single `teacher_students.teacher_notes` blob so
the notes are a timestamped journal (the use case — "what to do next class" — is
inherently dated), with room to later attach a note to a specific lesson, pin
one, or categorize, without a later data migration.

**Why it likely changed.** Teachers asked to record what they want to focus on
with each student between classes. The existing per-student controls (level,
custom price, archive) cover business state; there was nowhere to keep ordinary
teaching notes.

**What was affected.** New `student_notes` table + migration
(`20260623000000_student_notes`) following the §13.2 tenancy pattern (teacher_id
column, app-scoped reads/writes, teacher-owner RLS, no student policy — mirroring
`student_library_items`); the student detail page (one extra query + a "Private
notes" card); the new server action and form; the merge path
(`lib/students/merge.ts` repoints notes from the duplicate to the keeper and
counts them in `moved`); the teacher data export (`export-data.ts` includes the
notes — they are the teacher's own content); and student erasure
(`anonymize.ts` deletes a student's notes).

Two deliberate non-choices:

- **Notes are never written to the `overrides` audit table.** Those rows surface
  in the student's class history (§6.8), so auditing note edits there would leak
  the notes' contents. The rows' own `created_at`/`updated_at` are the only trail,
  and analytics events carry counts/ids only — never the note body.
- **Notes are excluded from the student data export.** They are the teacher's
  private assessment, not student-facing data — the same treatment as the
  teacher-private `teacher_students.custom_price_note`, which is in the teacher
  export but not the student export.

**Unresolved risks.** The feature is **ungated** (available on every tier);
if note-keeping later becomes a Pro differentiator, add a `gateProFeature` check
in the add/update actions (clearing/deleting should stay free, as with custom
price). The student-export exclusion is a judgment call inherited from
`custom_price_note`; revisit if a subject-access request should include a
teacher's private notes about the subject.
