# D-27. Live in-class captions: teacher-toggled, real-time Spanish→English subtitles, client-streamed and ephemeral

> **Superseded in part by [D-106](./D-106.md) (2026-07-25).** The
> client-streamed design below rested on one constraint — a serverless deploy
> cannot host a long-lived worker — and that stopped being true once the
> self-hosted box existed. Captions for ordinary classes now run in a
> server-side agent. Everything else here (reuse the two vendors already in the
> stack, ephemeral by default, long-lived keys stay server-side, the
> dark-until-enabled gate) is unchanged.

**Status: Active** (web; an addition to the in-class call — see
[`D-16`](./D-16.md) and `live-notes-panel.md`).

**What changed.** The in-class video call (D-16) can now show the student live
English subtitles of what the teacher says in Spanish. The teacher turns it on
and off from inside the call, exactly like the mic, camera, and record controls.
When it is on, her speech is captioned for the student in near-real-time; when it
is off, the student's caption band clears. Nothing is stored — captions are
ephemeral and exist only for the duration of a spoken line.

**What was decided.**

1. **Client-streamed, not a server agent.** The app runs on serverless (Vercel),
   which can't hold a long-lived websocket, so there is no LiveKit "agent"
   process. Instead the **teacher's browser** taps its own LiveKit microphone
   track, streams it to **Deepgram's streaming ASR** socket, and the resulting
   Spanish text is translated and published into the room. This keeps the feature
   deployable on the existing infra and makes the teacher toggle a pure client
   control, like Record.
2. **Reuse the two vendors already in the stack — no new vendor.** ASR is
   **Deepgram** (the same vendor as the post-class transcription pipeline, D-19,
   here in _streaming_ mode); translation is the **platform Anthropic key** (the
   same key as class-content compose, D-17), on a fast/cheap model (Haiku by
   default) because it's a hot path of one short call per finished utterance.
   Only finalized utterances are translated — interim partials are not — to keep
   the on-screen text clean English rather than half-translated Spanish.
3. **The teacher streams; the student only receives.** The teacher's browser is
   the only side that opens an ASR socket or calls translation. Finished English
   lines are published over a dedicated **LiveKit data-channel topic**
   (`captions`); the student (and the teacher's own confirmation view) renders
   whatever arrives. The toggle state rides the same channel, so turning captions
   off clears the student's band immediately.
4. **The long-lived keys never reach the browser.** The Deepgram key is exchanged
   server-side for a ~30-second **grant token** (`/api/captions/token`), and
   translation runs server-side (`/api/captions/translate`). The browser holds
   only the short-lived token, mirroring the per-visit LiveKit join grant.
5. **Same Pro gate, same dormant-until-enabled switch.** Captions ride the
   `lesson_notes` Pro entitlement (D-15), like the call itself, and are gated by
   `liveCaptionsEnabled()` — which requires **both** vendor keys present **and**
   an explicit `LIVE_CAPTIONS_ENABLED` flag. With the flag off (or a key missing)
   the teacher's toggle simply doesn't appear and the call behaves exactly as
   before.
6. **Launch direction is Spanish→English, as named constants.**
   `CAPTION_SOURCE_LANGUAGE`/`CAPTION_TARGET_LANGUAGE` in `lib/captions/config.ts`,
   matching the platform default locale and `DEFAULT_LESSON_LANGUAGE`. A future
   per-booking language pair slots in there without touching the plumbing.

**Why.**

- _Client-streamed over an agent:_ an agent would be the textbook LiveKit pattern,
  but it needs a long-lived process this serverless deploy can't host. The
  teacher's browser already has her mic track and the room connection, so tapping
  it is both cheaper and the natural home for an on/off control.
- _Reuse over a new vendor:_ Deepgram and Anthropic are already configured,
  billed, and CSP-cleared in spirit; adding a third speech vendor (Gladia, Azure
  Speech Translation, Google) would be more infra for a marginal latency gain.
- _Ephemeral by default:_ unlike the post-class pipeline, live captions never
  persist, so they avoid the retention question — but **not** the consent one
  (below).

**What it constrains.**

- Don't add a media/ASR SDK call straight from a component — the streaming +
  translation seam lives in `lib/captions/` and the API routes; keep the UI
  agnostic, like the `VideoProvider` seam.
- The Deepgram **streaming** host (`wss://api.deepgram.com`) must stay in the CSP
  `connect-src` allowlist (`lib/csp.ts`) and its mirror in `tests/lib/csp.test.ts`
  — without it the socket is silently blocked under enforcement, exactly how the
  LiveKit signaling host once was.
- Long-lived keys stay server-side; the browser only ever holds the short-lived
  grant token and the translated text.

**Unresolved risks.**

- **Live audio to a vendor is a new consent surface.** The post-class pipeline is
  gated on explicit per-student (minor-aware) consent (D-22). Live captions stream
  the _teacher's_ voice (not the student's) to Deepgram in real time, which is a
  lighter case, but it is still lesson audio leaving the device — which is why it
  ships behind `LIVE_CAPTIONS_ENABLED`, dark by default.
- **Latency and accuracy.** Finalized-utterance translation adds ~1–3s of lag and
  imperfect machine translation; it is a comprehension aid, framed as such, not a
  transcript of record.
- **A second client received but did not publish.** It rendered captions by
  reusing the shared protocol (`@spiralclass/shared` `captions.ts`, also the
  source of the web `lib/captions/protocol.ts` re-export), so the two could not
  drift. Its _publisher_ half was the remaining
  follow-up: `MediaRecorder` + a browser `WebSocket` to Deepgram differ in React
  Native, so the teacher still starts captions from the web app for now.
- **Media is unverified in CI.** Like the rest of the call layer, the streaming +
  publish logic follows the livekit-client / Deepgram APIs and passes typecheck;
  real audio needs on-device QA with keys set.
