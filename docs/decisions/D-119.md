# D-119. CI moves onto the dev machine; GitHub Actions keeps the deploy, the crons, and a fallback

> **Superseded in part by [D-157](./D-157.md) (2026-09-04), and only in part.**
> The registry is the durable half and is untouched: `scripts/ci/steps.mjs` is
> still the single definition of what "green" means, and the `local-gate`
> commit status still binds a verdict to one commit. What moved back is where
> it runs — a public repository's Actions minutes are free, and `ubuntu-latest`
> builds the amd64 image natively instead of under QEMU.

**What changed.** The test tiers that used to run on GitHub-hosted runners now
run on the operator's laptop, driven by a small runner in `scripts/ci/`. The
merge gate survives the move: branch protection on `main` now requires the
commit-status context **`local-gate`**, which the local run posts against the
exact SHA it certified.

| Tier                                                          | Before                                        | After                                                        |
| ------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| format · typecheck · lint · unit+coverage · audit             | `main-checks.yml` → `checks.yml`, on every PR | `pnpm gate`, run automatically by `.githooks/pre-push`       |
| mutation · integration (real DB · `next build` · drift) · E2E | `promote.yml` fan-out, on dispatch            | `pnpm gate:full`, wrapped by `pnpm promote`                  |
| fast-forward `production`                                     | `promote.yml`'s final job (PROMOTE_TOKEN PAT) | `pnpm promote` pushes it with the operator's own credentials |
| **web build + deploy**                                        | `fly-deploy.yml`, auto on push                | **unchanged**                                                |
| **nightly sweep · prod synthetic · prod DB backup**           | three crons                                   | **unchanged**, except the nightly is slimmed (below)         |

New surface, all of it on the `pnpm` script surface rather than the `justfile`
(the standing split — `just` launches long-lived dev processes, checks stay on
`pnpm`):

```sh
pnpm gate               # fast tier; what the PR gate used to run
pnpm gate:full          # + mutation, integration, E2E
pnpm gate --only lint   # re-run one step after fixing it
pnpm gate:status        # post the status for the last receipt (after a push)
pnpm promote            # full gate → fast-forward production → release tag
```

`scripts/ci/steps.mjs` is the single registry of what "green" means, and every
step names the workflow job it mirrors. `scripts/ci/{integration,e2e}.sh`
are line-for-line mirrors of the workflows of the same names, with three
deliberate differences: Postgres comes from `apps/web/docker-compose.test.yml`
(port 5433, three databases: `spiralclass_test`, `spiralclass_drift`,
`spiralclass_e2e`) instead of an Actions service container; `psql`/`createdb`
run inside that container so no local libpq is needed; and a detached
`git worktree` is fingerprinted instead of running `git checkout --force` over
the operator's tree. The dead `SUPABASE_*`/`VERCEL_ENV` stubs the
workflows still export were not carried over (D-89 Phase 5).

**How the merge gate still works.** A commit status is bound to one commit, so a
green `local-gate` can't drift onto later work — push another commit and the PR
returns to "waiting" until that commit is certified too. That property is the
whole reason this is a status and not an honour system. Two producers post the
same context:

1. `scripts/ci/status.mjs`, from the laptop. The pre-push hook runs the fast
   tier, and on success detaches a process that waits for the push to land and
   then posts. Running at push time is the point: the standing rule was always
   "run the checks immediately before every push", and the failure mode was
   always an edit made after a green run (confirmed 2026-07-20, which burned a
   billed dispatch on a type error a re-run would have caught).
2. `main-checks.yml`'s new `status` job, after a green manual dispatch. This is
   what makes a laptop-less day (a Claude Code cloud session, a borrowed
   machine) a complete substitute rather than a stranded PR.

**The nightly sweep is slimmed.** `checks.yml` gained a `time_dependent_only`
input; `nightly-checks.yml` passes it along with `mutation: false`. The sweep
exists to catch checks that can fail on an unchanged commit — time-bomb tests
(the clock moved) and the dependency audit (a CVE was published). Typecheck,
lint, formatting and Stryker are pure functions of the committed tree and can
only reproduce the answer the gate already got, so they no longer run nightly.
Five jobs become three, and the slowest one is dropped.

**Why it changed.** Operator directive: the new 16GB M4 Air is fast enough to
run what CI ran, so anything that doesn't specifically benefit from being a
GitHub Action should be local. The supporting facts line up:

- Every workflow has been back on billed `ubuntu-latest` runners since the
  self-hosted pool was retired,
  and `main-checks.yml` — five parallel jobs, each doing its own
  `pnpm install`, on every push to every PR — was the largest recurring line
  item left after `apk-build.yml` was removed.
- The hardware premise that put these checks on a server is gone. The
  no-local-tests policy (2026-07-06) and the format-only pre-push hook both
  existed because an 8GB laptop OOM'd on vitest + tsc across the monorepo; D-116
  retired that policy when the machine was replaced, but nothing had yet moved
  back.
- Turbo caches typecheck and lint, so the marginal cost of a re-push with no
  source change is seconds, against several billed minutes for the same answer
  in CI.

**What stays on GitHub Actions, and why each one is not an oversight.**

- **`fly-deploy.yml` (web preview + production).** Fly runs amd64 images only;
  this laptop is arm64, so a local image build means QEMU — the repo's own
  `.github/actions/fly-build-deploy` header measured that path at 20–30+ min and
  flaky, against a `next build --turbopack` that peaks ~3.45GB. It also has to
  keep auto-deploying on push: a human dispatch step is exactly the step that
  got skipped in the 2026-07-19 drift incident, which left `production` 96
  commits behind what was live.
- **`nightly-checks.yml`, `synthetic.yml`, `backup-prod-db.yml`.** A closed
  laptop cannot detect a time bomb, probe production, or take a backup. Their
  failure mode is silence, which is the one failure mode a schedule must not
  have.
- **`checks.yml`, `integration.yml`, `e2e.yml`, `gate.yml`, `promote.yml`.**
  Kept, dispatch-only,
  as the fallback path and as the thing that keeps the fallback honest — they
  cost nothing idle.
- **`quality.yml`.** Already dispatch-only; it targets a deployed environment
  rather than a commit, so where it runs is immaterial.

**What was affected.**

- **New:** `scripts/ci/` (`gate.mjs`, `status.mjs`, `promote.mjs`, `steps.mjs`
  with its `steps.d.mts`, `lib.mjs`, and the four suite scripts);
  `apps/web/tests/config/local-gate.test.ts`; `.gate/` (gitignored receipts and
  the native-guard worktree); the `gate`, `gate:full`, `gate:status` and
  `promote` root scripts.
- `.githooks/pre-push` runs the fast tier instead of only `pnpm format:check`,
  and hands the SHA to the status poster. `SKIP_GATE=1` and `--no-verify` skip
  it, at the cost of a PR with no status.
- `main-checks.yml` lost its `pull_request` trigger and gained the `status` job.
- `checks.yml` gained `time_dependent_only`; `nightly-checks.yml` passes it.
- `scripts/setup-branch-protection.sh` requires `local-gate` instead of
  `checks / Typecheck / lint / unit / audit`. **This needs a re-run with `gh`
  admin to take effect** — until then the old context is still required and
  every PR will sit unmergeable.
- `promote.yml` and `gate.yml` are documented as fallbacks; neither changed
  behaviourally.

**Unresolved risks.**

- **The gate is self-attested.** Nothing stops posting green by hand, and the
  hook can be skipped. For a solo repo the value is the mechanical "was this
  exact commit checked", not resistance to a determined operator; a second
  machine or a hosted runner is the answer if that ever stops being true.
- **Bus factor.** Preview and production deploys, the crons and the fallback
  gate all still run without the laptop, but nothing merges to `main` without
  either it or a manual dispatch.
- **Drift between the local scripts and the workflows they mirror.** The guard
  test locks the mapping (every step names a workflow that exists; the fast tier
  contains every command `checks.yml` runs) but cannot diff a shell script
  against a YAML `run:` block. Change both halves together.
- **Integration reuses its database between runs** (`GATE_FRESH_DB=1` to force a
  wipe), where a runner always got a fresh one. A test that depends on
  leftover rows would pass locally and fail in the fallback.
- The M4 is arm64 and the fallback runners are amd64. Everything here is
  interpreted or JIT'd, so no architecture-specific failure is expected — but
  the E2E suite in particular has never been run on arm64 in this repo, and the
  first divergence found there belongs in an addendum here.
