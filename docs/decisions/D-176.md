# D-176. The tenant a request is entitled to is carried, not inferred

**Status.** Active. The runtime half of [D-175](./D-175.md); together they are
the application-level enforcement that [D-70](./D-70.md) left to convention. It
changes the premise [D-142](./D-142.md) reasons from — see below.

**What changed.** A Prisma client extension (`apps/web/src/lib/tenancy/`) reads
every query's arguments as it runs and compares them against the tenant the
auth gate said the request is for. The tenant is recorded once, at
`attachActorToObservability` in `lib/auth.ts`, and carried on an
`AsyncLocalStorage` context rather than threaded through the call stack. A
query that names a **different** tenant than the one being served throws in
development and test, and reports to Sentry in production.

## Why — the question no static check can answer

D-175's scanner proves a query **names** a tenant. It cannot prove the tenant it
names is the right one, and it says so in its own trade-offs: _"Passing another
teacher's id into a correctly-scoped query passes this check completely."_

That is not a corner. It is the shape of an IDOR: an id arrives from a URL, a
form field, a stale cache or a webhook, reaches a `where` clause that is
flawless by every static and review standard in this repository, and returns
somebody else's rows. Every enforcement layer that takes the tenant **from the
caller** is blind to it by construction.

The tenant a request is entitled to is known exactly once — at the auth gate —
and nowhere after it. So the fix is not a better check on the query; it is
carrying the answer from the one place that has it to the one place that can
use it.

## What was considered and rejected

**Postgres row-level security.** Still the strongest answer, and still not this
one. The reasons are unchanged from D-175 and are now tracked as work rather
than as a paragraph: RLS is the reversal
[`data-model.md`](../architecture/data-model.md) says must be a decision, it
needs a role split, `FORCE ROW LEVEL SECURITY`, and per-transaction
`SET LOCAL` against a transaction-mode pooler. **This record is a step toward
it, not away from it**: the context module is precisely where that
`SET LOCAL` value would come from, which is why the tenant is a context rather
than a parameter.

**Enforcing in production from day one.** Rejected, and this is the
uncomfortable half. This code runs in front of every query in a system on live
payment rails. A false positive is a teacher who cannot take a booking, and
`TeacherShareGroup` means a teacher-scoped request can legitimately touch
another tenant's material — so "I could not construct a false positive" is not
evidence. Production reports; `TENANCY_GUARD=enforce` promotes it once the
reports have been watched. That is a decision to take on evidence, and the
evidence does not exist yet.

**Checking shape at runtime as well** — re-deriving "does this query name a
tenant at all" from the arguments. Rejected as a restatement: the scanner
answers that question over the whole tree including code no test exercises,
and two implementations of one judgement drift. The runtime layer asks the
question the scanner cannot, and the vocabulary they share is asserted equal in
`tests/tenancy/guard.test.ts` rather than kept in step by hand.

**Wiring the student portal in the same change.** Deferred to an issue. A
`Student` is a per-teacher row, so it is a real second axis and worth having —
but the beachhead should be one gate until the reports show what enforcement
costs.

## What it constrains

- **The extension inspects arguments and never rewrites them.** It calls
  `query(args)` with exactly what it was given, so a bug here cannot change what
  the database is asked for — only what is logged, or in `enforce` whether the
  call happens. Keep it that way; an extension that edits queries is a much
  larger thing to trust.
- **`lib/prisma.ts` casts the extended client back to `PrismaClient`.** That
  cast is sound only while this stays a query-only extension. Adding a `result`,
  `model` or `client` component changes the client's surface and the cast would
  hide it from 258 annotation sites;
  `tests/tenancy/client-surface.test.ts` is what notices.
- **`runInTeacherScope` and `runCrossTenant` await inside the scope.** Not
  ceremony — see the trade-offs below.
- **A deliberate cross-tenant read says why**, via `runCrossTenant("<reason>",
…)`, the runtime twin of D-175's `// tenancy-exempt:` directive.

## What was affected

`apps/web/src/lib/tenancy/context.ts` and `guard.ts`, `lib/prisma.ts`,
`lib/auth.ts`, `lib/env.ts` and `.env.example` (`TENANCY_GUARD`), and
`apps/web/tests/tenancy/`.

## ⚠️ It changes D-142's premise

[D-142](./D-142.md) decided the `/demo` fixture question on the reasoning that
"there are 68 server-action files and **no Prisma client extension**, so there
is no chokepoint", and named its own reopening condition: _"The moment to
reconsider a real account is if a Prisma client extension ever lands for
another reason."_

That moment is this record. The chokepoint now exists. **D-142's decision is
not reversed here** — nothing about the demo account has been re-argued, and
this record has no opinion on it. What has changed is that its stated blocker
is gone, so the question is now open rather than settled, and it should be
answered on its own merits by whoever picks it up.

## Trade-offs accepted, and unresolved risks

**A Prisma query is a lazy promise, and that nearly made this useless.** A
`PrismaPromise` does nothing until awaited, so a scope helper written the
obvious way —

```ts
storage.run(scope, fn); // fn returns an unawaited prisma.booking.findMany(…)
```

— exits the scope the instant `fn` returns, and the query then executes with no
scope at all. The guard waves it through and reports a tenant-scoped request as
unattributed: a silent hole that reads exactly like a clean system. It was found
by a test written to prove interception happens, which failed against a real
database connection error. The helpers now await inside the scope, and
`tests/tenancy/interception.test.ts` fails if that is ever simplified back.
**The general lesson is worth more than the fix**: an async-context guard is
only as good as the proof that its context reaches the thing it guards, and
that proof has to be a test, because the failure mode is silence.

**One gate is wired, and it is the teacher's.** Everything reached by the
student portal, the admin console, webhooks, Inngest jobs and the seed runs with
no scope, and for those the guard is inert. That is honest rather than
accidental — an unattributed query is not evidence of anything — but it means
today's coverage is the teacher dashboard and nothing else.

**Production reports and does not throw**, so today this prevents nothing there.
It makes the leak visible, which is what the enforce decision will be taken on.

**Raw SQL is outside it**, exactly as it is outside the scanner. `$queryRaw`
carries no arguments to inspect.

**It cannot see a `where` the extension is not reached for.** A code path no
request exercises reports clean here forever — which is the mirror image of the
scanner's blind spot and the reason both exist.
