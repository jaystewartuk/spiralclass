# D-172. The board moves into this repository's Issues

**Status.** Active. Supersedes the location [D-110](./D-110.md) chose — not its
argument, which is why there is still no backlog file in the tree.

**What changed.** Open SpiralClass work lives in this repository's GitHub Issues
at <https://github.com/jaystewartuk/spiralclass/issues>, not on the maintainer's
private planning board. D-110's prohibition on a markdown queue is unchanged and
unweakened: no `TODO.md`, no `BACKLOG.md`, no `plans/` directory, no dated audit
whose last section is a findings list.

⚠️ **The decision was taken on the board, not here.** The planning repository's
routing table already sends "a project's backlog" to "that repo's GitHub
issues", with the rule that **an undated idea is an issue, never a row**, and
its weekly rhythm carries a fifteen-minute triage against this repository's
issue list — set `p1`/`p2`/`p3`, close what will not happen with a reason,
promote at most one. This record is the SpiralClass half: five documents here
still told a reader the opposite, which is the drift D-110 itself exists to
prevent.

## Why — the premise that expired

D-110 made two decisions at once and only one of them was about markdown.

The first — a queue in the tree rots, because nothing closes a bullet in a file
— is as true as it was, and this record does not touch it. The evidence D-110
gathered still stands: a backlog last refreshed 2026-06-07 that by August cited
eleven documentation paths deleted in the July reorg.

The second was **where** the board should be, and it answered "the maintainer's
private planning repository" for a reason that has since expired: this
repository was private too, so an issue filed here was no more visible than a
row on the board, and keeping one board beat keeping two. Publication changed
that. The work, the reasoning and the code are now readable by anyone, and the
queue was the only part still behind a login — for no remaining benefit, since
what is on it is the same kind of thing the decision records already say out
loud.

D-110 also reserved Issues narrowly, for "machine-filed reports (the Sentry
integration) and for anything a pull request closes with `Closes #N`". That
carve-out was pointing at the right property and drawing the boundary in the
wrong place: what makes an issue better than a bullet is that **its state
changes without a human remembering to edit a list** — a PR closes it, or a
person closes it, and the list is correct afterwards either way. That is true
of a hygiene item as much as of a Sentry report.

## What was considered and rejected

- **Keep the private board and mirror the public-facing items into Issues.**
  Two homes for one commitment, which is the exact failure D-110 was written
  about. Rejected on its own record.
- **Keep everything on the private board.** Defensible, and it is what stood
  until now. It fails only on publication: a repository whose whole argument is
  that the reasoning is inspectable had one category — what is known to be
  wrong and not yet fixed — that a reader could not see. That is the category a
  sceptical reader most wants.
- **Re-admit a markdown backlog now that the repo is public.** No. The rot
  D-110 measured had nothing to do with visibility, and a file cannot be closed
  by a merge.

## What it constrains

- **Still no queue in the tree.** Every prohibition in D-110's own list stands.
  A finding from an investigation goes in an issue; the document keeps only
  what it established.
- **An issue is a closable statement of work, not a note to self.** It says
  what is wrong or missing and what "done" looks like, so that a pull request
  can close it and the closing is the only bookkeeping. The existing issues set
  the shape: a sentence naming the problem from the user's side, then a
  **Done when** line, and a `p1`/`p2`/`p3` label that the weekly triage sets.
- **An undated idea is an issue, never a board row.** The board carries what has
  a date or a trigger; everything else belongs here. That boundary is the
  board's rule, not this repository's, and it is the reason this record exists
  rather than a second queue.
- **Issue titles follow the same rule as commit subjects** — a full sentence
  naming the problem from the user's side, not a category prefix.
- **Nothing that belongs in a decision record goes in an issue instead.** A
  decision is a thing that has been settled; an issue is a thing that has not.

## Trade-offs accepted, and unresolved risks

- **The queue is now public, including what is known to be broken and unfixed.**
  Accepted deliberately: the same argument that publishes the decision records
  publishes this. A reader who wants to know what is wrong with SpiralClass can
  now find out, which is the point, and an item that would be irresponsible to
  publish — an unpatched vulnerability, say — belongs in
  [SECURITY.md](../../SECURITY.md)'s private channel and not in an issue.
- **Two trackers exist during the changeover.** Whatever remains on the private
  board is not migrated by this record, and nothing checks that it empties.
  Until it does, "the board" is ambiguous in exactly the way D-110 warned about.
- **Nothing enforces the issue shape.** The commit-subject rule has the gate
  behind it; issue titles and **Done when** lines have only this record and the
  existing examples. A drift check is possible and is not built.
- **Issue volume is its own rot.** D-110's deeper point was that a 40-item list
  nobody reads is worth nothing wherever it is stored. Moving the board does not
  make it get groomed, and this record makes no claim that it will be.
