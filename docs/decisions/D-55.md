# D-55. Admin capability layer + an interactive `/admin/uat` runbook

**What changed.** Two things, shipped together.

1. A **capability layer** sits alongside the existing `/admin` rank ladder
   (`superadmin > finance > support`, D-25). Two new `AdminRole` values,
   `tester` and `engineer`, rank **below** every existing tier
   (`ROLE_RANK` in `apps/web/src/lib/admin.ts`) so they see nothing via rank
   — access to a specific tool comes only from an explicitly granted
   capability (`apps/web/src/lib/admin-capabilities.ts`, one
   `AdminCapability` union + one `ROLE_CAPABILITIES` map). `requireAdmin()`
   and `resolveAdminActor()` now take an optional second `capability`
   argument and authorize on `meetsRole(actor, minRole) || hasCapability(actor, capability)`.
   `finance` (accountant) and `support` (customer service) already existed
   and are unchanged; `tester`/`engineer` are the first roles to use the new
   path. `tests/admin/gate-coverage.test.ts` needed no changes — every new
   page/action still calls the same `requireAdmin(` the test greps for.
2. The manual UAT runbook (originally `docs/launch/UAT_PRELAUNCH.md`)
   now lives natively at `/admin/uat`, gated by the new `uat:run` capability.
   **The page is the canonical source** — content is a structured TS array
   (`apps/web/src/lib/uat/runbook-steps.ts`: sections → items, each with a
   stable `id`, optional copy-value chips, an optional expected-result line,
   and an optional `action` binding), edited directly, no build step, no
   markdown, no parsing. This replaced an earlier markdown-rendering pass —
   purpose-built UI (per-section accordion, copy-to-click chips, inline
   PASS/FAIL) reads far easier for a tester than a rendered doc, and the
   `action`/`id` fields are now explicit data instead of pattern-matching
   rendered text. Checkboxes persist per environment in a new
   `uat_checklist_state` table (ephemeral run tracker, not an audit record),
   keyed by each item's real id — no more fragile document-order indexing.
   The standalone markdown doc is retired in favor of this page.

   Three of the runbook's manual/CLI steps became real buttons, each writing a
   `system`-targeted `Override` audit row (new `OverrideTargetType` value —
   these actions have no single teacher/student/booking/payment target):
   - **Run UAT probe** (§0) — the same two checks as `scripts/uat-probe.sh`
     reimplemented in plain `fetch()` (no `child_process` precedent exists
     in this codebase, and Vercel's serverless runtime isn't a place to
     shell out to bash/tsx).
   - **Run PostHog check** (§K.2) — queries PostHog's HogQL Query API
     directly server-side (`POSTHOG_PERSONAL_API_KEY`, already configured
     for local feature-flag eval) for the events the earlier sections should
     have generated, replacing "open the dashboard and eyeball it" with a
     real PASS/FAIL.
   - **Run Stripe check** (§B/§G) — reads charge/transfer/refund state
     directly from Stripe's API (two new **read-only** methods added to the
     existing `StripeClient` interface, `getCharge`/`getTransfer` —
     `apps/web/src/lib/stripe/client.ts`), independent of what our own
     DB/webhook handling recorded (`uat-verify.ts` already proves the DB
     side; this proves Stripe's side).
   - **Reseed preview** fires an Inngest event rather than blocking the
     request (reseeding is slow/bulk); the function
     (`apps/web/src/lib/inngest/functions/admin-reseed-preview.ts`) calls the
     CLI seed script's own `main()` (now exported, and now accepting the same
     `bulkTeachers`/`studentsPerBulkTeacher` knobs as the CLI's
     `SEED_BULK_TEACHERS`/`SEED_BULK_STUDENTS_PER_TEACHER` env vars, exposed
     as form fields) rather than duplicating its Supabase Auth Admin API /
     storage-upload wiring. It's guarded THREE times independently:
     `assertReseedAllowed()` in the server action before the event is even
     sent, `isProductionDeployment()` in the Inngest function, and
     `seedAll()`'s own `assertNotProductionTarget()` (`scripts/seed.ts`,
     inspects the actual DB connection string's project ref) inside the seed
     itself — the real backstop, since it checks what the process is
     actually connected to rather than trusting a flag. The button no longer
     just says "Queuing…" and leaves you to check `/admin/audit` — `main()`
     now returns its teacher/student summary, the completion/failure
     `Override` row carries it as `afterJson`, and the page polls
     `getReseedStatusAction()` every 1.5s (giving up after ~2 minutes) to
     show "✓ Reseeded — N teachers, M students" or the failure reason inline.

**Why it likely changed.** The UAT runbook required a command line and manual
PostHog/Stripe-dashboard eyeballing, so a non-technical tester couldn't run it
unassisted. Rather than bolt on a one-off page, this doubles as the first real
use of narrow, non-technical admin roles — testers today, accountants/
customer-service/engineering staff later — that see only their own slice of
`/admin` rather than a rung on the money-adjacent rank ladder.

**Unresolved risks.**

- **Hand-authored item ids can collide.** `runbook-steps.ts` assigns each
  item's id by hand (e.g. `"B.checkout"`) instead of deriving it from
  document position; a copy-paste duplicate would silently share checked
  state between two items. `tests/uat/runbook-steps.test.ts` asserts every
  id is unique and section-prefixed.
- **Checklist state is not audit-critical.** `uat_checklist_state` rows are
  an ephemeral per-environment run tracker, not the audit trail — that's the
  `Override` rows the four actions above write.
- **Reseed still depends on Supabase Auth Admin API.** `seedAll()`'s account
  provisioning (via `scripts/seed.ts`'s `main()`) predates this change and is
  tied to the still-in-progress better-auth migration (D-40); this ships that
  existing dependency through a button rather than removing it. Not new
  lock-in, but not resolved either — revisit once the better-auth cutover
  completes.
- **"Production" mode only covers §0/§K.2/§B/§G's automatable checks**, not a
  full replay of the §A–§J walkthrough (there's no seeded Beatriz/
  Fernando/Gabriela in production) — matches the doc's own narrower
  post-promote step, not a claim of full parity.

**2026-07-09 hardening (resolved).** Two follow-up gaps closed after
review:

- **Reseed form is now hidden server-side, not just disabled.** The page
  itself (`page.tsx`) passes `isProductionDeployment()` into `UatRunbook` as
  a prop; the component renders a short note instead of the reseed form/
  bulk-option inputs/status display when true. Belt-and-suspenders on top of
  the three existing guards (`assertReseedAllowed`, the Inngest function's
  own check, `seedAll()`'s connection-string guard) — there was no reason to
  even render a destructive control that's structurally impossible to use
  from a production deployment.
- **Stripe check's `env` label could silently lie.** `runStripeCheck()`
  always read from whatever Prisma/Stripe client the running deployment
  actually has — `env` was a pure passthrough label in the report, never
  used to pick a data source. Selecting "Production" while browsing preview
  silently checked preview data mislabeled as production (not a cross-
  environment leak — the check never reached the _other_ environment's
  data — just a misleading label). Fixed: `runStripeCheck` now compares
  `env === "production"` against `isProductionDeployment()` and, on
  mismatch, returns an early `environment-match` failure instead of running
  the check at all. Covered by `tests/uat/stripe-check.test.ts`.
