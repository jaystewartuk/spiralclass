# D-158. No account identifier is committed: where each one lives instead

**What changed.** Every identifier naming an account, a tenant or a box this
project owns is out of the tree and replaced with a placeholder, and
`scripts/check-leaks.mjs` grew a third gate that fails the build if one comes
back. This repository is published, so the rule is now load-bearing rather than
tidy.

**⚠️ This document deliberately contains no values.** It says what shape of
thing must not be committed and where each shape lives instead. A document
listing the identifiers that must not be in a public repository, committed to
that public repository, publishes them — which is the whole failure it would
exist to prevent. The values live in Infisical, in gitignored overlays, and in
the operator's own notes outside this repo.

## What counts as an identifier

Not a credential. Nobody can use an OCID, a Stripe account id or a GCP project
number on its own, and that is exactly why they get committed without anyone
flinching — each one is individually harmless and the check for credentials
correctly ignores them.

**In a public repository they are the reconnaissance surface, and they
aggregate.** The account, the box, the region, the tenant and the project
together say a great deal more than any one of them does alone: which provider
holds what, which box answers on which address, which accounts belong to one
person. That aggregate is worth removing even though no single line of it is
dangerous.

**The rule, stated once:** publish the shape, never the account.

| Shape                                                    | Where the real value lives                                                                                                                                      |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OCI resource ids (OCID)                                  | The operator's OCI console, and Tofu state. ⚠️ **Never a variable default** — `infra/oracle-box/variables.tf` takes `compartment_id` with no default on purpose |
| Box addresses, public and tailnet                        | Tofu state (`tofu output`), the Tailscale admin console. Docs reference how to get one, never the address                                                       |
| GCP project, and service-account addresses that carry it | `GEMINI_VERTEX_PROJECT_ID` in Infisical, projected into `config/env/*.runtime.local.env` (D-85 as amended by the `__LOCAL__` overlay work)                      |
| Stripe account, product and price ids                    | Infisical, or the Stripe dashboard. Fixtures in tests are built from `example`-shaped strings                                                                   |
| Cloudflare account and R2 bucket hosts                   | Infisical, and gitignored `*.tfvars`                                                                                                                            |
| LiveKit API keys                                         | Infisical. ⚠️ A retired key is still a key: it names the account that issued it                                                                                 |
| Another person's account ids                             | Nowhere in this repository, ever. See the second rule below                                                                                                     |

**The evidentiary cost of all of this is zero**, which is what makes it easy to
hold. What a configuration file, a runbook or a decision record is worth to a
reader is its keys, its structure and its reasoning. **No value carries any of
that.** A placeholder loses nothing a reader wanted.

## Two rules that are not about this operator

- **Another person's identifiers are not ours to publish.** A teacher's Stripe
  account ids were in a decision record, two tests and a source comment, as the
  worked example of a real failure. The failure is the evidence; the account
  number is not part of it. **Replaced with fixtures, and the record reads
  exactly as well.**
- **A placeholder is drawn from a reserved range**, so that a reader can tell at
  a glance that it is one: `203.0.113.0/24` and the other two documentation
  ranges for addresses, `example-`-prefixed strings elsewhere. ⚠️ **Never a
  plausible-looking invented value** — the next reader will try it.

## Decision records are edited for identifiers and for nothing else

This repository's convention is that a decision record is verbatim and is never
edited after the fact (D-133). **Replacing an identifier inside one does not
breach that convention and removing reasoning would.** What the convention
protects is the account of what was decided and why — including the parts that
are unflattering. An account number is not part of any argument; it is a
pointer, and the sentence around it survives its replacement unchanged.

⚠️ **The test is whether the record still says the same thing.** D-143's
worked example of a teacher's pre-existing Stripe account reads identically
with a fixture id. If a replacement ever makes a record say something different
or something false, the replacement is wrong, not the record.

## How this is enforced

`scripts/check-leaks.mjs` has three gates now, and this is the third:

- **SECRETS** — zero tolerance, no baseline. A committed key is compromised.
- **ACCOUNT IDENTIFIERS** — zero tolerance, no baseline. This decision.
- **PERSONAL DATA** — ratcheted against a baseline, because real addresses reach
  a repo through ordinary work and deleting them is a product decision.

It runs in the unit tier, so it runs on every pull request and every push. **The
patterns are shapes, never values**, for the reason at the top of this file.

⚠️ **The address pattern is scoped to `infra/`, `config/`, `scripts/`,
`.github/` and the two documentation trees.** A routable address in `apps/` is a
bot-detection fixture or a request-header test; one in `infra/` is a box. A
check that cannot tell those apart becomes noise, and a noisy check gets
switched off, which costs more than the finding it was guarding.

**When a match is genuinely not ours** — a vendor's published edge address, a
sequential hand-typed fixture — it goes in `IDENTIFIER_ALLOWLIST` with a reason.
⚠️ **Adding an entry to silence a red check is the failure this gate exists to
prevent.** The question to answer in the pull request is not "how do I make it
green" but "why is this string not an account".

## When an identifier is legitimately needed

**Add it to Infisical, and read it at run time.** The three shapes that already
exist, in order of preference:

1. **A key in `config/env/*.runtime.env` set to `__LOCAL__`**, with the real
   value in the gitignored overlay generated from Infisical. This is the route
   for anything the application itself reads.
2. **An environment variable with no default**, for scripts —
   `"${SOME_ID:?message saying where to get it}"`. A default that works is a
   committed identifier wearing a different hat.
3. **A gitignored file with a committed `.example` sibling**, for tooling that
   needs a file rather than a variable.

⚠️ **Never a fallback default.** `"${THING_ID:-<the real one>}"` is the pattern
that put an identifier in two deploy scripts and read as safe in review, because
the variable at the front makes it look configurable. It is not configurable; it
is a committed value with a switch beside it.

## What this cost

An afternoon, and nothing else. **No value removed here was carrying any
information a reader of this repository wanted**, which is why the sanitisation
touched 20 files and changed the meaning of none of them.

## Addendum — the Infisical project link, and the reason it needed a second pass

**`infra/infisical/.infisical.json` is gitignored, and `.infisical.json.example`
is the committed shape.** This reverses an earlier convenience on one point only: the
file still lives exactly where it lived, and every module still reaches it via
`--project-config-dir=../infisical`. What changed is that it holds a project id
and this repository is public.

⚠️ **It needed its own change because two of its readers run.**
`scripts/oracle-deploy.sh` and `scripts/oracle-render-livekit.sh` both carried
the id as `"${INFISICAL_PROJECT_ID:-<the real one>}"` — **the exact pattern the
rule above names**, and the reason it is named: the variable at the front makes
the line read as configurable in review, when what it actually is is a
committed identifier with a switch beside it. Both now take the environment,
then the gitignored link file, then fail with a message naming the setup step.

✅ **A machine that already works keeps working.** Gitignoring a file does not
delete it, so the link file stays on disk and every script resolves it exactly
as before. **A fresh clone is the case that changes** — and a fresh clone is
precisely when publishing this id would have mattered.

⚠️ **Restore it alongside `config/env/*.local.env`.** Both are gitignored, both
are needed, and neither is in any repository — so a clone replaced or moved has
to carry both across by hand.

## Addendum 2 — the PostHog project id, and the one that was hardest to argue

**`POSTHOG_PROJECT_ID` is configuration**, read from `serverEnv()` like every
other key. It was a constant in `lib/uat/posthog-check.ts`, with a comment
calling it _"non-secret, stable"_ — which was true and is not the test.

⚠️ **This is the weakest item on the list and it still goes.** A PostHog project
number grants nothing without `POSTHOG_PERSONAL_API_KEY`, and it appears in
every dashboard URL the operator opens. What it does is name an account, and
the rule is not "remove what is dangerous" — it is **publish the shape, never
the account**, precisely so that each judgement does not have to be made one
value at a time by someone who will get tired of making them.

**Absent means unconfigured, not broken.** The `/admin/uat` PostHog check
reports itself unconfigured rather than failing the page, the same way it
already does when the API key is missing. **The runbook step lost its
copy-paste URL and gained an instruction** — PostHog's own navigation is one
click, and a runbook step is a thing a person reads.

⚠️ **It is deliberately NOT in `config/env/*.runtime.env`.** Adding a key there
commits this repository to resolving it at build, at deploy and at boot
(#1051's three gates), which is the right treatment for a value the product
needs and the wrong one for a value only an admin check reads. **An optional
server key costs nothing when absent.**
