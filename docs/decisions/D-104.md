# D-104. Teacher activation model: public listing gates on Marketplace Ready, not just onboardingCompleteAt

**Status: Active (built; needs promote + operator monitoring of the first
cutover — see risk section).**

**What changed.** Implements the redesign proposed in
`the teacher-activation review`. Before this,
`Teacher.onboardingCompleteAt` was the _only_ activation signal in the
product — it means "submitted the 4/5-step wizard," nothing more, and it was
also the sole gate on public listing (`/b/[slug]`, checkout, leads, the
sitemap). A teacher could finish the wizard in under
two minutes, keep every auto-seeded default, connect no payment rail, and
still be a fully public, bookable, indexed listing.

- **New shared resolver** (`packages/shared/src/activation.ts`):
  `isMarketplaceReady()` — onboarding complete AND a real profile
  (photo + bio) AND a reviewed teaching offer AND a reviewed availability
  schedule AND a connected payout rail (Stripe `chargesEnabled` or
  `isWiseReady()`). `resolveActivationState()` additionally names
  `firstBookingReceived`/`firstPaymentReceived`/`activeTeacher` (all
  informational — see "design principle" below). Reuses the codebase's
  existing derived-state style (`isNewTeacher`, `isWiseReady`, `growthSteps`)
  rather than a stored status enum.
- **Two new nullable `Teacher` columns** distinguish a genuinely
  (re-)submitted onboarding step from the untouched starter-seed defaults
  (migration `20260725000000_add_teacher_activation_touched_at`):
  `templatesTouchedAt`, `availabilityTouchedAt` — set on every real call to
  `saveTemplatesAction`/`saveAvailabilityAction`, whether from onboarding or
  Settings. Same migration adds
  `marketplaceReadyAt` (a one-time-analytics-fire cache, never a gate — see
  `lib/marketplace-ready.ts`) and `stripeRequirementsDisabledReason`
  (mirrors Stripe's `requirements.disabled_reason` so a restricted/rejected
  Connect account is distinguishable from "not yet verified").
- **Public listing gate: `isPubliclyListed()`**
  (`apps/web/src/lib/marketplace-ready.ts`) = `isMarketplaceReady()` AND not
  moderation-disabled. Replaces the previous `!onboardingCompleteAt ||
disabledAt` check, independently repeated with no shared helper, at every
  public/anonymous-funnel call site: `/b/[slug]` (page + metadata +
  `opengraph-image.tsx`), `/b/[slug]/buy`, `sitemap.ts` (translated to a
  Prisma `where` by hand, since a JS predicate can't run inside a query),
  `actions/checkout.ts`'s `createCheckoutIntent` (the anonymous funnel only —
  see below) and `actions/leads.ts`. One of these (`opengraph-image.tsx`'s
  `disabledAt`) was found not checking moderation status at all before this
  change — a real,
  independently-discovered gap closed as a side effect.
- **Deliberately NOT re-gated**: `requireOnboardedTeacher()` (the entire
  authenticated teacher app —
  a teacher must be able to reach Settings to become Marketplace Ready in
  the first place, so gating those on the stricter bar would be a
  chicken-and-egg lockout), the onboarding wizard's own internal checks, and
  any EXISTING-relationship flow (`createPortalCheckoutIntent`,
  `(student)/my-classes/buy`) — a student who already
  has a teacher relationship shouldn't lose access to it because the
  teacher's public profile isn't "complete" by marketplace standards.
- **Design principle**: `marketplaceReady` is the _only_ state in the model
  that changes product behavior (the listing gate). Every other resolved
  state (`profileComplete`, `teachingOfferCustomized`,
  `firstBookingReceived`, `activeTeacher`, …) is informational/telemetry
  only — mirrors the existing "never fully lock out a Free-tier teacher"
  posture already established for subscriptions.
- **Dashboard banner fix.** The old "Start here"
  banner (gated on `teacherStudents===0 && bookings===0`, hand-rolled
  styling) is replaced with an `!marketplaceReady`-gated `<Alert>` that
  correctly re-shows once a teacher has real bookings but still lacks a
  payout rail — the exact case the old gate silently stopped surfacing.
  The "Crecer" growth checklist (`packages/shared/src/growth.ts`) gains a
  `payment` step (ordered first — every other step is moot if a teacher can't
  get paid) and an aggregate `percent`, rendered as a progress bar.
- **Analytics**: web previously fired zero onboarding-step events server-side; new
  `onboarding_started`/`onboarding_step_completed`/`onboarding_finished`
  close that gap. `trial_started` + the starter-template seed events
  previously never fired for one signup path (a duplicated code path bug,
  not by design) — unified into one `provisionNewTeacher()` helper every
  lazy-create call goes through. New `marketplace_ready` (fired once, via the
  `marketplaceReadyAt` conditional-update guard — the same "first
  transition" idiom the Connect webhook already used for
  `payout_rail_connected`), `first_booking_received`/`first_payment_received`
  (a plain count check at the existing `booking_created`/`payment_received`
  call sites — an acceptable analytics-only race, not guarded like a real
  state transition), and `dashboard_viewed` (previously absent on both
  platforms — the denominator any activation funnel needs).
- **Stripe UX**: the Connect return route's `refresh=1` param (sent when an
  Account Link expired/was abandoned) was read into the URL but never
  branched on — an abandoned flow looked identical to a completed one. Now
  redirects `?incomplete=1` distinctly when a refresh-triggered return still
  isn't charge-ready. `stripeRequirementsDisabledReason` is surfaced in the
  payments settings UI as a specific "action needed" line instead of the
  previous generic "pending verification" for every not-yet-enabled state.
- **Country-change guard**: `saveTimezoneAction` now refuses a `country` change
  once
  `teacher.stripeAccountId` is set (Stripe fixes a Connect account's country
  permanently at creation — changing the local field afterward would desync
  the record from what Stripe actually has on file, not just move the
  teacher in/out of the payout circle).
- **Admin re-engagement query**: a new `stalled=yes` filter on
  `/admin/teachers` (`lib/admin-filters.ts`) surfaces teachers who finished
  onboarding 14+ days ago (`STALLED_TEACHER_DAYS`) and still aren't
  Marketplace Ready — a DB-level translation of the same predicate, kept in
  sync by hand. Deliberately just the query + an admin-visible list, not an
  automated nudge (email/push) — the audit's own recommendation was to
  validate the query against real data first.

**Why apply the listing gate immediately to every teacher, not just new
signups.** Operator decision (2026-07-25), explicitly choosing the highest-
blast-radius option over a grandfather period or grace window: any
currently-live teacher without a payment rail is, by construction, a teacher
who cannot actually be paid through the platform today regardless of this
change — the risk is a visibility/optics drop for those accounts, not real
lost revenue, since they were never collectable through Stripe/Wise in the
first place. No staged rollout, no feature flag, no grace period was built
for this cutover.

**Deferred, per the audit's own recommendation, not built here.** A
structured subject/level taxonomy on `PackageTemplate` (currently free
text) — the audit itself labeled this "no evidence of current demand,"
explicitly not a firm recommendation; the automated re-engagement
email/push send (query only, per above); a real credentials/qualifications
model; per-teacher cancellation-policy configuration (currently a hardcoded
platform-wide rule).

**Unresolved risks — read before/while promoting.**

1. **The listing-gate cutover has no staged rollout or feature flag.** The
   audit's own risk section recommended shipping every measurement/UI change
   first, observing the real distribution of teachers below Marketplace
   Ready for a full measurement cycle, and only then flipping the gate with
   an explicit grandfather decision. The operator chose to skip that
   staging and apply immediately. Before/immediately after promoting, check
   how many currently-live teachers this newly unlists (via the `stalled`
   admin filter above, adapted, or a direct query on `isMarketplaceReady`'s
   five sub-conditions) so the actual blast radius is known, not assumed.
2. **No grace period for an affected teacher.** A teacher who was previously
   bookable and suddenly isn't (e.g., she never uploaded a photo) gets no
   in-product warning before the cutover — only the dashboard banner/growth
   checklist after the fact. If this causes real support friction, the next
   lever is a time-boxed grace window keyed off `marketplaceReadyAt`/
   `onboardingCompleteAt`, not built here.
3. **`isPubliclyListed()`'s Prisma `where` translations (`sitemap.ts`,
   `admin-filters.ts`'s `stalled` filter) are hand-kept in sync with the JS
   predicate** — a future change to `isMarketplaceReady()`'s logic must be
   mirrored in both `where`-clause translations by hand, or they will
   silently drift from the actual gate.
4. **Stripe's `disabled_reason` strings are surfaced verbatim** (e.g.
   `"requirements.past_due"`) — not translated to friendly copy. Acceptable
   for a first cut per the audit; a follow-up could map the known reason
   codes to localized guidance.
