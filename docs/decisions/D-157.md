# D-157. GitHub Actions comes back, because the repository is public — the registry and the deploy script stay the single definitions

**What changed.** `.github/workflows/` exists again, with three files, on a
repository that is now public. It supersedes [D-119](./D-119.md),
[D-120](./D-120.md), [D-129](./D-129.md) and [D-146](./D-146.md) in part — the
parts that were arithmetic against a metered Actions allowance. **The parts
that were about correctness are kept, and two of them are now enforced harder
than before.**

| Workflow                | Fires                                                            | Runs                                                                                      |
| ----------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `gate.yml`              | every PR into `main`, every push to `main`                       | `node scripts/ci/gate.mjs --tier fast`, then posts the `local-gate` commit status         |
| `deploy-preview.yml`    | push to `main` that `relevance.mjs` says can change the artifact | `bash scripts/fly-deploy.sh preview`                                                      |
| `deploy-production.yml` | push to `production`, after a required reviewer approves         | `bash scripts/fly-deploy.sh production --gate-already-passed`, then the production probes |

**Read the second column before anything else.** Every workflow is one line of
work wrapped in setup. None of them lists a check, and none of them lists a
deploy step. That is the condition on which this was allowed back at all.

## Why the premise changed

D-129's opening sentence was the operator's constraint, stated directly: _no
GitHub Actions on private repos._ D-120 measured its way there — ~1,500-1,700
billable minutes a month against a 2,000-minute allowance, the deploy alone
~744 of them — and D-129 escalated it to a principle after the allowance
emptied mid-month and took **eleven days of production database backups** with
it.

**Actions minutes are free on a public repository.** The repository is public.
The arithmetic is not wrong; it no longer applies to anything.

## The better argument, which is not about money

`scripts/fly-deploy.sh` builds an `amd64` image because Fly runs `amd64` images
only. The operator's machine is an arm64 Mac, so that build has been a **QEMU
cross-build: 20-30+ minutes, and "flaky with threaded native addons"** by the
measurement in its own header. D-120 accepted that as the price of ~744
minutes a month and named it an unresolved risk: _"if it is worse, promoting
becomes something you schedule rather than something you do."_

`ubuntu-latest` is genuine `amd64`. The build is native, with no emulation at
all. **That is a better reason to move the deploy than the bill ever was**, and
it would have been a good reason even while the minutes were metered.

## The one architectural rule, and why it is the whole decision

> **`scripts/ci/steps.mjs` stays the single source of truth for what "green"
> means. `scripts/fly-deploy.sh` stays the single source of truth for what a
> deploy is. The workflows CALL them. They never restate them.**

D-119's real achievement was not moving CI to a laptop — it was collapsing two
definitions of the checks into one. Part of what D-129 deleted was a
dispatch-only copy of every gate job, and that copy was a second definition
waiting to drift. Re-adding workflows re-opens exactly that hazard, so the
guards are pointed straight at it:

- `gate.yml` runs `gate.mjs --tier fast` and names no steps. A guard test
  derives the forbidden command list **from `STEPS` itself**, so a check added
  to the registry is covered the moment it lands, with no list in the test to
  remember to widen.
- Neither deploy workflow contains `flyctl deploy`, `docker buildx build` or
  `prisma migrate deploy`. ⚠️ **The last time the deploy steps existed in two
  places, the copy that got re-typed was the one missing the Neon
  checkpoint** — that is D-120's own account of how a local deploy silently
  skipped the pre-migration restore point while `promote.mjs` went on claiming
  it had been taken.
- `deploy-preview.yml` asks `scripts/ci/relevance.mjs` whether a push can
  change the artifact, rather than declaring `paths:` globs. That predicate is
  pure and table-tested; a glob list would be a second answer covered by no
  test.
- Node's version is read out of the `Dockerfile`'s `FROM` line, and pnpm's out
  of `package.json`'s `packageManager`. Nothing about the toolchain is stated
  twice.

## What the guard tests do now

⚠️ **They were inverted, not deleted.** `apps/web/tests/config/local-gate.test.ts`
had a block asserting `.github/workflows` did not exist. It now asserts the
workflows exist **and** that they cannot do the things that made Actions a
liability:

- No `runs-on:` that is not exactly `ubuntu-latest`. Larger runners are billed
  by the minute **even on a public repository**, and the first sign would be a
  bill rather than a red build.
- Every `uses:` pinned to a full 40-character commit SHA, with the version in a
  trailing comment. `sha_pinning_required` is already on for this repository so
  `@v4` is rejected by policy — this is the copy of that rule that lives in the
  repo, where turning the server setting off does not turn it off.
- `permissions: contents: read` at the top of every file, elevated per job only
  where something is written. Exactly one job in the three writes anything: the
  one that posts the commit status.
- No `pull_request_target` anywhere. It runs with a privileged token against
  untrusted code and it is how public repositories get compromised.
- No `schedule:` trigger anywhere. D-157's scope is the gate and the deploys;
  bringing a cron back is a decision, not a drive-by.
- A `concurrency` group on every workflow, with `cancel-in-progress: false` on
  both deploys — cancelling a half-finished deploy leaves migrations applied
  with no image deployed against them.
- A `timeout-minutes` on every job. The default is six hours.
- `persist-credentials: false` on every checkout. None of these jobs pushes.
- No `${{ }}` interpolation of event-derived values inside a `run:` body; those
  go through `env:`, where they are data rather than shell.

A guard removed is a guard that stops guarding. A guard inverted still holds an
invariant, and these are the invariants worth holding now.

## What is kept from the four decisions this supersedes

- **D-119's registry.** Untouched, and now enforced against two runners instead
  of one.
- **D-119's `local-gate` status.** Untouched. It is a REST call bound to one
  SHA, which is what stops a green result drifting onto later work. Two
  producers post it — the pre-push hook and `gate.yml`'s `status` job — running
  the same registry, so they can only disagree about timing.
- **D-119's pre-push hook.** Kept, and it is not redundant. It is the reason
  the checks run **before** a push rather than after one, which was the failure
  mode it was written for (confirmed 2026-07-20: an edit made after a green
  run, pushed without re-checking).
- **D-120's anti-drift rule, which is the one that still binds.** What left
  `production` 96 commits behind live on 2026-07-19 was a **human dispatch
  step**. `pnpm promote` still runs the full tier and still ends by pushing
  `production`, and **that push is the trigger** — so there is still nothing to
  remember. It then watches the run with `gh run watch --exit-status`, so a
  green `pnpm promote` still means production is serving, which is what that
  command has always meant.
- **D-146's batching, for the heavy tier.** `pnpm ship-pr` still gates each PR
  fast, merges, and runs the full tier once against merged `main`. Nothing
  about that moved.
- **D-129's refusal of a scheduler.** No `schedule:` trigger came back. The
  production probes moved from `pnpm promote` into `deploy-production.yml`'s
  last step — still at the moment a deploy could have broken something, not on
  a clock.

## The production environment, and why a reviewer is not the 2026-07-19 drift again

Production deploys through a GitHub Environment named `production` with a
**required reviewer**, and the production Fly token and database URLs exist
**only** inside it — so no other workflow in this repository can reach them
even by typo.

That reviewer is a human in the path, which is what D-120 spent a decision
removing. The difference is that the two failures do not look alike:

- **A forgotten dispatch is invisible.** Nothing anywhere says a deploy is
  owed. That is how 96 commits accumulated.
- **A pending environment approval is a queued run** in the Actions tab with a
  notification attached, `pnpm promote` sitting in the foreground waiting on
  it, and `pnpm release:status` exiting non-zero the whole time `production` is
  ahead of what shipped.

It is worth having because this is the deploy that runs migrations against live
payment records. It is the last look before that, and the Neon checkpoint
(D-95) is taken seconds after it.

## ⚠️ What happens if this repository ever goes private again

**This is the question the premise change makes unavoidable, so it is answered
here rather than rediscovered.**

The minutes become metered again the moment visibility flips, and at the
measured rates in D-120's table the three workflows here would land near the
allowance on their own. **Nothing warns about this**: GitHub does not object,
the workflows keep running, and the first symptom is the one D-129 recorded —
runs failing mid-month, with the most important one being whichever mattered.

The reversal is deliberately cheap, and in this order:

1. **Delete `.github/workflows/`.** Nothing else has to change. The gate is
   `pnpm gate`, the deploy is `./scripts/fly-deploy.sh <env>`, and the probes
   are `pnpm local synthetic` — all three already exist, are already the
   things the workflows call, and are already run by hand today.
2. **Re-invert this file's guard block** so it asserts the absence again. The
   text D-129 wrote is in git history at `4a9f98e12^`.
3. **Restore the deploy inside `pnpm promote`** — one `run()` call, replacing
   the `gh run watch` block.
4. **Accept losing the native build.** The QEMU cross-build comes back, and
   with it D-120's unresolved risk that promoting becomes something you
   schedule.

**Nothing in this decision is load-bearing for shipping.** That is the property
to preserve: if a workflow file is ever the only way to deploy or the only
definition of a check, this reversal stops being cheap and the arrangement has
been broken.

## What is deliberately NOT done

- **The full tier stays on the laptop**, and for a concrete reason rather than
  inertia: the visual-regression baselines under `apps/web/tests/visual` are
  `-darwin.png`, so `scripts/ci/e2e.sh` cannot go green on a Linux runner until
  they are regenerated for Linux or the sweep is made platform-neutral. That is
  the single piece of work that would move integration and E2E onto runners,
  and it is worth doing.
- **No Docker layer cache on the deploy.** The `type=gha` backend needs runtime
  credentials that only an action can expose, and a `type=local` cache of a
  Next build risks the 10GB repository cache budget. `scripts/fly-deploy.sh`
  reads `BUILDX_CACHE_FROM`/`BUILDX_CACHE_TO`, so adding one later is a
  workflow change with no script edit — and the native build is already several
  times faster than what it replaces.
- **No Infisical machine identity.** The prompt that produced this work
  preferred one, on the sound argument that one source of truth for secrets
  beats two. It does not apply here: the six `__LOCAL__` **build-time** values
  in `config/env/<env>.build.env` have no home in Infisical, so they must come
  from GitHub environment secrets regardless — and adding Infisical for only
  the database URLs would create the second source rather than remove it.
  GitHub Environments give the property actually wanted, which is per-
  environment scoping. If those six values ever move into Infisical, the
  machine identity becomes the right answer and this should be revisited.
- **No branch protection changes.** They were impossible on a private free
  repository (paid feature, 403 on the API) and are now available. Requiring
  the `local-gate` context server-side is a real improvement and is its own
  small decision.

## Unresolved risks

- **A deploy run by Actions leaves no entry in the local release ledger.**
  `.gate/release.json` is written by `record-release.mjs` inside
  `fly-deploy.sh`, on a runner whose filesystem is thrown away. `pnpm
release:status` already reports a missing entry as _"no local record"_ rather
  than _"did not ship"_, so it degrades honestly rather than lying — but it is
  less useful than it was, and the authoritative record is now `git log
origin/production`, the Fly release list and the Actions run history.
- **A fork PR gets no `local-gate` status.** Fork PRs receive a read-only token
  and no secrets, so the `status` job cannot post. On a repository with one
  maintainer this is correct rather than a gap — nothing about a fork's code
  should be able to certify itself — but it means an outside contribution needs
  the maintainer to run the gate.
- **`gh run watch` inside `pnpm promote` blocks on the approval.** If the
  operator approves from a phone and the terminal is closed, the deploy carries
  on and the promote's exit code is lost. The deploy is the thing that matters
  and it is unaffected; the summary is not.
- **The turbo remote cache is a secret, so it is cold on fork PRs.** Additive,
  never required — a fork's gate is correct, just slower.

## Addendum, 2026-09-04 — both deploy workflows are suspended the day they landed

**What changed.** `deploy-preview.yml` and `deploy-production.yml` lose their
`push` triggers and keep only `workflow_dispatch`. `pnpm promote` now **refuses
before the fast-forward** when the production workflow has no `push` trigger.
`gate.yml` is untouched and still runs on every pull request and every push to
`main`.

**Why.** The operator's decision, hours after this record merged: **there are
no more Fly deploys.** The next deploy of this application is the Oracle A1
cutover ([D-150](./D-150.md)). Until that box is serving, both workflows point
at a target that is being retired, and a live `push` trigger would fire a
failing deploy at it on every merge.

**Why this is a suspension and not the re-manualization D-120 forbids.** The
distinction is worth being exact about, because the two shapes look identical
from outside. D-120's rule exists because a deploy someone has to remember gets
forgotten, and `production` sat 96 commits behind live when one was. That
argument assumes a live target and a reason to ship. Here shipping to the
target is the thing not wanted, so there is nothing to forget — and the fix
when Oracle lands is to **restore the trigger against the new target**, not to
leave a dispatch step in place and call it finished.

**The refusal in `pnpm promote` is the part that matters.** Without it, promote
would fast-forward `production`, wait a minute for a run that can never start,
and leave the branch ahead of what is live — the 2026-07-19 incident reached
from the other direction. It reads the trigger off the workflow file rather
than a hardcoded flag, so restoring the trigger clears the refusal with no
second edit to remember.

**⚠️ The architecture argument inverts with the target, and this record's
headline case goes with it.** "The better argument, which is not about money"
above rests on `ubuntu-latest` being genuine amd64 against an arm64 Mac.
Oracle's A1 shape is **`aarch64`** — D-150 notes the same fact from the other
side, that the move "stops needing the amd64 cross-build under QEMU". So on the
new target `ubuntu-latest` becomes the emulator and the laptop becomes native.
GitHub's arm64 runners are free on a public repository, which keeps the
native-build argument alive, but it changes the label — and
`apps/web/tests/config/local-gate.test.ts` asserts `runs-on` is exactly
`ubuntu-latest`. **Invert that guard when the workflows are repointed; do not
delete it.** It exists to stop a billable runner, so an arm64 runner has to be
allowed by name rather than by widening the check to anything.

**What is unaffected.** The whole point of D-157 — that the workflows CALL
`scripts/ci/gate.mjs` and `scripts/fly-deploy.sh` rather than restating them —
is what makes this cheap. Repointing at Oracle is writing one deploy script and
changing what the workflow invokes; the guards, the permissions, the pinning and
the environments all stand. `scripts/fly-deploy.sh` itself is kept: D-150
deliberately preserves Fly as a target rather than deleting it, and going back
is meant to be a command.

## Addendum 2, 2026-09-04 — production's trigger comes back the same day

**What changed.** `deploy-production.yml` gets its `push` trigger on
`production` back. `deploy-preview.yml` stays on `workflow_dispatch` alone.

**Why.** The suspension above rested on one premise — "there are no more Fly
deploys" — and hours later that premise was narrowed to preview only.
[D-150](./D-150.md)'s second addendum: **the production web app stays on Fly
and production's database stays on Neon; Oracle carries preview, preview's
database and the LiveKit stack.** So Fly is production's target, not a target
being retired, and there is nothing about this workflow to suspend.

**Leaving it suspended would have been the worse mistake.** A `production`
branch that fast-forwards and deploys nothing is the 2026-07-19 incident
reached from the other direction, which is exactly what the refusal in
`pnpm promote` was built to prevent. That refusal reads the trigger off the
workflow file, so restoring the trigger clears it with no second edit — the
property this record claimed for it, exercised on the first occasion it was
needed.

> [!WARNING]
> **A live trigger is not a working deploy, and the gap is worth naming.**
> Measured 2026-09-04: the `production` environment holds **zero** secrets. The
> job reads `DATABASE_URL`, `DIRECT_URL` and six `NEXT_PUBLIC_*` from it, and
> `scripts/env-config.mjs` throws naming every unsatisfied key — so a promote
> today would fast-forward `production` and then fail, which is the drift state
> in miniature. **Filling both environments is already boarded for the day the
> repository goes public**, and it has to happen there anyway: the flip creates
> a NEW repository, and environments and secrets are repository settings that
> no history rewrite carries.

**Preview's suspension stands, and its restoration is not symmetric.** Its
target really is moving. When the box is serving, restoring it means three
changes at once, none of them cosmetic:

- **`runs-on: ubuntu-24.04-arm`.** The A1 shape is `aarch64`, so the argument
  in the first addendum applies to PREVIEW, not to production — production's
  Fly image is amd64 and `ubuntu-latest` is still native for it. ⚠️ **Invert
  the `runs-on` guard in `apps/web/tests/config/local-gate.test.ts` for the
  preview job only; do not delete it.** It exists to stop a billable runner.
- **It calls `scripts/oracle-deploy.sh`**, not `scripts/fly-deploy.sh` — one
  line, per this record's own rule that a workflow invokes a script and
  restates nothing.
- **It needs two credentials that do not exist yet**: a Tailscale OAuth client,
  because the box's `:22` is closed to the internet and the tailnet is the only
  way in, and an Infisical machine identity, because the deploy renders config
  from Infisical and a runner has no operator session to borrow. Plus GHCR, to
  replace the laptop's `docker save | docker load` over the tailnet.

**What is unaffected.** `scripts/fly-deploy.sh` — kept, as this record already
said, and now for the plainer reason that it is what ships production.

## Addendum 3, 2026-09-05 — the heavy tier moves after all

**What changed.** The "What is deliberately NOT done" section above opens with
_"The full tier stays on the laptop"_, on one concrete blocker: the
visual-regression baselines are `-darwin.png`, so `scripts/ci/e2e.sh` cannot go
green on Linux. [D-161](./D-161.md) removes that blocker and moves the heavy
half — the mutation spot-check, integration and the browser suites — onto
`ubuntu-latest`, on every pull request.

**The blocker was real; the remedy this record imagined was not the cheapest
one.** Both options named above — regenerate the baselines for Linux, or make
the sweep platform-neutral — treat the darwin set as something to be replaced
or diluted. Neither is necessary. Playwright suffixes a snapshot with
`process.platform`, so **two sets can coexist**, each authoritative for the
machine that reads it. D-161 commits 120 `-linux.png` beside the 120
`-darwin.png` and changes nothing about what the laptop asserts.

**What is unaffected, and it is the part this record cared about.**
`scripts/ci/steps.mjs` is still the single definition of what "green" means,
and `heavy.yml` names no step: it asks the registry for the tier as JSON and
fans a matrix out over the answer, so a heavy step added to `steps.mjs` gets a
runner in the same commit. Every guard this record lists — `ubuntu-latest` only,
SHA-pinned actions, explicit permissions, no `pull_request_target`, no
`schedule:`, a timeout per job, `persist-credentials: false`, no event-derived
interpolation in a `run:` body — applies to the new workflow and is asserted
against it by the same tests.

**The reversal stays cheap, which is this record's own stated test.** Deleting
`.github/workflows/` still leaves `pnpm gate:full` running every one of these
suites on the laptop. D-161 adds a third file to delete and no new dependency:
the `-linux.png` baselines would simply go unread, exactly as the `-darwin.png`
set does on a runner today.
