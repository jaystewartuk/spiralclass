# D-204. What a teacher sends, a new student is told about by default; a send that will not reach them says so on the teacher's screen

**Status.** Active · reverses the `class_materials: false` half of the
new-student defaults (an undocumented code-comment decision, written after
PostHog showed new students returning to `/settings/notifications`). Does not
touch the dispatcher's category gate, any stored preference, or the roster
import's all-off snapshot.

**What changed.** `defaultNewStudentNotificationPrefs()` now starts
`class_materials` **on**, alongside `class_reminders`, `booking_updates` and
`messages`. Only `expiry_reminders` (package renewal and expiry nudges) still
starts off. The category keeps its name but covers what a teacher sends or sets:
class materials, library assignments, and the whole homework lifecycle. Where a
teacher assigns or sends one of those (the class page and the student's
Materials tab) a notice now says when the student will not be told — her
category is off, or the student is still paused after a roster import — and that the
item still appears in the student's portal.

**Why.** Measured on production's `/admin/notifications` on 2026-10-22: a
student's two `materials_send` rows from 2026-10-16 were both `suppressed
preference-disabled:class_materials`, with no email row after them. The
dispatcher gates by category before any channel is tried
(`lib/notifications/dispatcher.ts`), so "off" silences push and email alike. The
teacher's screen gave no sign of it, and a call on 2026-10-22 ended with that
student believed not to be receiving notifications at all. Their reminders and
confirmations were all being sent; only the category a teacher's own sends rely
on was off, because every new student was stored with it off.

Materials and homework are the teacher doing the job, not the platform
marketing. A send that is dropped silently is worse than one that is
over-delivered: the teacher believes it landed.

**What was considered and rejected.**

- **Email fallback when push is suppressed.** Wrong diagnosis. The category gate
  runs before channel resolution and is meant to; a fallback would override an
  explicit opt-out.
- **Backfilling stored values.** A stored `false` cannot be told apart from a
  student's own choice: `Student.notificationPrefs` is a bare JSON column with
  no marker or timestamp. Flipping all of them would override people who really
  opted out. Not done here; see the trade-offs.
- **Default-on for `expiry_reminders` too.** Renewal nudges are the platform
  talking about a package, not a teacher talking to a student. They stay opt-in.
- **Warning the student instead.** The person who can act on the gap is the
  teacher, who can message the student or switch notifications on, so the notice
  is teacher-only.

**What it constrains.**

- A new `student.create` must stamp `defaultNewStudentNotificationPrefs()`
  and never a literal map. `tests/notifications/student-creation-prefs.test.ts`
  fails on a fourth creation site that does either.
- An explicit opt-out is honoured. Nothing may re-enable a category the
  student turned off, and the notice describes the gap; it does not close it.
- The roster import stays all-off and is launched by the teacher
  (`allDisabledPrefs`, `isNotificationsFullyDisabled`). That is what `paused`
  names in the notice.
- The suppression reason stays recorded on the notification row, so the gate
  remains visible in the admin list.

**What was affected.** `lib/notifications/preferences.ts`,
`lib/notifications/student-gap.ts` (new, pure), `components/notification-gap-notice.tsx`
(new), the class detail page, the student Materials tab, the notification
settings form's "essential" group, the i18n catalogs (en, es, fr),
`docs/features/notifications.md`.

**Trade-offs accepted, and unresolved risks.**

- **Existing students are mostly unchanged.** Anyone created before this keeps
  `class_materials: false` until the student or the teacher changes it, except
  the narrow group the backfill below turns on. The notice makes the rest visible;
  it does not fix them.
- **The backfill is deliberately narrow, and a heuristic.** Migration
  `20261025230000_backfill_untouched_class_materials_pref` sets only
  `class_materials` to `true`, and only where the stored JSON equals the exact
  old default map (`class_reminders`, `booking_updates`, `messages` true;
  `class_materials`, `expiry_reminders` false; no `channelPrefs`) **and** the
  student has never signed in (`authUserId` null), so could not have chosen
  anything. A signed-in student whose row still equals the old default is left
  alone, because a saved identical choice looks the same. Roster-import all-off
  rows, null rows and every other shape are untouched. A student who never
  signed in cannot have saved that exact shape on purpose, so the heuristic errs
  toward not flipping. Telling chosen from default for signed-in students would
  take a "last saved by the student" marker on every write path
  (`app/actions/notification-prefs.ts`, the teacher's launch toggle and student
  merge); that is not built, and is the place to start if a second backfill is
  ever wanted.
- **Nothing measures whether the notice changes what teachers do.**
