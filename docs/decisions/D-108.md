# D-108. Captions Agent ships from a git checkout on the box, not GHCR (interim)

**What changed.** The LiveKit captions Agent — the **only first-party code on
the self-hosted Oracle box** — now reaches production through a real git
checkout on the box plus a locally-built, SHA-pinned image. Concretely, as of
2026-07-29 (deployed `a9d039a8`):

- `~/spiralclass` on the box is a genuine checkout of **`main`** (originally
  `production` — reversed hours later, see the addendum). It
  replaces `/home/ubuntu/captions-agent-src`, a hand-copied partial source
  tree with **no `.git`**, whose contents could only be identified by hashing
  files over SSH.
- **The box holds no GitHub credential.** The repo is private and the box's
  existing `id_ed25519` is not an authorized deploy key. Rather than add one,
  the operator's machine pushes over Tailscale SSH into a repo configured
  `receive.denyCurrentBranch=updateInstead`, so the push updates the working
  tree directly and refuses whenever that tree is dirty. Commit SHAs survive
  the transport, so `git rev-parse HEAD` is still a verifiable answer to
  "what is deployed?".
- Images are built on the box and **double-tagged `:<sha>` + `:latest`**, and
  `~/oracle-livekit-production/docker-compose.yml` pins the **`:<sha>`**.
  Rollback is repointing that tag plus `docker compose up -d --no-build` — no
  rebuild, no network. The SHA tags survive both `docker image prune` and
  `docker builder prune`; an untagged previous image would not.
- ~~Tracking `production` rather than `main` is deliberate: the Agent's
  `captionsOn` contract is shared with the clients, and
  `production` is the only branch that advances through the full promote
  gate.~~ **Reversed the same day — the box tracks `main`. See the addendum.**

Runbook: [`ORACLE_LIVEKIT_PRODUCTION.md`](../deployment/ORACLE_LIVEKIT_PRODUCTION.md)
§"Captions Agent — deploy & rollback". Rollback also cross-referenced from
[`RELEASE_AND_STAGING.md`](../deployment/RELEASE_AND_STAGING.md).

**Why it likely changed.** On 2026-07-28 a teacher saw no captions for a full
class while the student saw them. The running image had been built 2026-07-26
from the hand-copied tree and predated `19307f60` (the teacher-only toggle).
The bug itself was a two-line semantic change; what made it a two-day silent
outage was that **nothing reported what was deployed** — no version in the
logs, no image label, no checkout to diff against.
`CAPTIONS_AGENT_DELIVERY.md`
specified the durable fix (GHCR build workflow + Tailscale-to-box CI deploy +
version stamping), but that plan carries a blocking arm64-runner decision and
introduces credentials in **both** directions (a Tailscale OAuth client for
CI→box, a GHCR read token on the box). This interim path fixes the
_provenance_ half — the half that actually caused the outage — with **zero new
credentials** and no CI surface, and does not foreclose any of it.

Choosing it also settled two of that plan's open questions cheaply: arm64 is a
non-issue when building natively on the box, and immutable-tag rollback turns
out not to require a registry at all — local tags are enough for a single-box
deployment.

**What was affected.**

- Box-local only: `~/spiralclass` (new), `~/oracle-livekit-production/
docker-compose.yml` (`build:` context repointed, `image:` pinned to a SHA).
  **No file under `infra/` was touched** — see the drift note below.
- `docs/deployment/ORACLE_LIVEKIT_PRODUCTION.md` — new deploy/rollback/
  interlock/verification section.
- `docs/deployment/RELEASE_AND_STAGING.md` — Agent rollback next to the Fly
  rollback.
- `the captions-agent delivery design`, `plans/README.md` —
  status moved to partially-shipped; Pieces 1–3 still open.
- `packages/livekit-captions-agent/Dockerfile` — header corrected; it had
  asserted the box has no checkout and that the image is pulled from GHCR,
  both of which are now false.

**Deliberate, temporary drift from the Tofu template.**
`infra/oracle-runner/services/docker-compose.livekit.yml.tftpl` declares
`image: ghcr.io/jaystewart-dev/spiralclass-captions-agent:latest`. **Nothing
has ever published that image**, and the template has never rendered onto this
box — the box is hand-provisioned. This decision
widens that pre-existing gap rather than creating it: the box's compose now
carries a `build:` stanza the template does not have. Do **not** reconcile the
template to the box. The intended end state is the reverse — when the box is
rebuilt from Tofu, the `build:` stanza and `~/spiralclass` both go away and
`image:` becomes correct again.

This partially reverses the OpenTofu module's removal of the repo-clone step,
but only in scope: that removed cloning as a _config-provisioning_ mechanism (LiveKit
service configs now render from Tofu at apply time, not pulled onto the box
afterward). That remains true and untouched. The checkout here is a **build
input for one image**, nothing else reads from it.

**Unresolved risks.**

- **The box cannot self-update.** Every deploy needs the operator's machine
  online to push. Acceptable for a solo operator deploying by hand; it would
  not be for a team or for automated delivery.
- **Build and deploy are still coupled, and both are manual.** A ~9-minute
  build occupies both of this box's 2 OCPUs and must be timed outside lesson
  hours — as must the restart, independently and for a different reason.
- **The live-call interlock is documented, not enforced.** Restarting the
  Agent kills captions for any class in progress, with no graceful drain.
  Piece 4 of the delivery plan would make it a gate; today it is a manual
  `lk room list` check whose safe state is "0 publishers, ≤1 participant"
  (the Agent itself being that one participant).
- **`:latest` remains ambiguous** on the box. Only the pinned `:<sha>` in the
  compose file is authoritative, and nothing enforces that they agree.
- **No version stamp yet.** Piece 1 (`AGENT_VERSION` in the `agent_starting`
  log + an OCI revision label) is still worth shipping — it would make the
  answer readable from the logs alone, without SSH-ing to compare a checkout.

---

**Addendum (2026-07-29, hours after the original decision).** The box now
tracks **`main`**, not `production`. The original rationale — "the Agent's
`captionsOn` contract is shared with the clients, and `production` is the only
fully-gated branch" — described a coupling that **does not actually exist**:

- **`promote.yml` never ships the Agent.** `fly-deploy.yml`'s `paths` exclude
  `packages/livekit-captions-agent/**`, and the on-box build is manual either
  way. So tracking `production` bought no synchrony with anything; it only
  required a full production gate and a `production` fast-forward before an
  Agent fix could be built — for a change that production itself does not
  deploy. That cost was paid immediately: the first fix after this decision
  (the #745 rejoin race, a stuck worker per class accumulating in production)
  would have needed an unrelated promote to reach the box.
- **This box serves both preview and production** (D-94, one box for both
  environments). Preview clients run `main`. Tracking `production` therefore
  kept the Agent _behind_ half the clients it serves — the opposite of the
  stated goal.
- Every Agent change so far has been box-internal lifecycle logic (leaked
  workers, mic re-handling, the rejoin race), touching nothing the clients
  parse.

**The risk this accepts, and its mitigation.** A change that _does_ alter the
shared wire contract (`packages/shared/src/captions.ts` — `CAPTION_TOPIC`,
`encodeCaption`, the `for` field) or the meaning of the `captionsOn` attribute
can now reach the Agent before production clients understand it. A mismatched
contract between Agent and client is exactly what the 2026-07-28 outage was,
so this is not hypothetical. Such a change must be sequenced deliberately:
**client to production first, Agent second.** That is a judgment call at
change time rather than a branch-enforced guarantee — the trade accepted here
is that a rule which fired on every change to buy protection against a rare
one was not worth its cost.
