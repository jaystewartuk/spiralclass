# D-93. Homework review/feedback/AI-assist architecture — proposed, not yet built

> [!NOTE]
> **Status corrected 2026-09-06: it was built, largely as designed.** The
> record below is left exactly as written, because what it is worth reading for
> is the design and the two tensions it had to resolve — not its status line.
> What has since shipped: `HomeworkAttempt`, `HomeworkFeedback` and
> `HomeworkAiReviewDraft` (migration `20260722010000_homework_review_and_material_linkage`),
> the `Assignment → LibraryMaterial` link, the teacher review surface under
> `dashboard/classes/[bookingId]/homework/`, and `lib/homework/ai-review.ts` —
> teacher-triggered, never auto-sent, exactly as §11 proposed. The behaviour of
> record is [`docs/features/homework.md`](../features/homework.md).

**What changed.** Nothing in the codebase yet — this records a **proposal**
for closing the gap in the homework feature that shipped one day earlier
(`20260720000000_add_homework_submissions`, `Assignment` /
`HomeworkSubmission` / `HomeworkSubmissionFile`): that slice
covers teacher-authors-assignment → student-submits-and-gets-notified, and
deliberately stops there, with `HomeworkSubmissionStatus.returned`/`.graded`
reserved but unreachable. The full audit and design —
`docs/product/HOMEWORK_WORKFLOW.md` — proposes: an optional
`Assignment → LibraryMaterial`/`MaterialRevision` reference (so a teacher's
AI-generated `[!homework]` callout can auto-draft a real, submittable
assignment instead of just being styled prose), an append-only
`HomeworkAttempt` snapshot per submit (so resubmission gets real history
without changing `HomeworkSubmission`'s existing "current state" semantics
or its `@@unique([assignmentId, studentId])` constraint), a
`HomeworkFeedback` model (teacher decision: approved /
resubmission_requested / rejected) and a `HomeworkAiReviewDraft` model
(teacher-triggered, never auto-sent, retained for audit/regenerate — not a
throwaway API response), plus the web-dashboard homework surface and
teacher-review UI that don't exist on either platform today.

**Why it likely changed.** The shipped slice was explicitly built with this
in mind — its own schema comment says `returned`/`graded` and
`allowResubmission` are "wired for the future teacher review slice without
needing a schema change then" — so this is the anticipated next step, not a
reversal of anything. Two things forced treating it as a full audit-first
design exercise rather than a quick add-on: (1) the request described
homework-questions-live-in-materials as if that connection already existed
structurally, when in the actual schema "homework" inside materials is only
a presentational `[!homework]` Markdown callout with zero relation to
`Assignment` — the two concepts needed to be reconciled deliberately, not
assumed compatible; (2) the request's literal "student receives homework
automatically" is in tension with its own "teacher remains in control"
principle, so the design proposes an editable/deletable auto-draft rather
than either fully silent creation or a from-scratch manual-only flow.

**What was affected.** Documentation only so far:
`docs/product/HOMEWORK_WORKFLOW.md` (full audit + design + migration +
incremental implementation plan) and this entry. No schema, API, or UI
changes have been made. The document's §11 lists open product questions
(auto-draft-visible-immediately vs. requiring explicit publish; whether the
feedback-available notification should bypass the usual suppressible
category; score scale; default due-date derivation) that should be resolved
before implementation begins, and recommends building in the order
schema/backfill → web-dashboard parity for the _existing_ shipped feature →
material↔assignment linkage → teacher review/feedback UI → AI review, so
that the highest-value, lowest-novelty gap (a teacher being able to see and
respond to a submission at all, on either platform) lands before the AI
feature that's more novel but useless without it.

**Unresolved risks.** Entirely unimplemented — the risk at this stage is
scope: the full design (rubrics, inline comments, plagiarism detection,
homework-focused AI chat) is intentionally sketched as "doesn't require a
redesign later" rather than committed to for v1; only the incremental
plan's slices 1–4 (schema, web parity, material linkage, review/feedback UI)
are considered load-bearing for a usable end-to-end workflow, with AI review
and audio-attachment support (slices 5, 7) recommended but explicitly
sequenced after.
