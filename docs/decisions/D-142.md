# D-142 — The public demo is a rendered fixture, not a demo account

- **Date:** 2026-08-29
- **Status:** Accepted
- **Supersedes:** nothing. Closes the "read-only demo teacher account" item in
  the design plan, by rejecting the mechanism that item assumed.

## Context

The teacher dashboard is the part of this product most worth showing to
somebody evaluating the work, and the part nobody can see. It sits behind an
email-OTP wall, so a reviewer's options were screenshots or nothing.

The design plan called for a "read-only demo teacher account — a seeded teacher
with populated data and writes disabled". It also flagged, correctly, that this
needed a security decision of its own. That decision is this document, and it
goes the other way.

## What a demo account would actually require

Two things, both measured rather than assumed:

- **A way to sign in without proving identity.** Sign-in is email OTP only.
  A demo account means a published credential, a magic URL, or a bypass branch
  in the auth flow — a new authentication surface on a system that holds live
  payment records and real teachers' student data.
- **Write enforcement in 68 places.** There are 68 server-action files and no
  Prisma client extension, so there is no chokepoint where "this actor may not
  write" could be enforced once. "Read-only" would have to be re-asserted in
  every one of them, and the failure mode of missing one is a stranger mutating
  production.

The second point is the decisive one. A guarantee that has to be restated 68
times is not a guarantee; it is 68 chances to be wrong, on the surface with the
least reason to carry that risk.

## Decision

**Ship `/demo` as a public page that renders the real dashboard component from
a fixture.** No session, no queries, no actions.

The dashboard's presentation was extracted into
`src/components/dashboard/dashboard-view.tsx`, which takes a
`DashboardViewModel` and knows nothing about Prisma, auth or analytics.
`/dashboard` builds that model from the signed-in teacher's rows; `/demo`
builds it from a literal.

This buys three properties that a demo account does not have:

- **It cannot mutate anything**, because no action is wired and no session
  exists. The capability is absent, not disabled — nothing has to be enforced,
  and so nothing can be forgotten.
- **It cannot drift from the real screen**, because it is not a copy of the
  real screen. A layout change to the dashboard changes the demo in the same
  commit, and the visual-regression suite covers `/demo` as a portfolio route,
  so a regression on either is caught on both.
- **It cannot leak a real row**, because it never reads one.

Anything with an effect stays on the page side of the split — notably the
`dashboard_viewed` PostHog event, which is why demo traffic cannot pollute the
activation funnel.

## What this costs, stated plainly

**It is one screen, not a walkthrough.** A reviewer cannot click into Students,
open a booking, or see the calendar. Every authenticated destination renders
inert, and the page says so in a banner at the top rather than letting someone
discover it by clicking.

That is a real loss against the original ambition. It is accepted because the
alternative buys the extra screens with an auth bypass and 68 enforcement
points, and the marginal reviewer value of screen four is not worth either.

**The figures are invented and the teacher does not exist.** The page is
`noindex` for that reason: a prospective student who found it in a search
result would be reading fiction about a real product.

## If this is revisited

The version worth building is not a demo account either — it is more fixtures.
Extracting a second and third screen the same way costs the same split again
and adds no security surface at all. The moment to reconsider a real account is
if a Prisma client extension ever lands for another reason, since that is the
chokepoint whose absence is the actual blocker here.
