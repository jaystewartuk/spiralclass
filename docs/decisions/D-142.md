# D-142. The public demo is the real dashboard rendered from a fixture, not a demo account

`/demo` ([`app/demo/page.tsx`](../../apps/web/src/app/demo/page.tsx)) is a
public page that renders the real dashboard component,
[`DashboardView`](../../apps/web/src/components/dashboard/dashboard-view.tsx),
from a literal `DashboardViewModel`: no session, no queries, no actions.
`/dashboard` builds the same model from the signed-in teacher's rows.

## Why

The teacher dashboard is the part of the product most worth showing a reviewer
and it sits behind email-OTP sign-in, so the options were screenshots or
nothing. A plan called for a read-only, seeded demo teacher account and flagged
that it needed a security decision; this is that decision.

## Options considered

- **A read-only demo account** — needs a way to sign in without proving
  identity (a published credential, a magic URL, or a bypass branch in the auth
  flow): a new authentication surface on a system holding live payment records
  and real students' data. And "read-only" had to be enforced somewhere: in
  August 2026 there were 68 server-action files and no single point where "this
  actor may not write" could be enforced once.
- **Screenshots** — drift from the product the day the dashboard changes.
- **A fixture through the real component** — chosen. It cannot mutate anything
  (no action is wired, no session exists), cannot drift (it is the real
  component, and `/demo` is a portfolio route in the visual-regression suite,
  [`tests/visual/routes.ts`](../../apps/web/tests/visual/routes.ts)), and cannot
  leak a real row (it reads none).

## What it cost

- One screen, not a walkthrough. Every authenticated destination is inert, and a
  banner says so rather than letting a reviewer find out by clicking.
- The figures are invented and the teacher does not exist, so the page is
  `noindex`: a prospective student finding it in search would be reading
  fiction about a real product.

## What it constrains

- **No sign-in path that does not prove identity**, for a demo or anything else
  ([authentication](../features/authentication.md)).
- **Anything with an effect stays on the page side of the split.** The
  `dashboard_viewed` event fires from `/dashboard`, not from `DashboardView`,
  which is why demo traffic does not pollute the activation funnel. A data read
  or a server action added inside `DashboardView` would reach `/demo`.
- **More of the product is shown by extracting more screens the same way** — the
  same split again, with no new security surface. Nothing guards the demo page's
  imports; review is the check.
- **Reopen only** if sign-in gains a sanctioned path that does not prove
  identity for another reason, or if the tenancy guard
  ([`lib/tenancy/guard.ts`](../../apps/web/src/lib/tenancy/guard.ts)) ever runs in
  `enforce` with a write rule of its own. Turning it into a write gate is a
  decision under [D-175](./D-175.md); `tests/tenancy/client-surface.test.ts`
  fails if the client's surface changes.

## How we got here

- **2026-08-29.** Decided as above. The record then named the missing Prisma
  client extension as the decisive blocker and invited a revisit if one landed.
- **2026-10-14.** One had: the tenancy guard is a client extension in front of
  every model query ([D-175](./D-175.md)). Re-examined at the request of issue
  [#64](https://github.com/jaystewartuk/spiralclass/issues/64); the answer stands.
  The guard inspects queries and refuses no writes, and defaults to `report` in
  production, so it is not a write gate — and the first objection, signing in
  without proving identity, never depended on it.
