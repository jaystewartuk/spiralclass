# D-193. A public page has one URL per language: a path prefix for every locale but English, and the bare URL is English (2026-10-04)

**Status.** Active, built 2026-10-04. Three things were settled while building
it, and are written into the sections below:

- A link followed from inside the site is never redirected.
- A page is advertised only in the languages its content exists in.
- The site-wide social card was one URL, so it was not per language. Fixed
  the same day; see the risks below.

**What changed.** Each public marketing, help and legal page gets one URL per
launched locale. The prefix is the registry tag in lower case:

- `/pricing` is English (`DEFAULT_LOCALE`).
- `/es/pricing` is Spanish.
- `/fr/help/…` is French, and later `/pt-br/…` and `/de/…`.

The URL decides the language. A page reached at a prefixed URL renders in that
language whatever the cookie or the browser says, and so does its metadata and
social card.

- **Which pages.** An allowlist: `/`, `/pricing`, `/features`, `/about`,
  `/help/**`, `/terms`, `/privacy-notice`. A locale prefix on any other path is
  a 404. A prefix can never make an authenticated route look public.
- **Not prefixed.** The teacher's app, the student portal and admin follow the
  signed-in person's language setting; nothing there is indexed. `/b/**` is
  pinned to the teacher's `booking_page_locale` (D-194).
- **The bare URL.** It serves English. Before it does, a reader arriving from
  outside the site is redirected with a 302 to the prefixed URL of the
  language they prefer:
  - an explicit choice is the `locale` cookie, written only by the language
    switcher, and it is obeyed, so a reader who picks English is never
    redirected again;
  - with no choice, a launched locale their `Accept-Language` matches.

  The redirect varies on `Cookie` and `Accept-Language` and is never cached as
  public.

- **A link inside the site is never redirected.** A request whose Referer is
  this site's own origin renders where it was sent. Internal links are
  localized on purpose, so a bare one means English. The "English" link on the
  Spanish terms is the way to the text that controls (D-196), and a
  Spanish-preferring reader bounced back to `/es/terms` could never read it.
- **`hreflang`.** Every allowlisted page lists the URL of every language its
  **content** exists in, plus `x-default` (the bare URL), in its metadata and in
  the sitemap. The set is the same on each of its URLs. The terms exist in
  English and Spanish, and the privacy policy in English only. Their other
  languages' URLs render the English document with a line in the reader's
  language saying so, and canonicalise to the English URL. Listing `/fr/terms`
  as the French terms would point French searchers at an English contract.
- **Old links.** `/terms?lang=es` is in sent email. It redirects permanently
  to `/es/terms`.

**Why.** Search engines index one language per URL. Today a public page picks
its language from the cookie, then `Accept-Language`, then English
(`getPreferredLocale` in `apps/web/src/lib/i18n.ts`). Google's crawler sends no
`Accept-Language`, so every public page is most likely indexed in English only,
and the Spanish and French marketing pages exist for nobody who searches in
those languages. That is inferred from Google's published crawler behaviour;
Search Console would confirm it, and a session cannot read it. Google's own
guidance is one URL per language, and never content swapped by cookie, header
or IP for the same URL.

The redirect keeps what readers get today. A Mexican teacher typing the bare
domain into a Spanish browser sees Spanish now, and would see English under a
pure "bare is English" rule.

**What was considered and rejected.**

- **Subdomains (`es.spiralclass.com`).** Each one is a DNS record, a
  certificate and a Cloud Run domain mapping. The session cookie would also
  have to span subdomains, which widens what a leaked cookie reaches. A path
  prefix is one middleware rewrite.
- **A prefix on English too (`/en/pricing`), with the bare URL only
  redirecting.** Every English link already shared, and every English page
  already indexed, would gain a redirect hop for no reader's benefit.
- **Keep negotiating by header, and add `hreflang` only.** `hreflang` has to
  point at distinct URLs. Pointing alternates at the same URL tells a search
  engine nothing.
- **A suggestion banner ("Ver en español") instead of a redirect.** It is the
  gentler choice where readers are mixed. Here it would make most first visits
  from the platform's main market one click worse than they are today.
  Revisit if analytics show readers switching back from the redirected
  language (see the risks below).
- **Redirect by IP or country.** It rejects the reader's own stated language.
  An English-reading expat in Mexico is the counterexample, and the first
  teacher's buyers are English readers.

**What it constrains.**

- A public page's language comes from its URL and nothing else. Never add a
  cookie or header read that changes what an indexed URL renders.
- The allowlist is the only way a path gains a locale prefix. Adding a public
  page means adding it there, and to the sitemap's alternates.
- `/b/**` is never prefixed (D-194).
- The rewrite lives in `updateSession` (`apps/web/src/lib/auth/middleware.ts`),
  behind `src/middleware.ts`. It is Tier 2 code.
- A locale is in the redirect and in `hreflang` only once it is launched. An
  unlaunched or half-reviewed locale must not be advertised to search engines.
  That is the `launched` field on the registry row (#178 step A1, built
  2026-10-05): an unlaunched locale has no prefix, is never a redirect target
  and is in no hreflang set or sitemap, and
  `packages/shared/src/i18n/launched-locales.test.ts` proves each.
- A link from a public page to another public page goes through
  `localizedHref`, so it stays in its language. A link that changes language is
  a full page load, because the root layout carries the language and a
  client-side navigation keeps the layout it has.

**What was affected.**

- `packages/shared/src/i18n/localized-paths.ts` holds the allowlist, the path
  helpers and `resolvePublicLocaleRoute`, the whole decision as a pure function.
  It is exported to the middleware through the `@spiralclass/shared/localized-paths`
  subpath, so the catalog stays out of the middleware bundle.
- `updateSession` (`apps/web/src/lib/auth/middleware.ts`):
  - deletes any client-sent `x-locale`;
  - rewrites `/<locale>/<path>` to `/<path>` and sets `x-locale`;
  - issues the redirects after the maintenance wall.
- `getPreferredLocale` reads `x-locale` first. `getLanguagePickerValue` shows
  the page's language when the URL names one the preference does not.
- The switcher saves the choice through `chooseLocaleAction`, which returns the
  resolved locale. It then loads that locale's URL for the same page.
- `lib/seo/localized-alternates.ts` feeds the seven pages' `generateMetadata`
  and `sitemap.ts`.
- The footer, the marketing and help headers and the public pages link through
  `useLocalizedHref` / `getLocalizedHref`.
- Cancellation-policy links in email and the funnel point at the terms in the
  reader's language. The funnel's link was hard-coded to the English terms.
- Tests:
  - `packages/shared/src/i18n/localized-paths.test.ts`;
  - `apps/web/tests/lib/middleware-locale-routing.test.ts`;
  - `tests/i18n/url-locale.test.ts`;
  - `tests/i18n/legal-pages-language.test.tsx`;
  - `tests/components/language-select.test.tsx`;
  - `tests/config/locale-prefix-routes.test.ts`, which proves no route answers
    a prefixed private path;
  - `tests/seo/`.

**Trade-offs accepted, and unresolved risks.**

- **Google discourages redirecting by the visitor's language.** The
  mitigations: crawlers send no `Accept-Language` and so are never redirected;
  `x-default` names the bare URL; the switcher's cookie overrides the header.
  This does not remove the risk. If Search Console shows the prefixed pages
  missing from the index, the redirect is the first suspect.
- **A shared link to a bare URL lands differently for two readers.** One URL
  still serves one language: the bare URL is always English, and the other
  reader is redirected away from it, not served Spanish at it.
- **Nothing measures whether the redirect is wanted.** The funnel events gain
  the rendered locale in #178 step D. Until then, a reader who is redirected
  and switches back is invisible.
- **The allowlist is code, so it can fall behind a new public page.** A page
  added to the sitemap but not to the allowlist would be listed once per
  language at the same URL. `tests/seo/sitemap.test.ts` fails on a duplicate
  URL.
- **RESOLVED 2026-10-04: the site-wide social card was one URL for every
  language.** It was the `app/opengraph-image.tsx` file convention. A crawler
  fetched it with no cookie, so `/es/…` pages shared an English card under a
  Spanish title. It is now `app/social-card/[locale]/route.tsx`, at
  `/social-card/<locale>`, named by `socialCardImages()` in the root layout and
  on `/help`, which sets its own `openGraph`. It is cached for a day, not a
  year: Next's `ImageResponse` default is `immutable`, which is safe only on a
  URL with a content hash, and this one has none. A page that sets its own
  `openGraph` must pass `socialCardImages(locale)`, or it loses the card.
  `tests/seo/social-card.test.ts` covers both pages that exist.
- **Sign-in and sign-up follow the reader's own language, not the URL's.** An
  English-preferring reader who arrived at `/es/pricing` from a search and
  clicks "Sign in" gets English. Accepted. The links are full page loads, so
  the page they reach is in one language throughout.
