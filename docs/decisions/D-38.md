# D-38. Teacher and Student are mutually exclusive roles per auth identity

**What changed.** Closed an identity-collision gap: one Supabase auth
identity (`auth.users.id`) could become both a Teacher (`Teacher.id ===
auth.users.id`) and a linked Student (`Student.authUserId === auth.users.id`)
with no guard and no clear error. The guard is now symmetric and fails loud:

- `resolveLinkedStudent()` (`src/lib/auth/student-link.ts`) returns a
  discriminated `{ status: "linked" | "conflict" | "none" }` instead of a bare
  nullable row. Before linking an unlinked roster row to the signing-in auth
  user, it checks for an existing Teacher row with the same id and returns
  `"conflict"` instead of linking. Both callers (the `/api/auth/callback` route
  and the `finalizeSignIn` server action) surface a clear, locale-aware message
  on conflict rather than a silent dead end.
- `findOrCreateRosterStudent()` (`src/lib/students/find-or-create.ts`) now
  checks the checkout email against `Teacher.email` before creating a new
  roster Student row, throwing `TeacherEmailConflictError` instead of
  minting an orphaned row no auth identity could ever sign into. The checkout
  call site (`src/app/actions/checkout.ts`) catches it and fails the purchase
  with an explicit message, using its existing `{ error }` contract.
- `createStudentAction()` (`src/app/actions/teacher-students.ts`, manual
  roster add) gained the same `Teacher.email` check alongside its existing
  same-teacher-roster duplicate check.
- `requireTeacher()`'s existing `asStudent` block
  (`src/lib/auth.ts`) already redirected a student-linked identity away from
  teacher signup; the redirect now carries `?notice=already-student`, which
  `/my-classes` reads and renders as a banner instead of redirecting
  silently.
- No bulk/CSV roster import exists in the codebase (confirmed by search —
  `src/lib/csv.ts` is an admin export serializer only), so there was no
  fourth call site to cover.

**Why it likely changed.** Teacher and Student are orthogonal identities in
this product: a Teacher is a payee (Stripe Connect, payout rails), a Student
is a payer (checkout, package consumption). Merging them under one login
would tangle RLS scoping, billing context, and moderation (a disabled
student could pay through their own teacher identity, or a disabled teacher
could receive money through a student-side flow). This does **not** change
the existing, correct multi-tenancy model: one person can still have many
per-teacher Student rows (`docs/architecture/multi-teacher-students.md`), and
one Teacher can have many Students. The new rule is orthogonal — it blocks a
single human from being a teacher-payee _and_ a student-payer under the same
login, not from having multiple roster rows as a student.

**What was affected.** `src/lib/auth/student-link.ts` (Tier 2),
`src/lib/auth.ts` (Tier 2), `src/lib/students/find-or-create.ts`,
`src/app/actions/checkout.ts`,
`src/app/api/auth/callback/route.ts`, `src/app/actions/session.ts`,
`src/app/actions/teacher-students.ts`,
`src/app/(auth)/sign-in/{page,sign-in-form}.tsx` (renders
`?error=teacher-email-conflict`), `src/app/(student)/my-classes/page.tsx`
(renders `?notice=already-student`).

**Unresolved risks.** The phone-OTP rail
(`src/lib/auth/phone-link.ts`, since removed by [D-40](./D-40.md)) is
unaffected: it is student-only by
design (a phone login never lazy-creates a Teacher row) and already checks
for an existing Teacher row before calling `resolvePhoneLinkedStudent()`, so
the same collision can't arise there. If a future caller of
`resolveLinkedStudent()` skips the existing teacher-row pre-check, the
in-function guard still catches it (defensive, not just caller discipline).
