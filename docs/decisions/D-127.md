# D-127. Social-preview image generation moves from the public Gemini API to Vertex AI

**What changed.** `lib/ai/gemini-image.ts` now calls the same model
(`gemini-3.1-flash-image`) through **Vertex AI**'s `generateContent` endpoint
instead of the public Generative Language API (AI Studio). The request and
response bodies are byte-for-byte identical between the two surfaces —
confirmed against a live call before writing any code — so nothing about
prompting, aspect ratio, or response parsing changed. What changed is
**auth and billing**: `X-Goog-Api-Key` is gone; every call now carries an
OAuth2 Bearer token minted from a dedicated service account
(`agendaprofe-vertex-image@example-project-00000.iam.gserviceaccount.com`,
`roles/aiplatform.user`, scoped to this one project) via a hand-rolled
self-signed-JWT exchange in the new `lib/ai/google-vertex-auth.ts` — same
`node:crypto` RSA-signing posture `wise/api.ts` already uses for its own SCA
statement signing, not a new `google-auth-library` dependency. `env.ts`'s
`GEMINI_IMAGE_API_KEY` is replaced by
`GEMINI_VERTEX_SERVICE_ACCOUNT_KEY_BASE64` (the key JSON, base64-encoded
onto one line — Infisical) plus `GEMINI_VERTEX_PROJECT_ID` (non-secret,
`example-project-00000`, committed to `config/env/*.runtime.env`) and an
optional `GEMINI_VERTEX_LOCATION` (defaults to `global` — the only location
this model is actually published to; `us-central1` 404s on it, confirmed
empirically).

**Why it likely changed.** The public Gemini API gates every call on a
**Prepay balance** — a product-level billing mechanism specific to the
"quick API key" consumer surface, entirely separate from a linked Cloud
Billing account. D-124 (the same day) had already linked a Cloud Billing
account to `example-project-00000` and set a budget alert on it, on the
reasonable assumption that having billing enabled was sufficient; the first
real generation attempt in production instead returned `429
RESOURCE_EXHAUSTED — "Your prepayment credits are depleted"`, and the
project didn't even appear in AI Studio's project list (it was never
"imported" there, since the API key had been minted via `gcloud` directly
rather than through AI Studio's own onboarding flow) — importing it
surfaced the real status: `Tier 1 · Postpay`, **Prepay required**. Buying
prepay credits needs a human at a payment screen, which is out of scope for
an agent to do unattended. Vertex AI has no such product-level gate at
all — it bills through ordinary Cloud Billing, the same postpaid mechanism
as every other GCP line item this project incurs, so the billing account
already linked is already sufficient.

Every other provider evaluated shares the same shape of wall: OpenAI's
`gpt-image-1` also moved to prepaid-by-default (a $5 minimum) and is being
deprecated 2026-10-23 besides; fal.ai and Replicate both moved new accounts
to prepay-credit billing during 2025. Vertex AI is the one path here that is
genuinely postpaid, because it isn't a low-friction anonymous-feeling
consumer product — it's core GCP infrastructure billing, which was never
going to add a fraud-prevention prepay wall on top of an account a card is
already on file for.

**What was affected.** `apps/web/src/lib/ai/gemini-image.ts` (endpoint +
auth only — every response-parsing branch, and its "blocked" vs. "empty" vs.
"timeout" vs. "error" distinctions, are untouched), the new
`lib/ai/google-vertex-auth.ts`, `env.ts`'s Gemini-image section, both
`config/env/*.runtime.env` (the new non-secret project id),
`apps/web/.env.example` (which also still said `D-122` from before the
D-122/D-123/D-124 renumbering collision — fixed in the same pass, since it
isn't a `.ts`/`.tsx` file the earlier bulk rename covered), and the test
suite: `tests/social-preview/gemini-image.test.ts` now mocks the token
seam instead of a bare key, and a new
`tests/social-preview/google-vertex-auth.test.ts` verifies the JWT is
actually signed with the configured key (round-tripped through a real
`RS256` verify against a throwaway keypair, not just "fetch was called"),
that a cached token isn't re-minted per request, and that every failure
mode (transport error, non-2xx, unparseable body) degrades to `undefined`
rather than throwing.

Two GCP APIs were enabled on the project as part of this
(`generativelanguage.googleapis.com` for the original AI Studio key,
`aiplatform.googleapis.com` for Vertex) and a service account + key created
— all via `gcloud`, none via Infisical (out of reach for an agent session by
design; the base64 key was handed to the operator to store).

**Unresolved risks.**

- **The AI Studio API key created for D-124 is now dead weight.** It still
  exists, still resolves to a project that will never fund its Prepay
  balance, and costs nothing sitting unused — but it's a credential nobody
  needs anymore. Revoke it (`gcloud services api-keys delete`) once this
  path is confirmed live in production, rather than leaving two credentials
  for the same feature.
- **The service account key is a long-lived, non-rotating credential** —
  same shape as every other secret in the rotation runbook (since moved out
  of this repository),
  but Google's own guidance prefers Workload Identity Federation (no
  long-lived key at all) over a downloaded JSON key. WIF wasn't used here
  because this app runs on Fly, not GCP, and WIF's off-GCP path (configuring
  an external OIDC provider trust relationship) is materially more setup for
  a feature this size. Revisit if the blast radius of this one key
  (`roles/aiplatform.user`, scoped to one project, callable only for
  `generateContent`) ever stops being an acceptable trade.
- **`global` as the Vertex location is empirical, not documented as
  permanent** — Google could publish `gemini-3.1-flash-image` to regional
  endpoints later, or deprecate the global one. `GEMINI_VERTEX_LOCATION` is
  overridable via env for exactly that reason; nothing about the code
  assumes `global` specifically.
- **No integration test exercises the real Vertex endpoint** (correctly —
  that would spend real money on every CI run). The unit suite proves the
  JWT is well-formed and correctly signed; whether Google's token endpoint
  actually accepts it was verified manually, once, via `gcloud`-minted
  credentials before writing any code, not by an automated test that runs
  again on every future change to this file.
