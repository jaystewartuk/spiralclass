# D-56. `/sign-in` never auto-provisions a Teacher — only an explicit sign-up intent does

**What changed.** Under D-40's single email-OTP rail (`disableSignUp: false`),
`/sign-in` and `/sign-up` were behaviorally identical: both called the same
`verifySignInCodeAction`, and any identity that resolved to neither an
existing Teacher nor a linked Student silently fell through to
`requireTeacher()`'s lazy-create — a full Teacher row (booking slug, starter
package templates, starter availability, 30-day Pro trial) minted for
_whatever email happened to verify a code_, regardless of whether the person
meant to sign up as a teacher, sign in as an already-rostered student, or
just mistyped an address. This is what happened when testing on Preview with
a "test student" email that had no pre-existing `Student` roster row: it
became a teacher account instead, requiring a manual DB delete to unblock.

The fix threads an explicit `intent: "sign-in" | "sign-up"` through every
entry point on both platforms, sourced from which page/button the user
actually used — never inferred from the identity being unmatched:

- **Web:** `verifySignInCodeAction` reads a hidden `intent` field
  (`sign-in-form.tsx` sends `"sign-in"`, `sign-up-form.tsx` sends
  `"sign-up"`); `GoogleSignInButton` carries the same `intent` through
  `/auth/complete`'s `callbackURL` query string.
- **Shared resolver:** `finalizeSignIn` takes the intent. When an identity
  matches neither an existing Teacher nor a linkable Student:
  - `intent === "sign-up"` → unchanged, lazy-creates the Teacher row (this is
    the legitimate self-serve teacher signup / growth funnel — untouched).
  - `intent === "sign-in"` (the default) → **no account is created.** It
    redirects to `/sign-in?error=no-account&email=…` with a clear message
    instead of the generic "invalid code" one.

Note what does **not** change: better-auth's `disableSignUp: false` stays
global — the `User` row itself (the bare auth identity, no Teacher/Student
attached) is still created on any verified code, because better-auth has no
per-call override and flipping it globally would break real teacher signup.
An orphan `User` row with no Teacher/Student is harmless (nothing reads or
displays it) and gets attached correctly the next time that email is
properly rostered as a student, or if the same person deliberately uses
`/sign-up`.

**Why it likely changed.** Teacher self-serve signup (`/sign-up`, the
"start free trial" marketing CTA) is the growth funnel and needed to stay
frictionless — killing auto-provisioning everywhere was rejected in favor of
making the _existing_ `/sign-in` vs `/sign-up` distinction behaviorally real
instead of cosmetic. Building two fully separate login _identity systems_
(rather than just gating the one existing auto-create branch on intent) was
also rejected as unnecessary duplication for a problem
that was really about an ungated default, not about which URL a user landed
on. Student accounts were already never self-service-created at login (see
[D-38](./D-38.md), `docs/architecture/multi-teacher-students.md`) — this
closes the asymmetric gap where an _unmatched_ identity, which should behave
like "no student row exists yet," instead fell through to the _teacher_
branch by default.

**What was affected.** `apps/web/src/app/actions/session.ts`
(`finalizeSignIn`), `apps/web/src/app/actions/auth.ts`
(`verifySignInCodeAction`), `apps/web/src/app/(auth)/sign-in/sign-in-form.tsx`,
`apps/web/src/app/(auth)/sign-up/sign-up-form.tsx`,
`apps/web/src/app/(auth)/google-sign-in-button.tsx`,
`apps/web/src/app/auth/complete/route.ts`,
plus the shared i18n catalog (`packages/shared/src/i18n/catalog.ts`) for the
new "no account found" copy.

**Follow-up (shipped same slice).** The public booking page's inline OTP
step also defaults to `intent:
"sign-in"` (no `name` collected there) — this was _already_ a latent
instance of the same bug (a mistyped email at checkout could have minted a
spurious Teacher) and was closed as a side effect of the resolver change,
but initially fell back to the generic "invalid code" message instead of a
clear one. It now gets its own `mapError` copy
(`publicProfile.noAccount`: "we couldn't find any classes under that
email — buy a package above to get started"), distinct from the sign-in
screen's `auth.noAccount` since this surface is student-only (no "sign up
as a teacher" framing makes sense here).

**Unresolved risks.**

- `requireTeacher()` itself (`apps/web/src/lib/auth.ts`, ~85 call sites)
  still lazy-creates unconditionally when invoked directly — this decision
  only closes the _entry-point_ routing that reaches it with a fresh
  identity. A signed-in "no account" session that manually navigates to a
  teacher URL (e.g. bookmarking `/dashboard`) would still provision a
  Teacher row on the spot. This is judged low-risk (it requires deliberately
  ignoring the "no account found" bounce and typing a teacher URL by hand)
  and out of scope for this slice — refactoring `requireTeacher()`'s ~85
  call sites to distinguish "just completed sign-up" from "any other
  navigation" is a materially larger change than the reported bug warrants.
  Revisit if this path is ever actually hit in practice.
