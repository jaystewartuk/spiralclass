# D-186. The Vercel failover is retired; Cloud Run is the only production target

**Status.** Active. Reverses [D-177](./D-177.md), which keeps its reasoning
trail and gains a pointer here. The coupling D-89 removed stays removed, exactly
as D-177 left it.

**What changed.** Production releases no longer deploy to Vercel. The `vercel`
job is gone from `deploy-production.yml`, and with it every piece of machinery
that existed only for that job:

| Removed                                          | What it did                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| `scripts/vercel-deploy.sh`, `pnpm deploy:vercel` | Built and deployed the failover without taking the domain                |
| `scripts/vercel-await.mjs`                       | Polled a deployment to a terminal state                                  |
| `scripts/vercel-env.mjs`                         | Kept the project's env store a derived copy of production's              |
| `infra/infisical/push-vercel-env.sh`             | Pushed production's runtime secrets into the Vercel project              |
| `config/vercel/`                                 | The project config, passed with `--local-config`                         |
| The `vercel` dispatch target, the standby report | `target: vercel`, and the line `pnpm promote` printed about the failover |
| Their tests and settings/hook entries            | `vercel-deploy`, `vercel-env`, `vercel-await`, `push-vercel-env` tests   |

`scripts/vercel-env.mjs` owned one thing the Cloud Run target still uses: the
definition of the runtime secret set (`pushedEntries`, `r2Entries`). That moved,
unchanged in behaviour, into `scripts/cloudrun-env.mjs`, its only remaining
caller, with its tests in `apps/web/tests/scripts/cloudrun-env.test.ts`.

**What stays.** The `database` job stays separate from the target. It was split
out so two targets could deploy independently, and it outlives the second
target because it is also a credential boundary: the job that builds the image
runs the most third-party code and never holds `DATABASE_URL`. `pnpm promote`
still reads the verdict job by job. The root `vercel.json` ban, the
`VERCEL_ENV`/`VERCEL_URL` read ban and the `@vercel/*` dependency ban all stay,
now joined by a ban on the failover's own files
(`apps/web/tests/config/decommissioned-platforms.test.ts`). The guard hook still
blocks the bare `vercel` CLI.

## What changed about D-177's premise

D-177's warrant was that a failover proven on every release cannot rot into a
dormant project nobody deploys. That premise did not hold in practice:

- **It never served a request, and its job was unreliable.** The three
  `VERCEL_*` credentials were missing on the first production deploy from this
  repository (#65), so the job was red. When it did run, a stalled build could
  leave the failover a release behind, reported only as a cancelled job 30
  minutes later (#80). A job that is often red or grey is one people learn to
  skim. That is the D-164 rot D-177 was built to avoid, reached by a different
  route.
- **It was never a complete failover.** D-177 said so itself: Inngest stays with
  the serving target, LiveKit reachability was unmeasured, the `cle1` region pin
  was an unverified guess about Neon, and handing it the domain meant rewriting
  DNS records that point at Google.
- **The serving target changed underneath it.** D-177 was written as a standby
  for Fly. Cloud Run took the domain on 2026-09-23 ([D-184](./D-184.md)'s
  addendum). Rolling back a bad release there is a traffic shift to a previous
  revision, which needs no second platform.

What D-177 proved stays proved: the application is provider-neutral. It ran a
second target with no change to `apps/web/src`, and Cloud Run later did the
same. Keeping that true is the job of the coupling bans, not of a second
deploy.

## What it constrains

- **Bringing Vercel back is a new decision record, not a revert of this one.**
  The bans in `decommissioned-platforms.test.ts` fail on any of the retired
  files. A standby that cannot take the domain, sync Inngest or reach LiveKit is
  not a failover, and the next attempt should say how it closes those gaps.
- **Do not fold the `database` job back into the Cloud Run job** because there
  is now only one target. The credential boundary is the reason it stays.

## Trade-offs accepted, and unresolved risks

- **There is no warm standby.** If Cloud Run is unavailable, recovery means
  standing up a new target and following "If the domain ever moves again" in
  [`RELEASE_AND_STAGING.md`](../deployment/RELEASE_AND_STAGING.md). Rollback
  within Cloud Run covers a bad release; it does not cover a regional outage.
- **⚠️ The Vercel project is not deleted by this change.** It is the operator's
  to delete, along with revoking `VERCEL_TOKEN` and removing the three
  `VERCEL_*` values from Infisical `production` `/deploy` and the `production`
  GitHub environment. Until then the project holds a copy of production's
  runtime secrets, pushed as `sensitive` by the retired
  `push-vercel-env.sh`, and nothing refreshes or reports on it. That is why the
  guard hook still blocks the `vercel` CLI.
- **Historical comments still mention Vercel**, in `apps/web/src` and
  `next.config.ts`, mostly about D-70's move off Vercel. They describe the past.
  They were not changed here.
