# D-79. A Stripe webhook event counts as handled only once its handler has finished, and an hourly sweep re-sends lost `payment.paid` events

Both Stripe webhook routes claim an event before handling it
(`recordWebhookEvent`). They stamp `processedAt` only after the handler
succeeds (`markWebhookEventProcessed`), and delete the claim if it throws. If
an unprocessed claim is younger than `DEFAULT_STALE_CLAIM_MS` (10 minutes), the
route answers 409 so that Stripe retries. If it is older, the next delivery
takes the claim over and handles the event again. The billing endpoint
prefixes its claims with `billing:<id>`. Separately, the hourly
`reconcile-paid-payments` Inngest cron re-emits `payment.paid` for paid
payments whose class was picked at checkout but never booked.

## Why

Stripe delivers each event at least once. A process can die after the claim
row commits but before the handler finishes. Under the old layer that left a
permanent "seen" row, so Stripe's retry was treated as a duplicate and the
event was lost.

The paid transition survived this, because a sibling event re-drives it
(`checkout.session.completed` and `payment_intent.succeeded`). Single-event
transitions have no sibling: `charge.refunded`, `charge.dispute.closed` and
`charge.dispute.lost`. A lost refund or dispute left a charged-back student
with active credits.

The webhook commits the paid state first and then emits `payment.paid` as a
best-effort step. If that emit is lost, the database says `paid` but the
consumers never run: auto-booking the picked class, the referral reward and
the first-payment magic link.

## Options considered

- **Claim up front and delete only on a thrown error** (the old layer) — a
  crash or timeout after the claim leaves a row that swallows every retry.
- **Record the event only after the handler succeeds** — a concurrent or
  replayed delivery could then run side effects that are not idempotent
  twice. The up-front claim exists to prevent that.
- **Rely on sibling events** — fine for the paid transition, but there is no
  sibling for a refund or a dispute.
- **Detect stranded payments by `stripeTransferId IS NULL`** (the first
  version of the sweep) — that meant "the payout never ran". It stopped
  meaning anything on 2026-08-30, when direct charges removed the payout
  ([D-143](./D-143.md)). Both rails now use one signal: an intended slot that
  was never used.

## What it cost

- **The takeover window is time-based.** It must be longer than any real
  handler run, so a live attempt is never stolen, and shorter than Stripe's
  retry horizon.
- **The sweep does not cover a lost emit for a package with no intended
  slot.** Only the magic-link and referral consumers had work to do there, so
  the cost is a student without a sign-in email, which signing in normally
  fixes.
- **A legitimately unbookable slot gets re-emitted.** When auto-book left
  the credit unspent because the slot was taken, the sweep re-runs it and
  reports `slot-unavailable` again until `maxAgeDays` (default 3) runs out.

## What it constrains

- **Every webhook handler must be idempotent** (status-guarded `updateMany`).
  The same goes for every `payment.paid` consumer, because both mechanisms
  re-run them on purpose.
- **Mark the claim processed only after the handler has fully succeeded.**
  Never answer 2xx for an `in_flight` claim, or the event is dropped.
- **Keep `DEFAULT_STALE_CLAIM_MS` longer than the slowest handler.** If a
  handler grows much slower, revisit it.
- **Keep the `billing:` prefix,** so that a Stripe endpoint misconfigured to
  "send all events" cannot let one endpoint's claim hide the other's.
- **The sweep's filter checks the student's actual booking at the intended
  start.** A top-up whose first class drew on an older package's credit keeps
  `classesUsed: 0` forever and would otherwise be re-emitted on every run.

## How we got here

- **A Tier-2 bug hunt (undated in the original record)** traced three ways to
  lose money or access, and fixed them together:
  - `webhook_events.processed_at` with re-claiming of stale claims, on both
    Stripe endpoints.
  - The `reconcile-paid-payments` cron.
  - A bearer-token superuser gate that accepted an allowlisted caller with no
    second factor enrolled. It was changed to answer `403 admin-mfa-required`.
- **Since then:** that bearer gate was deleted with the API route tree it
  served (see the header of
  [api/auth.ts](../../apps/web/src/lib/api/auth.ts)). The cookie gate
  `requireAdmin()` in [admin.ts](../../apps/web/src/lib/admin.ts) still
  requires enrolled TOTP. That rule belongs to [D-25](./D-25.md).
- **2026-08-30:** the sweep's Stripe branch lost its transfer signal and was
  merged with the Wise branch into one query.
- **Where the code and the record differ, the code wins.** The record said an
  in-flight duplicate was "swallowed". The route now answers 409 so that
  Stripe retries it.
