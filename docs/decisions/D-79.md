# D-79. Webhook durability: admin MFA, claim-completion tracking, and a paid-fan-out reconcile

**What changed.** Three related hardening changes from the Tier-2 bug hunt.

1. **Bearer-authed admin MFA (D-25 parity).** The bearer-token superuser gate
   now rejects an allowlisted caller with no second factor enrolled
   (`403 admin-mfa-required`), matching the cookie gate `requireAdmin()`
   (`lib/admin.ts`). Previously it checked only the `SUPERUSER_EMAILS`
   allowlist, so an intercepted email-OTP session reached full-privilege admin
   (Stripe refunds, teacher/student moderation, and minting a new `admin_users`
   row) with no second factor, defeating the control D-25 makes mandatory on
   every admin surface.

2. **Claim-completion tracking on both Stripe webhook endpoints.** The
   idempotency layer (`lib/webhooks/idempotency.ts`) recorded the claim row
   BEFORE running the handler and only deleted it on a thrown error. A crash /
   timeout after the claim committed but before the handler finished left a
   permanent "seen" row, so Stripe's retry was swallowed as a duplicate and the
   event was never processed. For the paid transition a sibling event
   (`payment_intent.succeeded` vs `checkout.session.completed`) covered it, but a
   single-event transition — `charge.refunded`, `charge.dispute.closed`/`lost` —
   had no sibling, so a lost refund/dispute was never applied (student keeps the
   credits, the teacher transfer is never reversed). The `WebhookEvent` row now
   carries `processed_at`: a claim means "in flight", and only a row with
   `processed_at` set is a true duplicate. A retry of an event whose prior
   attempt died (claim present, `processed_at` null, older than a short
   in-flight window) atomically re-claims and reprocesses. Handlers remain
   idempotent (status-guarded `updateMany`), so re-running is safe.

3. **Paid-fan-out reconcile cron.** Even with (2), the webhook's post-commit
   `payment.paid` emit is best-effort (a transient Inngest failure is logged and
   swallowed, and the DB write already committed so a retry no-ops). A new
   `reconcile-paid-payments` cron (`lib/payments/reconcile-paid.ts`) re-emits
   `payment.paid` for paid Stripe payments whose transfer never ran
   (`stripeTransferId IS NULL`, teacher connected, within a bounded window). All
   `payment.paid` consumers (transfer, auto-book, referral reward, magic link)
   are idempotent, so re-emitting is safe.

**Why it likely changed.** All three are money- or auth-loss paths the unattended
bug hunt traced: an intercepted admin credential reaching admin; a lost
refund/dispute leaving a charged-back student with active credits and the
platform out of pocket; and a lost `payment.paid` leaving a teacher permanently
unpaid for a real sale. None were sanctioned trade-offs — the MFA gap was named
only in an abandoned plan.

**What was affected.**

- The bearer-token superuser gate; every admin route behind it inherits the
  check.
- `prisma` migration adding `webhook_events.processed_at`;
  `lib/webhooks/idempotency.ts` (`recordWebhookEvent` reclaim + a new
  `markWebhookEventProcessed`); both `app/api/stripe/webhook/route.ts` and
  `app/api/stripe/billing-webhook/route.ts` mark completion on success. The
  billing endpoint also namespaces its claim (`billing:<id>`) so it can't shadow
  the Connect endpoint's claim under a Stripe "send all events" misconfig.
- `lib/payments/reconcile-paid.ts` + `lib/inngest/functions/reconcile-paid-payments.ts`
  (registered in the functions index). Test: `tests/payments/reconcile-paid.test.ts`.

**Unresolved risks.**

- The reclaim window is time-based: it must exceed the longest plausible handler
  runtime (a couple of Stripe calls + a DB tx, well under the serverless
  timeout) so a still-in-flight attempt is never reprocessed, yet be short
  enough to recover before Stripe stops retrying. It is set conservatively; if
  handlers ever grow much slower, revisit it.
- The gate checks the _enrolled_ flag (`twoFactorEnabled`), exactly like the
  cookie gate — not a fresh per-session TOTP challenge. Periodic re-challenge
  on both gates is separate, larger work.
- The `SUPERUSER_EMAILS`-vs-DB-role-model tension D-25 notes is unchanged:
  admin still authorises off the env allowlist. Wiring it to the DB role model
  is follow-up work.
