# D-175. Tenant scoping is checked by a parser, not by a reader

**Status.** Active. Mechanises the assumption
[`docs/architecture/data-model.md`](../architecture/data-model.md) states and
[D-70](./D-70.md) created; reverses nothing.

**What changed.** `apps/web/scripts/tenancy-guard.mjs` parses every Prisma call
in `apps/web/src/` and reports each query against a tenant-owned model that
does not constrain itself to one tenant.
`apps/web/tests/authz/tenancy-guard.test.ts` runs it in the fast tier on every
push, as a **ratchet** against `scripts/tenancy-guard.baseline.json`: the count
in a file may shrink and may not grow, and a file with no entry must stay
clean. A call site that genuinely reads across tenants says so out loud —
`// tenancy-exempt: <reason>` — and the reason is itself asserted, because a
check that can be silenced without one has stopped being a check.

The guard added no gate step. It is a unit test, so `scripts/ci/steps.mjs`
already runs it and the laptop and the runner inherit it in the same commit.

## Why

There is no row-level security. D-70 took it out with Supabase and
`data-model.md` states the consequence plainly: "isolation is enforced by the
`where` clause on every query… the single largest security assumption in the
system", and a missing clause is "a reportable vulnerability, not a style nit".

What enforced it, until this record, was people reading diffs. That is the
class of claim CLAUDE.md says is eventually false, and the tree agreed: the
scanner's first run found **264 queries in 112 files**, out of 922 against the
58 models that carry `teacherId`. Nothing was hiding them. Nothing was looking.

Publication (D-172's premise, and the repository's) changed the cost of that.
An unscoped query used to be findable by someone with a checkout; it is now
findable by anyone with a browser, in the time it takes to run one search. The
asymmetry that made review-only enforcement survivable is gone.

⚠️ **The single existing check was instance-shaped.**
`tests/authz/teacher-data-isolation.integration.test.ts` seeds two tenants and
asserts the wrong one is rejected — for four accessors, hand-picked. It is a
good test and it stays. It says nothing about the fifth accessor, which is the
problem with writing them one at a time.

## What was considered and rejected

**Postgres row-level security.** The reversal `data-model.md` says should be a
decision rather than a discovery — and this record is not it. The argument
there still holds: for one application process and one connection pool, an
incomplete policy set is the same class of bug as a missing `where`, with the
added property that it is invisible from the application code. Re-establishing
the boundary in roles and policies is a larger change than the one that was
needed, and it would have replaced a checkable assumption with an unreadable
one.

**A Prisma client extension.** The real chokepoint, and the only layer that can
see a `where` object assembled at runtime. Rejected here on three counts. It
puts a new code path in front of every query in a system on live payment rails,
to catch a class of bug that has not yet cost anything. Its baseline would
depend on which code paths a test run happens to execute, which is not a
baseline. And [D-142](./D-142.md) reasons explicitly from "there are 68
server-action files and **no Prisma client extension**, so there is no
chokepoint" — adding one would reopen the demo-account question as a side
effect of a security change, which is not how that question should get
answered. **D-142's premise is intact.** If an extension ever lands for another
reason, it is the right home for the dynamic half of this check.

**A `grep` for `teacherId`.** This is the [D-140](./D-140.md) failure mode, and
it is not hypothetical — five shapes contain the string and none of them
constrain the query:

| Shape                                   | What Prisma does                            |
| --------------------------------------- | ------------------------------------------- |
| `where: { teacherId: undefined }`       | **no filter at all** — `undefined` is "any" |
| `where: { teacherId: null }`            | matches rows with a null tenant             |
| `where: { teacherId: t ?? undefined }`  | no filter, whenever `t` is absent           |
| `where: { OR: [{ teacherId }, { … }] }` | every row the other branch matches          |
| `where: { teacherId: { not: t } }`      | every tenant **except** this one            |

Each reads as scoped to a reviewer and to a regex. The scanner reports them as
`vacuous` and `negated` rather than as scoped, and the guard test asserts all
five directly — so the check is pinned to something outside its own vocabulary.

**Scoping all 264 in one change.** [D-52](./D-52.md)'s precedent, for the same
reason: a big-bang migration of a live tree is a worse change than the problem,
and a ratchet stops the bleeding without blocking on a cleanup nobody
scheduled.

**An ESLint rule beside the ratchet**, as D-52 paired one with the i18n guard.
Deferred, not rejected: the ratchet already protects every clean file at zero,
and a second implementation of the same judgement — ESTree beside the
TypeScript AST — is a thing that drifts. Worth adding for edit-time feedback
once the baseline is small enough that a rule would fire rarely.

## What it constrains

- **Never regenerate the baseline to turn a red check green.** That is the
  failure it exists to prevent, and it is the same rule
  `scripts/check-leaks.baseline.json` carries for the same reason. Regenerate
  after scoping a surface, never instead of scoping one.
- **The tenant-model list is derived from `schema.prisma`, not written down.** A
  hand-maintained copy drifts and then silently stops guarding whatever it
  missed. A new model with a `teacherId` column is covered by the next run with
  no edit here.
- **An exemption states why.** `// tenancy-exempt:` with an empty or one-word
  reason fails the guard test.
- Reversing this means arguing that mechanical enforcement is worse than
  review, on a repository anyone can read.

## Trade-offs accepted, and unresolved risks

**It reads source, so it cannot read runtime.** 61 of the 264 are `opaque` — a
`where` handed in as a variable, a spread, or a function's return. The scanner
refuses to guess and counts them as violations, which forces new dynamic code
to be deliberate; it cannot tell whether a baselined one is safe. That is the
half a client extension would own.

**`derived` scope is accepted on trust.** `where: { bookingId }` on a
CallRecording reaches one teacher's rows _because_ a Booking carries
`teacherId` — but only if that booking id was itself fetched under a tenant
check. The scanner accepts the shape and cannot follow the id to its origin.
Treating it as a violation would have tripled the baseline and turned the check
into something people stamp past; this is the honest cost of that call.

**It checks that a query names _a_ tenant, not the _right_ one.** Passing
another teacher's id into a correctly-scoped query passes this check
completely. Authorization is still the auth gates' job; this only guarantees
the query asked.

**Raw SQL is invisible to it.** `$queryRaw` has no `where` object to parse and
is not counted — the leak-scanner rule applies, that a guard which reports
clean on a shape it cannot read is worse than no guard, so it says so here
rather than in a summary line.

**The 264 are recorded, not audited.** This change stops the bleeding; it does
not clean the wound. 43 of them are the admin console, which reads across
tenants by design ([D-25](./D-25.md)) and should end up carrying exemptions
rather than being scoped. The rest — 37 in `app/actions/`, 25 in
`lib/notifications/`, 10 in `lib/payments/` — are unreviewed, and the baseline
file is the list to work down. Nothing currently schedules that work; per
[D-172](./D-172.md) it belongs in Issues, not in a section at the bottom of
this record.
