# D-09. Multi-package consumption made FIFO-by-expiry: a unified credit ledger (2026-06-12)

**What changed.** A student can hold several active packages with one teacher at once (top-ups, repurchases — fully supported). Previously the _student_ chose which package a class came off, and the booking page defaulted to the **newest** package (the picker ordered `purchasedAt desc` and the server trusted whatever `packageId` arrived). Consumption is now a first-class **server** rule: a booked class is always drawn from the **soonest-to-expire** eligible credit across the student's active packages with that teacher, for the requested class length. Never-expiring credits are spent last; ties break by purchase date then id. The booking page now shows **one combined balance per (teacher, class length)** instead of per-package chips, and the submitted `packageId` is just a pointer into that pool — the server re-derives FIFO at claim time.

**Why it changed.** The newest-first default was exactly backwards from what protects the student: someone who topped up before finishing an older package would drain the fresh credits while the older package quietly expired with paid-for classes still on it — a silent, in-the-moment-invisible money forfeiture that ends in goodwill refunds. Making the soonest-to-expire credit the one that's always spent removes the foot-gun without taking anything away (the student still picks the class _length_, which is a real choice, not an ambiguous one).

**What was affected.**

- New `lib/booking/credit-ledger.ts` — the consumption rule: `claimNextCredit` (atomic FIFO-by-expiry claim), `checkCreditAvailability` (precise exhausted-vs-expired reason), `summarizeCreditPools` (the combined-balance view), `compareCreditFifo`.
- `lib/booking/book-package-slot.ts` — the shared booking core now claims via the ledger instead of an inlined single-package `updateMany`, and binds the booking to whichever package the class actually came off. Takes `studentIds` (the inbox identity set) to scope the pool.
- `app/actions/booking.ts` and `app/actions/teacher-booking.ts` (default pool = the package's own student) — every caller was refactored onto the shared core, dropping a duplicate inlined claim.
- `app/(student)/mis-clases/reservar/page.tsx` — per-package chips → one chip per combined balance, with a "N classes left · soonest expires DATE" caption.
- New index migration `20260612300000_credit_ledger_fifo_index` supporting the pool lookup.

**Why race-safety didn't change.** The guard is still the per-package field comparison (`classes_used < classes_total`) under the row lock — identical to the old single-package claim. Ordering only decides _preference_; if a concurrent booking drains the front-runner, the loser advances to the next eligible credit. No raw SQL, so the same path runs against the real DB and the in-memory test fakes. Cancel/reschedule were untouched: they already key off `booking.packageId`, so a class always returns to the exact package it came off.

**Unresolved risks.**

- Expiry is still _lazy_ — a package with capacity that lapses isn't transitioned to `expired`; it just stops being bookable (and now, being consumed soonest-first, is far less likely to lapse with classes on it). A status-flipping sweep + a "classes forfeited" signal remain a separate, smaller follow-up.
- Credits are fungible only within one class length; a teacher who sells multiple durations shows the student multiple balances by design.
