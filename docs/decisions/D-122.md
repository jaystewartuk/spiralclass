# D-122. A tablet is a phone with more room, not a small desktop: the responsive scale moves above every tablet width

> **Superseded entirely by [D-141](./D-141.md) (2026-08-29).** The observation
> below is right — a tablet is a touch device and should not inherit
> mouse-sized controls — and it was answered in the wrong dimension. A width
> cannot tell a 1280px tablet from a 1280px browser window, so the threshold
> was not selecting tablets; it was selecting "not full screen", and every
> non-maximised laptop window got the phone layout. `pointer: coarse` asks the
> question this record was actually asking.

**What changed.** `apps/web` stopped using Tailwind's default breakpoints. The
scale now lives in `apps/web/src/lib/breakpoints.ts` and starts at **1281px**,
so every tablet viewport — 744px in portrait at the narrow end, 1280px in
landscape at the wide end — falls through to the unprefixed layout that phones
get: full-bleed, single column, touch-sized controls.

| Token   | Was    | Now        | What it means now                                               |
| ------- | ------ | ---------- | --------------------------------------------------------------- |
| `roomy` | —      | **640px**  | New. Not a device tier: the width at which an inline label fits |
| `sm`    | 640px  | **1281px** | Stop drawing for a finger, start drawing for a cursor           |
| `md`    | 768px  | **1281px** | Switch to the desktop chrome (nav rail, table frame, splits)    |
| `lg`    | 1024px | **1440px** | Wide enough for three-to-four columns                           |
| `xl`    | 1280px | **1680px** | Large external display (no utility uses it)                     |
| `2xl`   | 1536px | **1920px** | Full-HD monitor (no utility uses it)                            |

Three consumers read those numbers, and all three now read them from the one
module: `theme.screens` in `tailwind.config.ts`, the two raw media queries in
`src/app/globals.css` (via `theme("screens.md")`, replacing hardcoded
`max-width: 767px`), and the guard tests. `theme.container.screens` deliberately
does **not**: Tailwind's container plugin keys off the values in its own map, so
the content column keeps settling at 1280px on a real desktop no matter where
the layout breakpoints move.

Two companion changes make the result actually full-width rather than merely
single-column. The 76 `container max-w-2xl` and `container max-w-3xl` page
shells became `container md:max-w-2xl` and `container md:max-w-3xl` (plus the
five `mx-auto max-w-4xl` and `mx-auto max-w-5xl` inner shells on checkout and
the marketing pages). Those caps are a desktop reading width; on a phone they
are inert because the cap is wider than the viewport, but on a 1280px landscape
tablet they left roughly 256px of dead gutter on each side. And a handful of
`sm:` utilities that were never asking about the input device moved to the new
`roomy` token instead of riding the scale up.

**Why it likely changed.** The one teacher this product serves works from a
tablet — an **Amazon Fire HD 10, 9th generation** — and asked for the phone
layout there: it uses the whole screen. The default scale gave her the opposite
on both counts.

That device is why the threshold is 1281 and not a rounder number. Its 1920x1200
panel at a 1.5 device pixel ratio is exactly **800 x 1280 CSS px**, so in
landscape — how a 10-inch tablet in a stand is normally used — she sits at
exactly 1280. A `min-width: 1280px` breakpoint matches at 1280, so the obvious
round threshold would have handed her the desktop layout in the orientation she
actually works in, and the change would have done nothing. Verified in Chromium
at both 800x1280 and 1280x800 against the compiled stylesheet: page shell
full-bleed (1280px of 1280px), hamburger nav, 44px touch targets, 16px inputs,
tables collapsed to cards, single-column grids — and at 1281 every one of those
flips to the desktop value.

**A tablet is a touch device.** Every `sm:` variant on the form primitives is a
mouse affordance. `h-11 sm:h-10` on Button, Input and Select is a 44px touch
target shrinking to a 40px pointer target; `text-base sm:text-sm` is 16px, the
size that stops mobile Safari zooming the page on focus, dropping to 14px.
Firing those at 640px handed a finger the controls drawn for a cursor.

**A tablet is narrow.** At `md` 768px she also got the desktop chrome — the
inline nav instead of the roomy hamburger panel, the wide table frame instead of
the row-per-card collapse — inside a 768px reading column centred in a 1280px
screen.

The threshold is the widest tablet **plus one**, not the widest tablet. CSS
`min-width: N` matches a viewport of exactly N, so a `min-width: 1280px` query
is already live at 1280px, which would have handed the 800x1280dp Android
tablet class its desktop layout in landscape — the exact bug being fixed.

**What was affected.** `apps/web` only.

Beyond the scale, the config and `globals.css`, three places lost content or a
capability at tablet width and were repaired rather than left to the tier:

- **`components/calendar/day-cell.tsx`.** The month grid swapped `09:30 Alicia
Moreno` chips for four unlabelled 6px dots. The dots' only labels are a hover
  tooltip and a `title`, and the cell is a `<Link>`, so on a touch device a tap
  navigates away instead of revealing anything. The chip gate was always a
  question of whether a 7-column grid has room to spell a time out, which a
  375px phone does not and every tablet does, so it moved to `roomy` along with
  `calendar-month.tsx`'s matching row height.
- **`components/marketing/marketing-header.tsx`.** Features and Pricing are
  `hidden sm:inline` and that header has no hamburger, so both links simply
  vanished below the threshold. Moved to `roomy`.
- **`app/admin/admin-sidebar.tsx`.** `AdminQuickSearch` is the one `md:hidden`
  swap in the codebase with no drawer equivalent — the mobile drawer is a flat
  list with no room for a search box. Moved to `roomy`; collapsed it is a 36px
  icon button, so 640px is ample.

Both Playwright configs now pin `viewport: { width: 1440, height: 900 }`. The
`Desktop Chrome` preset is 1280x720, one pixel under the threshold, so every
browser spec would have silently started auditing the phone render and passing
— retiring desktop coverage without a single red test.

Two guards are new: `src/lib/breakpoints.test.ts` asserts the scale contract
against measured device widths, and `tests/config/responsive-breakpoints.test.ts`
asserts the config consumes the module, that `globals.css` holds no hardcoded
width media query, that no Playwright project is left on the preset viewport,
and that no source file introduces an arbitrary `min-[900px]:`-style variant —
a second, invisible scale answering to nothing.

Also fixed in passing, because the change moved it onto the teacher's primary
device: the teacher chat pane computed `calc(100dvh - 3.5rem - 5rem)`, where the
5rem reserved a bottom tab bar that no longer exists. The student twin
already computed it without that term.

**Unresolved risks.** **Every browser window narrower than 1281px gets the touch
layout, not just tablets.** A 1280x800 external display, a non-maximised window
on a 13-inch machine, and an exact half-screen split on a 2560px monitor are all
one pixel short. No threshold avoids this: a 1280px window and a 1280px tablet
are indistinguishable to CSS. The cost lands on the admin console (the 224px
sidebar rail becomes a hamburger, filter rows and KPI grids stack) and on the
marketing pages, and it is accepted — one operator against the product's only
teacher. Do not add a second scale to dodge it.

**The 12.9-inch iPad Pro and Surface-class devices stay on the desktop layout in
landscape** (1366px and 1368px). They share a viewport width with the classic
1366x768 laptop, so catching them would put every such laptop on the phone
layout. At 13 inches the desktop layout is the better of the two answers.

**`theme.screens` is a replacement, not an extension.** Omitting a key deletes
every utility using it, at build time, silently — which is why `xl` and `2xl`
are kept despite no utility using either, and why a guard test asserts that
every prefix in `src/` resolves to a declared screen.

**The density consequences are the point, not regressions.** Pages roughly
double in height at tablet width; the pricing comparison stacks, the public
teacher page's buy card falls below the fold, and landing-page CTAs render as
full-width bars up to 1248px. That is the phone layout, which is what was
asked for. If a specific surface later needs a middle tier, give it a named
screen the way `roomy` is named — do not reach for an arbitrary variant.
