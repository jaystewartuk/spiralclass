# D-48. Analytics region becomes config rather than a hardcoded constant

**Date:** 2026-06-24. **Content reduced 2026-09-06, before publication
([D-159](./D-159.md)).**

**What this record covered.** The data-residency stance for the launch window —
where each store holding user data physically sits, what would force a move, and
the runbook for making one. It reached a conclusion about the operator's
position under a data-protection regime.

**Why most of it is not published.** That is a privacy and regulatory position,
not an engineering decision — see [D-159](./D-159.md). The current privacy layer,
including the sub-processor register and where each supplier processes, is
published in full: [D-128](./D-128.md), and `packages/shared/src/legal/`.

⚠️ **It is removed, not reversed.** Where data lives is recorded in the
sub-processor register, which is code and is tested
(`apps/web/tests/config/subprocessors.test.ts`).

**The engineering finding, kept.** The PostHog region was env-driven
server-side but **hardcoded US in two places the server never touched**: the
browser reverse-proxy destinations in `next.config.ts` and `ui_host`. So a
region that looked like configuration was a code edit in practice. The fix was
`NEXT_PUBLIC_POSTHOG_REGION` (`us` | `eu`, default `us`) with a single source of
truth in `apps/web/src/lib/analytics/posthog-region.ts`, covered by
`apps/web/tests/analytics/posthog-region.test.ts`.

**The general lesson, which outlives the specific stance:** a setting is only
configuration if _every_ place that consumes it reads the config. One hardcoded
consumer makes the whole thing a code change, and nothing in the type system
says so.
