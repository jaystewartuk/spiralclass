# D-153. Money columns say `minor_units`, not `centavos`

**What changed.** Every money column, wire field, helper and constant that
named the Mexican minor unit now names the generic one. Eighteen Postgres
columns across thirteen tables were renamed
(`packages.price_paid_centavos` → `price_paid_minor_units`,
`payments.amount_centavos` → `amount_minor_units`, and so on), with the Prisma
fields renamed to match. The three shared money helpers were renamed with them:
`formatCentavos` → `formatMinorUnits`, `pesosToCentavos` → `majorToMinorUnits`,
`centavosToPesos` → `minorUnitsToMajor`. So were the constants
(`PLAN_PRICE_CENTAVOS_BY_CURRENCY` → `PLAN_PRICE_MINOR_UNITS_BY_CURRENCY`,
`STRIPE_MIN_CHARGE_CENTAVOS` → `STRIPE_MIN_CHARGE_MINOR_UNITS`), the chart
formatter key, two admin CSV export headers, and the admin amount label in all
three i18n catalogs. Roughly 2,000 occurrences across 258 files.

The migration is a pure `ALTER TABLE ... RENAME COLUMN` sweep. No value is
read, written, converted or reinterpreted.

**Why it likely changed.** The name had been wrong for two separate reasons,
and one of them was a live correctness hazard rather than a matter of taste.

The first is the one this file has been correcting everywhere else since
[D-72](./D-72.md): the platform is not Mexico-specific. A teacher prices in any
of roughly forty curated currencies ([D-64](./D-64.md)), banks in any of
fifteen payee schemes ([D-124](./D-124.md)), and the platform bills itself in
GBP ([D-99](./D-99.md)). MXN is the column default and the floor under
`pricingCurrenciesForCountry` — a sentinel, not an assumption — and every money
row already records its own currency explicitly beside the amount. Only the
column names still asserted that every amount on the platform was Mexican.

The second is sharper. **Eight of the supported currencies are zero-decimal**
— JPY, KRW, CLP, VND, PYG, UGX, XAF, XOF. They have no hundredth part at all,
so `amount_centavos` did not merely use the wrong word for those rows; it named
a unit that does not exist. That is not hypothetical: the currency-aware
conversion fix that added PYG, UGX, XAF and XOF to `MINOR_UNIT_EXPONENTS`
exists precisely because the entry half of the conversion had been multiplying
by a hardcoded 100 while the render half divided by the real exponent, storing a
20,000 CLP price as 2,000,000. A column whose name says "centavos" is a
standing invitation to write `/ 100` against it.

`cents` was considered and rejected for the same reason. It is the more
familiar word and it matches Stripe's own vocabulary, but it is wrong for the
same eight currencies, and it would have left `formatCents(minorUnits, …)`
disagreeing with itself. **Minor unit is ISO 4217's own term**, and the
codebase was already half-speaking it: `MINOR_UNIT_EXPONENTS`,
`currencyExponent()`, and the parameter of `formatCentavos` was literally
already named `minorUnits`. This finishes a rename that had started at the
inside and never reached the column names.

**What was affected.** The schema and one migration; `packages/shared`'s money,
pricing, subscription-config, validator and marketing modules; the web app's
payments, subscriptions, discounts, referrals, booking, marketing and admin
surfaces; the API routes; and every colocated test.

Prose was treated separately from identifiers. A comment that says "centavos
for MXN" or "50000 JPY ≠ 50000 centavos MXN" is factually about Mexican money
and keeps the word; a comment using "centavos" as the generic term for a minor
unit was changed. Applied migrations under `prisma/migrations/` were not
touched — Prisma checksums them — and neither was the narrative in earlier
decision docs, which records what those decisions actually said at the time.

**Unresolved risks.**

The column rename is not reversible by a code rollback. Redeploying the
previous Fly release against a migrated database leaves the old code querying
columns that no longer exist, so a rollback here needs the Neon pre-migration
checkpoint ([D-95](./D-95.md)), not just `fly releases rollback`.

Two admin CSV exports changed their header row (`net_centavos` →
`net_minor_units`, `payable_centavos` → `payable_minor_units`,
`amount_centavos` → `amount_minor_units`). Any spreadsheet keyed on those
headers needs re-pointing.
