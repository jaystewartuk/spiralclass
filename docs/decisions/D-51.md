# D-51. Multi-region _serving_ plane: codify the four layers past D-49 (connection · routing · config · residency) as a design so "serve users from the region their data lives in" is a planned build, not an afterthought — but keep it design-only and gated on a real second region, because unlike D-49 these layers change the hot path

**What changed.** We wrote down the **serving-plane** strategy that sits on top
of [D-49](./D-49.md). D-49's three layers (provision · schema · data) answer
_"stand up a region and get data into/between regions."_ They deliberately stop
there — D-49's own "Connection layer (downstream note)" flags that _serving_
traffic across regions is out of its scope. D-51 records the layers that close
that gap, and — importantly — records why they are **not built yet** while
D-49's three were built ahead of the trigger.

This is design-only. **No serving-plane code was written for this decision.** It
sets direction so that, when the [D-48](./D-48.md) residency trigger fires, the
serving build is a known sequence rather than an improvisation.

**The dividing line (why D-49 shipped early and D-51 does not).** D-49's layers
are **inert, reversible tooling** — an OpenTofu plan that touches nothing until
applied, plus scripts that act only on the connection strings you hand them. So
building them ahead of need cost nothing and de-risked the eventual move. D-51's
layers are the opposite: they change the **serving hot path** — middleware, the
Prisma client, the tenant schema, runtime secrets. Building them before a second
region exists is the _same_ "empty EU infra is pure cost" mistake D-48/D-49 warn
against, paid in code complexity and Tier-2 risk instead of hosting bills. So the
rule is inverted here: **write the design now, build the code with (or just
before) the first real region — never speculatively.**

**The four layers (continuing D-49's numbering).**

4. **Connection / pooling** — "a fast, pooled connection to whichever regional
   Postgres a request is routed to." The one D-49 already named. Serverless
   (Vercel) × Postgres × N regions is where connection exhaustion bites.
   _Today:_ single-region, already handled by **Supabase's pooler (Supavisor,
   port 6543, `pgbouncer=true`)** — see `apps/web/.env.example`, which already
   splits the pooled runtime URL (`DATABASE_URL`) from the direct migration URL
   (`DIRECT_URL`). _Future:_ **Cloudflare Hyperdrive** (we already front the app
   with Cloudflare; the Hyperdrive provider is available) becomes attractive
   when there are multiple regions to pool toward, or when a provider swap
   (Neon) makes a provider-neutral pooler worth it. **Do not adopt Hyperdrive
   for a single region** — it is complexity without payoff until multi-region.

5. **Routing / region resolution** — "resolve _which_ database serves this
   request." This is the real app-level one-way door for serving: today the app
   has a single `DATABASE_URL` and a single Prisma client (`src/lib/prisma.ts`),
   i.e. the hot path _assumes one database_. Multi-region serving needs (a) a
   **per-tenant region map** (a teacher — the tenant root, `teacher_id` on every
   scoped table — carries a `region` attribute recording where their rows live)
   and (b) **request-time client selection** (resolve the tenant's region in
   `src/middleware.ts`, hand the matching pooled connection to a per-region
   Prisma client factory). This is the invasive layer; it touches the tenant
   model and every request. It is also where a get-it-wrong bug **leaks PII
   across residency boundaries**, so it lands with tests and a default-deny
   posture (unknown region → refuse, never fall back to the wrong region).

6. **Config / secret distribution** — "the app runtime knows every region's
   connection string, reproducibly." The D-49 layers _produce_ per-region URLs;
   something must deliver them to Vercel/Cloudflare env per environment.
   `MIGRATE_REGIONS` (D-49 layer 2) is the _migration-time_ shape of exactly
   this; layer 6 is its **runtime sibling** — the pooled URL (+ any per-region
   keys) the router in layer 5 reads. Natural implementation: one structured env
   (a JSON region→URL map, mirroring `MIGRATE_REGIONS`) resolved once at boot,
   with the single-region case as the fallback so it stays a no-op until needed.

7. **Residency governance / audit** — "enforce and _prove_ EU residents' rows
   live in EU." This closes the loop back to D-48's actual reason for existing:
   the GDPR/residency obligation. Not just _making_ a move possible, but a
   continuous check that a tenant's `region` matches where their rows physically
   are, that no request served a tenant from the wrong region, and that schema
   hasn't drifted between regions. Extends the existing pieces — the promote-time
   `pg_dump`-to-R2 backup (`promote.yml`) becomes region-aware; the D-49
   `db-verify-clone.sh` checksum idea becomes a periodic cross-region drift
   check.

**Provider strategy (unchanged from D-49, restated for the serving plane).** The
provider picks stay reversible because layers 4–7, like 1–3, are built on plain
connection strings and one neutral routing seam — not on a provider's
multi-region product. Concretely: **Supabase pooler now → Hyperdrive when
multi-region**; routing/config/residency are ours (framework code), owned and
portable by construction. We do **not** adopt a proprietary "global database"
product (Aurora Global, Spanner, Cloudflare D1's regional story) that would
re-forge the lock-in D-49 spent its whole design shedding.

**Why it likely changed.** Leaving the serving-plane concerns unwritten would let
them be _discovered_ mid-incident when the first EU user signs up — the worst
time to design a PII-routing layer. Writing them down now, while explicitly
_not_ building them, gets the value (a known sequence, a default-deny routing
posture decided in calm) without the cost (hot-path complexity for a region that
doesn't exist). It also names the one genuine _now_ action hiding among the
deferrals: finishing D-49 layer 1's live wiring (create the R2 state bucket +
`tofu import` the existing Supabase project) so provisioning reflects reality —
that is pre-hardening, not a serving-plane build.

**What was affected.** Strategy/docs only — **no code, no infra**. Leans on /
extends: D-49 (the provision/schema/data layers this sits atop), D-48 (the
residency _why_ and its trigger), D-40 (better-auth on owned tables — keeps auth
region-portable), D-44 (HTTP polling not Realtime — keeps the DB portable), and
the standing self-hosting posture.

**Unresolved risks.**

- **Routing is a PII-safety boundary, not just a lookup.** Layer 5 done wrong
  serves one tenant's data from another region — a residency breach, not a 500.
  It must be default-deny (unknown/mismatched region → refuse) and land with
  tests; this is the highest-risk layer in either decision.
- **Tenant-region as new schema.** A `teacher.region` attribute is a schema
  change on the tenant root; adding it is cheap, but _backfilling_ it correctly
  and keeping it in lockstep with where rows actually live is the hard part
  (layer 7 exists to police exactly this).
- **Speculative-build temptation, inverted.** The pull will be to build routing
  "while we're in here" during the EU stand-up. Resist scope creep the other
  way too: build only what the first real region needs; a third region's
  concerns (active-active, conflict resolution) are not this decision.
- **Hyperdrive premature-adoption.** Adopting it single-region adds a dependency
  and a cache-coherence surface for no benefit. Gate it on real multi-region or
  measured connection-limit pain.
- **Still deferred, on purpose.** Like D-49 at first write, this is a commitment
  with no implementation. Until the trigger fires and layers 4–7 are built,
  multi-region _serving_ does not exist — only the move pipeline (D-49) does.

**Sequencing.** Nothing here is built speculatively. Order when the D-48 trigger
fires: finish D-49 layer 1 wiring (bucket + import) → provision EU (D-49 L1) →
migrate it (D-49 L2) → move/replicate data (D-49 L3) → **then** layer 6 (wire the
region→URL map) → layer 5 (router + `teacher.region`, default-deny, tested) →
layer 4 (Hyperdrive, only if pooling demands it) → layer 7 (residency audit) as
the closing, continuous check. Layers 4–7 land in that order because each needs
the one before it to have something real to point at.
