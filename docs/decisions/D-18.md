# D-18. Re-couple production migrations to the deploy (supersedes D-11's prod build change)

**What changed.** The production Vercel build runs `prisma migrate deploy`
again, reversing the production-build half of [D-11](./D-11.md). The web app's
`build` script (`apps/web/package.json`) ends with a guarded migrate:

```
… && next build && if [ "$VERCEL_ENV" = "production" ]; then prisma migrate deploy; else echo "Skipping … (not production)"; fi
```

So a push to `main` now applies any pending migrations to prod as part of the
deploy, exactly as it did before D-11 (the original `#142` gate). The migrate
runs **after** `next build` and **only** when `VERCEL_ENV=production`, so a
failed compile never reaches the migrate, and preview builds never touch the
prod database. Prisma's advisory lock makes concurrent prod builds wait rather
than race.

**This only reverses the production-build portion of D-11.** The deleted
`.github/workflows/preview-db.yml` (which migrated + seeded Supabase
preview-branch DBs) stays deleted — previews are still migrated/seeded by hand
per `docs/ops/PREVIEW_DEPLOYMENTS.md`. Re-coupling is production-only.

**Why it changed.** D-11 decoupled migration from deploy so a schema change
would be a deliberate, separately-timed step. In practice the decoupling's
named "unresolved risk" — _a deploy can run ahead of its schema_ — bit us:
the lesson-notes and student-notes table migrations shipped to prod in code
(auto-deployed on merge) while the migrations sat unapplied, so the live app
queried tables that did not exist until the migration was run by hand days
later. The mitigation D-11 relied on (remember to run `migrate deploy` as part
of every release) proved too easy to forget for a solo operator. Re-coupling
makes "code is live" and "schema is current" the same event again, which is the
safer default for additive migrations (the overwhelmingly common case here).

**What was affected.**

- `apps/web/package.json` `build` script (migrate tail restored).
- `docs/engineering/DEVELOPMENT_WORKFLOW.md` (Deploy-trigger + standing rules
  updated to describe auto-migrate again and cite this decision).
- `docs/orientation/09-infrastructure-and-deployment.md` (spoken narrative
  flipped back to auto-migrate-on-prod-deploy for the production path).
- `DIRECT_URL` on Vercel is **live again at build time** (it is the connection
  `migrate deploy` uses), reversing D-11's "dead weight" note. `VERCEL_ENV`,
  `DATABASE_URL`, `DIRECT_URL` are already allow-listed in `turbo.json`'s build
  `env`, so Turbo strict mode passes them through.

**Unresolved risks.**

- **Migrations run on the deploy's schedule rather than the operator's**,
  which is the coupling D-11 had separated and this decision re-accepts.
  Mitigations: (1) all
  migration changes are Tier 2 → `pnpm verify:local` + `git push --no-verify`,
  which runs the migration against ephemeral Postgres; (2) keep
  the **no-risky-pushes-during-lesson-hours** rule — it now also gates schema
  changes; (3) prefer **expand-then-contract** (additive) migrations so code
  and schema never have to flip in lockstep, and split destructive changes
  (drop/rename) across two deploys.
- **A failed migration blocks the deploy.** Because migrate runs inside the
  build, a migration that errors fails the build and prod stays on the prior
  deployment (no promote). Recovery = resolve the migration state, then
  re-deploy; see `docs/deployment/INCIDENT_RESPONSE.md`.
