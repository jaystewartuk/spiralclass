# D-44. Chat: portable HTTP delivery (drop Supabase Realtime) + a push-first / delayed-email cascade for message notifications

**What changed.** Two coupled changes to in-app messaging.

1. **In-app delivery no longer depends on Supabase Realtime.** The web
   `chat-room.tsx` `postgres_changes` subscription — and its
   `getRealtimeTokenAction` / `createClient({ accessToken })` wiring (the D-40
   Realtime JWT bridge) — is removed for chat. Both platforms now deliver over
   plain-HTTP polling that feels live:
   - Web (`chat-room.tsx`): ~4s poll while `document.visibilityState` is
     `visible`, paused when hidden, with an instant refetch on
     `visibilitychange`→visible and window `focus`.
   - A second client used a `useForegroundPolling` hook — ~4s poll while the
     screen is focused, with an instant catch-up on screen focus and on
     foreground
     (`AppState`→`active`). Replaces the old silent 15s poll that had **no**
     foreground refetch.

2. **Chat notifications route push-first with a delayed email fallback**, not
   the parallel push+email fan-out the dispatcher uses for every other template.
   - `dispatcher.ts`: for `chat_message` / `chat_message_teacher` the send loop
     `break`s after a successful push (a cascade), so it does **not** also email.
     A push _hard-failure_ still falls through to email in the same pass, and a
     recipient with no device token (or push opted out) is emailed immediately.
   - `sendChatEmailFallbackIfUnread()` (dispatcher) + the Inngest
     `dispatch-notification` fn: after a chat push, `step.sleep` a grace window
     (`CHAT_EMAIL_FALLBACK_GRACE`, currently `3m`) then send the email **only if
     the recipient still hasn't opened the thread**. "Opened" is read straight
     off `message.readAt` — the chat GET route already stamps the _sender's_
     messages read when the recipient views them — so no new state/metadata and
     no message-route edits are needed, and multiple unread messages coalesce
     (one read clears them all). It stays a **single** notification row (chat
     rows are inbox-visible, so a second row would duplicate the inbox entry) and
     honors the `messages` category's channel-prefs / opt-outs on both passes.

**Why it likely changed.** Two reasons converged. First, portability: the DB is
slated to move off Supabase to self-hosted Postgres (the infra-postgres
initiative), and Supabase Realtime is the one runtime coupling in the chat path
that wouldn't survive that move; plain polling against Prisma/Postgres is
host-agnostic. Second, correctness + UX: the Realtime path was the _only_ instant
delivery, and the other surface had none at all (15s poll, no foreground refetch), so
messages appeared to arrive only on a full close-and-reopen — and separately, the
fan-out meant every single message buzzed **both** a push and an email even while
the recipient was staring at the chat. Push-first + "email only if you didn't see
it" is the standard chat-notification shape: one interruption per message,
escalating to the costlier channel only when the cheaper one didn't land.

**What was affected.** Web `chat-room.tsx` (Realtime removed, visibility/focus
poll added); `lib/notifications/dispatcher.ts` (cascade `break`, `templateName` on the `sent`
outcome, `sendChatEmailFallbackIfUnread()`); `lib/inngest/functions/dispatch-notification.ts`
(grace `step.sleep` + fallback step). No schema change, no `resolve-channel.ts`
change (cascade is a loop behavior, not a channel-selection change), no
message-route edits. Tests: `tests/notifications/chat-notifications.test.ts`.
`student-live-notes.tsx`
(live lesson notes) still uses Supabase Realtime — deliberately out of scope here.

**Unresolved risks.**

- **Tier 2 (`lib/notifications/**`, `lib/inngest/**`).** The push→email semantics
  change is exercised by unit tests + `dispatcher.integration.test.ts`, but the
  live behavior only proves out at promote (integration + E2E). Verify the 3m
  fallback actually suppresses on read against a real DB before trusting it in
  prod.
- **Polling cost / DB read load.** ~4s foreground polling per open thread is
  fine at current scale but is a per-open-chat read multiplier; revisit the
  interval (or move to SSE/LISTEN-NOTIFY on the self-hosted Postgres) if chat
  usage grows.
- **Grace-window tuning is a UX judgement.** 3m balances "useful catch-up" vs.
  "don't email an active reader"; it's a single named constant, but the right
  value is empirical — watch for complaints of email-too-eager or too-late.
- **Read signal is thread-level, not message-level.** "Any unread sender message
  remains" drives the fallback; this is intentional (coalescing) but means the
  email says "you have messages", not "you have _this_ message" — correct for
  chat, but don't reuse the pattern where per-item read state matters.
