# D-124. Open the manual payout rail to any country, via a bank-scheme registry

> **`bank_account` was removed by [D-145](./D-145.md) (2026-08-31)**, once a
> teacher's own Stripe account began presenting SPEI at checkout and the same
> rail was being offered twice on one page. Wise is the only manual instrument
> now. The registry's argument outlives the registry and is why this record is
> still here: every payee value a student pays against must be
> machine-checkable, and re-adding a kind means re-adding a validator, never a
> free-form field.

**What changed.** A teacher anywhere in the world can now publish her own bank
account and be paid into it. The manual rail's instrument union stays two kinds
— `wise` and `bank_account` — but a bank account's FIELDS now come from a
per-country scheme registry in `@spiralclass/shared` rather than from columns:

- `PayoutInstrumentKind` is `wise | bank_account`. D-113's third kind, `spei`,
  was folded in. A CLABE is Mexico's account format, not a separate species of
  instrument, and keeping it as its own kind would have meant two ways to
  express "a Mexican bank account" forever. The teacher still sees the card
  labelled SPEI — that name is now the scheme's `displayName`, which is where a
  brand belongs.
- `teacher_payout_instruments` gained `scheme_id`, `country` and `details`
  (JSONB), and lost `clabe`. `country` is the ACCOUNT's country, not the
  teacher's: someone living in Spain may perfectly well bank in Nigeria.
- Fifteen schemes ship, layered so that "a teacher anywhere" is true rather
  than aspirational. A domestic format where the country has one worth naming
  (CLABE, PIX, NUBAN, IFSC, CBU, RUT, CCI, InstaPay, ACH, Faster Payments, EFT,
  BSB); IBAN for the roughly eighty countries in the IBAN registry; and
  SWIFT/BIC as the universal fallback for everything else.
- `PaymentRail`'s manual value is `bank_transfer`, and analytics carry the
  account format in a separate `scheme` property rather than splitting the rail
  dimension per country.
- The manual rail's pricing-currency list grew from six Latin American
  currencies to roughly fifty.

**Why it likely changed.** D-113 generalized the manual rail off Wise, and the
generalization stopped one step short. The rail could express two instruments,
both of which a teacher might not have: Stripe Connect only reaches its own
cross-border circle (D-58 — the United States, the United Kingdom, the EEA,
Canada, Switzerland), and Wise requires a Wise account. A teacher in Nigeria,
Indonesia or the Philippines with a perfectly good local bank account had no
way to get paid at all.

The currency list made it worse in a way that was easy to miss. Even a teacher
who did have Wise could only price in one of six Latin American currencies, so
the rail was reachable without being usable: a Nigerian teacher could publish a
working payee handle and still be unable to quote a price in naira.

**Why a registry rather than a free-text field.** `payout-instruments.ts`
argued from the start that the instrument union should stay closed, because
"instrument as data" invites a free-form bank-details textarea, and an
unvalidated payee field on a page a student pays from is the one place this rail
can lose real money with no way back. That argument was right, and the registry
is what preserves it while opening the union. Every payee value a student sees
has been through its scheme's own validator, including the real published
checksums where the format defines one — IBAN's mod-97, the CLABE control
digit, the ABA weighted mod-10, Nigeria's NUBAN check digit (which spans the
institution code AND the account number, so it cannot live on either field
alone), Argentina's two-block CBU, Chile's RUT mod-11, and Brazil's CPF and
CNPJ behind a PIX key. Where a format genuinely has no checksum — a UK sort
code, a Peruvian CCI, a BIC — the scheme says so in a comment rather than
implying a check it does not perform.

Adding a country is therefore a row in one file: no migration, no schema
change, no new form, no new API route. That property is the whole design, and
it is why scheme ids are validated in the application layer rather than
enumerated as a Postgres type — the same posture `teachers.pricing_currency`
already takes (D-64).

**What was affected.**

- **Schema.** One migration, folded into D-113's unmerged one rather than
  stacked on top: nothing had shipped, so creating a `clabe` column and then
  dropping it would have been pure noise in the history. Eight CHECK
  constraints on the instrument table, all exercised against a real Postgres 16
  before merge.
- **Validation.** `bankAccountInstrumentSchema` in the shared package is a thin
  Zod wrapper over `validateBankDetails`, so every write path applies exactly
  the same rule. If one were the looser, a teacher
  could save from her phone an account number the web form rejects.
- **Display.** `buildPayeeInstructions` is one builder feeding the web
  instructions page and its callers, so both render the same fields in the
  same order, grouped for read-back. The copy button hands over the canonical
  value, because a banking app that rejects spaces would choke on the grouped
  one.
- **The public-listing gate.** `HAS_PAYOUT_RAIL_WHERE` is now GENERATED from
  the registry via `bankSchemeIdsForCurrency`, so a hand-maintained SQL list
  cannot drift from it. See the unresolved risk below.
- **Backward compatibility.** An installed client is never in lockstep with the
  server. The
  transfer-instructions payloads still carry `clabe` and `clabeFormatted` for
  the Mexican scheme, which is the only one an older build knew how to render.

**Unresolved risks.**

- **The SQL gate is a deliberate over-approximation.** SQL tests that an
  enabled bank account exists for a settling scheme; the JS predicate
  additionally tests that every required field of that scheme is filled in. The
  two agree over every state the application can produce, because
  `saveTeacherInstrument` refuses to enable an incomplete account and the
  `details_required_when_enabled` CHECK backs that up. A row enabled with
  partial details is unreachable, and the sitemap parity test enumerates the
  reachable states rather than pretending SQL models the unreachable one. If
  something ever writes to this table outside `saveTeacherInstrument`, that
  invariant is what breaks first.
- **Field-level validation is application-layer only.** The database enforces
  shape (an object, a two-letter country, a scheme-id pattern, non-empty
  details when enabled) and nothing more. This is the accepted cost of not
  requiring a migration per country; the mitigation is that there is exactly
  one write path and both clients go through it.
- **One bank account per teacher.** `@@unique([teacherId, kind])` is unchanged,
  so a teacher cannot publish both a domestic account and an international one.
  This is a real limitation for a teacher with students abroad. Lifting it is a
  one-line constraint change plus UI work, deliberately deferred rather than
  designed in speculatively.
- **No auto-reconciliation, permanently.** No retail bank exposes a
  per-teacher statement API we could rely on across countries, so every
  bank-account payment costs the teacher one manual confirmation. This is a
  property of the instrument, not a gap that closes later, and the settings UI
  says so before she enables it rather than leaving her to discover it when a
  student's package fails to activate.
- **Some currencies are still unreachable for circle countries.** A Swedish
  teacher is inside the Connect circle and so prices from the Connect list
  (GBP, USD, EUR) — she cannot price in kronor even though SEK is now in the
  manual-rail list. Widening the Connect list is a Stripe presentment-currency
  question and was deliberately left out of scope here.
