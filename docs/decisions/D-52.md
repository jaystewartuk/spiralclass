# D-52. Web i18n is a shared key-based catalog with a registry and compile-time completeness, guarded against new hardcoded copy

**What changed.** Web string localization moved from three competing homegrown
patterns to a single key-based catalog, hosted in the **shared package** so
every surface draws from one source of truth.

- **One catalog, shared.** It lives at `packages/shared/src/i18n/catalog.ts`,
  and every surface reads it. Web-only surfaces add `web.*` keys there.
- **A locale registry, not a 2-value union.** `packages/shared/src/i18n/locales.ts`
  declares each supported language once (`tag`, `languageCode`, `label`,
  Accept-Language `match`). `AppLocale` is _derived_ from that list, and the old
  parallel hardcoded unions (`api.ts` `LocaleCode`, notifications `LanguageCode`)
  now alias/derive from it. Adding `pt-BR`/`en-GB` is **one row** plus the copy
  the compiler then demands — not an edit at every call site.
- **BCP-47 normalized.** The in-app identifier is the hyphenated tag
  (`es-MX`/`en`); the underscore `es_MX` used by email/push is a per-locale
  `languageCode` field on the registry, so the hyphen/underscore bridge
  (`localeToLanguageCode`) has a single source instead of a parallel mapping.
- **Completeness is a type error.** `catalog.ts` asserts
  `typeof strings extends Record<AppLocale, Record<StringKey, string>>`, so a key
  added to the source locale without every other locale's translation — or a
  registered locale with no catalog block — fails `tsc`. "New copy can't land
  untranslated," enforced by the compiler.
- **Two guardrails stop the bleeding.** A repo-wide **ratchet test**
  (`apps/web/tests/i18n-guard.test.ts` + `scripts/i18n-guard.mjs`, baseline
  `scripts/i18n-guard.baseline.json`) fails when a file adds user-facing JSX
  literals beyond its grandfathered baseline; migrated files carry 0. A scoped
  **ESLint rule** (`eslint-rules/no-literal-string.mjs`) is the edit-time backstop
  on files already converted.
- **Beachhead migrated.** The auth forms (client, via `useT()`) and the
  onboarding shell (server, via `getT()`) are on the catalog — proving both
  runtime halves. Everything else stays working; see
  `docs/development/i18n.md` for the path.

**Why it likely changed.** Web strings were inline across ~187 files in three
styles (`translate()` dicts, `locale === "en" ? …` ternaries, and ~50% pure
hardcoded Spanish with no English branch at all). Every feature shipped in that
style made the eventual third language
more expensive and let untranslated copy ship silently. This was the biggest
accruing-debt item for the global launch — scoped deliberately as
architecture-plus-guardrail, not "translate everything."

**What was affected.** `packages/shared/src/i18n/*` (new), `packages/shared`
barrel + `api.ts`; `apps/web/src/lib/i18n.ts` / `i18n-translate.ts`, `components/locale-provider.tsx`
(`useT`), `components/locale-toggle.tsx`, `app/actions/locale.ts`,
`lib/notifications/templates.ts`; the auth + onboarding-shell surfaces; new
guardrail files under `apps/web/scripts`, `apps/web/eslint-rules`,
`apps/web/tests`.

**Unresolved risks.** The remaining ~180 files still carry inline copy — the
ratchet holds the line but doesn't migrate them; that's follow-up work. The
shared catalog is a superset of every surface's keys, so unused keys accumulate
(same as before, now in one place). `nav.ts` labels stay a
fixed-2-locale shape for now; widening the registry will surface them as
compile errors to translate (intended).
