# D-177. Vercel comes back as a second production target that holds no domain; the coupling D-89 removed stays removed

**Status: Decided and built; never yet serving traffic.** The machinery is on
`main` and runs on every production release. No deployment it produces has ever
held `spiralclass.com`, and taking the domain is a separate operator command
that nothing in CI can perform.

**What changed.** [D-89](./D-89.md) Phase 5 tore the Vercel project down and
removed every line of code that knew about it. This reverses **the teardown of
the project** and nothing else:

|                                  | Before (D-89 Phase 5 → D-164)                 | Now (this decision)                                                                    |
| -------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Vercel project**               | Torn down                                     | Exists; receives a production deployment of every promoted commit                      |
| **Who serves `spiralclass.com`** | Fly `agendaprofe`                             | Fly `agendaprofe` — **unchanged**                                                      |
| **Deploy config**                | `vercel.json`, deleted by [D-164](./D-164.md) | `config/vercel/production.json`, passed with `--local-config`; root file still banned  |
| **Deploy trigger**               | —                                             | A job in `deploy-production.yml` that `needs:` the `database` job — not Fly (addendum) |
| **`VERCEL_ENV` in the app**      | None                                          | **None** — `APP_URL` still decides prod-vs-preview                                     |
| **`@vercel/*` dependency**       | Banned                                        | **Still banned** — the CLI is `npx --yes vercel@59.15.1`, a tool, not a dependency     |
| **Fly machinery**                | The deploy path                               | **Untouched** by this record; its checkpoint and migrations moved out in the addendum  |

**What changed about D-89's premise, since that is what this log asks for.**
D-89 Phase 5 bundled two things that are separable, and only one of them was
load-bearing:

1. **The app stopped knowing which platform it was on.** `VERCEL_ENV` branches
   became `APP_URL`; `VERCEL_GIT_COMMIT_SHA` became `NEXT_DEPLOYMENT_ID`; the
   Vercel Live CSP hosts went. This was the valuable half, and **nothing here
   touches it.**
2. **The Vercel account was closed.** This was bookkeeping — a dormant project
   on a stale plan, kept "as the rollback path" through a soak and then not
   needed.

The premise that has expired is the one behind (2), and
[D-150](./D-150.md)'s own reasoning is what expired it. D-150 set out to move the
app off Fly, measured carefully, and then reversed itself in an addendum: the app
stays on Fly because `ord` is 12 ms from Neon where the free box was 58 ms. Its
**first** decision, though, survived that reversal and is quoted here because it
is this record's whole warrant:

> The application is already provider-neutral; what is Fly-specific is small and
> stays isolated so that returning is a command, not a project.

That claim had never been tested. A repository with exactly one deployment target
cannot tell a provider-neutral application from one that merely has not been
asked. **Building the second target is the test, and the result is the strongest
evidence this decision has: it needed no change to `apps/web/src` at all.** Not
one file. The decoupling D-89 did was real, and the way to keep it real is to
exercise it.

## Why it holds no domain, and why it deploys anyway

`vercel deploy --prod` would assign `spiralclass.com` on every release.
`--skip-domain` builds and deploys the identical production artifact and leaves
the alias alone. So the target is **built, deployed and warm on every release**,
and serves nothing.

Both halves of that are deliberate, and they answer the two ways a standby gets
this wrong:

- **A dormant project nobody deploys is not a rollback path.** That is
  [D-164](./D-164.md)'s finding, applied rather than restated: three runbooks
  described infrastructure that had never been built or had been retired twice,
  and a reader who trusted the heading got the wrong answer. `ORACLE_RUNNER.md`
  carried four stacked banners above a `Status: LIVE` line that was false for
  seven weeks. Vercel was already this: "kept configured as the rollback path"
  in D-89's table, and by Phase 5 nobody had deployed it in months. A failover
  proven on every release cannot rot into that.
- **A CI job must not perform a DNS cutover.** CLAUDE.md's first rule reserves
  shipping to the operator, per change, on timing that is theirs. A deploy that
  silently moved the domain would be the largest possible violation of it,
  dressed as a convenience.

The handover is therefore one command, run by hand against a deployment that is
already live and already warm — stated once, in
[`docs/deployment/RELEASE_AND_STAGING.md`](../deployment/RELEASE_AND_STAGING.md).

## What the Vercel deploy deliberately does not do

`scripts/fly-deploy.sh` has seven ordered steps. `scripts/vercel-deploy.sh` has
four, and the three it drops are the point of the design rather than a
simplification of it. Two are hazards if added back.

| Dropped step                            | Why, and what adding it back would cost                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Neon checkpoint** ([D-95](./D-95.md)) | The `database` job cut one for this commit against the same Neon branch, minutes earlier (the Fly job did, until the addendum). A second is noise.                                                                                                                                                                                                                                             |
| **Migrations**                          | Same branch, same commit, already applied. One commit, one migration run, in the job that checkpoints first. A second run would be a no-op that makes this script look like it owns the schema; it does not, and the job is handed no `DATABASE_URL` so it cannot.                                                                                                                             |
| **Inngest sync**                        | ⚠️ **The sharp one.** Inngest registers an app **per URL**. Syncing a second URL registers a second app, so a cron defined once would fire **twice** — once from the thing serving and once from a failover carrying no traffic. The 2026-07-07 email+push outage was a cron that silently never ran; this is the same class pointing the other way, and it bills real Stripe customers twice. |
| **Production probes**                   | `scripts/local/synthetic.sh` probes `https://spiralclass.com`, which this deploy does not serve. Pointing it at the Vercel URL would be a second definition of "is production healthy".                                                                                                                                                                                                        |

`needs: [database]` is what turns "already migrated" from a hope into a fact, and
it is one word. (It was `needs: [deploy]`, the Fly job, until the addendum below.)
`apps/web/tests/config/vercel-deploy.test.ts` asserts it, and asserts the job
holds no database or Neon credential — the narrowest way to say a job has no
business with the schema is to not hand it the means.

## Why a second job and not a second workflow

The obvious shape is `deploy-vercel-production.yml` with its own push trigger.
It is wrong three ways, and the third is the one that decided it:

1. A separate push-triggered workflow runs **concurrently** with the Fly deploy,
   against one database. Prisma's advisory lock makes that block rather than
   corrupt, but "the failover may serve code against a schema that has not moved
   yet" is a property nobody should have to reason about.
2. A `workflow_run` trigger fixes the ordering and adds a second trigger surface
   and a default-branch context to understand.
3. A second file would have tripped
   `apps/web/tests/config/local-gate.test.ts`'s rule that every `deploy-*`
   workflow calls `scripts/fly-deploy.sh` — and the **wrong** fix is to relax
   that rule because a new file exists. It has been widened to "calls one of the
   known deploy scripts", with the forbidden-reimplementation list extended to
   both targets' verbs, because the rule was never about Fly. It is about a
   workflow having no opinion about what the steps are.

## Configuration, and the two locks on the trigger

Vercel reads a **root** `vercel.json` automatically. That is how a repository
acquires a deploy trigger nobody typed, and it is what D-89 ruled out ("no
Vercel native git integration") and D-150's addendum settled again ("every deploy
runs through GitHub Actions"). So:

- **The root `vercel.json` stays banned** by
  `decommissioned-platforms.test.ts`. The reason changed — from "it describes a
  torn-down project" to "it is an unreviewed path to production" — and the ban
  did not.
- **The config lives at `config/vercel/production.json`**, where only
  `scripts/vercel-deploy.sh` finds it, via `--local-config`.
- **That file sets `git.deploymentEnabled: false`**, so even a repository
  connected by hand in the dashboard deploys nothing on a push.

Two independent locks, because the failure they prevent is a second unreviewed
path to production.

`config/env/production.build.env` stays the one home of the `NEXT_PUBLIC_*`
values. `vercel pull` brings the Vercel project's own copy down, and the deploy
**overwrites it** with this repository's values, resolved through the same
`scripts/env-build-args.mjs` the Docker build calls. These are baked irreversibly
into the client bundle, so a dashboard that could win a disagreement would ship
different values for the same commit with nothing failing.

## Unresolved risks, and what would reopen this

- **⚠️ `regions: ["cle1"]` is an unverified premise.** D-150 says Neon
  production is "in Ohio"; the project's region is not committed anywhere in the
  tree, because the publication sweep removed the identifier
  ([D-158](./D-158.md)). `cle1` is Cleveland, `us-east-2`. **Confirm with
  `neonctl projects list` before this target ever takes the domain.** A function
  in the wrong region re-introduces exactly the 58-ms-versus-12-ms latency
  D-150's whole argument was about, silently and with nothing failing. The test
  pins the value so changing it is a deliberate edit in two places.
- **The failover has never served a request.** It builds and deploys; that is
  all that is proven. It has no LiveKit reachability story, its cold-start
  behaviour against Neon is unmeasured, and the Inngest endpoint stays with Fly
  — so promoting it would leave background work pointed at an app that is no
  longer serving. **Promoting it is not currently a complete failover**, and
  anyone reaching for it during an incident should know that before they do.
  Closing that gap is a separate decision.
- **Cost is unmeasured.** D-150 was prompted by a ten-dollar Fly invoice against
  a product with no paying teachers. A Vercel project that builds on every
  production release consumes build minutes, and nothing here measured how many.
  If that bill is material the answer is to drop the job's frequency, not to
  let the target rot back into a dormant one.
- **Preview is untouched and stays assigned to the Oracle box** (D-150's second
  addendum). `config/vercel/` has one file on purpose. Adding `preview.json`
  means deciding what serves `preview.spiralclass.com`, which is that record's
  question, not this one's.

## Addendum, 2026-09-12 — the two targets deploy independently; the database is a job of its own

**What changed.** The operator asked for the Fly deploy and the Vercel deploy to
run independently, neither needing the other's environment variables. The
premise that coupled them was this record's own: the checkpoint and the
migrations lived inside the Fly job, so the Vercel job `needs:`-ed the Fly job
to be sure the schema had moved. That was the right guarantee attached to the
wrong job, and it had two consequences nobody had yet been bitten by, because
neither target had deployed once.

- **The failover could only deploy after Fly had succeeded.** A failover is for
  when Fly is unavailable — and a Fly outage fails the Fly job at its first
  step, `flyctl status`, before a single migration. So the one case the target
  exists for was the one case it could not be deployed.
- **A missing Vercel credential made a shipped Fly release look unshipped.** The
  run goes red when any job does, and `pnpm promote` watched the run's exit
  status. On the day this was written none of the three `VERCEL_*` values were
  in the `production` environment, so the first promote would have deployed and
  probed Fly, then reported that the running app may not have moved.

|                               | Before (this record as merged)                              | Now                                                                                                  |
| ----------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Checkpoint and migrations** | Steps 1–2 of `scripts/fly-deploy.sh`, inside the Fly job    | `scripts/database-deploy.sh`, as the `database` job                                                  |
| **Fly job**                   | Needs nothing; holds database, Neon, Fly and LiveKit values | `needs: [database]`; holds Fly, LiveKit and the build values; passes `--database-already-deployed`   |
| **Vercel job**                | `needs: [deploy]`                                           | `needs: [database]` — never the Fly job                                                              |
| **A dispatch**                | Deploys both                                                | `target: both`, `fly` or `vercel`; the database job runs first either way. A push still deploys both |
| **What promote judges**       | The run's exit status                                       | The `database` and `fly` jobs; the failover's outcome is printed on its own line                     |
| **A hand-run Fly deploy**     | Checkpoints, migrates, deploys                              | **Unchanged** — it runs `scripts/database-deploy.sh` first                                           |

**What did not change**, and it is most of this record. One commit, one
migration run, in the job that checkpoints first. The Vercel job holds no
database or Neon credential, and now no Fly one either. It is still one
workflow, not two: the first reason under "Why a second job and not a second
workflow" is untouched, since a second push-triggered workflow would race the
migrations it depends on. And a push still deploys both targets, so the
failover never depends on someone remembering to dispatch it ([D-120](./D-120.md)).

**Each job holds its own credentials and no other job's.** `database` holds
`DATABASE_URL`, `DIRECT_URL`, `NEON_API_KEY` and `NEON_PROJECT_ID`. `fly` holds
`FLY_API_TOKEN` and `LIVEKIT_ORIGIN_IP`. `vercel` holds the three `VERCEL_*`
values. Both targets hold the `NEXT_PUBLIC_*` build values, which are the same
bundle for the same commit. Each job's preflight refuses on its own set and
nothing else. `apps/web/tests/config/production-targets.test.ts` holds all of
it, and runs both scripts' refusals rather than grepping for them.

**Costs, stated.**

- **`--database-already-deployed` is a claim, not a check.** With it the Fly
  script holds no database credential, so it cannot verify the schema has moved.
  It is honest in exactly one place — a job that `needs: [database]` — and the
  test pins that as its only caller. Passed by hand against an unmigrated commit,
  it deploys code ahead of its schema.
- **A hand-run Vercel deploy has the same dependency it always had**, now
  written where it runs: if the commit carries a migration, run
  `scripts/database-deploy.sh` for it first. The runbook says to confirm the
  database job before handing the failover the domain.
- **A push asks for approval twice.** GitHub approves per job, not per run:
  the `database` job, then both targets in one dialog. The layout as merged also
  asked twice — Fly, then Vercel once Fly had finished.
- **A Vercel-only dispatch cuts a checkpoint too.** Retention is
  `neon-checkpoint.sh`'s `KEEP`, so each dispatch spends one of those slots —
  rollback depth is counted in database-job runs, not in Fly releases.
