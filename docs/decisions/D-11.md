# D-11. Database migrations are applied manually, never by a deploy

> **Superseded in part by [D-18](./D-18.md) (2026-06-23).** The production
> Vercel build runs `prisma migrate deploy` again, so prod migrations are
> re-coupled to the deploy. The preview-db automation deletion below still
> stands — previews remain manual.

**What changed.** Automatic, deploy-time `prisma migrate deploy` was removed
everywhere it ran against a real (hosted) database:

- The web app's `build` script (`apps/web/package.json`) no longer runs
  `prisma migrate deploy` on `VERCEL_ENV=production`. The Vercel production
  build now compiles the app only.
- `.github/workflows/preview-db.yml` — the dormant GitHub Action that ran
  `prisma migrate deploy` + `scripts/seed.ts` against Supabase preview-branch
  databases — was deleted.

Migrations are now applied **by hand** against whichever database is being
changed (production included), via the existing manual scripts
(`pnpm --filter spiralclass-web prisma:migrate:deploy`, or `prisma migrate
deploy` with the target DB's connection strings inlined).

**Why it likely changed.** Coupling schema migration to the deploy puts the
migration on the deploy's schedule rather than the operator's, with no separate
human checkpoint — so a long-running migration lands when the pipeline reaches
it rather than when someone is watching. Decoupling makes schema
changes a deliberate, separately-timed step: build/ship the code, then run the
migration when you choose (and can watch it). It also removes the only reason
two GitHub Actions secrets and a repo variable existed.

**What was affected.**

- `apps/web/package.json` `build` script (migrate tail removed).
- `.github/workflows/preview-db.yml` (deleted).
- Docs: `docs/ops/PREVIEW_DEPLOYMENTS.md` (manual migrate/seed flow) and the
  infrastructure orientation narrative (`docs/orientation/09-…`).
- **Now-unused config** to delete out-of-band: GitHub Actions secrets
  `SUPABASE_ACCESS_TOKEN` and `SUPABASE_PROJECT_ID`, and repo variable
  `PREVIEW_DB_ENABLED` (all only ever read by the deleted workflow). On Vercel,
  `DIRECT_URL` is no longer read at build time and Prisma Client never reads it
  at runtime — it is only used by the manual migrate command — but the env
  schema still requires it, so it is **kept** (see Unresolved risks).

**What was NOT changed.** Migrations against throwaway/ephemeral test databases
stay: the `integration.yml` migrate + drift-check (a Postgres service
container), the local Vitest harness (`tests/_setup/global-setup.ts`,
`test-db.ts`), and the manual `prisma:migrate*` scripts. These never touch a
hosted DB and the integration drift check is the safety net that catches a
schema edited without a migration.

**Unresolved risks.**

- **A deploy can now run ahead of its schema.** If code that needs a new column
  ships before the migration is applied, prod errors until you run the
  migration. Mitigation: run `prisma migrate deploy` against prod as part of the
  release checklist, and prefer expand-then-contract (additive) migrations so
  code and schema don't have to flip in lockstep.
- **`DIRECT_URL` on Vercel is now dead weight** but still required by the env
  schema (`apps/web/src/lib/env.ts`). It is intentionally kept (incident-response
  runbooks reference it, and it's the connection the manual migrate uses). To
  actually drop it from Vercel, make it `.optional()` in the schema first.
