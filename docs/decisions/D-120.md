# D-120. The web deploy leaves GitHub Actions and moves inside `pnpm promote`

> **Superseded in part by [D-157](./D-157.md) (2026-09-04).** The arithmetic
> below was correct and no longer applies: the repository is public and the
> minutes are free. The half that still binds is the anti-drift rule — a deploy
> nobody is forced to run is a deploy that gets forgotten, which is how
> `production` once ended up 96 commits behind what was live. `pnpm promote`
> still ends by pushing `production`, and **that push is the trigger**.

**What changed.** `fly-deploy.yml` no longer fires on `push`. Everything that
runs on a _schedule_ stays exactly where it was.

- **`fly-deploy.yml` loses its `push` trigger.** The production deploy is now
  chained into `pnpm promote` itself — `scripts/ci/promote.mjs` runs
  `scripts/fly-deploy.sh production --gate-already-passed` after the
  fast-forward — so promoting is still one command that ends with production
  serving the new code. Preview is the real behaviour change: merging to `main`
  no longer deploys it, and `pnpm deploy:preview` does.
- **All three crons are untouched.** `nightly-checks.yml`, `synthetic.yml` and
  `backup-prod-db.yml` keep their schedules on GitHub Actions.
- Every other workflow was already `workflow_dispatch`/`workflow_call` only and
  is unchanged. `fly-deploy.yml` stays dispatchable as the escape hatch.

**Why it likely changed.** The Actions allowance kept running out mid-month.
Measured before deciding, rather than assumed:

| Workflow         | Fires                             | Measured                                 | ~Billable/mo |
| ---------------- | --------------------------------- | ---------------------------------------- | ------------ |
| `fly-deploy`     | every push to `main`/`production` | 30 runs over 2026-08-08..16, 7.4 min avg | ~744         |
| `nightly-checks` | daily                             | 9.5 min wall × ~4-5 parallel jobs        | ~600-750     |
| `backup-prod-db` | daily                             | pg_dump + R2 upload                      | ~120         |
| `synthetic`      | every 12h                         | curl probes                              | ~60          |

~1,500-1,700 against a 2,000-minute free-tier allowance, before a single
dispatched run — which is why a promote or a hand-dispatched gate late in the
month hit a wall. The deploy is the single largest line and the only one that
scales with how often you merge; the other ten workflows cost nothing until
dispatched and were left alone
(deleting them saves zero minutes and removes the fallback a cloud session
needs).

The deploy alone is ~45% of that, which is enough on its own — it takes the
month from ~1,500-1,700 to roughly 780, comfortably inside the allowance —
so the scheduled work did not have to move and **deliberately did not**:

- **A synthetic monitor has to live somewhere the thing it watches doesn't.**
  The case it exists for is production breaking while nobody is looking, and a
  closed laptop reports that at breakfast.
- **A backup fails silently.** One that did not run looks exactly like one that
  did, and the difference surfaces during a restore.
- **A nightly sweep on a laptop is a schedule nobody owns.** Even though
  launchd would fire a missed calendar job at the next wake, a week away is a
  week without detection, with nothing red to show for it.

An earlier draft of this decision moved the nightly sweep to launchd and the
synthetic probes to UptimeRobot. That was reverted before landing: scheduled
work stays on Actions.

**What was affected.** This reverses two of the four things
[D-119](./D-119.md) deliberately kept in Actions, and its stated reasons have to
be answered rather than ignored:

- _"Fly runs amd64 images only, and this laptop is arm64 — a local build means
  QEMU."_ True, and accepted. `.github/actions/fly-build-deploy`'s header
  measures it at 20-30+ min per Rust-native Turbopack compile under emulation,
  "flaky with threaded native addons". That is the price of ~744 minutes a
  month. The alternative — Fly's bundled Depot builder — is a fixed ~4GB against
  Turbopack's ~3.45GB peak, and was measured as a coin flip (two attempts of the
  same commit peaked 2MB apart; one died, one lived; `main` went red 2026-07-15).
  A larger Fly remote builder was considered and not tested; if the QEMU tax
  proves intolerable, that is the next thing to try, not a return to
  auto-deploy-on-push.
- _"Auto-deploy on push is what the 2026-07-19 drift incident proved you can't
  leave to a human."_ This is the half that still binds, and it is why the
  deploy is chained into `promote` rather than left as a step to remember.
  `production` sitting 96 commits behind live came from a **human dispatch
  step**, not from where the build ran. `apps/web/tests/config/local-gate.test.ts`
  asserts the chaining, so re-manualizing it fails the build.

Also updated: `scripts/fly-deploy.sh` gained `--gate-already-passed` (the
promote handoff) alongside the existing, louder
`--yes-i-understand-this-skips-the-promote-gate` for a human reaching for
production directly, since in that case the gate genuinely has not run.

**Unresolved risks.**

- **Preview goes stale by default.** The device flows run against the
  _deployed_ preview backend, so a run after a merge but before a
  `pnpm deploy:preview` tests old routes — and the symptom (a group of flows
  dying at ~3s on a TypeError) reads as flakiness. This is the sharpest edge of
  the change.
- **The QEMU build is untested at this scale here.** 20-30 min is the estimate in
  the action header, not a measurement of this Mac on this Dockerfile. If it is
  worse, promoting becomes something you schedule rather than something you do.
- **A promote that fails mid-deploy leaves `production` fast-forwarded but not
  deployed.** The branch moved and the running app did not. `promote.mjs` says
  so explicitly and prints the recovery command; there is no automatic rollback.
- **The cheap lever is now spent.** With the crons staying, the month lands
  around 780 minutes. That is comfortable, but the next reduction is no longer
  free: it means moving scheduled work off Actions (rejected above, for
  reasons that do not change with budget pressure) or paying for GitHub Team.
  See [`docs/deployment/COST_PLAYBOOK.md`](../deployment/COST_PLAYBOOK.md).
