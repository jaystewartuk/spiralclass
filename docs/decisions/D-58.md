# D-58. Platform Stripe entity moves from Mexico to the UK; Stripe Connect country gate widens to the cross-border circle

> **Its country gate was retired by [D-143](./D-143.md) (2026-08-30).** The
> entity move to the UK stands and is still why the platform bills in GBP under
> UK law. The cross-border payout _circle_ below does not: D-143 made the
> teacher merchant of record, so no `Transfer` crosses a border and the gate
> became "which countries will Stripe create a merchant account for" — measured
> at 44, including Mexico, which this record had dropped.

**What changed.** The platform Stripe account moves from the Mexican entity
(D-2026-06-11) to a UK entity. `SUPPORTED_CONNECT_COUNTRIES` in `@spiralclass/shared` widens
from `["MX"]` to Stripe Connect's cross-border payout circle — GB, US, CA, CH,
plus the 30 EEA states — and **drops MX entirely**. `isConnectCountrySupported()`
is unchanged in shape; only its allowlist moved. `PLATFORM_REGIONS`'s single
`MX` key keeps its name and `MXN` currency (both entity-agnostic — the key
name is historical, the currency is what teachers are actually charged, not a
property of the entity's country); no code reads a hardcoded entity anywhere,
so the actual credential swap (`STRIPE_SECRET_KEY`,
`STRIPE_WEBHOOK_SECRET`, `STRIPE_BILLING_WEBHOOK_SECRET`, the three
`STRIPE_PRICE_*` ids) happens entirely in the deploy environment, not in this
diff.

**Why it changed.** Stripe Connect's cross-border payout feature only works
when _both_ the platform and the connected account sit inside one closed
circle (US, UK, EEA, Canada, Switzerland) — this is permanent Stripe design,
confirmed against current docs, not a gap that closes with a different single-
country entity. The previous entity solved exactly one corridor (MX platform →
MX connected accounts, domestic) and would need a new local entity per market to
solve any other — a treadmill no small platform can sustain while trying to serve
teachers and students in any country. A UK entity trades that treadmill for a
five-region circle, at zero extra cost over what Stripe already charges. Every teacher outside the circle (Mexico included) moves
to the existing, already-built, genuinely country-agnostic Wise rail instead
of a per-country Stripe entity — see the payments/entity architecture review
this decision is drawn from for the full comparison against Global Payouts,
Adyen for Platforms, and Paddle (ruled out entirely — its Acceptable Use
Policy prohibits marketplace resale on behalf of non-Paddle sellers).

**What was affected.** `packages/shared/src/countries.ts`
(`SUPPORTED_CONNECT_COUNTRIES` widened to the circle, MX removed;
`EEA_COUNTRIES` added) and its test (`countries.test.ts`, the "guards against
accidental widening" assertion updated deliberately per its own instruction,
plus a dedicated MX-regression case). `apps/web/tests/actions/stripe-connect-action.test.ts`
(default fixture country moved from `MX` to `GB`; added an explicit test that
MX is now blocked). `packages/shared/src/platform-regions.ts` (comment fixes
only — the `MX` key's name and `currency` are unchanged, since both are
correctly entity-agnostic already). `CLAUDE.md` "Platform Stripe entity"
section rewritten.

**Unresolved risks / follow-up (ops, not code).** The country-gate widening
must not reach **production** before the production `STRIPE_SECRET_KEY`
actually points at the UK account — until then, a circle-country teacher
clicking "Connect Stripe" in production would get an account minted under the
still-Mexican entity, which the circle doesn't cover either
(`transfers_not_allowed` again, just inverted). Merging to `main` is safe
first (D-26: preview-only); production needs, in order: (1) the UK account's
live secret key + a webhook endpoint registered against it for both
`/api/stripe/webhook` and `/api/stripe/billing-webhook` + the three
subscription Prices recreated in the new account (Prices are account-scoped;
the old MX Price ids don't exist in the UK account) — all set as the
production env vars above; (2) _then_ Promote. Separately: a `stripeAccountId`
minted under the old entity stops being payable the moment the production key
swaps, and the fix is disconnecting Stripe from Settings → Payments (or an
admin doing it) once the swap lands, not a data migration. The
marketplace-commission pivot discussed alongside this review (which lane
carries commission, whether to reverse D-24) is a **separate, still-undecided**
question this decision does not resolve.
