# D-40. Authentication is better-auth on our own Postgres, and a sign-in never decides what kind of account to create

Authentication runs on better-auth. Its `user`, `session`, `account`,
`verification` and `twoFactor` tables live in the application's own Postgres,
and `teachers.id` and `students.auth_user_id` point at `user.id`. Sign-in is a
passwordless email code: 6 digits, valid for five minutes, three attempts, and
stored hashed ([`lib/auth/server.ts`](../../apps/web/src/lib/auth/server.ts)).
Google sign-in is added only where its credentials are configured. One login is
a teacher or a student, never both. A brand-new identity becomes a teacher only
when it arrived through an explicit sign-up.

## Why

Auth was inherited from the old database vendor's managed service and was never
a recorded decision. Owning the identity tables makes auth portable: it travels
with the database, so the later exit from that vendor ([D-70](./D-70.md)) did
not have to move identities a second time. It also let a large accreted surface
be deleted: magic-link-plus-code delivery, passkeys, phone/SMS login, a teacher
"remember this device" table, a teacher payout step-up and the vendor's AAL2
plumbing. What remained is one email-code rail, plus TOTP for staff
([D-25](./D-25.md)). For a code, throttling is the security lever, not length.

Teacher and student are kept apart because they sit on opposite sides of the
money. A teacher is a payee and a student is a payer. With one login holding
both, a disabled student could pay through her teacher identity, or a disabled
teacher could receive money through a student-side flow.

Intent comes from the page because the alternative already failed. While
`/sign-in` and `/sign-up` behaved identically, any verified email that matched
no row fell through to the teacher lazy-create. On preview, a "test student"
address became a full teacher account (slug, starter packages, availability, a
Pro trial), and it had to be deleted from the database by hand.

## Options considered

- **Stay on the managed auth service.** It stays locked to that vendor and
  keeps every accreted feature.
- **Migrate behind a feature flag with a compatibility shim.** Rejected for a
  hard cut. Only one user signed in on the live site, so a coordinated
  identity migration was trivial, and a shim would have stayed.
- **Keep magic-link delivery beside the code, or SMS.** Both were dropped. The
  phone rail can be re-added later.
- **Let one login hold both roles.** Rejected, for the money reasons above.
  This does not limit one person to one roster row: a student can still have a
  row under each of several teachers
  ([multi-teacher students](../architecture/multi-teacher-students.md)).
- **Stop auto-provisioning teachers anywhere.** Rejected, because self-serve
  sign-up is the growth funnel.
- **Turn off better-auth's `disableSignUp` globally.** Rejected. It has no
  per-call override, so turning it off breaks real sign-up. A bare `user` row
  with no teacher or student attached is still created on any verified code,
  and it is harmless.
- **Two separate identity systems.** This duplicates the whole problem, which
  was one ungated default.

## What it cost

- A one-time forced re-authentication for everyone at cutover. The installed
  client of the time had to be force-updated, and that client is now deleted.
- better-auth supports only its latest release, so a minor upgrade can be
  security work. The record of the time pinned at least 1.6.22 for an advisory
  on email-OTP account takeover (GHSA-qq9h-g4jm-xgf3). This configuration was
  not exposed to it, and `apps/web/package.json` is now on `~1.7.6`.
- A signed-in identity with no row that types a teacher URL by hand still
  reaches `requireTeacher()`'s lazy-create. This was judged low-risk and left
  as it is: `requireTeacher()` has around 85 callers.

## What it constrains

- **No auth vendor and no auth feature flag.** Nothing calls a hosted identity
  API. Supabase is guarded by
  `apps/web/tests/config/decommissioned-platforms.test.ts`.
- **Only `intent === "sign-up"` may create a teacher.** `finalizeSignIn`
  ([`actions/session.ts`](../../apps/web/src/app/actions/session.ts)) sends an
  unmatched sign-in to `/sign-in?error=no-account`. The intent comes from the
  form or button the person used, including Google's `callbackURL`, and is
  never inferred from a miss. The booking page's inline code step always sends
  `sign-in`. Tests: `apps/web/tests/auth/teacher-student-conflict.test.ts`,
  `apps/web/tests/actions/auth-action.test.ts`,
  `apps/web/tests/auth/redirect-if-signed-in.test.ts`.
- **Mutual exclusivity is enforced at every door.**
  - `resolveLinkedStudent()` returns `conflict` for an identity that owns a
    Teacher row
    ([`lib/auth/student-link.ts`](../../apps/web/src/lib/auth/student-link.ts)).
  - `findOrCreateRosterStudent()` and the manual roster add refuse an email
    that belongs to a teacher.
  - `requireTeacher()` refuses to provision for a login that has a claimable
    student row, and sends it to `/my-classes?notice=already-student`.
  - Tests: `apps/web/tests/auth/student-link.test.ts`,
    `apps/web/tests/students/find-or-create.test.ts`,
    `apps/web/tests/checkout/checkout-action.test.ts`.
- **Notification sign-in links are narrow capability tokens, never ids.** They
  are random, stored hashed, used once, short-lived, and bound to one student
  row, its email and one class or notification
  ([`lib/auth/notification-link.ts`](../../apps/web/src/lib/auth/notification-link.ts)).
  They sign in only a student. Behaviour:
  [authentication](../features/authentication.md).
- **One `session` table.** `revokeUserSessions(userId)` ends every session for
  a user, and account deletion depends on that.

## How we got here

- **Before July 2026.** Auth was the old vendor's magic-link service. One
  identity could become both a Teacher and a linked Student, with no guard and
  no clear error. A symmetric guard was added at sign-in linking, at checkout's
  roster create and at the manual roster add.
- **2026-07-03/04.** The cutover was chosen as a flagless hard cut. A
  UUID-preserving backfill (a migration since squashed into the baseline)
  was proven on staging first. The routes were deleted rather than translated, and
  a minimum-version gate stood in for an adoption window. Admin MFA kept its
  mandate and lost WebAuthn ([D-25](./D-25.md)). Teacher/student exclusivity was
  re-implemented unchanged on the new linking path.
- **July 2026.** The sign-in/sign-up split was made real (see Why).
- **2026-07-13.** A short-lived token bridge had kept the vendor's realtime
  socket authenticated. It was retired when both subscriptions moved to HTTP
  polling, ahead of moving the preview database to Neon.
- **2026-09-14.** Notification links became capability tokens. The original
  plan said these tokens would authorize one action "instead of minting a full
  session". That did not survive, because both destinations are portal pages
  that need a session. What narrows them instead: only a student is ever signed
  in, a teacher or staff address goes to the ordinary sign-in, and a link
  scanner's GET cannot spend a token.
- **Since then.** Google sign-in was added beside the code rail, linked to an
  existing user only on an exact verified-email match. This departs from the
  original "email code only" target, and the code wins.
