# D-179. CodeQL scans every pull request, and main refuses a merge that adds an alert

**Status.** Active. Applied by `scripts/setup-branch-protection.sh`. The
default setup and private vulnerability reporting were switched on by hand on
2026-09-13. The ruleset takes effect when the operator next runs the script.

**What changed.** Three repository settings now have a written, reapplicable
source:

- **Private vulnerability reporting is on.** `SECURITY.md` and the
  issue-template contact link both sent reporters to it while it was off, so
  the one private route this repository advertised led nowhere.
- **CodeQL runs in default setup** for JavaScript/TypeScript and Actions, on
  every pull request to `main`, on every push to `main`, and weekly.
- **A ruleset, `main: no new CodeQL alerts`, blocks merging a pull request that
  introduces a CodeQL alert** at severity `error`, or a security alert at `high`
  or `critical`. It has no bypass actor.

**Why.** The repository went public on 2026-09-09. The gate has a credential
scan, a dependency audit and a tenancy parser. It has no data-flow analysis, so
it cannot see a DOM value reaching `innerHTML` or a regex that backtracks on
input someone else controls. The first CodeQL scan of `main` found 11 open
alerts (10 high, 1 medium). That is the evidence the gap was real, not
theoretical.

**What was considered and rejected.**

- **Adding CodeQL to `scripts/ci/steps.mjs`.** This is the obvious home, since
  the registry is the one definition of green. It fails for two reasons. The
  analysis needs its baseline, the alerts already open on `main`, to tell a new
  finding from an old one, and that baseline lives on GitHub rather than on the
  laptop. And building a CodeQL database for this tree takes minutes, which
  would undo the fast tier's reason to exist.
- **An advanced-setup `codeql.yml` workflow.** A workflow that performs a check
  is exactly what `CLAUDE.md` forbids. Default setup is a repository setting
  with no file in the tree, so there is nothing for a guard to mistake for a
  second registry.
- **Requiring the `Analyze (…)` check contexts in branch protection.** Those
  names come from GitHub and move when a language is added. A required context
  that is never posted strands every PR: the same failure the 2026-07-18
  manual-only sweep caused. A required check would also go red for alerts that
  were already open on `main`.
- **Alerts only, no merge protection.** This was offered and declined. On a
  solo repository, nothing in the merge path makes anyone read an alert that
  does not block.

**What it constrains.**

- **This does not change [D-162](./D-162.md)'s rule that `local-gate` is the
  only required status context**, and does not make `CodeQL` one. The ruleset
  gates on the alert database, not on a status. Keep it that way: switching to a
  required context reintroduces both failures above.
- **Never add a `codeql.yml` workflow** to tune queries. Change the default
  setup's `query_suite` in the script instead.
- **Never add a bypass actor to this ruleset** to get a PR merged. Dismiss the
  alert on the Security tab with a reason, which leaves a record. A bypass
  leaves none.

**What was affected.** `scripts/setup-branch-protection.sh`,
`docs/deployment/BRANCH_PROTECTION.md`, and the guard in
`apps/web/tests/config/local-gate.test.ts`.

**Trade-offs accepted, and unresolved risks.**

- **The 11 alerts open on `main` are not triaged by this record.** The ruleset
  ignores them by design, so nothing forces them down. They need triage: fix
  each one, or dismiss it with a reason.
- **A PR cannot merge until CodeQL has analysed it.** The first full scan of
  `main` took 4½ minutes, measured from the run's timestamps, and the wait
  applies to docs-only PRs too.
- **Fork PRs are untested here.** Nothing has yet shown how default setup
  treats a fork PR under this ruleset. Check it the first time an outside PR
  arrives.
- **Validity checks and non-provider secret patterns stay off.** Enabling them
  through the API returned success and changed nothing, because on this account
  they are part of a paid GitHub product. Push protection and provider-pattern
  secret scanning are on.
- **Live protection on `main` has drifted from this script.** On 2026-09-13
  the required contexts were the `gate.yml` and `Heavy tier` job names rather
  than `local-gate`, linear history was off, and a ruleset named
  `A merge is a decision, not a step` requires one approval with an
  admin bypass. The script names none of that. Running it therefore reverts
  those settings, which is a separate decision this record does not make.
