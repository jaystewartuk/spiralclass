> Layer 2 originally resolved BOTH the ASR language and the coach's output
> language from `teacher.targetLanguage`. That column is the **subject** taught
> (D-72), which is neither of those two things. The fault is **latent, not
> live**: where a teacher's subject and her spoken language coincide (a teacher
> of Spanish who teaches in Spanish — both columns `"es"`) the old code was
> right by coincidence. It breaks as soon as they diverge, which is exactly what
> a language-first platform exists to support: a teacher OF English who teaches
> IN Spanish had her Spanish audio sent to ASR tagged `en` and got
> English-language feedback. The two questions are now answered separately: ASR
> from `teachingLanguage` (which the schema already documents as the ASR source
> language for her own speech), feedback language from `locale`, with the
> coinciding case and both divergent cases pinned by tests. The review also
> carries the prioritised follow-up backlog — the draft/approve step, captions,
> and a real poster frame.

**What changed.** A teacher can add a short intro video to their public booking
page (`/b/[slug]`) — recorded in the browser with `MediaRecorder`, or uploaded
as a file. The video renders under the hero and is the single highest-leverage
conversion asset a booking page can carry: a 30–60s "is this teacher a fit?"
before a prospect commits to paying.

**What was decided.**

1. **Self-hosted direct file, never a third-party embed.** The video is stored as
   one object per teacher in a **public R2 bucket** (`teacher-videos`), served
   from the R2 public host straight into `<video>`. We deliberately did **not**
   support YouTube/Vimeo/Loom embed links: an embed is an iframe, and a second
   client of the day had no WebView, so a direct file was the only form that
   played everywhere with no new native dependency.

2. **A public bucket like the photo, not the private/signed chat-video path.** The
   booking page is public and crawled for OG previews, so a signed URL that
   expires can't survive the SSR/CDN cache. `teacher-video.ts` mirrors
   `teacher-photo.ts` exactly: permanent public URL via `r2PublicUrl`, one object
   keyed by teacher id (a re-record replaces in place — no orphans), and a `?v=`
   cache-buster from `teacher.updatedAt`. The private, per-message signed-URL model
   of `chat-video.ts` is the wrong fit here.

3. **Degrade to hidden when unconfigured.** The R2 bucket is provisioned
   out-of-band (Cloudflare, like every other R2 bucket — `ensureBucket` is a no-op
   on R2). `introVideoStorageConfigured()` gates the whole feature on
   `NEXT_PUBLIC_TEACHER_VIDEOS_R2_PUBLIC_URL` being set: with it unset the editor
   card doesn't render and the public page skips the video, exactly like
   `getVideoProvider()` / `recordingEnabled()` degrade. **This makes Layer 1 safe
   to merge before the bucket exists** — nothing appears until the env is set.

4. **`media-src` is the CSP addition — no `frame-src` change.** Because we serve a
   file rather than embed a frame, the CSP change is a new `media-src` directive
   (`'self' blob: https:`): `https:` for the R2 public host (which varies per env,
   mirroring the broad `https:` already in `img-src`), and `blob:` for the web
   recorder's local preview before upload. Asserted exactly in
   `tests/lib/csp.test.ts`, per the maintenance rule that a missing directive is
   how the in-class call once shipped broken.

5. **The recorded video is the capture step for the AI intro-coach (Layers 2–3).**
   The real payoff — and why this is worth building over "paste a link" — is that
   owning the file lets us **transcribe it and coach the teacher on it**.
   - **Layer 2 (transcription infra) — BUILT.** An Inngest job on upload
     (`intro-video.ready`, emitted best-effort from the web action)
     runs the recorded object through the existing **batch** Deepgram path
     (`transcribeWithDeepgram`) into an `IntroVideoAnalysis` row. The video lives in
     a **public** bucket, so the vendor pulls the stable public URL directly — no
     presign needed (unlike lesson audio). A `canUseIntroVideoCoach` entitlement
     joins `canUseLiveNotes` in `subscriptions-entitlements.ts`,
     checked in the pipeline (injected) — a growth tool, Pro, never the payment
     rail. Dormant behind its OWN flag `INTRO_VIDEO_COACH_ENABLED` (not the
     lesson-insights gate), because the teacher's own public clip isn't blocked on
     the D-19 consent model. The pipeline is dependency-injected and unit-tested
     across the branch matrix (no-video / stale / not-Pro / success / vendor-failure).
   - **Layer 3 (the coach) — v1 BUILT (coaching feedback); captions + draft bio
     designed, not built.** The three sub-features were always independently
     shippable; v1 ships the first.
     - **(a) Coaching feedback — BUILT.** `lib/intro-video/coach.ts`: a pure
       `buildIntroCoachPrompt` + `parseIntroCoachFeedback` (both unit-tested, no
       network) and `generateIntroCoachFeedback` (Anthropic call, model
       `claude-opus-4-8`), mirroring `lesson-notes/summary.ts` and degrading via
       `IntroCoachUnavailableError` when `ANTHROPIC_API_KEY` is absent. The
       Inngest handler injects it into the Layer-2 pipeline as an **optional,
       best-effort** step after the transcript is stored: it asks Claude for
       strict JSON `{overall, strengths[], improvements[]}` in the teacher's
       language, and a throw/unparseable result just leaves `coachFeedback` null
       — it never fails the job or discards the transcript. Stored on
       `IntroVideoAnalysis.coach_feedback` (JSONB /
       `20260719010000_add_intro_video_coach_feedback`), surfaced as
       `introVideoCoach` on `TeacherPublicProfile`, loaded by
       `loadIntroVideoCoach()` and shown **teacher-only** in the booking-page
       editor (`intro-video-form.tsx`) — never
       on the public `/b/[slug]` page. Pro-gated by the same
       `canUseIntroVideoCoach` check that already gates the transcript, so a Free
       teacher's video is never analysed and the panel simply never appears.
     - **(b) Auto-captions** (VTT, accessibility + the only way an intro video
       helps SEO) and **(c) a draft bio/headline** (apply-in-one-tap suggestions
       to cut empty-profile friction) remain **designed, not built** — the
       transcript they'd build on is already captured, so each is a self-contained
       follow-up.

**Why.**

- _Direct file over embed:_ it's the only option that plays natively on both web
  everywhere without a WebView or a native build, so it satisfies parity by
  construction; and, decisively, it gives us the raw media the AI coach needs —
  an embed on someone else's platform does not.
- _Public bucket over signed URLs:_ the booking page is public + crawled; a
  permanent public URL is the pattern the teacher photo already proved for exactly
  this surface.
- _Capture first, coach later:_ the layered plan mirrors lesson-insights
  ([`D-19`](./D-19.md)) — the video is a data-capture step, and the differentiated
  product (coaching, captions, draft bio) is built on top once we own the file.

**What it constrains.**

- Don't reintroduce third-party video embeds without solving playback on every
  surface first — the no-WebView constraint was load-bearing for the
  direct-file decision.
- Keep the intro video in its own public bucket and helper; don't fold it into the
  private chat-video signing path or the teacher-photos bucket.
- The batch Deepgram host and the Anthropic call stay **server-side** (no CSP
  change — they aren't browser calls; the only browser-facing CSP addition is the
  R2 `connect-src` for the direct upload `PUT`), and the AI layers stay Pro-gated
  via the one entitlements resolver. This holds for the remaining Layer 3
  sub-features (captions, draft bio) too.

**Unresolved risks.**

- **Storage cost / abuse.** A public 50 MB-cap video per teacher is cheap on R2
  (no egress fee), but the object is world-readable by design. The 50 MB + ~5-min
  duration caps and one-object-per-teacher (no accumulation) bound it; a future
  lever is transcode-on-ingest (Cloudflare Stream/Mux) if raw-MP4 playback or size
  becomes a problem.
- **Content moderation.** Unlike an embed hosted (and moderated) elsewhere, we now
  host teacher-submitted video. Layer 1 relies on the teacher being the accountable
  account holder; if the surface is abused, moderation tooling (report + takedown,
  reusing the `disabledAt` moderation pattern) is the next step.
- **Media capture is unverified in CI.** As with D-16/D-27, the `MediaRecorder` /
  capture and playback follow the platform APIs and pass typecheck,
  but real recording + upload + cross-orientation playback need on-device QA.
- **Layer 3 privacy is lighter than lessons but non-zero.** The coach analyses the
  teacher's _own_ voice on their _own_ public page (no student data, no minors), so
  D-19's heavy consent/retention model doesn't apply — but the transcript is still
  derived data and should follow the same derive-then-discard-by-default stance for
  any raw intermediate it doesn't need to keep.
