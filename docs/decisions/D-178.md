# D-178. Production migrations run inside the deploy, before the new code and behind a Neon checkpoint, so every migration must work with the code already serving

A production deploy's `database` job (`scripts/database-deploy.sh`, called from
`.github/workflows/deploy-production.yml`) creates a Neon checkpoint branch of
`production` and then applies pending Prisma migrations, failing closed if it
cannot checkpoint; the Cloud Run job `needs:` it and holds no database
credential. Because old code serves against the new schema while the new image
builds, a migration may only **expand**: anything that drops, renames or
narrows ships a release **after** the code that stopped using it, with a
comment containing `CONTRACT` naming what shipped first. The migration history
under `apps/web/prisma/migrations/` starts from two files: a Prisma-generated
baseline and a hand-written invariants file.

## Why

- **Code and schema have to move together, and people forget.** When
  migrations were applied by hand, two table migrations (lesson notes, student
  notes) sat unapplied while the code that queried them auto-deployed, and the
  live app queried tables that did not exist for days.
- **A code rollback never undoes a schema change.** The restore point has to be
  taken by the same thing that migrates, every time, or it gets skipped.
- **Old code always meets the new schema.** The deploy migrates before the new
  image serves — the record estimated about twenty minutes of build — and the
  target job can fail after the database job succeeded. On 2026-09-13 the
  database job went green and the then-Fly job failed twice, on unset runtime
  secrets and on an image that would not build (#100). No migration was
  pending that day; had one been, the schema would have moved with no code
  following. The same day, #98's drop migration could not ship with the first
  deploy from `main`, because the code serving still mapped the dropped
  columns.
- **A history that mixes generated and hand-written SQL cannot be regenerated.**
  The earlier single squashed baseline carried the CHECK constraints and an
  index nobody could see were stale (below). Prisma will never write a partial
  index, a CHECK or an exclusion constraint, and the drift check in
  `scripts/ci/integration.sh` compares **models** — drop every invariant and it
  still reports no drift.

## Options considered

- **Apply migrations by hand, separately from the deploy.** Tried in June 2026;
  the code-ahead-of-schema outage above reversed it within weeks.
- **A `pg_dump` to R2 gating every deploy.** Built for Supabase, which had no
  PITR wired in. Slow and disk-bound, it ran twice per promote, and it broke
  silently on 2026-07-20 when the server moved to PostgreSQL 18 and the dump
  client was older. A Neon branch has no client-version constraint. The dump
  survives as a manual off-platform copy (`scripts/local/backup-prod-db.sh`).
- **A preflight job ahead of the database job** checking the target's token,
  secrets and build values. GitHub asks for approval per job, a target outage
  would stop the database job, and it still misses a failure inside the build.
- **Building the image before migrating.** Closes the build window but spends
  the build before the approval that matters, and still leaves the gap between
  image push and serving.
- **One squashed file** (tried in July 2026, 125 migrations into one) or
  **keeping all 46** incremental files. One file cannot be regenerated without
  losing its hand-written half; 46 files described five schemas that no longer
  existed (a removed payout kind, dropped transfer columns, a dropped table, a
  replaced enum, a column rename across seventeen columns). A fabricated
  `001_core`/`002_booking` sequence was rejected as untrue.

## What it cost

- Migrations run on the deploy's schedule, not the operator's; the
  no-risky-merges-during-lesson-hours rule now covers schema changes too.
- A destructive change takes two releases.
- The checkpoint step is a hard dependency: no Neon credential or
  `NEON_PROJECT_ID`, no deploy. On 2026-08-31 deleted Neon API keys left
  `production` fast-forwarded with the app on the previous release.
- An expand migration can be left applied by a failed target job; accepted,
  because an expand migration is by definition safe for the serving code.
- Every database migrated by the older history had to be adopted once with
  `prisma migrate resolve --applied` for both squashed files, and on production
  the adoption and the drop of left-behind objects took two releases. A
  `migrate deploy` that reaches such a database first stops at P3018 and
  records the baseline as failed. Per-migration `git log` history is gone.

## What it constrains

- **Do not write a migration the serving code cannot run against.** Add columns
  nullable or defaulted, add tables before code uses them, backfill before
  tightening. A data `UPDATE` that rewrites values old code reads is as breaking
  as a `DROP`; no test can see it, and the rule applies anyway.
- **Do not drop, rename or narrow in the release that stops using the thing.**
  [`tests/migrations/contract-migrations.test.ts`](../../apps/web/tests/migrations/contract-migrations.test.ts)
  refuses a destructive migration without a `CONTRACT` comment. The marker is a
  promise: the author checks the live commit for what is still mapped. Do not
  remove the check to land a drop faster. A change that truly must be atomic
  needs a maintenance window, not an exception.
- **No migration without a checkpoint.** The step is fail-closed and stays so;
  [`tests/config/neon-checkpoint-retention.test.ts`](../../apps/web/tests/config/neon-checkpoint-retention.test.ts)
  pins retention at 5 (under the project's 10-branch ceiling), `--no-compute`,
  the ceiling precondition, no defaulted project id, and that production
  refuses to migrate without a checkpoint. Restore is
  `infra/database/scripts/neon-rollback.sh`; see
  [DB_BACKUP_RESTORE.md](../deployment/DB_BACKUP_RESTORE.md).
- **Never edit an applied migration**, not even a comment: Prisma checksums
  them.
- **Regenerate the baseline; never hand-edit it.**
  [`tests/migrations/readme-commands.test.ts`](../../apps/web/tests/migrations/readme-commands.test.ts)
  regenerates it byte for byte. A new partial index, CHECK, exclusion
  constraint or trigger goes in a hand-written migration **and** in the list in
  [`tests/migrations/invariants.integration.test.ts`](../../apps/web/tests/migrations/invariants.integration.test.ts),
  which inventories a really-migrated catalog because the drift check cannot.
- Procedure: [migrations README](../../apps/web/prisma/migrations/README.md).

## How we got here

- **June 2026.** Deploy-time `prisma migrate deploy` was removed and migrations
  applied by hand, so a long migration would land when someone was watching.
  The lesson-notes and student-notes outage followed. **2026-06-23:** the
  production web build ran `migrate deploy` again, after `next build` so a
  failed compile never migrated; previews stayed manual. After the July move
  the migration was a step of the production deploy workflow, behind the
  checkpoint below.
- **2026-07-13.** The move to Fly and Neon squashed 125 migrations into one
  baseline with the raw SQL mixed in ([D-70](./D-70.md)).
- **2026-07-20.** The `pg_dump`-to-R2 gate was replaced by Neon PITR plus a
  named `pre-deploy-*` checkpoint branch before migrations. **2026-08-09:**
  retention shipped at 20, above the production project's ceiling of 10, which
  would have failed `branches create` and, fail-closed, blocked every deploy;
  cut to 5, with `--no-compute` and an up-front ceiling check.
- **2026-09-02 to 09-06.** Columns renamed on 2026-09-02 left the single
  baseline's CHECKs naming `*_centavos` columns (Postgres had rewritten the
  live constraints) and an index on a dropped table. The history was rebuilt
  as two files: 46 directories to two. Verified on a throwaway `postgres:16`:
  `migrate diff` empty in both directions against the old history; a catalog
  inventory of **1,648 objects each**, identical but for eight defaults
  rendered `now()` against `CURRENT_TIMESTAMP`; and behaviour checks (overlap
  refused, buffer refused, append-only `overrides`, list columns NOT NULL).
  The invariants file then held `btree_gist`, 10 partial indexes, 33 CHECKs,
  2 exclusion constraints, 4 list-column `NOT NULL`s, 2 functions and 3
  triggers in 363 annotated lines. Two things a naive regeneration loses were
  kept: the four list columns' `NOT NULL` (Prisma emits them nullable and its
  diff calls that equivalent), and the five better-auth defaults written
  `pg_catalog.gen_random_uuid()`, whose prefix had made the drift check print
  five phantom statements on every run for a week.
- **2026-09-12/13.** The checkpoint-and-migrate steps moved out of the Fly
  deploy script into `scripts/database-deploy.sh` and their own job, so either
  target could deploy alone. The Fly job failure above produced the
  expand/contract rule and its `CONTRACT` test. The objects the squash left
  behind on production were dropped by a contract migration
  (`20260912120000_drop_tables_the_squash_left_behind`) in a release after
  `a7fd8a5`, the first code that mapped none of them, served on 2026-09-13.
- **Now.** The target is Cloud Run; the database job is unchanged. The
  invariants list holds 37 CHECKs (counted in the test on 2026-10-16).
