# D-178. A migration must work with the code already serving; destructive changes ship a release after the code stops using them

**Status.** Active.

**What changed.** Every migration a release carries must leave the schema
usable by the code that is serving when it runs (**expand**). A migration
that drops, renames or narrows something ships in a **later** release than
the code that stopped using it (**contract**), and says so in a comment
containing the word `CONTRACT`, naming what shipped first.
`apps/web/tests/migrations/contract-migrations.test.ts` refuses a destructive
migration without that comment.

**Why.** A production deploy migrates **before** its new code is live, and
since [D-177](./D-177.md)'s addendum the database job and the Fly job are
separate jobs. So there are always two windows where old code runs against
the new schema:

- **The build.** Every deploy spends about twenty minutes between
  `migrate deploy` and the new image serving.
- **A Fly job that fails.** On 2026-09-13 the database job went green and the
  Fly job then failed twice: once on unset runtime secrets, once on an image
  that could not build (#100). No migration was pending that day. Had one
  been, the schema would have moved and no code would have followed. #103
  asked for the release to fail before touching the database instead.

Expand/contract makes both windows harmless by construction, and it was
already the rule production needed that same day. #98's drop migration could
not ship with the first deploy from `main`, because the code then serving
still mapped the columns it drops.

**What was considered and rejected.**

- **A Fly preflight job ahead of the database job**, which checks the token,
  the runtime secrets and the build values before anything migrates. It fails
  on three things:
  - GitHub asks for approval per job, so every push would ask three times.
  - A Fly outage would stop the database job, and with it the Vercel failover
    on the same run. That is the coupling D-177's addendum removed. A
    dispatch with `target: vercel` would still work, but only if someone
    remembered it.
  - It still catches nothing that goes wrong in the build itself (#101's
    problem), so migrate-then-fail stays possible.
- **The Fly preflight inside the database job.** It would hand the database
  job `FLY_API_TOKEN`, so a Vercel-only deploy would need Fly's credential
  again. That is the separation the operator asked for.
- **Building the image before migrating.** It closes the build window as well,
  but spends the build before the approval that matters, and it still leaves
  the time between image push and machine start.

**What it constrains.**

- Do not write a migration that the code serving at deploy time cannot run
  against. Add columns nullable or defaulted, add tables before code uses
  them, and backfill before tightening.
- Do not drop, rename or narrow in the same release as the code change that
  stops using the thing. Ship that code, let it serve, then ship the contract
  migration, marked `CONTRACT`.
- Do not remove the marker check to land a destructive migration faster. The
  comment is the moment someone checks what is serving.

**What was affected.** `apps/web/prisma/migrations/README.md` (§ "Adding a
schema change"), `apps/web/tests/migrations/contract-migrations.test.ts`.
`deploy-production.yml` is unchanged.

**Trade-offs accepted, and unresolved risks.**

- **The marker is a promise, not a proof.** The test sees that a destructive
  migration names itself a contract. It cannot see whether the code serving
  in production still maps what is being dropped. That check is the author's,
  against the live `?dpl=` commit, and #98's README shows how it was done
  once.
- **A failing Fly job still leaves an expand migration applied.** That is
  accepted: an expand migration is by definition safe for the code already
  serving, and the next successful deploy catches up.
- **Data migrations are outside the test.** An `UPDATE` that rewrites values
  the old code reads is as breaking as a `DROP`, and no regex can tell. The
  rule applies to them all the same.
- **Would reopen this:** a migration that has to change the schema and the
  code atomically. That calls for a maintenance window
  ([D-76](./D-76.md)), not an exception to this rule.
