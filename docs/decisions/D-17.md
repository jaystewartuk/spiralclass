# D-17. Class content is native in-app structured content, not distributed PDFs; AI authoring is in-house and Pro-gated (2026-06-23)

> **Superseded in part by [D-87](./D-87.md) (2026-07-19).** The model choice
> below (`claude-opus-4-8`) is no longer current — AI compose now defaults to
> `claude-sonnet-5`, for cost (~40% cheaper than Opus 4.8). It is deliberately
> **not** Haiku like the four short lesson-notes/intro-coach surfaces: the
> compose call sites pass `output_config.effort`, which Haiku 4.5 rejects with a 400. Everything else in this decision — native structured content over PDFs,
> in-house AI authoring, the Pro gate, the platform-key-only rail — still
> stands.

**Status: Active.** Phases 1 (native content field) and 2 (AI compose) have
shipped; PDF stays a transitional input and a print/export fallback. The full
framing and phasing live in
`../../product/CLASS_CONTENT.md`.

**What was decided.** Three things the class-content question can't pick by feel:

1. **Canonical format = native, app-rendered structured content, not PDF.** The
   long-term source of truth for a class's content is reflowable, responsive
   content the app renders (the way the materials library
   already renders items) — **not** an attached PDF. PDF is demoted to a
   _transitional input_ (a teacher may still attach a ChatGPT PDF as a
   `ClassMaterial`) and a _downstream export_ (one-click print), never the
   canonical artifact.

2. **AI authoring is in-house, not an external chatbot.** When AI-assisted
   generation lands (roadmap Phase 2), it runs through the platform's own model
   (the Claude API), seeded with the student's level and notebook-covered
   context — not a separate ChatGPT subscription the teacher maintains. The
   product's level + notebook data is the reason in-house wins: it can produce
   student-aware content an external tool structurally cannot.

3. **Authoring/AI gated Pro; viewing free.** AI compose is a **Pro** feature via
   the existing `gateProFeature` path, alongside `"materials"` and
   `"lesson_notes"`. Native _viewing_ of class content by students is always
   free.

**Why.**

- _Native over PDF:_ a PDF is a fixed-page, print-era artifact; on a phone it
  cannot reflow, which is the actual viewing pain. The app already owns the
  distribution spine (`ClassMaterial`, `LibraryMaterial`, the student portal,
  signed URLs, purge), so native content is a new _content type_
  on existing plumbing, not a new system. See
  `../../product/LEVEL_MATERIALS_PLAN.md`.
- _In-house AI:_ removes per-teacher lock-in and the "doesn't always work"
  inconsistency, and unlocks student-aware generation (level + covered items)
  that a separate ChatGPT tab cannot reach.
- _Pro gating:_ mirrors how class-materials scheduling and the live-notes
  surfaces are already Pro (`D-15`), and keeps both `CLAUDE.md` guardrails
  intact — content touches no payment rail (so this never paywalls _getting
  paid_), and on downgrade over-entitlement content goes **read-only**, never
  deleted.

**Relationship to the materials system.** This **extends**, not replaces, the
level-materials work. `ClassMaterial` (per-booking attachments) and
`LibraryMaterial` (reusable, level-tagged) stay as they are; native class
content is a new structured body that may live per-booking and/or on a library
item, composing with the existing browse/assign surfaces. The notebook
(`StudentLibraryItem`) is the context source for AI compose, not a thing being
rebuilt.

**What it constrains.**

- Don't make PDF the canonical store. New class-content schema holds structured
  content (sanitized JSON/HTML); PDF is input/export only. Revisit this decision
  before reintroducing PDF as the source of truth.
- Stored content is rendered to _other_ users (students), so it **must** be
  sanitized server-side on write and rendered safely — treat authored HTML as
  untrusted (CSP + sanitizer), the same posture the codebase already holds.
- AI generation must not call out to a per-teacher external account; route
  through the platform Claude API key with per-teacher rate limiting.
- Viewing stays free; only authoring/AI sits behind `gateProFeature`. The
  upgrade nudge must read as an upgrade, not a dead end (reuse `upgradeNudge()`).

**What shipped (the resolved calls).**

- **Placement = a dedicated `class_content` table, one-to-one with a booking**
  (`ClassContent`, `@unique` on `booking_id`, migration
  `20260623100000_class_content`). Per-booking is the canonical placement; the
  reusable per-level body on `LibraryMaterial` stays a later, additive step (no
  migration needed to add it). This resolves the placement question below.
- **Body format = Markdown, rendered with `react-markdown` + `remark-gfm` and
  `rehype-raw` deliberately OFF.** react-markdown escapes raw HTML by default,
  so that default _is_ the sanitization boundary — do not add `rehype-raw` to
  `ClassContentMarkdown`. No new editor dependency (Markdown in a `<textarea>`
  with a live native preview).
- **AI compose = the platform `@anthropic-ai/sdk`, `claude-opus-4-8`**
  (overridable via `ANTHROPIC_MODEL`), platform key only (`ANTHROPIC_API_KEY`),
  gated by `hasAnthropicCreds()` so a missing key degrades to hand-authoring.
  Seeded with the student's level + covered notebook items; returns Markdown the
  teacher edits before saving (it never writes to the DB itself).
- **Gating** reuses the Pro `materials` entitlement via
  `gateProFeature(teacherId, "class_content")` — authoring + AI are Pro, viewing
  is free, on downgrade content goes read-only (never deleted).
- **Native rendering.** `ClassContentMarkdown` (`react-markdown`) renders the
  content, holding a sanitization boundary — it parses only known Markdown
  constructs and has no HTML sink at all.

**AI cost control (resolved, 2026-06-23).** AI compose is **Pro + a per-teacher
monthly generation cap** (`CLASS_CONTENT_AI_MONTHLY_CAP`, 100/month, counted via
the `class_content_generations` table; migration `20260623110000`). Per call it's
also bounded by `max_tokens` + `effort: "medium"`. A teacher who hits the cap
still writes content by hand. Tune the constant. The
[`../../ops/COST_PLAYBOOK.md`](../deployment/COST_PLAYBOOK.md) "AI class-content
compose" section now documents the per-generation cost envelope, how to read
spend (the `class_content_generated` PostHog event + the
`class_content_generations` table), and how to tune the cap — the cost figures
there are estimates to replace with observed numbers once real usage exists.
(Closes the cost-playbook follow-up, #256.)

**Unresolved risks.**

- **Migration friction for the teacher** who has months of existing ChatGPT
  PDFs: Phase 0 (keep attaching PDFs) is the bridge, but there's no automatic
  PDF→native conversion in scope, so the cutover is gradual by design.
