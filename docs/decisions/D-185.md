# D-185. Live captions move into the participants' browsers, and a computer in the call covers a phone

**Status.** Active · supersedes [D-106](./D-106.md) (the server-side captions
agent) and [D-108](./D-108.md) (how that agent was deployed). The phone-to-phone
case is left for a follow-up change, a paid speech-to-text fallback used only
when no browser in the call can recognise; until it lands, two phones get no
captions and are told so.
That fallback landed on 2026-09-23 — see the addendum at the end.

**What changed.** Live captions no longer run in a server process. Each person's
speech is recognised by a browser's own `SpeechRecognition` — the speaker's
browser when it can recognise during a call, otherwise the **other**
participant's browser, fed the call audio it already receives — and each
finished utterance is translated on the device where the browser has a
translator (desktop Chrome's `Translator`), otherwise by a new session-
authenticated route, `POST /api/captions/translate`, through Google Cloud
Translation (v2) with `GOOGLE_TRANSLATE_API_KEY`. The recognising browser either
publishes the line to the other participant (the existing `CaptionLine` on
`CAPTION_TOPIC`) or, when it recognised the other person, shows it to its own
viewer. `packages/livekit-captions-agent`, `/api/internal/captions/room-config`,
`lib/captions/internal-auth.ts` and `CAPTIONS_AGENT_SHARED_SECRET` are deleted
in the same change, with no fallback path to them.

Unchanged from D-27 and D-106: the teacher's toggle is the room's one switch
and covers both directions; the student's speech is captioned only with her
recorded captions consent, her guardian's for a minor (D-22); the Pro gate
(`lesson_notes`) applies; captions are never stored; the feature is dark until
`LIVE_CAPTIONS_ENABLED` is on and its key is present; the server re-reads
consent and languages during a class (every browser polls
`POST /api/captions/config` each minute while captions are on, replacing the
agent's own 60-second room-config poll).

**Why.** D-106's premise was that the Oracle box existed and had room for a
worker. It no longer exists: the box was terminated on 2026-09-19 and could not
be relaunched ([D-182](./D-182.md), [D-183](./D-183.md)), so the agent has run
nowhere since, while `LIVE_CAPTIONS_ENABLED=1` kept showing teachers a toggle
that did nothing. Production video is on LiveKit Cloud's Build plan — 5,000
participant-minutes a month, no usage alerts. An agent is a third participant in
every captioned room: at the operator's target of 32 fifty-minute 1:1 classes a
month (3,200 minutes), it would add about 1,600 more, to roughly 4,800 of 5,000.
Hosting it anywhere else costs money, capacity or a rewrite. Browsers now ship
the two pieces the agent existed to provide: speech recognition that accepts a
`MediaStreamTrack` (Chrome shipped the overload in 2024) and, on desktop Chrome,
on-device translation. The operator asked for the best free option.

**What was measured (2026-09-23, before anything was built).** A harness
mirroring the class call's own capture (`new Room({ adaptiveStream: true,
dynacast: false })` + `setMicrophoneEnabled(true)`) against a local LiveKit dev
server, a desktop listener measuring what actually arrived (SFU speaker level
and received bytes: about 25 KB per 2 s in speech, about 12 KB in silence).
Chrome 153 on a MacBook Air, and Chrome 153 on a Galaxy S25 Ultra driven over
DevTools with the operator speaking.

- **Desktop Chrome recognises during a call.** `start()` and `start(track)` both
  produced finals while the listener received unchanged audio. `start(track)`
  genuinely consumes the track: with the LiveKit track disabled, recognition
  heard nothing — so there is no second capture of the microphone, and muting
  the call mutes captions.
- **One desktop tab runs two recognisers at once**, one on its own track and one
  on the remote participant's: both returned finals, the remote one
  transcribing the phone's speaker.
- **Android Chrome does not.** With the call publishing the microphone,
  `start()` and `start(track)` fired `audiostart` and never `speechstart`; no
  result in 45 seconds of the operator speaking. Starting recognition before
  the call took the mic, and publishing with `echoCancellation`,
  `noiseSuppression` and `autoGainControl` off, changed nothing. With the call
  mic stopped, the same phone transcribed the operator at once. The call's own
  audio was never affected. `SpeechRecognition.available()` reports on-device
  recognition `unavailable` there, and there is no `Translator`.
- **Desktop recognition keeps working in a hidden tab** — a first attempt
  looked otherwise, but it was a restart that had thrown inside `onend` and
  silently ended the loop; a fresh instance recognised normally. Hence a fresh
  instance per session, and every `start()` failure is caught and retried.
- **On-device models need a user gesture.** `SpeechRecognition.install()` and
  `Translator.create()` are both refused without one while the model is
  `downloadable`, and the speech install consumes the gesture: a translator
  created after it in the same click is refused, one created before it is not.
  With the translator first, one click installed both (130 ms and 6.5 s).
- **On-device recognition works fed a call track**, with two quirks: the first
  session straight after install produced nothing at all, and on-device
  sessions dropped the first word or two after starting.

**What was considered and rejected.**

- **Keep the agent, hosted elsewhere** (a GCP e2-micro, an Oracle micro,
  LiveKit Cloud's own agents). Each costs money, capacity the free tiers do not
  have, or a rewrite — and every one adds the third participant's minutes above.
- **Only ever the speaker's own browser** (the brief this started from). Android
  speakers would never be captioned, and a teacher cannot know in advance who
  joins from a phone — most of the first teacher's students use a computer,
  not all, and sometimes both people are on phones.
- **Pause or reorder the call's microphone on Android.** Measured above: nothing
  tried let Android recognise while the call holds the mic, and pausing the
  call's audio to caption it would defeat the call.
- **Hide the teacher's toggle when her browser cannot recognise** (also the
  original brief). With the other person's computer able to caption her, hiding
  the toggle would remove captions that work.
- **Paid streaming speech-to-text for everyone** (D-27's original client design,
  Deepgram from the browser). It covers every device, at a per-minute cost on
  every class. Kept as the fallback for phone-to-phone only, in the next change.
- **Speech recognition compiled to WebAssembly** (Whisper, Vosk). A model per
  language, heavy on phones, accuracy unmeasured; nothing here tested it.

**What it constrains.**

- **API presence is not the capability.** Android Chrome exposes every speech
  API and hears nothing during a call. `canRecognizeDuringCall`
  (`packages/shared/src/caption-recognition.ts`) claims only desktop Chromium
  with the on-device API; widen it only after measuring the browser in a live
  call, the way the harness above did.
- **The client never names a language.** `/api/captions/translate` takes whose
  speech it is and the text, and resolves both languages from the booking;
  a route that accepted languages would be a general translation service
  billed to the platform.
- **The student's consent is enforced where the audio is decided, and again at
  the server**: both browsers' shared assignment (`assignRecognizers`) never
  gives her speech a recogniser without it, and the translation route refuses
  her speech without it.
- **On-device downloads start inside the teacher's toggle click, translator
  first** (`installOnDeviceModels`); moving them after an `await` breaks them.
- **Never reintroduce a server path that captions the same room** alongside the
  browsers. The follow-up fallback runs only for a speaker no browser in the
  room can recognise.

**What was affected.** `packages/shared/src/caption-recognition.ts` (new: locale,
capability, assignment, translation route, line building);
`packages/shared/src/captions.ts` (agent identity helpers removed);
`apps/web/src/lib/captions/{recognizer,recognition-policy,recognition-environment,caption-translator,browser-captions,use-browser-captions,google-translate,access}.ts`
(new); `lib/captions/{config,class-access,consent,use-caption-feed}.ts`;
`apps/web/src/app/api/captions/{config,translate}/route.ts` (new);
`lib/api/auth.ts` (`requireApiCallParticipant`); `lib/rate-limit.ts` (a
per-call `cost`); `lib/env.ts`; `components/video/class-call.tsx`; the i18n
catalog; `packages/shared/src/legal/{subprocessors,privacy-policy}.ts`; the
Oracle box stack, scripts and runbooks (the agent service and its secrets); the
guard tests that named the agent.

**Trade-offs accepted, and unresolved risks.**

- **Two phones get no captions** until the paid fallback lands, and are told so.
- **Accuracy is the browser's**, not Deepgram's. No side-by-side measurement was
  made; the synthesised Spanish samples above came back word-for-word bar one
  "con" heard as "como", and the operator's own speech on the phone likewise.
- **Speech leaves the device for the browser vendor** (Google, for Chrome)
  unless the on-device model is installed — and a student's speech may be
  recognised by the teacher's browser, not her own. The privacy notice says
  both. The on-device model installs only on the teacher's computer (her click
  is the only gesture), so a student's desktop uses Chrome's service.
- **iOS was not tested**, and Safari and Edge were not measured; all read as
  unable to recognise, so a desktop Chrome on the other side does the work.
- **The capability check is an inference.** "Has the on-device API" stands in
  for "honours `start(track)`", because the specification offers no detection
  (web-speech-api issue #126). A browser that silently ignored the track would
  caption the teacher's own microphone as the student.
- **Two browsers can briefly caption the same speaker** at join, while their
  capability attributes propagate.
- **Google Cloud Translation bills past 500,000 characters a month** ($20 per
  million after that, checked 2026-09-23). The route budgets characters per
  caller per minute and per class per day, and logs the count per call, but the
  authoritative warning is the operator's Google Cloud budget alert.
- **On-device recognition's quirks** (a silent first session after install,
  clipped first words) are unhandled beyond the restart loop.
- **Pause-on-hidden was not built**, although the brief asked for it: its reason
  was Android, which no longer recognises at all, and desktop recognition was
  measured working in a hidden tab — a teacher who switches to a document
  mid-sentence keeps her captions.
- **No real two-device class had been run on this code** when this was written;
  the pull request says whether it has since.

## Addendum, 2026-09-23 — two phones stream to Deepgram

The phone-to-phone gap is closed by the paid fallback this record deferred,
used only in that case. The operator chose it on 2026-09-23: devices are not
known in advance, most of the first teacher's students are on a computer but
not all, and sometimes both people are on phones.

**What was built.** `assignRecognizers` gives a speaker `"cloud"` when neither
browser in the room can recognise and the fallback is configured
(`CaptionSession.cloudRecognition`, true when `DEEPGRAM_API_KEY` is set). That
speaker's own browser records its LiveKit microphone track with
`MediaRecorder` (WebM/Opus, 250 ms chunks — the call's track, never a second
capture) and streams it over a WebSocket to Deepgram's
`wss://api.deepgram.com/v1/listen` (Nova-3, finals only, `smart_format`,
`mip_opt_out=true`). Each final goes through the same translate → build →
publish path as a browser recogniser's (`lib/captions/cloud-recognizer.ts`).
A dropped socket reconnects with a fresh token after a 1 s, 2 s, 4 s …
backoff (capped at 30 s) and gives up after six consecutive failures.

Each connection starts at `POST /api/captions/stt-token`. It runs
`captionAccessFor` (flag, key, party to the class, Pro gate), refuses a
student caller without consent, resolves the model and language from the
booking (never the client), and then reads the room from LiveKit's server
(`listParticipants` on `class-<bookingId>`): the caller and someone else must
be present, the teacher's `captionsOn` must be `"true"`, and no participant's
`captionsAsr` may be `"1"` (`cloudRecognitionRefusal` in
`packages/shared/src/caption-recognition.ts`). Only then does it mint a token
with Deepgram's `/v1/auth/grant` (30-second TTL; the token only has to outlive
the handshake) and return it with the listen URL. Grants are rate-limited to
30 per caller per class per hour and 120 per class per day, and each grant is
logged; audio and the token never are. `wss://api.deepgram.com` joins the CSP
`connect-src`, and the privacy notice and supplier register name Deepgram for
this purpose.

**What it constrains, in addition to the list above.**

- **Never two paths for one speaker.** `"cloud"` is assigned only when no
  browser in the room can recognise, and the token route refuses a room where
  LiveKit shows one that can. A change that streams "to be safe" alongside a
  browser recogniser pays for minutes a free path already covers.
- **The long-lived key never reaches a browser**, and the client never names
  the model or the language — the route returns the URL.
- **Stay opted out of Deepgram's model training** (`mip_opt_out=true`). These
  are live lesson recordings, a student's (possibly a minor's) among them, and
  the notice says Deepgram is instructed not to keep them.

**What it costs.** Deepgram Nova-3 streaming was $0.0048 a minute on a
promotional rate and $0.0077 regular (checked by the operator on 2026-09-23).
Each phone streams its own speaker for as long as captions are on — silence
and a muted microphone included, since the recorder keeps sending — so a
50-minute phone-to-phone class with the student's consent is about 100 minutes:
roughly $0.48–0.77. If every one of the operator's target 32 classes a month
were phone-to-phone, about 3,200 minutes, $15–25 a month; any class with a
capable computer in it costs nothing. The route cannot see how long a socket
stays open (the browser talks to Deepgram directly), so Deepgram's own usage
view and a usage alert there are the authoritative measure.

**Verified, and not.** Verified against Deepgram's documentation and its own
JS SDK source (v5.12.0) on 2026-09-23: the grant endpoint and response, the
Member-role requirement, that the token is only needed for the handshake, the
browser subprotocol `["bearer", <token>]` (the SDK's `getWebSocketOptions`),
Nova-3's streaming language codes, and `mip_opt_out`. **Not** verified: a real
handshake with a grant token, a real Android `MediaRecorder` stream reaching
Deepgram, and whether `mip_opt_out` changes the per-minute price — no key was
available to the session that built it. The pull request says whether a
two-phone class has since been run.

**Accepted risks.**

- **The warranted-room check reads self-reported attributes.** A participant
  who published `captionsAsr="0"` from a capable computer would be granted a
  stream. The rate limits bound what that can cost.
- **A grant token carries Deepgram's `usage:write` for the core voice APIs**,
  not only `/listen`, and a socket opened with it may stay open indefinitely.
  The 30-second TTL and the per-caller limit bound it.
- **A browser that cannot record WebM or Ogg Opus** (possibly iOS Safari —
  untested) gives up and shows the generic "captions stopped" notice, whose
  wording is about the microphone permission.
