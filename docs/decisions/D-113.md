# D-113. A third rail for MX students: generalize the manual rail, don't add a `spei` sibling

**Status: Built (2026-08-23), then extended the same day by
[D-124](./D-124.md).** Shipped as one change rather than the two sequenced
pieces below — see "How it was built" at the foot of this doc for what the
implementation settled that the decision left open.

**Superseded in one respect.** This doc's target model gives `spei` its own
`PayoutInstrumentKind`, and the table below says a UK teacher's
sort-code/account-number would be "a third, at the cost of a row". D-124 took
that thought to its conclusion before either shipped: there is no `spei` kind.
The kinds are `wise | bank_account`, and a CLABE is one entry in a per-country
scheme registry — because a CLABE is Mexico's ACCOUNT FORMAT, not a separate
species of instrument, and a per-country kind would have needed a migration per
country. Everything else here — the generic manual rail, the instrument as
data, the reference-plus-self-attestation flow — is what shipped. Read D-124
for the current model.

**What changed.** SpiralClass will accept plain Mexican bank transfer (SPEI)
from students, and the way it is built is decided here: **the manual rail
becomes generic and the instrument becomes data.** Wise stops being a payment
provider and becomes one instance of "payee instructions the student follows
and the teacher confirms". SPEI is a second instance. A UK teacher's
sort-code/account-number would be a third, at the cost of a row.

Concretely, the target model:

| Layer                                                         | Today                              | After                                                            |
| ------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------- |
| `PaymentProvider`                                             | `stripe \| wise`                   | `stripe \| manual_transfer`                                      |
| `PaymentMethod` (wire type, `packages/shared/src/api.ts:911`) | `"stripe" \| "wise"`               | `"stripe" \| "manual_transfer"` + instrument id                  |
| `PaymentRail`                                                 | `card \| wise_transfer \| unknown` | `card \| wise_transfer \| spei \| unknown`                       |
| Payee details                                                 | 4 `wise*` columns on `teachers`    | rows in a `TeacherPayoutInstrument` table, `kind = wise \| spei` |
| Auto-reconcile credentials                                    | 3 `wiseApi*` columns on `teachers` | on the instrument, because it is an instrument capability        |
| Which instrument a student was shown                          | n/a (implied by provider)          | `payments.instrumentId`                                          |

The two-price model (`package_templates.wisePriceCentavos`) keeps its shape but
changes meaning: it is the **non-card price**, not the Wise price. That is what
it has always actually been.

**Sequencing.** Two pieces, deliberately split:

1. **The generalization is a pre-launch refactor** with no user-visible change
   — same screens, same flow, same copy, `wise` rows backfilled to
   `manual_transfer` + a `kind: "wise"` instrument. It happens before launch
   because launch is the volume event and the backfill is only free while the
   payment table is small.
2. **The SPEI instrument** — CLABE entry in `/settings/payments`, a checkout
   option, es-MX instructions copy — is then a form and a row. It may ship at
   launch or after; nothing about the decision forces it into the launch gate.

**Why it likely changed.** Four reasons, in order of weight.

_The rail was never Wise-shaped._ What the manual rail actually does is: render
payee instructions and a unique reference, let the student self-attest
("Ya envié el pago"), let the teacher confirm, then run the **same**
`advancePayment` reducer Stripe runs (`lib/payments/wise-confirm.ts`). The
platform never touches the funds. Nothing in that sentence is about Wise —
Wise supplies a `wise.com/pay/<handle>` URL where SPEI supplies an 18-digit
CLABE. Modelling the instrument as the provider was the original error, and
every branch on `provider === "wise"` inherits it.

_The blast radius is far smaller than the file count suggests._ 231 non-test
files mention Wise, but only **30 branch on provider identity** — the rest is
i18n copy (115 keys) and incidental prose, and that copy mostly stays, because
Wise remains a real named instrument in the UI. 30 files is a bounded sweep on
a codebase with colocated tests throughout.

_Adding `spei` as a third provider is strictly more expensive, just later._ It
duplicates the mark-sent → confirm → activate machinery rather than sharing it,
which is precisely the shape that diverges — one rail gets a bug fix, the other
does not. And the eventual collapse then costs 3 → 2 with two backfills plus a
de-duplication, against 2 → 2 with one backfill now. The sibling option is
cheaper this week and dearer every week after.

_It dissolves the cost that made this a hard call._ The objection was "a second
manual-confirmation rail to support at launch". Under this model a teacher
enables the instruments she wants, so a teacher with only a Wise instrument has
exactly one manual rail — support cost tracks what teachers actually enable,
not what the enum contains. The launch question is which instruments to
_offer_, and that is now reversible without a migration.

_Why not just turn on Stripe's own SPEI payment method?_ It cannot serve the
population that needs it. `lib/stripe/client.ts` pins
`payment_method_types: ["card"]` at all 3 checkout call sites (`:405`, `:472`,
`:619`) and the comment at `:398-404` gives two reasons — most students are not
in Mexico, and async methods confirm over hours or days, which breaks the
synchronous success-URL handoff that the booking flow depends on. D-58 adds the
decisive one: the platform is a UK entity and Stripe Connect only moves money
inside the US/UK/EEA/Canada/Switzerland circle, so a MX teacher has no connected
account to be paid out to. Funds collected by Stripe SPEI would land in the UK
platform account with no legal route onward to the teacher. Stripe-hosted SPEI
is closed to exactly the teachers this decision is for.

**What was affected.** The 30 provider-branching files, grouped:

| Group                        | Files | Note                                                                                                                                                 |
| ---------------------------- | ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Payments lib                 | 8     | `start-checkout`, `mark-wise-sent`, `wise-confirm`, `wise-reconcile`, `wise-confirm-reminder`, `reconcile-paid`, `cleanup-pending`, `lib/wise/index` |
| Web checkout funnel          | 4     | `b/[slug]/buy/{checkout-form,purchase-flow,result,wise/[ref]}`                                                                                       |
| Web teacher/student pages    | 3     | `(app)/payments/[id]`, `(student)/my-classes/buy`, `actions/wise-confirm`                                                                            |
| Shared + mappers + analytics | 5     | `shared/src/api.ts`, `lib/analytics/posthog`, `actions/admin-subscriptions`                                                                          |

refactor:

| Model                 | Columns                                                                                                                                                                  | In scope?                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------- |
| `Teacher`             | 7 — 4 payee details (`wisePaymentsEnabled`, `wiseHandle`, `wiseAccountHolder`, `wiseEmail`) + 3 API credentials (`wiseApiProfileId`, `wiseApiTokenEnc`, `wiseApiKeyEnc`) | Yes — become instrument rows        |

| `SubscriptionInvoice` | 1 (`wisePaymentRef`)                                                                                                                                                     | **No** — see below                  |

4 CHECK constraints (`payments_wise_reference_required_for_wise`,
`teachers_wise_handle_format`, `teachers_wise_handle_required_when_enabled`,
`package_templates_wise_price_nonnegative`) are rewritten against the new shape.

Route `/b/[slug]/buy/wise/[ref]` is a live URL students may hold in a tab or an
email, so the old path must keep resolving.

PII plumbing is already in place: `lib/sentry-scrub.ts:22,44-50` redacts a
`clabe` key wholesale and regex-scrubs any bare 18-digit run, so a CLABE cannot
reach Sentry through a log line. Nothing new is needed there.

This is a **Tier 2** change on every count (`lib/payments/**`, `prisma/**`), so
it goes through the full promote gate and lands as its own pull request — not
mixed with the other findings from the 2026-08-05 pre-launch review.

**Unresolved risks (as written; see the resolutions at the foot).**

- **`PaymentProvider` is shared with subscription billing, and that is a
  different concern.** `SubscriptionInvoice.provider` is the same enum
  (`schema.prisma:2808`) with its own `wisePaymentRef` — a teacher can pay her
  **SpiralClass subscription** by Wise, via the admin renewal form
  (`admin/subscriptions/wise-renewal-form.tsx`). CLAUDE.md holds these two
  concerns firmly apart: what a teacher pays SpiralClass is never entangled
  with the teacher→student payout rail. Renaming the shared enum value
  `wise` → `manual_transfer` silently renames it on the billing side too, and
  "manual transfer" is the wrong noun there — the platform _does_ receive
  those funds. **Resolve before the migration is written**, one of:
  1. split the enum (`PaymentProvider` for the payout rail,
     `SubscriptionPaymentProvider` for billing) — cleanest, and the two have no
     reason to move together again;
  2. keep the shared enum and add `manual_transfer` alongside `wise` rather
     than renaming, leaving billing on `wise`.
     Option 1 is the better end state and is the same argument this decision makes
     everywhere else: model the concern, not the vendor. It also enlarges the
     migration, so it is called out rather than assumed.
- **SPEI has no auto-reconciliation and never will.** The Wise rail has an
  escape hatch — the `poll-wise-statements` cron reads a teacher's own Wise
  balance statement via her own API token and matches pending payments
  (`lib/payments/wise-reconcile.ts`). Mexican retail banks expose no equivalent
  per-teacher statement API, so a SPEI payment is **100% teacher-confirmed,
  permanently**. Modelling auto-reconcile as a per-instrument capability makes
  that honest rather than surprising, but it does not remove it: every SPEI
  payment costs a teacher one manual confirmation, and
  `wise-confirm-reminder.ts` is the only thing standing between a forgetful
  teacher and a student whose package never activates. Watch the reminder's
  behaviour once a rail with no automated fallback is live.
- **The reference is the only matching key.** SPEI transfers carry a free-text
  concepto field that senders truncate, mistype, or leave blank far more often
  than a Wise reference — and unlike Wise there is no statement to match
  against afterward. Expect a higher rate of "student says sent, teacher can't
  find it" than the Wise rail produces.
- **A renamed provider is a renamed analytics dimension.** `payment_received`
  is tracked with `kind: "wise"` (`lib/analytics/posthog.ts`). Changing it
  splits every existing PostHog funnel and saved insight at the cutover date.
  Decide before the refactor whether to keep emitting the old value for
  continuity or to break cleanly and annotate the date in PostHog.
- **[D-111](./D-111.md) is also pre-launch and edits two of the same files.**
  The package-guest-booking decision changes `lib/payments/start-checkout.ts`
  (the `classCount === 1` gate) and re-reads
  `lib/payments/reconcile-paid.ts` — both are in the 30-file set this refactor
  sweeps, and its result-page copy sits on the Wise slow-rail path this
  decision renames. Land one, rebase the other; sequencing D-111 first is the
  cheaper order, because its diff is narrow and targeted while this one is a
  broad mechanical rename that will absorb a rebase more easily than it
  survives being rebased onto.
- **§3.5 of the same review overlaps this.** The Wise-discount checkbox shown
  in non-Stripe countries is a symptom of Wise-as-provider — the field is named
  for an instrument but means "non-card price". Fixing §3.5 independently means
  touching `templates-form.tsx` twice. Sequence §3.5 after the generalization,
  or accept the second pass.
- **Scope discipline.** "Instrument as data" invites a general payee-details
  builder. It should stay a closed union of known kinds (`wise`, `spei`) with
  per-kind validation — an 18-digit CLABE is checkable, a free-form bank-details
  blob is not, and an unvalidated payee field on a page a student pays from is
  the one place this rail could cause real money loss.

## How it was built (2026-08-23)

Both sequenced pieces landed together. The reason the split existed was that
the generalization needed to happen "while the backfill is still free" — but
there are no production payments at all, so there was no backfill to be free
of and no reason to pay the review cost twice.

**The two decisions this doc left open, resolved.**

- **The shared `PaymentProvider` enum: split (option 1).** `PaymentProvider`
  is the payout rail (`stripe | manual_transfer`); subscription billing gets
  `SubscriptionPaymentProvider` (`stripe | manual`), and
  `subscription_invoices.wise_payment_ref` became `manual_payment_ref`. The
  billing value is `manual` rather than `manual_transfer` for exactly the
  reason this doc gave: on that side the platform DOES receive the funds, so
  "manual transfer" would be the wrong noun. Naming the concern rather than
  the vendor is the same argument the decision makes everywhere else.

- **The analytics dimension: no split, no continuity hack.** The doc framed
  this as "keep emitting the old value or break cleanly and annotate the
  date". Neither was necessary. `payment_received.kind`,
  `checkout_started.method` and `payout_rail_connected.rail` now carry the
  INSTRUMENT kind, not the provider — so Wise keeps emitting `wise` with
  exactly its old meaning and `spei` arrives as a genuinely new value. Every
  existing PostHog funnel and saved insight is continuous across the cutover,
  and per-instrument adoption is a breakdown rather than a new event.
  `PaymentRail`'s `wise_transfer` was renamed `wise` to make the manual-rail
  values literally equal `PayoutInstrumentKind`, which is what lets a rail
  breakdown be an instrument breakdown with no join.

**What else the implementation added beyond the decision's scope.**

- **A per-instrument currency capability.** SPEI is the Mexican domestic
  clearing system: it moves MXN and nothing else. An instrument offered
  against a GBP price would quote a student an amount their bank physically
  cannot send, so `instrumentSupportsCurrency()` gates offerability on the
  teacher's own pricing currency, and the public-listing gate agrees (a
  GBP-priced teacher whose only instrument is SPEI is correctly not listed).
  The sitemap parity test sweeps that case.
- **A real CLABE checksum.** The DB CHECK enforces 18 digits; the mod-10
  weighted control digit is verified in `@spiralclass/shared`, validated
  against four published CLABEs. This is the guard the decision's
  "scope discipline" note was really about — shape alone would accept a
  transposition, and a mistyped CLABE sends a student's money to a stranger.
- **The payee bank, shown before sending.** `clabeBankName()` maps the
  Banxico institution code so the student can check the bank their app shows
  against the one we display. Cheap, and aimed squarely at the risk this doc
  names as the rail's most likely failure.

**Confirmed by the implementation, not changed.**

- Auto-reconcile moved onto the instrument, which makes it structural rather
  than surprising that SPEI has none: `supportsAutoReconcile()` returns false
  for it permanently, the reconciler queries Wise instruments only, and its
  pending-payment scan is now instrument-scoped so a SPEI payment can never be
  matched against a Wise statement.
- The two live student-facing URLs still resolve.
  `/b/[slug]/buy/wise/[ref]` permanently redirects to `/buy/transfer/[ref]`.
  The checkout path also accepts the legacy `method: "wise"` with no instrument
  id and resolves the teacher's Wise instrument, which is the only thing an
  older caller could have meant.
- The two-price model kept its shape: `package_templates.wise_price_centavos`
  became `transfer_price_centavos` — the non-card price, which is what it
  always was.

**Still open.** Review section 3.5 (the Wise-discount checkbox shown in
non-Stripe countries) is untouched and still sequenced after this, as the doc
directed. The field it names is now `transferPriceCentavos`, so the rename
half of that finding is already done.
