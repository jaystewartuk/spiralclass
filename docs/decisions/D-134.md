# D-134. Put `livekit.spiralclass.com` behind Cloudflare's proxy

> [!IMPORTANT]
> **Partly superseded 2026-08-29 by [D-139](./D-139.md).**
> `cloudflare_dns_record.livekit` no longer exists — `infra/oracle-runner` is
> deleted and the record is managed by hand in the Cloudflare dashboard. **The
> renewal risk this decision identified is not superseded; it got worse.**
> Both records are proxied, so tls-alpn-01 is impossible and http-01 is now
> the only path. See
> [`ORACLE_BOX_REBUILD.md`](../deployment/ORACLE_BOX_REBUILD.md) § TLS.

**What changed.** `cloudflare_dns_record.livekit` in `infra/oracle-runner/main.tf`
goes from `proxied = false` to `proxied = true` (and `ttl = 300` to `ttl = 1`,
which Cloudflare requires on a proxied record). The hostname now resolves to
Cloudflare edge addresses, IPv4 and IPv6, instead of a single IPv4-only A
record pointing straight at the Oracle box. Nothing on the box changed: Caddy,
`livekit.yaml`, the OCI security list and the host iptables are untouched.

**Why it likely changed.** On 2026-08-27 the platform's one teacher could not
join a class from her iPhone. Fifteen consecutive attempts between 08:48 and
08:53 failed identically, while her student joined the same room throughout and
her own Android tablet joined it at 08:55. Her session replay's console showed
the failure precisely:

```
signal connecting to wss://livekit.spiralclass.com/rtc/v1?access_token=…
websocket closed  {"reason":"","code":1006,"wasClean":false}   ← 30-130 ms later
Couldn't connect to server, attempt 1 of 1
```

The signalling socket died before any handshake completed, so the media server
never saw her — there is no server-side `call_participant_joined` for the
teacher on any of the fifteen attempts. Everything app-side was identical to
2026-08-25, when the same iPhone on the same iOS 18.7.8 and Chrome iOS 151
connected to a call four times: same connect URL shape and size, same
`livekit-client`, same TLS certificate (issued in July). The failure was in the
network path between that one device and that one host.

That host was the only one in the product with nothing in front of it. The app
is dual-stack behind Cloudflare; `livekit.spiralclass.com` was a bare A record
at a single Oracle IP, so any VPN, DNS filter, IPv6-only or NAT64 carrier path
or middlebox on one phone broke calls from it while the rest of the site worked
perfectly. Orange-clouding the record fixed her immediately.

The reason the record was grey-clouded is written in the code it is being
changed in: "raw WebSocket/TCP/UDP traffic Cloudflare's HTTP proxy can't
carry". Half of that is wrong and the other half never applied to this
hostname. Cloudflare's proxy carries WebSockets natively, and the wss
signalling on :443 is the only thing that ever resolves this name — RTC media
does not resolve it at all, because `livekit.yaml`'s `rtc.use_external_ip: true`
makes livekit-server advertise the box's own public IP in its ICE candidates.
UDP 3478, UDP 50000-60000 and the TCP 7881 fallback all still go straight to
the origin, past Cloudflare, exactly as before.

**What was affected.** One line of Tofu, its comment, and the DNS section of
`docs/deployment/ORACLE_LIVEKIT_PRODUCTION.md`, whose manual-instructions block
told a future operator to grey-cloud it. No application code, no environment
variable, no box-side config. A box replacement or the blue-green cutover still
changes only the resource's `content`.

**Unresolved risks.**

- **Certificate renewal now runs through Cloudflare.** Caddy's ACME HTTP-01
  challenge on :80 is proxied from 2026-08-27 onward. It works as long as the
  zone's SSL/TLS mode stays on Full (or Full strict) and "Always Use HTTPS" is
  not enabled for this hostname; either would break renewal silently. The
  current certificate expires 2026-10-19 and the first proxied renewal is due
  around 2026-09-19 — that is the date to watch, and nothing in this repo
  watches it.
- **The change was made in the Cloudflare dashboard first and codified after.**
  Until `tofu apply` runs, the live record and the declared record agree only
  by coincidence; this commit is what stops the next apply from reverting the
  fix, the same failure mode `fly scale vm` had before it was written into
  `fly.production.toml`.
- **The original diagnosis is not fully closed.** What exactly on that iPhone
  rejected the socket in 30 ms was never identified — only that it stopped
  once the hostname moved behind Cloudflare's anycast edge. If it recurs from a
  proxied hostname, this decision did not address the real cause.
- **Cloudflare is now in the path of every call's signalling.** A Cloudflare
  edge incident now takes calls down; previously only an Oracle incident could.
  Judged a good trade against a single un-fronted IP, but it is a trade.
- `client_ip` seen by livekit-server is now Cloudflare's unless Caddy is told
  to trust `CF-Connecting-IP`. Nothing reads it today; noted so a future
  rate-limit or geo rule is not written against the wrong address.
