# D-08. Reschedule cap moved from per-booking to a per-package "schedule change" budget (2026-06-11)

**What changed.** The student reschedule limit used to live on each booking row: `reschedule_count >= 1` blocked a second reschedule of _that_ class. It now lives on the package as a pooled budget — `packages.schedule_changes_used` against an allowance of `classes_total` (one change per class). A reschedule and a ≥24-hour (refundable) student cancellation each consume one unit. When the budget is spent, both self-serve paths are refused (`schedule-changes-exhausted`) and point the student to the teacher. A <24-hour forfeit is unchanged: always allowed, never charges the budget.

**Why it changed.** The per-booking cap was trivially bypassable: a student could cancel a class ≥24h out (which refunds the class to the package), then book a _fresh_ booking that started over at `reschedule_count = 0` — unlimited free reschedules in disguise. The cost of a "move" has to be charged where it can't be dodged. Cancel→rebook and reschedule are the same act (give up a committed slot, take another), so they now draw from one per-package pool, and the ≥24h cancel — the only free-move primitive — is what the budget gates. Charging at cancel time (not rebook time) is deliberate: the fresh booking that follows a cancel is indistinguishable from any first booking, so there's nothing to gate there.

**What was affected.**

- `lib/cancellation/classify.ts` — `canStudentRescheduleBooking` now takes `scheduleChangesUsed`/`scheduleChangesAllowed`; added `scheduleChangeBudget()` and `decideStudentCancel()`. Reject reason renamed `reschedule-cap-reached` → `schedule-changes-exhausted`.
- `reschedule-handler.ts` (spends a unit), `cancel-handler.ts` (spends a unit on ≥24h refund; blocks ≥24h cancel when exhausted; new outcome `schedule-changes-exhausted`).
- Every reschedule eligibility call site (the server action, the detail and slot-picker pages) and the student-facing copy. The UI leads with reschedule; the per-class "reschedule 1 time" hint became a per-package "N schedule changes left".
- New column + check constraint: migration `20260611000001_package_schedule_changes_used`.

**Why the allowance is generous (= classes_total) rather than tight.** This is tuned for an early teacher's reality: a handful of trusted 1:1 students, a teacher comfortable "being the bad guy" with manual override tools (waive, extend expiry). The budget exists to cap pathological churn, not to police honest rescheduling — a student would have to make as many schedule changes as they have classes before hitting it. Revisit with real reschedule/cancel data once students are live.

**Unresolved risks.**

- `reschedule_count` (per-booking) is retained as lineage/audit depth alongside `reschedule_of_booking_id`; it no longer gates anything. A future reader might assume it still does.
- A teacher _restore_ of a ≥24h cancel does not refund the schedule-change unit it spent (the counter is monotonic by design). Near-unreachable given the generous allowance; the teacher can adjust manually if it ever bites.
