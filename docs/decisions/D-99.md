# D-99. Mexico-incorporation audit: the platform's own subscription pricing/billing currency moves from MXN to GBP, matching the UK entity that has actually been billing since D-58

**Status: Active (built).**

**What changed.** The platform's own commercial model — SpiralClass Free/Pro
subscriptions, i.e. what a TEACHER pays the PLATFORM, never what a teacher
charges her own students — was still priced, billed, and reported in MXN a
full 11 days after D-58 moved the actual Stripe entity to the UK.
D-58 explicitly flagged this as unresolved ("no code reads a hardcoded
entity... the actual credential swap happens entirely in the deploy
environment, not in this diff") and separately left "the marketplace-
commission pivot... a separate, still-undecided question." This decision
closes that gap for the SUBSCRIPTION side:

- **New canonical currency: GBP.** `PLAN_PRICE_CENTAVOS_BY_CURRENCY.GBP` is
  now the default/checkout table (`packages/shared/src/subscriptions-config.ts`):
  Monthly £7.99, Annual £79.90 (exactly 10× monthly, same ~2-months-free ratio
  as the original MXN pricing), Founding £5.99 (price-locked for life, same
  ~75%-of-monthly ratio). These are a reasonable first cut sized off the
  existing MXN→GBP FX assumption already in the Financial Intelligence
  dashboard (D-86, 0.04249 as of 2026-07-15) and rounded to clean price
  points — **not a definitive pricing decision**; the operator should sanity-
  check them against current UK EdTech-SaaS pricing before promoting.
- **`PLATFORM_REGIONS`'s key renames `MX` → `GB`, currency `MXN` → `GBP`**
  (`packages/shared/src/platform-regions.ts`), removing the "historical
  residue" naming D-58 explicitly called out as awkward but didn't fix. A new
  `PLATFORM_MONEY_CURRENCY` export is the one place every currency-aware
  reader (display, analytics, admin) resolves "the platform's own currency"
  from.
- **Existing MXN subscribers are never silently reinterpreted.**
  `teacher_subscriptions.currency` / `subscription_invoices.currency` already
  stored the row's real currency explicitly (not inferred) — this was already
  well-designed for exactly this transition. Only the DEFAULT for a row
  created without one changes; a migration backfills `teachers.platform_region`
  (a single-entity marker never used for routing) from `"MX"` to `"GB"` for
  every existing row, but deliberately does **NOT** touch the subscription/
  invoice currency columns — those record what a specific row was ACTUALLY
  billed in, and a pre-D-99 MXN subscriber's Stripe subscription is still
  literally denominated in MXN until they renew under the new entity.
- **Architectural fix, not just a relabel:** `handleSubscriptionChanged`
  (the billing webhook's activation path) previously derived the currency to
  persist from `Teacher.platformRegion` (an app-internal, always-MX-until-now
  config value) instead of the ACTUAL currency on the live Stripe subscription
  object. Fixed to read `sub.currency` directly (added to
  `stripeSubscriptionSchema`) — the single genuine bug this audit found that
  would otherwise have silently relabeled a live MXN renewal as GBP the moment
  the region default flipped. `invoice.currency` was already read correctly
  from Stripe for invoices; subscriptions now match.
- **Admin financial analytics made currency-safe.** `getSubscriptionOverview`'s
  MRR calculation previously re-derived a subscriber's price from the CURRENT
  config table (`monthlyEquivalentCentavos(s.plan)`, implicitly MXN) instead of
  their own persisted `lockedPriceCentavos` — already wrong for price-lock
  semantics, and would have silently summed MXN and GBP raw minor units
  together as one number the moment mixed-currency subscribers existed. Now
  computed from each row's own locked price, partitioned by currency
  (`mrrCentavos` = canonical-currency total, `mrrOtherCurrencyCentavos` = the
  rest, surfaced as a separate admin note — never blended). `money-metrics.ts`'s
  subscription-revenue series had the identical latent bug (summed
  `SubscriptionInvoice.amountCentavos` across ALL currencies with no filter)
  and gets the same fix, mirroring the currency-partition pattern the
  running-costs series (`PlatformExpense`) already used — generalized off a
  hardcoded `"MXN"` to the same canonical-currency constant. The Financial
  Intelligence estimate layer's MRR→GBP conversion (D-86) also hardcoded
  `"MXN"`; now sums each currency bucket through its own FX rate.
- **Marketplace multi-currency (D-64) stays completely untouched** — this is
  explicitly NOT about what a teacher charges her own students. One real,
  narrow marketplace-side bug was found and fixed in passing:
  `teacherProfileJsonLd` (the `/b/[slug]` page's schema.org Offers) hardcoded
  `priceCurrency: "MXN"` for every teacher's packages regardless of the
  teacher's actual chosen currency, even though each `PackageTemplate` row
  already carries its own `currency` — now uses it. `pricingJsonLd` (the
  platform's own `/precios` Offers, a single canonical currency by design)
  takes an explicit `currency` param instead of a hardcoded one.

**Why GBP as one canonical currency, not multi-currency presentment.**
Evaluated and rejected for now: Stripe Billing subscriptions COULD be issued
with multi-currency Prices (per-currency `currency_options`), letting the
checkout page show USD/EUR/GBP based on the visitor's locale. That adds real,
ongoing complexity (FX-rate maintenance inside Stripe's own multi-currency
pricing, Stripe Tax implications per presentment currency, more Price objects
to keep in sync across three plans) for a solo-founder, pre-revenue-scale
product where the existing pattern — one global card-network-billed price,
letting the customer's own card issuer convert — is exactly how the vast
majority of bootstrapped global SaaS operates (Linear, Notion, etc. bill
globally in one currency). A teacher anywhere in the world can still subscribe
and pay by card; only the PRESENTED currency is fixed. If usage data later
shows meaningful friction from a single presentment currency, Stripe's
multi-currency Prices are the documented upgrade path — not implemented here.

touched), `packages/shared/src/i18n/catalog.ts` (a "MXN only" hint that was
about to become factually wrong, all three locales), and tests throughout.

**Migration / production risk (ops, not code) — read before promoting.**

1. **Stripe-side setup is a prerequisite, same as D-58 already flagged for
   Connect.** Stripe Prices are account-scoped — the UK Stripe account needs
   three NEW GBP Price objects created (Monthly/Annual/Founding) before
   `STRIPE_PRICE_MONTHLY`/`STRIPE_PRICE_ANNUAL`/`STRIPE_PRICE_FOUNDING` can
   point at them. The old MX-entity MXN Price ids do not exist in the UK
   account and must not be reused.
2. **Any teacher with a LIVE Stripe subscription under the old MX entity
   becomes unreachable the moment `STRIPE_SECRET_KEY` swaps to the UK
   account** — Stripe subscriptions/customers don't carry over between
   accounts (this is the same fact D-58 already surfaced for the one teacher
   with a live Connect account under the old entity; check whether that
   teacher, or any other, also has a live Billing subscription before
   promoting). Their `teacher_subscriptions` row keeps its correct historical
   `currency: "MXN"` forever — this decision does not silently reprice them —
   but Stripe can no longer manage that specific subscription going forward.
   Ops needs a plan for that teacher specifically (likely: comp them or
   re-checkout them fresh in the UK account) before flipping the production
   secret key.
3. **Merging to `main` is safe first** (D-26: preview-only); the credential
   swap + new GBP Prices + the migration above should land together at
   Promote time, matching D-58's own sequencing note.
4. Per D-64's own sizing note, real production scale today is tiny (~2
   teachers) — this genuinely limits blast radius, but does not remove the
   need to check point 2 above by hand before promoting.

**Unresolved / deliberately not implemented.**

- **Marketplace commission (GMV/`Payment.commissionCentavos`) currency
  blending** is a pre-existing, separate gap from D-64 (a teacher can already
  price in GBP/USD/EUR/MXN/COP/ARS/CLP/PEN/BRL, but `getCommissionSeries` /
  `getGmvSeries` sum across ALL teachers' currencies with no partition,
  exactly the bug this decision fixes for subscription revenue). Left
  untouched: fixing it is a materially larger, marketplace-wide surface
  (`money-metrics.ts`'s GMV/commission series, the `/admin/money` dashboard,
  the ambassador-commission report) and is explicitly out of this audit's
  scope (marketplace multi-currency is a separate, already-shipped concern
  the task brief said must stay intact). Recommend a dedicated follow-up.
- **Ambassador commission (`commission.ts`) mixing currencies within one
  ambassador's referred cohort** across a currency-era boundary (some
  referred teachers' invoices pre-D-99 MXN, some post-D-99 GBP) is a
  theoretical edge case for a manually-reviewed, paid-out-of-band process —
  not fixed, flagged for the admin running the report to eyeball.
- **Multi-currency subscription presentment** (see rationale above) —
  evaluated, not built.
- **Exact GBP price points** are a reasonable first cut, not a pricing
  decision — the operator should revisit before this reaches production.
