# D-200. Preview comes back as a second Cloud Run service, deployed by every merge before production's approval

**Status.** Decided, not built. Reverses the "no preview for now" choice in
[D-184](./D-184.md)'s addendum. Builds on [D-199](./D-199.md): the merge that
deploys preview is the same merge that queues production's approval.

**What changed.** Every push to `main` deploys that commit to a Cloud Run
service `web-preview` at `preview.spiralclass.com`. It has its own database,
its own secrets, Stripe test mode and its own Inngest environment. There is no
approval: preview is the place to look **before** approving production. The
release becomes merge → preview is live → look at it → approve production.

**Why.** Since D-199, approving the production deploy is the release decision,
and today there is nothing to look at when making it. The heavy tier already
proves a production build against a real Postgres, so preview is not more
testing. It is the one place the things that exist only in a deployed copy get
exercised:

- the runtime secret set and `config/env/*.runtime.env`
- the entrypoint and the Cloud Run revision
- the Inngest sync
- the migration run by `scripts/database-deploy.sh` rather than by the test
  container
- Stripe test-mode checkout and webhooks against a public URL
- a phone on a real network

D-184 chose "no preview for now" when shipping still meant typing a command.
That premise changed with D-199.

**The shape.**

1. **It is called preview, not staging.** Most of preview's plumbing outlived
   its host:
   - `config/env/preview.build.env` and `preview.runtime.env`
   - Infisical's `preview` environment, with `seed-preview.sh` and
     `reset-preview.sh`
   - `isProduction()` in `apps/web/src/lib/env.ts`, which reads `preview` in
     `APP_URL` as not-production

   A new name would be a second vocabulary for the same thing.

2. **Hosting.** `config/cloudrun/preview.env` describes the service:
   `SERVICE=web-preview`, the same region, minimum instances 0, maximum 1, and
   its own `SECRET_NAME` and `RUNTIME_SA_ID`. `scripts/cloudrun-deploy.sh`
   gains a `preview` case, and the Inngest sync URL moves into that file
   rather than being hard-coded to the production domain.
3. **Trigger.** A new `deploy-preview.yml` runs on every push to `main`,
   behind a `preview` GitHub environment that only `main` can reach and that
   has no reviewer. It runs in parallel with Gate and Heavy rather than after
   them. Preview's data is disposable, and running early means preview is live
   well before the approval appears, about seventeen minutes later.
4. **Database.** A separate Neon project, seeded by `seed-preview.sh` with test
   data only. Preview's migrations run first, through
   `scripts/database-deploy.sh preview`, so every production migration has been
   rehearsed on preview by the time anyone approves it.

**Hard requirements, each because the obvious shortcut is a real hole.**

- **Preview's deploy key cannot deploy `web`.** The `preview` environment has
  no reviewer, so a key in it that can deploy production would bypass
  production's approval. It gets a service account of its own, holding
  `run.developer` on `web-preview` alone, and never a copy of
  `GCP_DEPLOY_KEY`.
- **Preview's runtime cannot read production's secrets.** It gets a runtime
  service account of its own, with `secretAccessor` on preview's secret alone.
- **Preview gets its own Inngest environment, with its own event key and
  signing key.** Infisical's README says Inngest keys are currently the same
  value in both environments. With shared keys, a second synced URL is a second
  app in the **same** Inngest environment. Events fan out to every app there,
  so a booking event on preview would run production's functions against
  production's database, and production's crons would also fire on preview.
- **Stripe test-mode keys only**, with webhook endpoints and secrets of their
  own. Never a live key, and never a reference (`${production.…}`) to one.
- **Never a branch of the production database.** A Neon branch copies the real
  students' data. Preview's database is a separate project, seeded with test
  data.
- **Its images go to a separate Artifact Registry repository.** The
  `NEXT_PUBLIC_*` values are baked into the image, so one commit produces two
  different images. Both in one repository would make the cleanup policy's
  keep-five count preview builds, halving production's rollback depth.

**What was considered and rejected.**

- **No preview at all.** This is the choice D-184 made, and it is defensible
  with one real teacher. It means approving production on CI's word alone.
- **Rebuild the Oracle box** (`scripts/oracle-deploy.sh`). Oracle destroyed it
  once ([D-182](./D-182.md)), and a second, different platform is a second
  deploy path to keep alive. That script is deleted when this is built.
- **A Neon branch of production for realistic data.** It holds personal data
  on a host with weaker access control. Rejected outright.
- **A job inside `deploy-production.yml`.** The `production` environment's
  secrets are limited to the `production` branch, and a preview job beside
  them would sit one typo away from production's credentials. A separate
  workflow and a separate environment keep that boundary as it is.
- **Deploying preview only after Heavy is green.** It would delay the
  rehearsal by seventeen minutes and protect nothing, because preview's data is
  disposable.
- **A preview per pull request.** That would mean a database, a secret set and
  an Inngest environment per branch. It is far more to keep alive for one
  maintainer, and the question asked before approving is about `main`, not a
  branch.

**What it constrains.**

- Nothing on preview may hold a credential that reaches production, or real
  student data. The service accounts, the Infisical `preview` environment and
  the GitHub `preview` environment are each checked for this.
- `promote` and production's approval stay exactly as D-199 left them. Preview
  is advice to the person approving, never a gate in code.
- `isProduction()` stays keyed on `APP_URL`. Preview must keep `preview` in its
  host, or it starts behaving as production.

**What would be affected.** A new `deploy-preview.yml` and
`config/cloudrun/preview.env`. `scripts/cloudrun-deploy.sh` and
`scripts/database-deploy.sh` (a `preview` case each), and
`scripts/inngest-sync.sh`'s caller. `scripts/setup-branch-protection.sh` (the
`preview` environment). `infra/gcp/` (two service accounts and a repository).
`config/env/preview.runtime.env` (its Fly-era comments). These documents:

- `docs/development/workflow.md` §5
- `docs/deployment/RELEASE_AND_STAGING.md`
- `infra/database/neon/README.md`

These guards:

- `local-gate.test.ts`'s workflow list
- `cloudrun-deploy.test.ts`
- `production-targets.test.ts`

Each says "preview has no host" today. `scripts/oracle-deploy.sh` is deleted,
with its guards in the same change.

**Operator steps, in order, once it is built.** None of these can be done from
a session.

1. Create a Neon project for preview, and seed it.
2. Create a preview environment in Inngest, and put its keys in Infisical
   `preview`.
3. Put Stripe test-mode keys and webhook secrets in Infisical `preview`.
   Register the webhook endpoints against `preview.spiralclass.com`.
4. Create the two service accounts and the repository, then push preview's
   runtime secret.
5. Map `preview.spiralclass.com`.
6. Run `scripts/setup-branch-protection.sh`, which creates the `preview`
   environment.

**Trade-offs accepted, and unresolved risks.**

- **It is a third place secrets go.** Infisical already pushes to the GitHub
  environment and to Secret Manager. Preview adds a second Secret Manager
  secret and a second GitHub environment.
- **Preview is ungated.** A merge that breaks the build or boot breaks preview
  first. That is the point, but it means preview can be red while production
  is fine.
- **Cold starts.** At minimum instances 0, the first visit after idle waits
  for a container. That is acceptable for a rehearsal.
- **Not verified:**
  - whether the Inngest account allows a second environment without a plan
    change
  - whether the Neon account allows a second project
  - whether `isProduction() === false` already keeps preview out of search
    engines

  Each is an operator check before building.

- **Preview has no video.** It holds no LiveKit key pair (D-94's 2026-09-16
  addendum), so call changes still need `pnpm call:local`. A free LiveKit Cloud
  project for preview is a separate decision.
- **Email.** Preview's Resend sender is still unverified, per the note in
  `preview.runtime.env`. That is harmless while the database holds only test
  addresses, and broken the day anyone wants to read a preview email.
