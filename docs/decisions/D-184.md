# D-184. Cloud Run `us-east4` becomes a third production target, built to take the domain from Fly

**Status.** Serving production. Cloud Run took `spiralclass.com` on
2026-09-23, and Fly `agendaprofe` was destroyed the same day — see the addendum
at the end, which is current where it and the body disagree.

**What changed.** Every promoted commit is now also built and deployed to a
Google Cloud Run service (`web`, region `us-east4`), alongside the Fly release
and the Vercel failover
([D-177](./D-177.md)). Unlike Vercel, this target exists **to become primary**:
Fly `agendaprofe` costs ~$7/month against no revenue, and Cloud Run's always-free
grant covers this workload several times over. The cutover — map the domain,
move the Inngest registration, stop the Fly app — is the operator's, taken per
[CLAUDE.md](../../CLAUDE.md)'s first rule.

**Why.** Cost, and nothing else. The platform has one teacher on lifetime free
access and earns nothing. Fly is $5.70–7.23/month depending on how the machine
idles, so the whole prize is **$70–85/year**. That is small enough that it would
not justify moving a live payments app on its own — what makes it worth taking
is that the move is cheap: the image, the entrypoint and
`config/env/<env>.runtime.env` are already platform-neutral, so this needed **no
change to `apps/web/src`**, exactly as D-177 found when it built the Vercel
target. The second time that has been true is worth more than the first: two
independent targets is evidence of portability, one is a coincidence.

## What changed about D-150's premise, since that is what this log asks for

[D-150](./D-150.md) set out to move the web app onto free hosting, measured
carefully, and reversed itself in an addendum. Its number was latency to Neon:

> 58 ms from the free box in `mx-queretaro-1` against 12 ms from Fly `ord`

times ~28 round trips on a database-heavy page — ~1.3 s added, which it rightly
refused to pay. **That measurement is not refuted. It simply does not apply to
this candidate**, and the way to show that is the way D-150 itself demanded:
take the number from a deployed instance rather than asserting it.

Measured 2026-09-21, from Cloud Run jobs running **inside each region**, 25 TCP
connects each (one connect is one round trip, and authenticates nothing):

| From                                  | To `aws-us-east-2` | p50         | vs Fly `ord` |
| ------------------------------------- | ------------------ | ----------- | ------------ |
| Cloud Run `us-east4` (N. Virginia)    | Neon proxy `:5432` | **21.1 ms** | +9 ms        |
| Cloud Run `us-east5` (Columbus, Ohio) | Neon proxy `:5432` | 21.0 ms     | +9 ms        |
| Cloud Run `us-east1` (S. Carolina)    | Neon proxy `:5432` | 31.6 ms     | +20 ms       |
| Fly `ord` (Chicago)                   | Neon               | 12 ms       | — (D-150)    |

Two things in that table are worth keeping. The first is the answer: **+9 ms per
round trip, a fifth of what D-150 refused.** On its own arithmetic — 28 round
trips — the same page pays ~250 ms rather than ~1.3 s. The second is a trap
avoided: `us-east5` is physically in Ohio, the same state as the database, and
is **no faster than Virginia**. The path between two clouds is not the path a
map suggests, which is why the region was chosen from this table and not from
geography. `us-east4` wins on a tiebreak instead — it carries Cloud Run's custom
domain mapping, which the cutover needs.

⚠️ **The multiplier behind both figures was itself unverified — and wrong.**
D-150's ~28 round trips per page comes from "Prisma spends FOUR round trips on
every query" (`fly.production.toml`), which is the documented signature of
Prisma ≤6's Rust engine with `pgbouncer=true`. This repo is on Prisma 7.10 with
`@prisma/adapter-pg`, and `db-pool.ts` strips that parameter.

**Measured 2026-09-21** by recording what Prisma hands the `pg` driver against a
real Postgres — `apps/web/tests/db/round-trips.integration.test.ts`: **one
statement per read.** No `BEGIN`, no `COMMIT`, no `DEALLOCATE ALL`, and one
statement for an `include` too, because `relationJoins` makes it a LATERAL join
rather than a second query. Explicit `$transaction` calls still wrap, which is
the point of asking for one.

So a 7-query page pays ~7 round trips, not ~28, and **this decision gets easier
rather than harder**: the +9 ms costs such a page ~60 ms, not ~250 ms.
[D-150](./D-150.md)'s addendum carries the same correction, and the multiplier
is an executable check now — the next Prisma upgrade that reintroduces the
wrapping fails a test instead of silently invalidating three documents.

## Cold starts, and the monitor that already prevents them

Cloud Run scales to zero, which is what makes it free and is also the objection
to it. [D-150](./D-150.md) and `fly.production.toml` both record why
`min_machines_running = 0` was rejected on Fly: `/` and `/b/[slug]` are
cookie-read and DB-backed, cannot be edge-cached, and a 10–15 s cold boot in
front of promoted traffic is not acceptable.

Measured on the real image (2 vCPU / 1 GiB, `--cpu-boost`, `us-east4`):

|                                                                                |                             |
| ------------------------------------------------------------------------------ | --------------------------- |
| Container start (Cloud Run logs, instance created → port 3000 listening, n=12) | p50 **0.90 s**, max 1.63 s  |
| Cold request as a visitor feels it (n=9, forced onto new instances)            | median **2.0 s**, max 3.7 s |
| Warm request                                                                   | 0.16–0.20 s                 |

1 vCPU was measured too and start time was identical (p50 0.87 s), which says the
boot is not CPU-bound. 2 vCPU is chosen anyway, for the half this measurement
cannot see: `/api/health/live` does no work, while server-rendering a DB-backed
page does, and both sizes stay inside the free grant.

**Why a 2 s tail is acceptable here when 10–15 s was not**, and this is the part
that would be dishonest to leave implicit: it is not the number alone, it is that
almost nothing will pay it. `spiralclass.com/api/health/live` is checked
**about once a minute** by an external HetrixTools monitor
(`spiralclass production liveness`, active since 2026-08-25), well inside Cloud
Run's ~15-minute idle keep. The monitor is pointed at the **domain**, so after a
cutover it keeps one instance warm with no change to it, and it already hits the
DB-free endpoint rather than `/api/health` — which matters, because a
sub-5-minute check against the DB-touching one would hold Neon's compute awake
and exhaust the free plan's 100 CU-hours around day 17.

So a cold start follows a deploy or a Cloud Run reap, not a visitor. **This is a
dependency and is written down as one**: if that monitor is ever deleted or
re-pointed, the first visitor after each idle period pays ~2 s. It is not a
guarantee either — Google keeps idle instances "up to 15 minutes" and may reclaim
one at any time.

## What this target deliberately does not do

The same five omissions as D-177's Vercel target, for the same reasons, and they
are load-bearing rather than unfinished:

- **No domain.** CI never runs `gcloud run domain-mappings create`. A DNS-level
  cutover performed by a CI job is precisely what CLAUDE.md's first rule reserves
  to the operator.
- **No Inngest sync.** `scripts/inngest-sync.sh` PUTs an endpoint URL and Inngest
  registers an app **per URL**, so a second live URL would register a second app
  and fire every cron twice — including ones that bill Stripe customers. The
  Inngest endpoint belongs to whichever deployment holds the domain. At cutover
  it **moves**; it is never added.
- **No Neon checkpoint and no migrations.** `scripts/database-deploy.sh` owns
  both and `deploy-production.yml` runs it as the `database` job this one
  `needs:`. One commit, one migration run.
- **No production probe.** `scripts/local/synthetic.sh` probes
  `https://spiralclass.com`, which this deploy does not serve.
- **No `GOOGLE_*`/`GCP_*` branch in `apps/web/src`.** `APP_URL` still decides
  prod-vs-preview. `apps/web/tests/config/decommissioned-platforms.test.ts` keeps
  asserting the app cannot tell which platform it is on, and this target is the
  second proof that it cannot.

## Cost, which is the whole point and so is stated as arithmetic

Cloud Run's always-free grant is 180,000 vCPU-s, 360,000 GiB-s and 2M requests
per billing account per month, applied at Tier 1 rates; `us-east4` is Tier 1.
(The project that holds it is named nowhere in this tree, for the reason
[D-158](./D-158.md) gives — it is an account identifier. It reaches CI as a
`production` environment secret, exactly as the Vercel project id does.)
Request-based billing means CPU is allocated during requests only.

At this traffic — tens of sessions a day, plus a once-a-minute liveness check —
the dominant consumer is the monitor: 43,200 checks/month × ~0.2 s × 2 vCPU ≈
**17,000 vCPU-s, under 10% of the grant.** Real traffic is a rounding error on
top. The image is 118 MB against Artifact Registry's 0.5 GB free allowance, and
egress to North America has a 1 GiB monthly free tier.

**The honest risk is not the bill, it is the shape of it.** Fly charges a fixed
~$7/month and cannot surprise anyone. Cloud Run charges $0 and has **no hard
spending cap** — a traffic spike, a crawl or a loop bills rather than throttles.
The mitigations are `--max-instances`, a budget alert, and the fact that
`--concurrency` is left at the default so one instance serves many requests. A
cap that stops the service would trade a bill for an outage on a payments app,
which is the wrong trade; the alert is deliberately the softer one.

## Cost of the decision itself

Three targets is one more than two, and each is a thing that can rot. D-177
argued a standby is worth keeping because it is exercised every release, and the
same argument carries here — but only until the cutover. **Once Cloud Run holds
the domain, Fly should be retired rather than kept as a third warm target**, and
the record that does it should delete this machinery's Fly half rather than
leaving a guard whose premise has died. That lesson is already written down in
CLAUDE.md, learned from an `/api/mobile` tree that outlived its client by a
month.

## What is not yet closed

- **Custom domain mapping on Cloud Run is a Preview feature** with no SLA. It is
  available in `us-east4` (checked 2026-09-21). The alternative — a global
  external load balancer — is ~$18/month and would cost more than Fly, and
  putting Cloudflare's proxy in front of a `run.app` URL does not work on the
  free plan because the Host header arrives unrewritten. If mapping proves
  unreliable, **the cutover stops and Fly keeps the domain**; nothing else in
  this record depends on it.
- **CPU is throttled between requests** under request-based billing, so work
  scheduled after a response can stall until the next one. Two call sites use
  `after()` — `apps/web/src/app/b/[slug]/page.tsx` and
  `apps/web/src/lib/marketing/bots.ts` — and both are best-effort analytics whose
  own record (`acquisition_events`, written best-effort and never inside a
  payment transaction) already tolerates loss.
- **LiveKit reachability from `us-east4` is unmeasured**, exactly as D-177 left
  it unmeasured from Vercel. It is on the cutover checklist, not this record.
- **No load test.** Every number here was taken at n≤25 against an idle service.

## The cutover, which is not this record

For the operator, in order, in `docs/deployment/RELEASE_AND_STAGING.md`:
verify the `run.app` URL serves a signed-in page → map `spiralclass.com` → move
the Inngest registration off Fly → watch one real class join → stop the Fly app,
keeping it stopped (not destroyed) for a week as the rollback. Reversing is a DNS
record, exactly as D-150 said of the choice it made.

## Addendum, 2026-09-23 — the cutover happened, and Fly is gone rather than stopped

**What changed.** The operator ran the cutover. `spiralclass.com` is mapped to
Cloud Run `web`, the Inngest registration moved with it, and Fly `agendaprofe`
was stopped and then destroyed the same afternoon — the operator's call, taken
knowing it gave up the runbook's week-long rollback. The body above describes
a target that "takes no domain"; that stopped being true today, and the
omissions it calls load-bearing were load-bearing _for a standby_.

**What the release path now does**, and why each one moved rather than being
added:

- **The Cloud Run job decides whether production shipped.** `deploy-verdict.mjs`
  reads `productionOk` from the database and Cloud Run jobs. The rule never
  changed — "whichever job deployed the thing holding spiralclass.com" — only
  its answer did. Vercel is the one remaining standby.
- **It probes production.** `scripts/local/synthetic.sh` moved from the Fly job,
  with `LIVEKIT_ORIGIN_IP` and its preflight. A probe run from a job that no
  longer serves the domain would have been testing Cloud Run and crediting Fly.
- **`scripts/cloudrun-deploy.sh` syncs Inngest, against the domain.** The URL
  Inngest holds did not change: it was always `https://spiralclass.com/api/inngest`,
  and the cutover moved what answers it. The sync is the script's last step, so
  it registers the revision the deploy just made live. ⚠️ It must never sync
  the `run.app` URL — a second URL is a second app and every cron fires twice.
  `cloudrun-deploy.test.ts` runs the script with its tools stubbed and asserts
  exactly one PUT, to the domain, after `gcloud run deploy`.
- **It writes the `web-deploy` ledger kind**, the row `pnpm release:status`
  reads as production web. The distinct kind existed so a standby could not be
  mistaken for what serves; it is what serves.
- **The Fly job is deleted** from `deploy-production.yml`, and `fly` from the
  dispatch choices. Promote's recovery path is `scripts/database-deploy.sh`
  then `scripts/cloudrun-deploy.sh`, because the second holds no database
  credential.

**What the cutover taught that the runbook did not say.**

- **The records must be DNS-only.** The domain was Cloudflare-proxied, and
  Google cannot issue the mapping's certificate through the proxy. The apex
  records were replaced with Google's A and AAAA set, grey-clouded.
- **HTTPS is down between the DNS switch and the certificate.** Measured:
  records live at ~16:05 UTC, `CertificateProvisioned` at 16:11, a clean
  handshake on every request from ~16:21. About fifteen minutes with no site —
  a step to take outside lesson hours, which the runbook now says.
- **`www` needed nothing.** An existing Cloudflare redirect rule already sends
  it to the apex, and the rule runs at Cloudflare's edge whatever the apex
  points at.
- **`fly scale count 0` destroys machines; `fly machine stop` stops them.** The
  runbook's "stop, never destroy" was right and its implied command was not.

**What is left, and belongs to the change that deletes it.** The Fly half of
the tree — `scripts/fly-deploy.sh`, both `fly.*.toml`, the preview workflow's
Fly job, the `push-fly-secrets.sh` scripts and the guards and documents that
name them — describes an app that no longer exists. It goes in the next
change, whole, rather than being edited around here.
