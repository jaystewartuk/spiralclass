# D-85. Non-secret config moves out of `fly.<env>.toml` into platform-neutral `config/env/` files

**What changed.** The web app's non-secret configuration no longer lives in
`fly.preview.toml` / `fly.production.toml`. It moved to four committed,
platform-neutral files under `config/env/`:

- `config/env/<env>.runtime.env` — the runtime non-secret vars that were in
  `fly.<env>.toml`'s `[env]` (`APP_URL`, `CSP_ENFORCE`, feature flags,
  `LIVEKIT_URL`, Stripe Price IDs, …).
- `config/env/<env>.build.env` — the `NEXT_PUBLIC_*` build-time vars that were
  in `fly.<env>.toml`'s `[build.args]`, inlined into the client bundle at build.

`fly.<env>.toml` now carries only the three platform-owned vars —
`NODE_ENV`, `PORT`, and a new `APP_ENV` (`preview`/`production`) that selects
which runtime file to load. Every environment loads the _same_ files:

- **Fly runtime** — `scripts/docker-entrypoint.sh` (new `ENTRYPOINT`) sources
  `config/env/$APP_ENV.runtime.env` before starting the server. Already-set
  container env (Infisical secrets, `fly secrets`) wins over the file.
- **Fly build** — `scripts/env-build-args.mjs <env>` reads
  `config/env/<env>.build.env` and passes each as `--build-arg` (replaces the
  old `scripts/fly-build-args.py`, which parsed `[build.args]`). Wired in
  `.github/actions/fly-build-deploy` and `scripts/fly-deploy.sh`.
- **Codespaces / local dev** — `.devcontainer/dev.sh` sources both files before
  `next dev`, then Infisical layers secrets on top.

Secrets are untouched: genuine secrets still live in Infisical (D-66). This
only moves the _non-secret_ half out of Fly's own config format.

**Why it likely changed.** Setting up the preview site on GitHub Codespaces
surfaced the root problem: the non-secret config was stored in two **Fly-only**
formats (`[env]` and `[build.args]`) that only Fly reads. Codespaces pulled
secrets from Infisical but had no way to get the non-secret values, so the app
booted with an incomplete config anywhere that wasn't Fly. The fix is to make
the store platform-neutral rather than duplicate it per platform (the rejected
alternative — parsing `fly.<env>.toml` from `dev.sh` — is a fragile
TOML-in-bash hack that keeps the config conceptually Fly-owned). Pushing the
values into Infisical was also rejected: it reverses D-66 (non-secret config is
deliberately git-reviewed and diffable, not buried in a secrets manager) and
would require Infisical auth just to boot with defaults.

**What was affected.** `fly.preview.toml`, `fly.production.toml`, root
`Dockerfile` (new `ENTRYPOINT` + COPY of the runtime files/entrypoint),
`.devcontainer/dev.sh`, `.github/actions/fly-build-deploy/action.yml`,
`.github/workflows/fly-deploy.yml`, `scripts/fly-deploy.sh`. New:
`config/env/*` (+ README), `scripts/env-config.mjs` (+ `.d.mts`),
`scripts/env-build-args.mjs`, `scripts/docker-entrypoint.sh`. Removed:
`scripts/fly-build-args.py`. Guarded by
`apps/web/tests/scripts/env-config.test.ts` (grammar, a drift guard that the
moved keys never creep back into the Fly configs, Dockerfile ARG parity,
build-args emission, and live entrypoint sourcing). `infra/infisical/README.md`
updated to point at `config/env/`.

**Unresolved risks.**

- Production boot now runs a shell entrypoint before the server. It fails
  loudly if `APP_ENV` is set but its file is missing (real misconfig) and warns
  but continues if `APP_ENV` is unset. Both env files are baked into the image,
  so a missing file would be a build/deploy error, caught before real users.
  Still, this is a new step on the production boot path — validated on preview
  first (D-26: `main` is preview-only) before any promote.
- The `.env` grammar is parsed by three languages (bash entrypoint + `dev.sh`,
  the Node module, the Docker shell). They must stay in agreement; the grammar
  is deliberately the strict intersection (unquoted values, whole-line comments
  only) and the test enforces it, but a future value containing a space or `#`
  would need a grammar change in all three, not just the file.
- Values duplicated across `runtime.env` and `build.env` (e.g. `SENTRY_DSN` and
  its `NEXT_PUBLIC_SENTRY_DSN` twin) are kept in sync by a test, not deduped —
  a deliberate scope limit to avoid changing behavior in this move.
