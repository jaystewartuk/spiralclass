# D-174. A server action revalidates exactly one path

**Status.** Active.

**What changed.** Every server action now calls `revalidateAfterAction()`
(`apps/web/src/lib/revalidate.ts`) exactly once, for the page it was invoked
from. `revalidatePath` is no longer called directly anywhere under
`app/actions/**`, and the 62 actions that used to revalidate a detail page and
its sibling list now revalidate only the one the form is on. Held by
`apps/web/tests/config/revalidate-once.test.ts`.

**Why.** A second `revalidatePath` in one action makes the client throw the
entire action response away. The write commits, the server returns its
`{ ok }`, and the browser discards it: `useActionState` never receives the
state, the page never picks up the new data, and on next 15.5.25 the transition
never commits at all — the submit button stays disabled on "Saving…" forever
and every link on the page stops working until a manual reload.

Found on the teacher's custom-price form, where the reported symptom was
"saving a reason does nothing". It saved every time. What the teacher could
see was a dead button, so she clicked again: four identical audit rows on one
student, a minute apart, are what the bug looks like in the data.

Measured on a production build of this app, one variable at a time:

| Configuration                       | Result             |
| ----------------------------------- | ------------------ |
| one page-scoped call, current route | works              |
| detail path + list path             | response discarded |
| the same path twice                 | response discarded |
| one layout-scoped call              | response discarded |

So it is the number of calls, not which path — two calls to the _same_ path
break it exactly as reliably as two different ones. `pnpm dev` never reproduces
any of it; it is production-build-only, which is why it survived this long.

Still present on next 16.3.4, where the permanent hang becomes a flat
10.0-second stall (measured over four consecutive trials: 10001, 10000, 10001,
10002 ms). The Next 16 upgrade does not fix this and must not be mistaken for
the fix.

**What was considered and rejected.**

- _Keep both calls and widen to `revalidatePath(path, "layout")`._ Measured:
  one layout-scoped call breaks the response the same way. It is not an escape
  hatch.
- _Leave the sibling-list revalidation and accept a stale list._ There is
  nothing to accept: `next build` prerenders **no** route in this app (every
  route is `ƒ`), so `revalidatePath` has no Full Route Cache entry to
  invalidate. Its only effect is on the client Router Cache, where
  `staleTimes.dynamic` defaults to 0 — the list refetches on navigation
  regardless. The dropped calls were doing nothing before they started doing
  harm.
- _Fix only the custom-price form._ The same pattern was in 62 actions,
  including refunds, cancellations, reschedules and the Wise confirmation
  path. Every one of them was silently failing to refresh its page.
- _Enforce at runtime by making a second call a no-op._ The failure is
  per-request and silent; there is nothing to throw and nobody to tell. The
  rule is a property of the source, so it is checked in the source.
- _A cross-audience helper (`revalidateClassMaterialLists`)._ Deleted. It
  revalidated `/dashboard/classes` and `/my-classes` from one action — but the
  client Router Cache is per-browser, so a teacher's action could never
  invalidate a student's, and with no server cache the call was inert in both
  directions. It also made its callers three-call actions, which is how the
  worst instances got there.

**What it constrains.** An action may revalidate one path. If a second surface
looks stale, it is refetching on navigation already — check before adding a
call. Where the path depends on a branch, compute it and pass it to a single
call site rather than revalidating in two arms; the guard counts call sites,
not runtime calls, because a reader should not have to redo the control-flow
proof each time. `revalidatePath` stays importable in exactly one file.

**What was affected.** `apps/web/src/lib/revalidate.ts` (new),
`apps/web/src/lib/materials/revalidate.ts` (deleted), 62 actions under
`apps/web/src/app/actions/**`, and
`apps/web/tests/config/revalidate-once.test.ts` (new).

**Trade-offs accepted, and unresolved risks.**

- The six `revalidateAfterAction(path, "layout")` callers in `reading.ts` and
  `onboarding.ts` are **not** fixed. They are whole-app refreshes that the root
  layout genuinely needs, and they are fire-and-forget `startTransition` calls
  with no `useActionState` result to lose — but a layout-scoped call was
  measured to break the response, so they are suspect and unverified. Nothing
  checks them. Deciding how the root layout should refresh after a preference
  change is its own change.
- Whether the sibling list is genuinely fresh after a browser **back/forward**
  navigation, which restores from the client cache rather than refetching, was
  not measured. If a stale list turns up there, the fix is on the page, not
  another `revalidatePath`.
- The guard is a regex over the source, not a control-flow analysis. It will
  not catch a second revalidation reached through a helper it does not scan
  (it scans `app/actions/**` and `lib/**/revalidate.ts`), which is exactly how
  the deleted materials helper hid two calls from view.
- The upstream Next.js behaviour is not understood, only characterised. If a
  later Next release fixes it, this record's premise changes and the rule can
  be relaxed — measure the table above again before doing so.
