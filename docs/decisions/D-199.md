# D-199. A merge to `main` starts its own release, and the owner's approval is the only human step

When Gate and Heavy both finish green on the push run for a commit on `main`,
`.github/workflows/promote-on-green.yml` runs `scripts/ci/promote.mjs
--when-certified`, which fast-forwards `production`; that push triggers
`deploy-production.yml`, which waits for the owner's approval on the
`production` environment before it migrates the database and deploys Cloud Run.
Production is always a fresh build of the `production` branch, never a promoted
preview artifact. Nobody types `pnpm promote` unless they want to.

## Why

A release step that someone has to remember gets forgotten silently. On
2026-07-19 `production` was found 96 commits behind what was live, because the
deploy was a human dispatch step. An approval cannot be forgotten the same way:
it is a queued run with a notification attached.

## Options considered

- **A human dispatch step** — the 2026-07-19 failure.
- **No approval at all** — rejected by the operator. The approval is the last
  look before migrations run against live payment records, behind a Neon
  checkpoint.
- **Approval only for migration-bearing commits** — needs a second environment
  and a guess at what counts as migration-bearing.
- **A lesson-hours window in code** — rejected by the operator ("don't restrict
  deploys. I'll decide"). Nothing in the repository ever defined the window, so
  the judgement stays at the approval click.
- **Push with `GITHUB_TOKEN`, or a deploy key** — a `GITHUB_TOKEN` push triggers
  no workflow, and either would need a non-admin bypass actor on the
  `production` ruleset, letting any workflow with `contents: write` move
  `production`. `deploy-protection.mjs` rejects that.
- **Deploying straight from the `workflow_run`** — the `production` environment
  only accepts the `production` branch, which stops a dispatch shipping an
  arbitrary ref and keeps `git log origin/production` as the record.
- **Promoting a built preview artifact to production** — `NEXT_PUBLIC_*` values
  are inlined at build time, so production would serve preview's config.

## What it cost

- `PROMOTE_TOKEN` is a long-lived, fine-grained token that can move
  `production`. It cannot skip the approval; when it expires the run goes red
  and `pnpm promote` from the laptop still works.
- A merge now starts a release (auto-merge too). Approving the pending deploy
  ships everything merged before it.
- A held commit is not retried. If Heavy is red or cancelled, the commit ships
  with the next green one, a re-run, or by hand; nothing sweeps it up.
- Lesson hours depend on the owner reading the clock at approval time.
- Two queued approvals can share the deploy's concurrency group; the older one
  ships a commit the newer one overtakes.

## What it constrains

- **`promote-on-green.yml` decides nothing.** `promote.mjs` reads the verdict
  and the protection settings; the workflow restates neither and runs no deploy
  script and no install.
- **`--when-certified` only turns "not certified yet" into exit 0**: the other
  run still going, a cancelled or red run, or `production` already at or past
  the commit. Every other refusal stays red.
  [`promote-on-green.test.ts`](../../apps/web/tests/config/promote-on-green.test.ts)
  runs the real script to hold this.
- **Only push runs certify.** A squash merge does not preserve the PR's head
  SHA, so a `pull_request` run never saw the commit on `main`. Promote fails
  closed: no `gh`, no network, a moved API shape, a run in flight or aged out
  are all refusals. `--force-gate` runs the full tier locally instead.
  Guarded in [`local-gate.test.ts`](../../apps/web/tests/config/local-gate.test.ts)
  ("promote asks about the PUSH run", "promote fails closed").
- **`PROMOTE_TOKEN` lives on the `promote` environment**, which only `main` can
  reach, and appears in one step of one workflow. Never repository-wide.
- **Production is the owner's alone.** The `production` environment requires
  the owner's approval with admin bypass off and self-review allowed; a ruleset
  lets only an admin move the `production` branch. `pnpm promote` reads both
  live and refuses without them
  ([`scripts/ci/deploy-protection.mjs`](../../scripts/ci/deploy-protection.mjs)).
  [`production-access.test.ts`](../../apps/web/tests/config/production-access.test.ts)
  holds that what `scripts/setup-branch-protection.sh` applies is what promote
  accepts. This is a promote check, not a gate step, because the gate runs
  offline and on fork PRs.
- **The deploy is triggered, never dispatched.** Promote refuses before the
  fast-forward if `deploy-production.yml` has no `push` trigger, reading the
  trigger off the file. A target moving is never a reason to suspend
  production's trigger. (`local-gate.test.ts`: "the deploy is triggered, never
  dispatched by hand", "promote refuses to fast-forward when nothing is
  listening for the push".)
- **A session never merges, deploys or promotes** (CLAUDE.md rule 1).
- **Preview, when built, is advice to the approver, never a gate**, and must
  hold no credential that reaches production and no real student data: its own
  database (never a branch of production's), its own Inngest environment and
  keys, Stripe test keys only, its own deploy and runtime service accounts, its
  own Artifact Registry repository. Production is recognised by `APP_URL`, so
  preview's host must contain `preview` (`isProductionDeployment()` in
  `apps/web/src/lib/env.ts`).
- Dark launches use [`flagEnabled()`](../../apps/web/src/lib/flags.ts): on in
  preview, off in production until promoted.

## How we got here

- **Before July 2026.** `main` stopped deploying to production once real
  students used the system. `main` deployed a staging tier; a promote workflow
  ran E2E once and fast-forwarded a `production` branch, which was rebuilt
  rather than artifact-promoted. The tier was soon renamed preview.
- **2026-07-19.** The drift: `production` 96 commits behind live, from a human
  dispatch step.
- **2026-08-17.** To save Actions minutes the deploy left Actions and was
  chained into `pnpm promote` (`--gate-already-passed`), so promoting stayed one
  command ending with production serving. Preview stopped deploying on merge.
  The deploy steps were re-typed and lost the Neon checkpoint.
- **2026-09-04.** The production deploy returned to a runner
  ([D-157](./D-157.md)), triggered by promote's push to `production`. It was
  suspended and restored the same day when the target question was settled.
  Measured that day: the `production` environment held **zero** secrets
  ([D-163](./D-163.md)).
- **September 2026.** Promote stopped running the full tier on the laptop and
  began reading the runners' verdict for the exact commit.
- **2026-09-23.** The required reviewer was found never configured; a promote
  had deployed with nobody approving. The environment, the admin-only ruleset
  and promote's live check followed.
- **October 2026.** `promote-on-green.yml` removed the last typed command. Not
  verified at merge: whether a fine-grained token with `Administration: read`
  can see a ruleset's `bypass_actors`; if not, promote fails closed.
- **October 2026, decided, not built.** Preview returns as a second Cloud Run
  service, `web-preview` at `preview.spiralclass.com`, deployed by every push to
  `main` with no approval, running its migrations first so each production
  migration is rehearsed. Unverified before building: a second Inngest
  environment and a second Neon project on the current plans. Preview will hold
  no LiveKit key pair, so call changes still need `pnpm call:local`.
