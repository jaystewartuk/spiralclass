# D-199. A merge to `main` starts its own production deploy; the approval is the release decision

**Status.** Active. Narrows [D-157](./D-157.md) (who moves `production`) and
[D-119](./D-119.md) (promote is typed by the operator). Keeps D-157's
required reviewer, [D-162](./D-162.md)'s certification and
[D-129](./D-129.md)'s ban on schedules exactly as they were.
2026-10-26: narrowed by [D-205](./D-205.md). The deploy asks once, on the
database job, and Cloud Run follows, rather than once per job as below.

**What changed.** `.github/workflows/promote-on-green.yml` runs
`scripts/ci/promote.mjs --when-certified` whenever Gate or Heavy finishes green
on a push to `main`. Once both are green for the same commit, promote
fast-forwards `production`. The push triggers `deploy-production.yml`, which
still waits for the owner's approval on the `production` environment before the
database job and before Cloud Run. Nobody types `pnpm promote` any more unless
they want to. The approval click is now the moment production changes.

**Why.** [D-120](./D-120.md)'s binding lesson: a step nobody is forced to take
gets forgotten, and `production` once sat 96 commits behind `main`. After D-157
the deploy was chained to the promote push, but the promote itself was still a
command somebody had to remember. The step left is the approval. Unlike a
command, it cannot be forgotten silently: it is a queued run with a
notification attached.

**What was considered and rejected.**

- **No approval at all.** Rejected by the operator. The reviewer is D-157's
  last look before migrations run against live payment records, behind a
  Neon checkpoint, and the 2026-09-23 hardening made it binding on purpose.
  Nothing about that premise changed.
- **Approval only for migration-bearing commits.** Would need a second
  environment, and a guess at what counts as migration-bearing. Not wanted
  yet.
- **A lesson-hours window in code.** Rejected by the operator: "don't restrict
  deploys. I'll decide". Nothing in the repository ever defined the window.
  Every mention says "outside lesson hours" and no more. So the judgement
  stays human and moves to the approval click, which is the one moment that
  is still the owner's.
- **Push with `GITHUB_TOKEN`.** A push made with it never triggers other
  workflows, and the `production` ruleset lets only an admin move the branch.
  Adding GitHub Actions as a bypass actor would let any workflow holding
  `contents: write` move `production`, including one on a session's branch,
  and `deploy-protection.mjs` rightly rejects a non-admin bypass. Rejected.
- **A deploy key.** Same reach as the token below, but it needs a non-admin
  bypass actor on the ruleset, with the same objection. Rejected.
- **Deploying from the `workflow_run` itself, skipping the `production`
  branch.** The `production` environment only accepts the `production` branch,
  which is the guard that stops a dispatch shipping an arbitrary ref, and
  `git log origin/production` stays the record of what shipped. Rejected.

**What it constrains.**

- `promote-on-green.yml` decides nothing. promote.mjs reads the verdict and
  the protection settings. The workflow restates neither, and it runs no
  deploy script and no install.
- `--when-certified` may only turn "not certified **yet**" into exit 0: the
  other run still going, cancelled, red, or `production` already at or past
  the commit. Every other refusal stays red. `promote-on-green.test.ts` runs
  the real script to hold this.
- `PROMOTE_TOKEN` lives on the `promote` environment, which only `main` can
  reach, and appears in one step of one workflow. It is never a
  repository-wide secret.
- **A session still never merges, deploys or promotes** (CLAUDE.md rule 1).
  Its job still ends at an open PR. What changed is what the operator's merge
  _starts_.

**What was affected.** `.github/workflows/promote-on-green.yml`,
`scripts/ci/promote.mjs` (`--when-certified`), `scripts/setup-branch-protection.sh`
(the `promote` environment), `docs/deployment/BRANCH_PROTECTION.md` (the token),
`docs/development/workflow.md`, the `deploy-production.yml` header,
`apps/web/tests/config/promote-on-green.test.ts`, and `local-gate.test.ts`'s
workflow list.

**Trade-offs accepted, and unresolved risks.**

- **A long-lived credential that can move `production`.** It cannot skip the
  approval, but it is one more thing to rotate. A fine-grained token expires,
  and when it does the runner fails red rather than drifting quietly.
  `pnpm promote` from the laptop still works meanwhile.
- **Not verified before merge: whether `Administration: read` lets a
  fine-grained token see a ruleset's `bypass_actors`.** If it does not,
  promote's protection check fails closed and the first run goes red with
  "can be moved by anyone with write access". That is the safe direction, and
  the fix is the token's permissions, not the check.
- **Merge now starts a release.** Auto-merge, enabled per PR, starts one too.
  Every pending approval is a deploy request, and approving the one in front of
  you ships everything merged before it.
- **Lesson hours depend on the operator reading the clock at approval time.**
  Nothing checks that. That was true before as well; it just moved from typing
  a command to clicking a button.
- **A held commit is not retried.** If Heavy is red or cancelled, nothing
  re-runs promote for that commit. It ships with the next commit that goes
  green, or by a re-run of the red workflow, or by hand. There is no schedule
  to sweep it up, deliberately (D-129).
- **Two queued approvals can reach the same deploy concurrency group.**
  `cancel-in-progress: false` queues them in order. Approving the older one
  ships a commit the newer one then overtakes, which is harmless but costs a
  build.
