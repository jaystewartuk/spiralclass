# D-162. `pnpm ship-pr` is deleted, and the runners certify the release

**What changed.** `scripts/ship-pr.sh`, the `/ship-pr` skill, the `pnpm ship-pr`
alias and the `just ship-pr` recipe are gone. `heavy.yml` gains a `push` trigger
on `main` and a summary job with one stable name. `pnpm promote` no longer runs
or reads a full-tier gate: it asks GitHub whether the **Gate** and **Heavy**
workflows both concluded green on the push run for the exact commit being
promoted, and refuses otherwise.

This finishes what [D-161](./D-161.md) started. D-161 moved the heavy suites
onto runners for pull requests and deliberately left `ship-pr` alone, on the
ground that it also wrote the receipt `promote` reused and deleting it would
move forty minutes rather than remove them. That was the right call at the time
and it is the thing this record fixes.

## What ship-pr was actually doing, and where each part went

It is worth being exact, because "delete the batch script" sounds like dropping
four capabilities and is really dropping one.

- **Fast gate on each branch as authored** → `gate.yml` and the pre-push hook.
- **Fast gate on each branch merged with `main`** → a `pull_request` run tests
  exactly that tree, and does it on a runner.
- **Squash-merge with careful state verification** → `gh pr merge --squash`.
  ship-pr wrapped it because `gh` once reported failure after GitHub had
  actually merged, and a summary saying nothing merged when two things had was
  the worst output it could produce. That wrapper is worth remembering; it is
  not worth a script nobody else needs.
- **The full tier once, against merged `main`** → `heavy.yml` on `push: main`,
  which is new here.

The one genuine capability lost is **batching**, and batching was never wanted
for itself. It was arithmetic against one laptop that could only run the suites
serially. Three concurrent runners removed the premise, so the batching bought
nothing except the delay between finishing a PR and finding out about it.

## The merged-tree check had to survive, and it does

⚠️ **A `pull_request` run tests HEAD merged with base AS OF THAT MOMENT.** If
`main` moves between the last green run and the merge, the tree that landed is
not the tree that was tested. D-146's whole argument for batching was that a
combination can break though each half was green alone, and that argument is
still true.

So `heavy.yml` now runs on `push: main` as well. Same registry, same three
legs, no command to remember — which is strictly better than ship-pr's version,
where the check only happened if somebody ran it.

## What certifies a release

**Before:** a local `.gate/receipt.json` written by `pnpm ship-pr` and read back
by `pnpm promote`, matched on SHA, tier, result and a not-dirty flag.

**After:** the Gate and Heavy workflows, both `success`, on their **push** runs
for that exact SHA.

The receipt was a self-attestation — a file the release path wrote and then
believed. What replaces it is bound to the same commit, produced on the machine
that also builds the production image, and checkable by anyone with the
repository open. That is a better answer to "what proves this commit is safe to
ship" than a JSON file on one laptop, and it happens to be free.

⚠️ **It fails closed, and every branch is a refusal rather than a warning.** No
`gh`, no network, an API shape that moved, a run still in flight, a run that
has aged out of GitHub's retention — all of them stop the promote. The single
thing that must never happen on this path is shipping a commit because nothing
could be found to say it was broken. `--force-gate` runs the full tier locally
instead, and is the deliberate offline and recovery path — the same property
D-157 insisted on for the deploy.

**Only push runs count.** A `pull_request` run's head SHA is the branch tip,
which a squash merge does not preserve; the commit on `main` is a different
object that run never saw. Accepting it would certify a tree that was never
built.

## The summary job, and why the matrix could not provide one

`heavy.yml`'s legs are named from the registry (`matrix.step.title`), which is
the property D-161 wanted — add a heavy step and it gets a runner in the same
commit. It also means the job names move, and neither a required check nor
promote's query can depend on a name that moves.

So there is one more job, `complete`, named **Heavy tier**, which `needs` the
matrix and fails unless the aggregate says success. `always()` makes it run even
when a leg is red, so it always produces a verdict rather than leaving something
waiting on a job that has already decided. A guard test asserts it cannot pass
while a leg failed — a summary that is green whenever it ran is worse than no
summary, because promote reads it.

## What is deliberately NOT done

- **`local-gate` stays the required status on `main`, and the `gate.yml` job
  does not replace it.** Switching to the job context was considered and
  rejected on a measurement: the laptop posts `local-gate` about 90 seconds
  after a push and the runner reaches the same verdict in about ten minutes.
  They cannot disagree — they run the same registry — so requiring the job
  would make every merge wait for the slower of two producers computing one
  answer. The whole reason the fast tier stayed on the laptop in D-161 was that
  it is eight times faster there; spending that saving at the merge button
  would undo it.
- **Heavy is not a required check.** Seventeen minutes on every merge, to gate
  a signal that is better read than waited on. `pnpm promote` is what refuses to
  ship a commit the heavy tier did not pass, and that is the moment where being
  wrong is expensive.
- **⚠️ Fork PRs still cannot post `local-gate`, and this does not change that.**
  A fork's `pull_request` run gets a read-only token, so nothing about a fork's
  code can certify itself — which D-157 already recorded as correct rather than
  a gap. Both workflows still RUN on a fork PR, so an outside contributor sees
  real verdicts; the maintainer runs the gate against the fork head and posts
  the status. That is now written down in
  `scripts/setup-branch-protection.sh` instead of being discovered.
- **`pnpm gate:full` is kept.** It no longer certifies anything by itself, but
  it is still how you run everything locally before you have a PR.

## Unresolved risks

- **Promote now depends on `gh`, the network and GitHub's run retention.** It
  degrades to a refusal rather than to a wrong answer, and `--force-gate` is
  the way through — but a promote from a plane is a promote that runs the full
  tier on the laptop, which is what this record otherwise stopped doing.
- **Nothing blocks a merge over a red heavy run.** That is deliberate, and it
  means `main` can go red on the heavy suites — caught at promote, and fixed
  forward, which is the same shape D-120 accepted for a Tier 2 PR merged on the
  fast tier alone.
- **`heavy.yml` cancels the previous push's run on `main`** through its
  concurrency group. A superseded run certifies nothing, and promote asks about
  a specific commit, so this cannot produce a false green — but promoting a
  commit that a newer push superseded means asking for a run that was cancelled,
  and the answer is a refusal.
- **The careful `gh pr merge` verification is gone with the script.** On
  2026-08-30 believing `gh`'s exit code cost a deploy: both PRs merged, `gh`
  then failed doing local housekeeping, and the run reported nothing merged. A
  human merging one PR at a time sees the result on the page; a future batch
  helper would need that lesson back.
