# D-70. The application does not know which platform it runs on

The web app runs on any host that can run its Docker image, against any
Postgres. It reads no platform's environment variables, so `APP_URL` alone
decides production versus preview. It imports no platform SDK and uses no
provider-specific SQL. It receives all of its configuration as plain
environment:

- non-secret values come from the committed `config/env/<env>.runtime.env` and
  `config/env/<env>.build.env` files
- secrets come from Infisical
- R2 credentials come from the `infra/cloudflare-r2` OpenTofu state

No value is ever passed on argv.

## Why

The host has changed four times in four months: Vercel, Fly, Vercel again as a
standby, then Cloud Run. The database provider has changed once, from Supabase
to Neon, and its region once. Each move was cheap only where nothing in the
application knew where it was. Where something did know, the move broke
silently. On the move to Fly, two features keyed on `VERCEL_ENV`, which Fly
never sets. The preview `noindex` header and a build-time migration both
stopped working, and nothing failed. A seed guard that matched the Supabase
project ref matched nothing on Neon. The 125-migration history carried
Supabase's RLS policies, `auth.uid()`, role grants and a Realtime publication,
so it could not be replayed against any other Postgres.

## Options considered

- **Stay on Supabase and codify it with OpenTofu.** This lost because the
  migration history itself was Supabase-shaped. Realtime was also the last
  runtime coupling in the app.
- **Keep non-secret config in the host's own format** (`fly.<env>.toml`'s
  `[env]` and `[build.args]`), and parse it elsewhere. This lost because only
  Fly read that format. Codespaces booted with incomplete config, and the fix
  would have been TOML parsed from bash.
- **Put non-secret config in Infisical.** This lost because booting with the
  defaults would then need Infisical auth, and non-secret config is meant to be
  reviewed in a diff.
- **Self-host Infisical.** This lost because it adds a stateful Postgres and
  Redis service for a solo operator, which is more risk than the plaintext
  `.env.fly.local` it replaced.
- **Keep a warm second target to prove the app stays portable.** This was
  tried as the Vercel failover, and it lost. It never served a request, its job
  was often red, and it was never a complete failover: Inngest, LiveKit and its
  region were all unresolved. The coupling bans prove portability. A second
  deploy does not.

## What it cost

- **Polling replaced Supabase Realtime** in chat, student live notes and the
  call instructions overlay (`apps/web/src/hooks/use-visibility-polling.ts`).
  A message can take a few seconds to appear.
- **Vercel's Skew Protection has no equivalent.** Only the client-side reload
  in `apps/web/src/lib/server-action-recovery.ts` covers a stale server action
  across a deploy.
- **Three parsers share one `.env` grammar:** the entrypoint's shell, Node and
  the Docker build. The grammar is the strict intersection, with unquoted
  values and whole-line comments only. A value containing a space or `#` needs
  a change in all three.
- **There is no warm standby.** See [D-184](./D-184.md).

## What it constrains

- **No `SUPABASE_*` or `VERCEL_ENV`/`VERCEL_URL` read, no Supabase SDK, and no
  `@vercel/*` runtime dependency** (`@vercel/analytics` is exempt). There is
  also no root `vercel.json` or `vercel.jsonc`, because Vercel reads that file
  automatically, which makes it a deploy trigger nobody typed. The retired
  failover's files must not come back either. All of this is enforced by
  [`decommissioned-platforms.test.ts`](../../apps/web/tests/config/decommissioned-platforms.test.ts).
  Bringing Vercel back needs a new record that says how it closes the Inngest,
  LiveKit and domain gaps above.
- **The host sets only what it owns.** The Cloud Run deploy sets exactly
  `APP_ENV` and `SECRETS_ENV_FILE`. Everything else comes from `config/env/`,
  which
  [`scripts/docker-entrypoint.sh`](../../scripts/docker-entrypoint.sh) sources
  at boot. Container env wins over the file.
  [`env-config.test.ts`](../../apps/web/tests/scripts/env-config.test.ts) holds
  the grammar, the Dockerfile `ARG` parity, the twins between `runtime.env` and
  `build.env`, and the entrypoint.
- **A secret never enters argv.** Use stdin or a file instead, because
  `gcloud`'s env-var flags and a process list both expose argv. Production's
  secrets reach Cloud Run as one Secret Manager file
  ([`config/cloudrun/production.env`](../../config/cloudrun/production.env)).
- **R2 credentials belong to OpenTofu, not Infisical.** Preview and production
  have separate buckets and separate tokens, and only production's buckets
  reach the production secret: `r2Entries()` in
  [`scripts/cloudrun-env.mjs`](../../scripts/cloudrun-env.mjs). One map,
  `R2_ENV_PREFIX` in `apps/web/src/lib/storage/provider.ts`, reads every R2
  bucket's env vars.
- **No provider-specific SQL or extension in the hot path, and no
  database-side RLS.** Tenant isolation is application-level only, which
  [D-175](./D-175.md) checks.
- **Data moves between Postgres instances with Postgres-native tools only:**
  `pg_dump`/`pg_restore` and logical replication, in
  [`infra/database/scripts/`](../../infra/database/scripts/). Never use a
  provider's proprietary migration service. An OpenTofu state file can hold
  connection details, so its R2 bucket is treated as a secret store.
- **Multi-region is not built, and should not be built speculatively.** The
  only built piece is `MIGRATE_REGIONS` (`apps/web/src/lib/migrations/regions.ts`),
  which does nothing while it is unset. If a second region is ever built, its
  per-tenant routing must default to deny: an unknown region is refused, never
  served from another. A wrong route is a residency breach, not a 500.

## How we got here

- **June 2026.** Database provisioning, schema and data movement were written
  down as three independently reproducible layers, so that the provider would
  be a variable. The tooling was built and left dormant: an OpenTofu module for
  the Supabase project, a region-parameterized `migrate deploy`, and the clone,
  replication and verify scripts. A design for serving several regions was
  written and deliberately not built. Chat moved off Supabase Realtime to
  polling.
- **2026-07-12.** The R2 OpenTofu module had been written without live API
  access, and it was wrong. It listed three buckets where four were real, and
  guessed a `-r2` suffix that only one bucket had. Preview got its own buckets
  and tokens.
- **2026-07-13.** 125 migrations (2026-04-23 to 2026-07-12) were squashed into
  one baseline with no Supabase-specific SQL. It was applied to a throwaway
  Postgres 17 and exercised against the booking-buffer trigger, both GiST
  exclusion constraints, the `overrides` audit trigger and a `CHECK`. Skipping
  `migrate resolve --applied` on an existing database was confirmed to fail as
  Prisma's `P3005` refusal rather than as corruption. The last two Realtime
  subscriptions moved to polling.
- **July 2026.** Infisical replaced the hand-pasted `.env.fly.local`. The
  cutover then ran. Production moved to Fly and Neon after a real
  `pg_dump`/`pg_restore` clone, and the two `VERCEL_ENV` regressions above were
  found and fixed. The preview `noindex` header now keys off
  `NEXT_PUBLIC_DEPLOY_ENV`. The seed guard now refuses any host in
  `PROD_DB_HOSTS`.
- **Phase 5, after the soak.** The Vercel and Supabase projects were torn
  down. The Supabase dependency, its env vars, the Supabase Storage rollback
  path and every `VERCEL_*` branch were removed. Storage became R2 only.
- **Undated.** Non-secret config left `fly.<env>.toml` for `config/env/` after
  Codespaces booted without it.
- **2026-09-10.** Vercel returned as a production target that held no domain.
  It needed **no change to `apps/web/src`**, which made the decoupling a
  measured claim rather than an intention.
- **2026-09-23.** The failover was retired. On the first production deploy
  from this repository, its three `VERCEL_*` credentials were missing and the
  job went red (#65). Another time, a stalled build left it a release behind,
  and this was reported only as a job cancelled 30 minutes later (#80).
  Production had moved to Cloud Run that day, also with no application change.
  The operator deleted the Vercel project, which held a copy of production's
  runtime secrets, and removed its tokens. Those secrets were not rotated.
  `TURBO_TOKEN`, the Turborepo cache token, is still a Vercel account token.
