# D-70. Full exit from Supabase and Vercel — both environments move to Fly + Neon, migration history squashed to one portable baseline

**What changed.** SpiralClass stops depending on Supabase (Postgres, RLS,
Realtime, PostgREST/GoTrue) and Vercel entirely, for both environments —
not just the preview-only Fly experiment that started it. Concretely, three
things landed together:

1. **The two remaining Supabase Realtime subscriptions** (student live-notes,
   the call instructions overlay) converted to portable HTTP polling
   (`use-visibility-polling.ts`) — finishing what D-44 already did for chat.
   These were the last thing making the database provider-specific at the
   application layer.
2. **The entire migration history squashed to one baseline.** 125 migrations
   (2026-04-23 → 2026-07-12) — accumulated Slice-by-Slice, feature-by-feature
   — are replaced by a single migration
   (`apps/web/prisma/migrations/20260713120000_portable_postgres_baseline`)
   containing zero Supabase-specific SQL: no RLS policies, no `auth.uid()`/
   `auth.users`, no `anon`/`authenticated` grants, no Realtime publication.
   None of that was ever expressed in `schema.prisma`'s Prisma models — it
   was hand-authored raw SQL layered on top for Supabase's platform benefit,
   dead weight once the app stopped needing PostgREST/GoTrue for anything.
   The squash was **tested, not just assembled**: applied via real `prisma
migrate deploy` against a throwaway Postgres 17 container, exercised
   functionally (the booking-buffer trigger, both GiST exclusion constraints
   preventing double-booked/buffer-violating slots, the `overrides`
   append-only audit trigger, a `CHECK` constraint all confirmed correct),
   and the adoption path for an _already-migrated_ database (`prisma migrate
resolve --applied`, for production) verified separately — including
   confirming the failure mode of skipping that step is Prisma's own safe
   `P3005` refusal ("schema is not empty"), not silent corruption.
3. **Both environments move to Fly + Neon, not just preview.** The existing
   Fly app (`agendaprofe`, the preview experiment) gets promoted in place
   to serve production; a new `agendaprofe-preview` Fly app takes over the
   preview role. Both get their own Neon Postgres project — production's
   seeded via a real `pg_dump`/`pg_restore` data clone from Supabase
   (D-49's layer-3 tooling, finally exercised for real rather than staying
   dormant), preview's via a fresh `migrate deploy` + reseed (disposable
   data, no clone needed). Vercel and Supabase both get decommissioned —
   not deleted outright, kept dormant as a rollback path through a soak
   period. Full sequencing: `docs/ops/PRODUCTION_CUTOVER.md`.

## Why it likely changed

the operator's own framing: going with Supabase was a mistake, and D-49/D-50's
vendor-neutrality strategy (decouple provision/schema/data so the provider
is a swappable variable) had already done the hard conceptual work — this
decision is that strategy's layer-1 provider swap finally executed for
real, on both environments, rather than staying a dormant capability. The
preview-only Fly move was originally scoped as a cost spike, not a
full exit; once the migration history itself turned out to be the actual
blocker (not just a preview inconvenience — replaying Supabase-authored SQL
against any non-Supabase Postgres was a real, structural coupling), fixing
it once for both environments was less work and less risk than fixing it
twice.

## What was affected

- `apps/web/prisma/migrations/` — squashed to one baseline (see above).
- CI simplified as a direct consequence: `apps/web/tests/_setup/bootstrap-auth.sql`
  (the shim that let CI's plain `postgres:16` container replay the _old_
  Supabase-authored history) is retired, along with its
  `docker-compose.test.yml` mount and the bootstrap-then-drop-schema
  workaround in `integration.yml`'s migration-drift-check job (a plain
  `prisma migrate diff --from-url` works directly now — no cross-schema
  `P4002` to work around).
- Dead code removed: `backfillBetterAuthUsers` (`lib/auth/backfill-users.ts`)
  and its two tests — mirrored a migration (`20260704010000_backfill_better_auth_users`)
  that no longer exists, backfilling from a Supabase `auth.users` table no
  future environment will ever have.
- `apps/web/src/hooks/use-visibility-polling.ts` — new, shared by both
  Realtime replacements.
- `infra/database/neon/README.md`, `infra/database/RUNBOOK.md` — simplified;
  Neon (or any Postgres) needs zero special-case handling now, the same
  `migrate deploy` as everywhere else.
- `docs/ops/PRODUCTION_CUTOVER.md` — new, the full phased runbook (Neon prod
  provisioning + data clone, new preview app, `fly.toml`/Infisical rewrite
  for the promoted app, DNS cutover, decommission sequencing).
- `prisma-dbml-generator` wired into `schema.prisma` (gitignored output) —
  unrelated to the exit itself, but landed in the same session: a
  dbdiagram.io-compatible ERD export for ongoing schema review.

## Unresolved risks

- **Stripe production readiness (D-58) is a hard prerequisite, not a
  parallel task.** Production needs the UK entity's live Stripe keys, whose
  Prices and webhook registrations don't carry over from the old Mexican
  entity. If D-58 isn't actually done when this cutover is ready to execute,
  this cutover either waits or ships payments pointed at a not-fully-live
  account — the runbook's Pre-flight section gates on this explicitly.
- ~~`scripts/seed.ts` still has a live Supabase Auth Admin API dependency~~ —
  **resolved.** `provisionTeacherAuthUser`/`ensureStudentAuthUser` now
  generate a UUID directly and insert into `user` (matching how every other
  identity in this app already works, post-D-40); `uploadMaterial` goes
  through `getStorageProvider()` (R2) instead of Supabase Storage.
  `.github/workflows/e2e.yml` no longer runs `supabase start` — a plain
  `postgres:16` service container, matching `integration.yml`. The repo's
  entire CI surface is now Supabase-free, and the orphaned `supabase/`
  directory (config, email templates) was removed.
- **Legal-gated feature flags** (`LESSON_INSIGHTS_TRANSCRIPTION_ENABLED`,
  `LIVE_CAPTIONS_ENABLED`) are on for preview via a
  deliberate override of D-21/D-22's blockers (see the
  `project_legal_gated_flags_enabled_override` memory). The production
  cutover forces an explicit decision — ship them to real users, or turn
  them back off in production's `fly.toml` — that has been implicitly
  deferred until now.
- **Infisical's `production` environment is currently empty by design**
  (`infra/infisical/README.md`: "do not wire it into any script or CI until
  [the promotion] happens"). The documented secret-reference mechanism
  (`${preview.KEY}` for shared values) has never been exercised live —
  needs verification, not blind trust, during the cutover.
- **Vercel's Skew Protection has no Fly equivalent** — only the client-side
  reload fallback (`lib/server-action-recovery.ts`) exists on Fly. A user
  active across a production deploy is more likely to hit a stale
  server-action bounce than they were on Vercel. Not a blocker; a known,
  accepted behavior change.
- **Supabase Storage's decommission status is unconfirmed** — a manual
  rollback path through Supabase Storage was deliberately kept live pending
  full R2 migration (see `infra/database/neon/README.md`). Don't assume
  Supabase can be fully torn down without checking this first;
  `apps/web/scripts/migrate-storage-to-r2.ts` exists if any bucket still
  needs moving.
- ~~**The actual cutover (`docs/ops/PRODUCTION_CUTOVER.md`) has not been
  executed as of this decision.**~~ **UPDATE — the cutover has since been
  executed; see D-89.** Production now runs on Fly (`agendaprofe`) + Neon; the
  DNS flip and the Neon prod data clone are done. D-89 is the current-policy
  record of the executed reality, including its own **Phase 5 decommission**
  update: Vercel and Supabase are now fully torn down (not just kept dormant
  as a rollback path) — see D-89's "Phase 5 — decommission (EXECUTED after the
  soak)" section.

**Update (2026-07-20, D-95):** the cutover wasn't caught and recorded in this
doc at the time it happened, which is exactly the kind of drift D-89 exists
partly to close out — see that decision for the current-policy record, and
see D-95 for the follow-on database-safety-net redesign the cutover enabled
(Neon PITR + branch checkpoints replacing a pg_dump-to-R2 deploy gate).
