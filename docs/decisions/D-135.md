# D-135. The class recording is audio-only

**What changed.** `startRoomRecording` passes `audioOnly: true` to LiveKit's
room-composite egress. The stored object moves from `recordings/<booking>/<ts>.mp4`
to `.m4a` (MP4 container, AAC), and the teacher's replay page renders an
`<audio>` player instead of a `<video>` one. Recordings made before this stay
`.mp4`, stay video, and still play — the extension is what the replay page reads
to decide, so nothing already captured is orphaned.

Nothing else moves. `CLASS_RECORDING_ENABLED`, the teacher's Record control, the
`autoRecordClasses` opt-in ([D-132](./D-132.md)), the [D-22](./D-22.md) insights
consent gate and the whole transcription pipeline are untouched.

**Why it likely changed.** The first real class recorded under
[D-131](./D-131.md)/[D-132](./D-132.md) — 51 minutes, 2026-08-27 — produced an
**846 MB** file and dropped **2,586 video frames** producing it. Three things
followed from that, in the order they matter:

1. **Capacity.** The Oracle A1 box has 2 OCPUs and also runs livekit-server,
   Redis, Caddy and the captions agent. Compositing 720p30 (LiveKit's default
   preset, which the call site never overrode) is the expensive part of that
   workload, and it was already dropping frames with a **single** class in
   progress. Two concurrent classes would have degraded the live call, not just
   its recording. Audio compositing is close to free by comparison.
2. **Retention surface.** Stored video carries a materially heavier retention
   and consent obligation than stored audio, and the retention path for
   recordings was still open when D-131 shipped. This decision shrinks that
   surface; closing it is [D-136](./D-136.md)'s job.
3. **Storage cost, which is the weakest of the three and is recorded here so it
   is not later mistaken for the reason.** R2 charges no egress fees, so ~25 GB
   a month is cents. Cost alone would not have justified this.

Against that, what the video was actually worth on this product: a language
lesson's replay value is what was **said**. The one genuine video case is a
screen-shared document — but those materials are already attached to the class
as library items, and at any bitrate this box can sustain, shared text is
unreadable anyway.

MP4/AAC rather than OGG/Opus, even though `lessonAudioKey` uses OGG for the
insights capture: this file is played back by a human in a browser, and WebKit
only gained Ogg support in Safari 17.5. The teacher is on iOS.

**What was affected.** `livekit-provider.ts`'s `startRoomRecording`, a new
`callRecordingKey`/`isAudioOnlyRecordingKey` pair in `lib/video/recording.ts`,
the replay page and viewer, and the `replay.videoUnavailable` string in all three
catalogs (it said "video"; the thing is now a recording). No schema change, no
migration, no environment variable.

The **insights pipeline is not affected at all**, and the reason is worth stating
because the two are easily conflated: transcription has always consumed a
SEPARATE per-participant audio egress (`startParticipantRecording`), one file per
speaker, never this composite. The composite is the replay artefact and only
that.

**Unresolved risks.**

- **No backfill.** The one 846 MB video already in R2 stays a video. It is the
  only object of its kind and is left alone deliberately — deleting a teacher's
  existing recording is her call, not a migration's.
- **"Replay" is now a listen-back.** If a teacher ever does want to see a
  screen-share after the fact, this removes that, and the answer would be to
  record the screen-share track separately rather than to re-enable a full
  composite.
- The `videoUnavailable` **key name** still says video even though its copy no
  longer does. Renaming a catalog key touches three files and the i18n ratchet
  for no user-visible gain, so it is left as debt and noted here so the next
  reader does not think the copy drifted.
