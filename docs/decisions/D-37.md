# D-37. Discount codes are the single reward primitive for referrals; teacher-funded, qualify-on-settled, no credit ledger

**What changed.** Shipped Phase 2 of student acquisition
(`the referrals design`) in two slices on one primitive.

Slice 2a — a teacher-scoped **discount-code primitive**: `discount_codes` +
`discount_redemptions` tables (owner-only RLS), a teacher dashboard at
`/dashboard/discounts` (percent or fixed MXN, optional total cap, per-student
limit, expiry), an optional code field on the public checkout, and a
`discount_applied` event. The discount is applied in the checkout core
(`lib/payments/start-checkout.ts`) and recorded as a `DiscountRedemption` in the
same transaction as the pending Package + Payment.

Slice 2b — **student→student referrals** on top: `ReferralProgram` (per teacher,
off by default), `ReferralCode` (per student), `Referral` (attribution), plus
`DiscountCode.reservedForStudentId`. A friend's code applies the teacher's
referred-side discount at checkout and records a `Referral`; when that payment
settles, the `grant-referral-reward` Inngest function (on `payment.paid`) mints
the referrer a **reserved single-use** code and emails it. Refunds/lost-disputes
void an unredeemed reward (`voidReferralRewardForPayment`). Self-referral is
blocked by identity + email. Teacher config `/dashboard/referrals`; student share
surface in the portal; `?ref=` prefills the checkout; events
`referral_attributed/qualified/rewarded`.

**Why it likely changed.** Phase 2's referral loop needs a way to _grant value_,
and the app had none (checkout charged the catalog price as-is). Resolved design
(D-24 strategy): **one primitive — discount codes — for both sides, no credit
ledger**. Three deliberate choices:

- **Teacher-funded.** A discount is just a lower charge → lower settled net, out
  of the teacher's margin. No platform subsidy, no separate money to move.
- **Composes last in the price stack.** After the catalog price, the Wise/Stripe
  split (`priceForMethod`), and the grandfathered
  `TeacherStudent.customPriceCentavos`, clamped to ≥ 0.
- **Package-status accounting, minimal clawback.** A redemption/attribution
  counts toward limits only while its package is `pending`/`active`, so a refund
  (→ `refunded`) or superseded checkout (→ `expired`) releases the use and
  reverses the referred discount for free; only the minted _referrer reward_ code
  needs an explicit void on refund.

**What was affected.** `apps/web/prisma/schema.prisma` + migrations
`20260625800000_discount_codes` and `20260625900000_referrals`;
`src/lib/discounts/`, `src/lib/referrals/`; `src/lib/payments/start-checkout.ts`
(apply + record); `src/lib/payments/webhook-handler.ts` + `src/app/actions/refund.ts`
(reward clawback); `src/lib/inngest/functions/grant-referral-reward.ts`;
`packages/shared/src/validators.ts` (discountCode on both checkout schemas);
the `b/[slug]/buy` checkout form/flow (code input + `?ref=`); teacher dashboards
`/dashboard/{discounts,referrals}`; the student portal share surface;
`src/lib/analytics/posthog.ts`; `packages/shared/src/nav.ts` (+ web routes).
Free on every tier (D-24).

**Unresolved risks.** The redemption limit is validated just before the checkout
transaction, so a burst of concurrent checkouts could exceed `maxRedemptions` by
a hair (bounded by the per-IP/per-buyer rate limits; acceptable at MVP). An
abandoned Stripe checkout holds its slot until superseded/expired. A referrer
reward already redeemed before a refund is not clawed back (teacher bears it).
Concurrent `payment.paid` deliveries are guarded so only one reward is minted.
Slice 2c (a credit ledger + teacher→teacher) stays deferred.
