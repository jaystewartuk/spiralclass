# D-49. Provider-neutral DB provisioning & region-migration strategy: codify the three layers (provision · schema · data) so "deploy Postgres in any region and move the data" is a parameterized pipeline, not a one-way door

> **Executed by [D-70](./D-70.md) / [D-89](./D-89.md).** The three layers below
> were built and left dormant against a residency trigger that never fired.
> What actually exercised them was a provider change: the schema-portability
> discipline is what made the Supabase → Neon move a runbook rather than a
> rewrite, and layer 3's clone tooling ran for real on the production data.

**What changed.** We committed to a **strategy** (not yet an implementation) for
how SpiralClass provisions databases and moves data between regions, so that the
residency moves D-48 anticipates are _quick, reproducible, and reversible_. The
core decision: **the optimum is not a provider — it is decoupling three layers
so the provider becomes a swappable variable.** Pick a provider for cost/ops in
each region; keep the switching cost near zero so no single choice is a bet.

This is the **"how"** to D-48's **"whether/when."** D-48 records the residency
_stance_ and the trigger that forces an EU region; D-49 records the _mechanism_
that makes acting on that trigger a Tuesday rather than a project.

**The three-layer model.** The reason a Supabase project created in the
dashboard is a one-way door (D-48) is that **provisioning isn't codified** — it
is a click, so it can't be re-run, versioned, or re-pointed at a new region.
Codify that and everything downstream becomes a parameterized pipeline. Three
layers, each independently reproducible:

1. **Provision** — "a Postgres exists in region X." Tool: **OpenTofu**
   (the open-source, Terraform-compatible IaC standard), state stored in an
   **R2 bucket** (we already run R2 — no new vendor). A project's region +
   settings become code (`region = var.region`), so standing up EU is
   `tofu apply -var region=eu-west-1` — a reviewable diff, not an
   un-undoable click. **This is the keystone and is worth doing before any
   second region exists.**
2. **Schema** — "its structure is identical everywhere." Tool: the existing
   **Prisma `migrate deploy`** (D-18), with the runner **region-parameterized**
   (promote loops over a region list of connection strings). Discipline:
   keep the schema **vendor-neutral** — plain Postgres, no Supabase-only
   extensions in the hot path — which is already the trajectory of
   [D-40](./D-40.md) (better-auth on owned tables) and [D-44](./D-44.md)
   (dropped Supabase Realtime for HTTP polling to keep the DB portable). That
   neutrality is exactly what lets the same migrations run unchanged on
   Supabase, Neon, RDS, or self-hosted Postgres.
3. **Data** — "get rows in / move them between regions." Tools:
   **Postgres-native logical tools only** — never a provider's proprietary
   migration service (AWS DMS et al. re-lock you). Two tiers:
   - **`pg_dump` / `pg_restore`** (logical snapshot) — the universal path
     between any two Postgres of compatible major version, any provider, any
     region. Needs a short freeze window; at our data scale it is minutes and
     stays optimal for one-time region moves for a long time. Scripted as a
     `db-clone-to-region.sh <source-url> <target-url>` so it is reproducible.
   - **Logical replication** (`CREATE PUBLICATION` / `SUBSCRIPTION`) — the
     **near-zero-downtime** cutover: seed the target from a copy, stream the
     delta, flip the app's region pointer, drop the publication. Works across
     providers/regions on any real Postgres. The tool for the day a residency
     cutover must not drop an in-flight booking.
   - **Rehearse it.** A reproducible deploy is only trustworthy if tested — a
     `verify` step that spins an ephemeral target, restores, runs a row-count +
     checksum diff, and tears down. **Branching** (Neon branches or Supabase
     branching) is genuinely useful _here_, for cheap migration rehearsal, even
     if prod lives elsewhere.

**Provider strategy (opinionated, reversible by construction).** Because layers
1–3 are provider-neutral, the provider choice is a config line, not a bet:

- **Supabase now, codified via the Terraform provider** — the pragmatic optimum
  for the near/medium term. Don't rip out what works; just make it reproducible.
  (Residency = separate projects, as expected; note Supabase has **no Mexico
  region** — MX users are served from a US region today.)
- **Neon as the leading long-term default for cheap multi-region silos.** Once
  auth is on better-auth (D-40), realtime is polling (D-44), and media is R2
  (already), Supabase is _"just Postgres + PITR"_ to us — at which point Neon is
  "just Postgres, but with **scale-to-zero**," which directly answers D-48's
  "an empty EU silo is pure cost" objection: a speculative region costs
  ~nothing at rest and wakes on first traffic. Not an urgent switch; the
  direction the lock-in-shedding already points.
- **Cloud-managed (RDS/Aurora, Cloud SQL)** only if an enterprise/regulatory
  demand forces it (max region coverage incl. MX, Aurora Global) — the "if we
  get big" tier, not the now tier.
- **Self-hosted Postgres** kept as a **capability, not the prod home.** Keep the
  tooling so no provider can hold us hostage, run it for dev/test on the free
  Oracle ARM box — but do **not** make multi-region prod PII depend
  on VMs a solo operator personally babysits. The standing rule is already that
  prod must never depend on a box being powered on; the same logic keeps prod
  data on a managed provider's backups/failover.

**Connection layer (downstream note).** Since we front the app with Cloudflare,
**Hyperdrive** (Cloudflare's Postgres pooler/accelerator) is the natural way to
give the app a fast, pooled connection to whichever regional Postgres it routes
to. That is the "serve multi-region" concern, downstream of this doc's
"provision + transfer" scope — flagged so it isn't rediscovered later.

**Why it likely changed.** "Which tool / which provider" is the wrong frame — it
treats a durable architecture question as a product pick. The durable answer is
that **reproducibility and portability come from the abstraction layers, never
from a provider**: let provider-specific anything leak into the schema or the
data-movement and you rebuild a one-way door; keep those two neutral and every
provider/region choice stays reversible. That reversibility _is_ the "plan for
all eventualities" hedge — it means we can shop per region on cost/ops without
ever being locked in. Codifying provisioning (layer 1) is also the specific act
that dissolves the D-48 one-way-door problem at its root.

**What was affected.** Strategy/docs only — **no code, no IaC, no infra created**
in this decision. It sets the direction; the build is deferred (see risks +
sequencing). Related decisions it leans on / extends: D-48 (residency stance —
the "whether/when"), D-40 & D-44 (the vendor-neutrality that makes it possible),
and the standing self-hosting posture (the Oracle box is a dev/test host, never
prod-critical).

**Unresolved risks.**

- **All three layers now built and dormant; none has been run against prod.**
  _Layer 1:_ the OpenTofu provisioning module exists (`infra/database/supabase/`,
  state in R2 — concern-keyed so a Neon module can sit beside it) and plans
  cleanly. The R2 state bucket (`agendaprofe-tofu-state`) now exists, the live
  project coordinates are known (prod ref `qtgtjxmbhewrsyfxphyk`, org
  `izbpzmrzqnrhtbuezakq`, `us-east-1`), and `import.sh` is ready — but the actual
  `tofu init` + `import` still **must be run where OpenTofu + the Supabase PAT +
  R2 keys live** (the codified state does not yet exist), so provisioning is
  wired-but-not-yet-adopted. _Layer 2:_ the migrate
  runner is region-parameterized (`apps/web/scripts/migrate-regions.ts` +
  `src/lib/migrations/regions.ts`) — `MIGRATE_REGIONS` (JSON list) fans a single
  `migrate deploy` across the fleet; unset, it falls back to the single
  `DATABASE_URL`/`DIRECT_URL`, so it is a **behavioral no-op until a second
  region exists**. _Layer 3:_ the data-movement tooling exists in
  `infra/database/scripts/` — `db-clone-to-region.sh` (pg_dump/pg_restore
  snapshot), `db-logical-replication.sh` (near-zero-downtime cutover, incl. the
  sequence-sync gotcha), `db-verify-clone.sh` (row-count + content-checksum
  parity) and `db-rehearse-clone.sh`, with the operator procedure in
  `infra/database/RUNBOOK.md`. These are inert operator scripts (they only act on
  the connection strings you hand them) — **the one-way door is now closed in
  mechanism, but no region move has been performed.** What remains is the live
  work when the D-48 trigger fires: wire creds, `tofu apply` the EU region,
  rehearse, and cut over.
- **Neutrality is a discipline, not a guarantee.** The whole strategy collapses
  if Supabase-specific SQL/extensions creep back into the hot path. Every Tier-2
  DB change must stay portable (holds the D-40/D-44 line); a single vendor-locked
  dependency re-forges the door.
- **IaC state holds secrets.** An OpenTofu state file in R2 contains connection
  details/keys — it must be access-scoped and never committed to git; treat the
  R2 state bucket as a secret store.
- **Supabase LatAm gap.** No Mexico region on Supabase means MX-resident data,
  if MX residency were ever required, would force a provider change for that
  region specifically — a live example of why the neutral layers matter.
- **Self-hosted temptation.** The cheapest-at-scale option is also the one that
  makes a solo operator the 24/7 DBA for payment + PII data. Keep it break-glass;
  do not let cost pressure quietly promote it to the prod home without revisiting
  this decision.
- **Provider migration is still real work.** "Reversible in principle" is not
  "free": a Supabase→Neon move still means re-provisioning, re-pointing every
  connection/secret, and a data transfer + rehearsal. The layers make it a known
  runbook, not a zero-cost flip.

**Sequencing.** Codify **layer 1 (OpenTofu provisioning) first** — it is
valuable pre-EU and is what actually removes the dashboard one-way door. Layers
2–3 (region-parameterized migrations + the data-movement scripts) land when the
D-48 trigger fires (first EU user with a genuine residency demand / DPA request /
adverse legal read), or sooner if convenient. Do **not** stand up a second
region's infra speculatively — the migration is cheap with zero data and
expensive after a cohort accumulates, so time the build to the trigger.

**Update (built ahead of the trigger, dormant).** All three layers' _mechanisms_
have now been built and committed — layer 1 (`infra/database/supabase/`), layer 2
(`apps/web/scripts/migrate-regions.ts` + `src/lib/migrations/regions.ts`), and
layer 3 (`infra/database/scripts/` + `infra/database/RUNBOOK.md`) — each
verified but inert (no creds wired, no region stood up, no data moved). This is
the "or sooner if convenient" path: the reproducible pipeline exists end-to-end
so that acting on the trigger is running a tested runbook, not writing one under
pressure. The **"do not stand up a second region speculatively"** rule still
holds — building the _tooling_ is free and reversible; provisioning _live_ EU
infra is the speculative cost to keep deferred until the trigger fires.
