# D-111. Package guest booking is "pick your first class" at checkout — not post-payment guest booking

**Status: Decided, not yet built.** The implementation is a separate board item
on the private board; this doc is the scope it must be built to.

**What changed.** Multi-class package purchases get the same pre-payment slot
selection single classes already have: the student picks **one** class — the
first — before paying, it rides through checkout as `Package.intendedStartUtc`,
and `auto-book-on-paid` turns it into a real booking when the payment confirms.
The remaining credits are booked from the student portal after sign-in, exactly
as they are today. Post-payment guest booking — letting a paid-but-sessionless
student book any or all of their classes without signing in — is **rejected**.

Concretely, the gate that changes is the `classCount === 1` test, in the two
places it is written:

| Site                                                                                      | Today                                                              | After                                  |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------- |
| [`lib/payments/start-checkout.ts:205`](../../apps/web/src/lib/payments/start-checkout.ts) | `template.classCount === 1 ? args.intendedStartUtc ?? null : null` | carry the chosen slot for any template |

and the UI gate that mirrors it — `selected.singleClass` in
[`b/[slug]/buy/purchase-flow.tsx:237,274`](../../apps/web/src/app/b/[slug]/buy/purchase-flow.tsx).

**The picker is required for a single class and optional for a package.** A
single class _is_ the reservation — `requireSlot` blocks the pay button with no
slot chosen, and that stays. A package is a credit balance that happens to open
with a first class; requiring a time there would add friction to the higher-value
purchase to solve a problem the student may not have yet ("I want the classes,
I'll figure out when later"). So multi-class renders the picker with a skip
affordance, and a package bought with no slot behaves exactly as it does
today — `intendedStartUtc` null, `auto-book-intended` returns `no-intent`, the
student books from the portal.

**Why not full guest booking.** The dead-end Alicia Moreno hit is real — after "I've
sent the payment" the result page says wait for confirmation, then sign in via
the emailed magic link
([`buy/result/page.tsx:173-178`](../../apps/web/src/app/b/[slug]/buy/result/page.tsx)
documents this as deliberate). But the reason it is a dead-end is the
[`middleware`](../../apps/web/src/middleware.ts) session-cookie gate, which
bounces every student path with no session. Opening booking to a sessionless
buyer means inventing a _third_ authorization state — neither anonymous nor
signed in, but "holds a token proving they paid for this package" — with its own
expiry, revocation, replay, and email-enumeration story, on the booking path, at
launch. First-class-only needs none of that: the slot is chosen while the student
is already an anonymous visitor on a public page, and the booking is performed
**server-side by the payment webhook**, which is authorized by the payment
landing, not by the student holding anything.

It is also the path that is already proven in production. `auto-book-on-paid`
runs today for every single-class Wise purchase — including the slow-rail case
the review names, where minutes or hours pass between the student paying and the
teacher confirming — and
[`lib/booking/auto-book-intended.ts`](../../apps/web/src/lib/booking/auto-book-intended.ts)
already carries the degradation that makes that safe: if the slot is taken or in
the past by the time payment clears, it does not refund or error, it leaves the
credit bookable and lets the student pick a new time. That behaviour is _more_
correct for a package than for a single class, because a package always has
remaining credits to fall back on anyway.

**What this does not do.** It does not shorten the path to booking classes 2..N —
those still require the magic link. The claim is only that the first class,
which is the one that decides whether the student ever comes back, no longer
depends on an email round-trip.

## Implementation notes for whoever builds it

- **`singleClass` and `classCount` are two columns, and only the application
  layer keeps them in sync.** The UI gates on the `singleClass` boolean; the
  server gates on `classCount === 1`. Both editors pin `classCount` to 1 when
  `singleClass` is toggled on
  ([web](<../../apps/web/src/app/(app)/onboarding/templates/templates-form.tsx#L118>)),
  and the schema comment at
  [`schema.prisma:1259`](../../apps/web/prisma/schema.prisma) says so explicitly —
  "Enforced at the application layer". Once the slot picker is no longer
  single-class-only, prefer gating on one concept in one place rather than
  widening both tests independently.
- **The auto-book idempotency guard is written for a 1-class package and must be
  re-derived.** `auto-book-intended.ts` returns `already-booked` when
  `classesUsed >= classesTotal`. For a 1-class package that is exact: after the
  first booking `1 >= 1`, so a re-delivered Stripe webhook no-ops. For a 4-class
  package `1 >= 4` is false, so a duplicate `payment.paid` re-enters the booking
  core. It does not double-book today — `bookPackageSlot` re-validates the slot
  and the second attempt lands on `slot-unavailable` — but that is the _slot
  collision_ saving it, not the idempotency check, and it will log a spurious
  warn every time. Make it explicit: clear `intendedStartUtc` once booked, or
  check for an existing booking at that start.
- [`lib/payments/reconcile-paid.ts:103`](../../apps/web/src/lib/payments/reconcile-paid.ts)
  (the Wise stranded-payment sweeper) filters on `classesUsed: 0`, which stays
  correct for a package whose first class has not been booked. No change needed,
  but re-read it before changing the guard above — the two interact.
- The "absent for package buys" comments on
  [`validators.ts:342,657`](../../packages/shared/src/validators.ts) and the
  module header of `auto-book-intended.ts` become wrong and should be updated in
  the same change.
- `SingleClassSlotPicker` already exists and is the component to reuse — its
  name becomes inaccurate, which is a fine rename to fold in.
- Result-page copy changes: with a slot chosen, "your first
  class is reserved for `<time>`, pending confirmation" replaces the generic
  wait-then-sign-in text.

**Unresolved risks.** The window between paying and confirming is
teacher-latency-bound on the Wise rail, and a popular teacher's slot can be
taken inside it — the student who "picked" a time can still lose it. That is the
existing single-class behaviour and it degrades safely, but it is now on the
higher-value purchase, so the pre-payment copy must not promise the slot is
_held_ (it is not — nothing reserves it until payment lands). Second: this leaves
two different post-purchase experiences to support at launch, since a package
bought without a slot still lands on the sign-in path. Third: nothing here
narrows the underlying complaint that a paid student cannot reach their own
classes without an email round-trip; if that resurfaces after launch for classes
2..N, the answer is a proper sessionless-but-authorized student path, which is
the option this decision defers rather than forecloses.
