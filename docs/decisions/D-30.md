# D-30. Teachers can sell individual classes the student pays for at reservation

**What changed.** Teachers can now offer an **individual class** (sold one at a
time) alongside multi-class packages, and the student **pays at the moment they
reserve a slot**. A single class is modelled as a `PackageTemplate` with the new
`single_class` flag and `class_count` pinned to 1 — it reuses the entire
existing checkout → payment → transfer → booking machinery rather than adding a
parallel product. The chosen slot rides through checkout on the new
`packages.intended_start_utc` column, and once payment lands (the existing
`payment.paid` Inngest event, fired by both the Stripe webhook and Wise
confirm) the new `auto-book-on-paid` function turns it into a real booking via
the shared `bookPackageSlot` core.

**Why it likely changed.** Until now the only sellable unit was a fixed package
bought up front, then drawn down slot-by-slot. Selling a single class with
pay-at-reservation is a common ask (trials, one-offs, irregular students) and
removes the "commit to N classes before you've met the teacher" barrier.

**What was affected.**

- Schema: `package_templates.single_class`, `packages.intended_start_utc`
  (migration `20260627020000_single_class_sales`).
- Validation: `packageTemplateSchema` (pins `class_count` to 1 when
  `single_class`) and `checkoutIntentSchema` / `portalCheckoutIntentSchema`
  (carry the intended slot) in `packages/shared/src/validators.ts`.
- Checkout core (`startCheckout`) carries the intended slot for a 1-class
  template and stores it on the pending package; the public and portal checkout
  entry points pass it through.
- Booking: `auto-book-intended.ts` + the `auto-book-on-paid` Inngest function.
- Teacher config: a "sell as an individual class" toggle in the templates form,
  which pins `class_count` to 1.
- Student flow: a slot picker before payment on the booking page (new public
  `…/teacher/[slug]/slots` endpoint).

**Unresolved risks.** A slow rail (Wise) can confirm hours later, by which time
the chosen slot may be taken or in the past. By design we do **not** refund or
error: the paid class stays a bookable 1-class credit and the student re-books
from their balance (they already get the `payment_received` notification). The
in-portal repurchase flow does not yet show a slot picker, so a single-class
repurchase there degrades to the same pay-then-book fallback rather than the
combined flow.
