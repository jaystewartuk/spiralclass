# D-205. A production deploy asks for one approval, on the database job

**Status.** Active. Narrows [D-157](./D-157.md) and [D-199](./D-199.md): the
required reviewer, and what approving means, are unchanged. Keeps
[D-177](./D-177.md)'s addendum (two jobs, each holding only its own
credentials) and [D-163](./D-163.md)'s addendum (values pushed, never fetched).

**What changed.** `deploy-production.yml`'s Cloud Run job reads its values from
a second GitHub environment, `production-app`, which has no reviewer and which
only the `production` branch may use. The database job stays on `production`,
behind the owner's approval. GitHub asks once per job on a reviewed
environment, so a deploy now asks once: approving the database job ships the
commit, and Cloud Run follows when the migrations finish.

**Why.** The first deploy promoted from a runner (v2026.10.26.1) asked twice,
and the second click guarded nothing. By the time GitHub offered it, the
Neon checkpoint had been taken and the migrations applied. The release decision
had already been made, and the only thing left for the second click to do was
stall: approve the first job, walk away, and production runs the previous
image against the new schema until someone comes back. That is safe only for as
long as every migration is additive, which is a property of each migration and
not something a click can check.

**What was considered and rejected.**

- **Keep two approvals.** Rejected for the reason above: a click after the
  irreversible step is a delay, not a checkpoint.
- **One job instead of two.** One environment, one click. Rejected: the split
  is a credential boundary as well as an ordering, and merging the jobs would
  put `DATABASE_URL` in front of the image build, the step that runs the most
  third-party code. D-177's addendum gave the reason, and nothing about it has
  changed.
- **Move the reviewer to the Cloud Run job, so the database job runs first
  unattended.** Rejected: migrations against live payment records then run with
  nobody having looked, which is the exact thing D-157's reviewer exists to
  prevent.
- **A bypass of the reviewer for one job.** GitHub has none per job, and admin
  bypass on the environment would also waive it for the database job.

**What it constrains.**

- **Every job on `production-app` must `needs: [database]`.** That edge is the
  whole reason no reviewer is safe there. A job on it without the edge would
  deploy production with nobody having approved anything.
  `apps/web/tests/config/local-gate.test.ts` refuses one.
- **`production-app` may be reached by the `production` branch only.** The
  branch is admin-only (D-157), so the environment is too.
  `scripts/ci/deploy-protection.mjs` checks this on every promote, and
  `scripts/setup-branch-protection.sh` applies it.
- **Each environment holds its own job's values and no others.**
  `infra/infisical/push-github-secrets.sh` pushes each name to the environment
  of the job that reads it, and reports a name an environment's job does not
  read as stale there. Its `--delete-stale` is how the Cloud Run values leave
  `production`.
- **A reviewer added to `production-app` is accepted, not refused.** It brings
  back the second click, which wastes time but endangers nothing.

**What was affected.** `.github/workflows/deploy-production.yml`,
`scripts/ci/deploy-protection.mjs` (and its `.d.mts`), `scripts/ci/promote.mjs`,
`scripts/setup-branch-protection.sh`, `infra/infisical/push-github-secrets.sh`,
`docs/development/workflow.md`, `docs/deployment/BRANCH_PROTECTION.md`,
`infra/infisical/README.md`, and the tests `production-access`,
`promote-on-green`, `local-gate` and `push-github-secrets` under
`apps/web/tests/config/`.

**Trade-offs accepted, and unresolved risks.**

- **The rollout has an order, and nothing enforces it.** `production-app` and
  its secrets must exist before the first deploy that reads them. Out of order,
  promote refuses (the environment is missing) or the Cloud Run job's preflight
  refuses (its values are missing) — fail-closed both ways. But the second one
  fails _after_ the database job migrated, so the previous image serves the new
  schema until the values arrive and the job is re-run.
- **The approval now ships both halves.** Whatever is decided at the click is
  decided for the image too. That was already true in practice; it is now true
  in the mechanism.
- **A run approved and then left alone completes.** Previously, the second
  click doubled as a pause. Nothing replaces it. A deploy that must not finish
  is cancelled in the Actions tab, and per the workflow's own warning, a
  cancelled run can leave the migrations applied with no image deployed
  against them.
