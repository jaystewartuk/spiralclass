# D-76. Maintenance mode: one env flag walls off the app

**What changed.** Both apps gained a **planned-maintenance switch** driven by a
single env var, `MAINTENANCE_MODE` (`1`/`true`/`on`). When it's set:

- **Web** — `updateSession` (`apps/web/src/lib/auth/middleware.ts`)
  short-circuits _before_ the auth gate. Page requests are `rewrite`-n to a
  localized `/maintenance` wall with HTTP **503 + `Retry-After`**; non-allowlisted
  API requests get a **503 JSON** (`{ ok:false, reason:"maintenance" }`). A small
  allowlist stays reachable: `/api/health` (Fly health check + monitors must stay
  200), `/api/csp-report`, `/monitoring`, and the wall page itself.
- **Operator bypass** — `?maintenance_bypass=<MAINTENANCE_BYPASS_TOKEN>` sets a
  cookie the web middleware honors, so the operator browses the real site to
  verify the fix before flipping the flag off. Bypass is disabled when no token
  is configured.
- Optional `MAINTENANCE_MESSAGE` / `MAINTENANCE_UNTIL` env vars surface custom
  copy / an ETA on both walls.

Copy lives in the shared catalog (`maintenance.*`, `packages/shared/src/i18n`).
The operator runbook is in `docs/deployment/RELEASE_AND_STAGING.md` (§ Maintenance
windows).

**Why it likely changed.** The site is in production and there was **no way to
take it offline** for risky maintenance (a destructive migration, an infra
cutover, the pending D-58/D-70 credential/DB cutovers) — the operator had to
hope nobody hit a half-migrated state. This reuses the exact shape of the
existing force-update gate (env-overridable floor → public config endpoint →
client-polled blocking wall), so it's a familiar pattern, not new
infrastructure.

**Why an env var, not a DB row or PostHog flag.** The primary use case _is_
database maintenance — a flag you can't read while the DB is down is
self-defeating, which rules out a DB-backed toggle. PostHog flags load async and
fail-closed to `false` (the app would read a flag-fetch failure as "not in
maintenance"), making them a weak sole gate. An env var reads from `process.env`
in Edge middleware with no dependency on the DB or the Zod env schema, matching
the minimum-supported-version floor (D-42) and the `flagEnabled()` convention.

**What was affected.**
`apps/web/src/lib/maintenance.ts` (new), `apps/web/src/lib/auth/middleware.ts`,
`apps/web/src/app/maintenance/` (new page + retry button).
`packages/shared/src/i18n/catalog.ts`. Tests: `middleware-session.test.ts`
and i18n completeness (shared).

The gate touches middleware, a **Tier 2** path — the _first_
ship goes through a PR and the promote gate. **After it ships, entering/exiting a
window is an env flip only, no deploy** (Vercel needs a redeploy of the current
commit to apply an env change; Fly hot-applies on `fly secrets set`).

**Unresolved risks.**

- **Vercel env changes aren't instant** — flipping `MAINTENANCE_MODE` in
  production requires redeploying the current commit. Acceptable for _planned_
  windows (the operator controls timing); not a fast panic button. A future
  instant path (Edge Config / PostHog secondary trigger) is deliberately out of
  scope here.
- **Set in three places** — Vercel dashboard (production) + `fly.production.toml`
  and `fly.preview.toml` `[env]` (or `fly secrets`). Forgetting one leaves that
  environment live; the runbook checklist is the mitigation, not the platform.
- **Bypass token is a shared secret in a cookie** — httpOnly, operator-set,
  8-hour cookie; fine for a solo operator, not a multi-user RBAC bypass.
- **A redirect after a query-param bypass drops the just-set cookie** (the
  redirect is a different response object) — the operator re-appends the param or
  bypasses from a public path first. Minor.
