# D-163. Infisical is the only home for a deploy value, and the runner authenticates to it with OIDC

**What changed.** `.github/workflows/deploy-production.yml` no longer reads a
single GitHub secret. It declares `id-token: write`, fetches every value it
deploys with from Infisical's `production` environment as a machine identity
authenticated by a GitHub-signed OIDC token, and passes them to
`scripts/fly-deploy.sh` exactly as before. The `config/env/*.local.env`
overlays are deleted from the laptop's path in the same move.

This revisits [D-157](./D-157.md) on the condition D-157 itself named. Its
"what is deliberately NOT done" declined an Infisical machine identity, and
said why, and said what would change its mind:

> It does not apply here: the six `__LOCAL__` **build-time** values in
> `config/env/<env>.build.env` have no home in Infisical, so they must come
> from GitHub environment secrets regardless — and adding Infisical for only
> the database URLs would create the second source rather than remove it. …
> **If those six values ever move into Infisical, the machine identity becomes
> the right answer and this should be revisited.**

They have moved. This is that revisit.

## What forced it

On 2026-09-04 the sanitisation ahead of publication turned six committed
`NEXT_PUBLIC_*` values into `__LOCAL__` and put the real ones in
`config/env/production.build.local.env`, gitignored. That was correct about
git and wrong about where they landed, and `infra/infisical/run.sh`'s header
had already written the argument against it, about a different set of values:

> …required each developer to keep a private, uncommitted file of production
> and preview database URLs on disk. Two things were wrong with that and
> neither is hypothetical: **the file is the copy nobody rotates** … **it
> silently diverges**.

`run.sh` exists to abolish that pattern. The sanitisation reintroduced it four
days before the repository went public, and nothing noticed, because a
gitignored file is invisible to exactly the review that was running.

⚠️ **The state this replaces was not "working but untidy".** The `production`
environment held **zero** secrets. A push to `production` would have cut a Neon
checkpoint and then died on an Infisical CLI a runner has no login for
(`#1071` made that a
40-second refusal instead, and is what this builds on).

## Why OIDC and not the two alternatives

Three ways to get eleven values onto a runner. The question is how many copies
of the truth exist afterwards.

|                                                                 | Copies                      | Deploy survives Infisical being down | Visible in the repository        |
| --------------------------------------------------------------- | --------------------------- | ------------------------------------ | -------------------------------- |
| A `push-github-secrets.sh`, matching `push-fly-secrets.sh`      | 2, reconciled by hand       | Yes                                  | Yes                              |
| Infisical's GitHub Secret Sync, at Repository-Environment scope | 2, reconciled automatically | Yes                                  | **No** — dashboard configuration |
| **OIDC + `Infisical/secrets-action`**                           | **1**                       | No                                   | Yes                              |

The script was rejected first and for its own reason: it is a **manual** sync,
so it carries the drift of the sync option with none of the automation. The
evidence is in the repository — `infra/infisical/push-fly-secrets.sh` still
carries **"UNVERIFIED IN THIS SESSION"** in its header, written when it was
added, which is what a hand-run sync script's lifecycle actually looks like.

Between the remaining two, OIDC wins on the thing being optimised:

- **One home.** Not "no file on the laptop" — no second copy anywhere. That is
  the property the operator asked for and the only option that delivers it.
- **No credential to store or rotate.** Universal Auth would have put a client
  secret in GitHub, which is the objection D-157 raised. OIDC has none: the
  runner mints a short-lived GitHub-signed token per run.
- **A boundary that is real rather than asserted.** D-157's header claimed
  production's Fly token and database URLs existed only inside the `production`
  environment. They did not — `FLY_API_TOKEN` and `NEON_API_KEY` were
  repository-wide, reachable by every workflow here. The OIDC subject claim
  carries `environment:production`, so the identity's trust policy can refuse a
  job that does not name the environment. The claim becomes enforced instead of
  documented.
- **Eleven fewer secrets.** The `production` environment needs two `vars` —
  `INFISICAL_IDENTITY_ID` and `INFISICAL_PROJECT_SLUG` — and nothing else. Both
  are identifiers rather than secrets; they stay out of git for
  [D-158](./D-158.md)'s reason, not a secrecy one.

## ⚠️ What this costs, stated plainly

**Every production deploy now depends on Infisical being reachable**, and this
repository has an incident of exactly that shape. `scripts/fly-deploy.sh`'s
header records it:

> This used to read the key from Infisical's `infra` environment on every
> production deploy. That coupling broke a deploy for real on 2026-08-31: the
> Neon API keys were deleted, the checkpoint fail-closed as designed, and
> `production` was left fast-forwarded with the app still on the previous
> release.

That comment then moved `NEON_API_KEY` **off** Infisical, to a machine-local
`neonctl auth` credential, on the ground that "since this laptop is the only
thing that deploys (D-129), a machine-local credential loses nothing that was
in use". **D-157 removed that premise** — the laptop is no longer the only
thing that deploys — and a runner has no machine-local credential to hold
instead. So the key has to live in a store, and the choice is Infisical or a
GitHub copy of it. This takes Infisical and accepts the coupling knowingly
rather than rediscovering it.

Three things make it tolerable and none of them make it free:

- It is not a **new** class of dependency. The laptop path has read
  `DATABASE_URL`/`DIRECT_URL` from Infisical on every deploy for months.
- The failure is fail-closed and legible: the preflight names what did not
  arrive, before the Neon checkpoint, having touched nothing.
- The recovery path does not go through Actions at all — export the values and
  run `scripts/fly-deploy.sh` by hand, which is what `--yes-i-understand-this-skips-the-promote-gate`
  is for.

**If that trade stops being acceptable, the reversal is the Secret Sync at
Repository-Environment scope**: same store, one automated copy, and no change
to any file here — the workflow would go back to reading `secrets.*`. It is
written down so it is a decision rather than a scramble.

## The preflight did not go away, and why

It changed job. It used to prove eight GitHub secrets were set; it now proves
the fetch actually delivered. That is not the same check and the new one is
harder to do without: **a machine identity that cannot read a path does not
error — it returns fewer secrets**, and the step reports success. Without the
preflight the first symptom would be `prisma migrate` running against a
`DATABASE_URL` that is the empty string.

## What is deliberately NOT done

- **The identity reads the `production` environment's whole tree** — `/` with
  `recursive: true` — rather than a narrowed path. This is not laziness, and
  the first version of this record got it wrong by assuming one path would do.
  The values are deliberately split: the database URLs live at `/` because that
  is where `scripts/fly-deploy.sh`'s own `infisical secrets get` reads them
  from, and the build values live under `/config`. A single non-recursive path
  can name only one of those, and **the half it misses does not error** — the
  fetch succeeds having returned fewer secrets. Consolidating onto one path
  would mean duplicating the database URLs or breaking the laptop's read of
  them, which is the thing this record exists to stop. The controls that do
  exist are the identity's own scope and the fact that every fetched value is
  `core.setSecret()`-masked before export, verified in the action's source at
  the pinned SHA. **Re-check that masking on a version bump**; it is the only
  thing standing between a live Stripe key and the log of a public repository.
- ~~**`NEON_PROJECT_ID` stays a GitHub variable.**~~ **Reversed 2026-09-10 —
  it is an environment secret.** Both reasons given here expired; the second
  addendum below is the argument.
- **`deploy-preview.yml` is untouched.** It is still suspended and its target is
  moving to the Oracle box ([D-150](./D-150.md)). It gets the same treatment
  when it comes back, not before.
- **`scripts/env-config.mjs` still supports an overlay file.** The files are
  gone and are not to come back, but the fallback is three lines and is the
  documented way to override one key for one build without editing a store.
  Deleting the mechanism as well would be tidying, and would take the
  single-key override with it.

## Addendum, same day — Infisical pushes the values in; the runner does not pull them

**What changed.** The OIDC machine identity is gone, hours after it merged.
`deploy-production.yml` reads twelve `production`-environment secrets again,
declares no `permissions:` block, and holds no `id-token: write`. Infisical is
still the single source of truth; it now **pushes** a copy into the environment,
the same direction `infra/infisical/push-fly-secrets.sh` already pushes the
app's runtime secrets into Fly.

**Everything above about where values live still stands.** The
`config/env/*.local.env` overlays are still gone and are still not to come
back; the laptop still reads through
`infra/infisical/run.sh production ./scripts/fly-deploy.sh …`. What reversed is
the direction of travel between Infisical and GitHub, and only that.

### Why: the fetch could not be narrowed, only the request

The record above argues that the identity reading the whole tree is acceptable
because "the controls that do exist are the identity's own scope". Restated as
a question — _what can a compromised npm dependency reach?_ — that argument
fails, and it fails in a way `secret-path` cannot fix:

> **`id-token: write` is granted per JOB, not per step.** GitHub puts
> `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` into the
> environment of every step in that job. `pnpm install --frozen-lockfile`
> executes the lifecycle scripts of the entire dependency tree, and the Docker
> build runs whatever the image says. Any of it could mint its own OIDC token,
> authenticate as the identity, and read **everything the identity may read** —
> regardless of how narrow this workflow's own `secret-path` was.

So narrowing the fetch bounded only the _accidental_ case, a dependency that
dumps `process.env`. The targeted case was unbounded, and the bound that
mattered was the identity's project role — which is `Viewer` across the whole
project, because custom roles are Enterprise-only on this plan. That put every
live secret in the project, the Stripe live key included, one compromised
transitive dependency away.

The two ways out were a second Infisical project holding only these twelve, or
pushing the values in. Pushing is **strictly simpler and no less safe**:

|                      | Blast radius                | Rotation    | Moving parts                                                        |
| -------------------- | --------------------------- | ----------- | ------------------------------------------------------------------- |
| OIDC, one project    | every secret in the project | central     | identity + trust policy                                             |
| OIDC, second project | 11                          | central     | identity + trust policy + second project + duplicated database URLs |
| **Pushed secrets**   | **11**                      | **central** | **a sync**                                                          |

**The rotation column is what makes this cheap**, and it is the column the
original record got wrong. Its argument against a copy was
`infra/infisical/run.sh`'s "the file is the copy nobody rotates" — but that is
about an _original_ sitting on a laptop, not a _derived_ copy that a sync
rewrites. Rotate in Infisical and the copy follows. The `.local.env` overlays
were originals; these are not.

### ⚠️ The mechanism: a script, and this is the third position on it

`infra/infisical/push-github-secrets.sh`, run by the operator. Both earlier
positions in this record — reject the script, then require the native GitHub
Secret Sync instead — were argued from **drift**: a manual sync is the one you
forget after a rotation, with
`infra/infisical/push-fly-secrets.sh`'s "UNVERIFIED IN THIS SESSION" header as
the evidence.

That argument was about the wrong thing. Drift is a property of how a script is
**written and referenced**, not of scripts as a category, and two things fix it
directly rather than by hoping:

- **The script verifies itself.** It re-reads what GitHub holds afterwards and
  fails on any name it meant to push and did not. It cannot detect a value that
  has gone STALE — no API returns a secret's value — which is precisely why
  re-running it belongs in the secrets-rotation runbook (since moved out of
  this repository) rather than in
  someone's memory, and it is named there.
- **It derives its list from the workflow**, parsing `${{ secrets.X }}` out of
  `deploy-production.yml`. A hand-kept list would have been the drift, and this
  has none.

Two things the native sync could not offer, which decide it:

- **It needs a standing GitHub credential** — an App install or a PAT held by
  Infisical, with write access to this repository's secrets. The script uses the
  operator's own `gh` session at the moment they run it and leaves nothing
  behind. Removing a standing credential is the same move this whole record is
  about.
- **A dashboard integration is invisible here.** A reader of this repository can
  see the script; nobody can see a sync configured inside an Infisical account.

⚠️ **It pushes only the values the workflow reads, and that constraint is
load-bearing.** An `infisical export | gh secret set` of everything would put
forty secrets in the deploy environment instead of twelve, which is the blast
radius this addendum exists to bound.

### What this costs

- **It is not zero-credential.** Infisical needs a GitHub credential to write
  the secrets. That is one managed credential in the vault rather than twelve
  values maintained by hand in GitHub, but the OIDC version genuinely had none.
- **Three source paths**, and the split is by CONSUMER rather than by how
  secret a value feels. `push-fly-secrets.sh` exports with no `--path` — `/`,
  not recursive — and pipes the result into `fly secrets import`, so **`/` is
  the only path Fly gets, and everything in it becomes an environment variable
  inside the running production app.** That makes the path a decision about
  exposure: `/` is what the app needs, `/config` is the build-time values D-85
  says must never be Fly secrets, and `/deploy` is this deploy's own
  credentials. ⚠️ `FLY_API_TOKEN`, `NEON_API_KEY` and `LIVEKIT_ORIGIN_IP` go in
  `/deploy` and **must not sit at `/`** — a Fly token that can deploy the app,
  living inside the app it deploys, is a privilege escalation waiting for one
  code-execution bug. An earlier revision of this record put them at `/`.
- The preflight is unchanged and is if anything more necessary: an absent
  GitHub secret interpolates to the **empty string**, silently, so a value the
  sync has not carried yet looks exactly like one that is set.

### What is kept from the reversed half

`apps/web/tests/config/local-gate.test.ts` gains an assertion that **no
workflow** grants `id-token: write` — not just the deploy. The gate and heavy
tiers run far more third-party code than the deploy does and have no business
holding a token-minting capability either. The guard is pointed at the
mechanism that failed rather than at the file it failed in.

## Second addendum, 2026-09-10 — `NEON_PROJECT_ID` is a secret

**What changed.** `deploy-production.yml` reads
`${{ secrets.NEON_PROJECT_ID }}` rather than `${{ vars.NEON_PROJECT_ID }}`.
The eleven become twelve, and the `production` environment now holds no `vars`
at all. **This reverses a bullet in "What is deliberately NOT done" above**,
and nothing else in this record moves.

### Both reasons that bullet gave had expired

> It is not a secret — it is in `infra/database/neon/README.md`

Not since the publication sweep, which replaced the value with *"see `neonctl
projects list`"*. The bullet argues from a premise the same week's work
removed.

> leaving it outside Infisical means the deploy can still say which Neon
> project it meant when Infisical is the broken thing

**This was written for the pull model and did not survive its own reversal.**
Under OIDC, Infisical being unreachable meant the value never arrived at the
runner, so keeping one value outside bought real legibility. Under the push
model in the addendum above, every value already sits in the GitHub
environment — Infisical being down removes none of them. The argument was left
standing next to the change that made it false.

### The repository had already decided this, four days earlier

The 2026-09-06 publication audit removed a hard-coded Neon project id from
`scripts/fly-deploy.sh` and gave `check-leaks.mjs` a pattern for the shape.
`apps/web/tests/config/neon-checkpoint-retention.test.ts` records why:

> an id is not a credential and it kept the laptop path zero-config — and it
> is **not free in a public repository**: it names the exact Neon project
> holding real student data, which is the reconnaissance surface D-158 exists
> to remove.

A `vars` entry is plaintext in a run log, and this repository's run logs are
world-readable. So the gate that scans the tree for this identifier was being
walked around by the deploy that prints it. **The audit's own reasoning applies
to a public run log exactly as it applies to a public file**; this record was
the one place still carrying the pre-audit position.

### The exposure is narrow, and it is on the failure path

No step prints the value on the happy path: `fly-deploy.sh` exports it,
`neon-checkpoint.sh` passes it as `--project-id`, and the one call that reads
the raw project API discards both streams. But two `neonctl` calls in
`neon-checkpoint.sh` redirect **stdout only** — the `branches list` capture and
the `branches create` — so on a Neon failure the CLI's own stderr reaches the
log, and that text carries the project it was called against. It is
third-party output whose format is not ours and can change on a version bump.

### What it costs

**A failing deploy prints `***` where the project id was** — in the log you are
reading to find out what happened, and on the same failure path as the leak.
The trade is whether that string is readable by the operator or by the
internet, and on a public repository that is not close. The branch names and
the app name in the same log already identify the deploy.

### What this is not

**Not a claim that the id is a credential.** `NEON_API_KEY` is what grants
access, and anyone holding it can enumerate projects anyway. This is defence in
depth against target selection and against an identifier used as weak proof of
ownership in a support channel — small, and one-directional.

### ⚠️ It must be in Infisical at `/deploy`, not `/`

`infra/infisical/push-github-secrets.sh` derives its list from the workflow, so
it picks the new name up with no edit — but it can only push a value Infisical
holds, and `/` is the path that becomes a Fly runtime secret inside the running
app. This value is used by the deploy alone. It goes to `/deploy`, beside
`FLY_API_TOKEN`, `NEON_API_KEY` and `LIVEKIT_ORIGIN_IP`, for the reason stated
in "What this costs" above.
