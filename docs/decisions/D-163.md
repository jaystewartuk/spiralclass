# D-163. Infisical holds every deploy value and pushes copies out; no CI job can read Infisical

Every value the production deploy needs lives in Infisical's `production`
environment and reaches the runner as a secret on the GitHub `production`
environment, copied there by the operator running
`infra/infisical/push-github-secrets.sh`; no workflow grants `id-token: write`,
and no CI job authenticates to Infisical. The app's runtime values are pushed to
Secret Manager the same way, by `infra/gcp/push-cloudrun-env.sh`. On the laptop,
only [`infra/infisical/infisical.sh`](../../infra/infisical/infisical.sh) runs the
Infisical CLI.

## Why

Two constraints pull against each other. A deploy value kept anywhere but the
vault is "the copy nobody rotates" and it diverges silently. But a runner that
can fetch from the vault hands that ability to every step of its job:
`id-token: write` is granted per job, so the token-minting variables reach
`pnpm install`, which runs the lifecycle scripts of the whole dependency tree,
and the Docker build. A pushed copy is derived (rotate in Infisical, re-push),
and a job holding twelve values cannot ask for a thirteenth.

## Options considered

- **Gitignored local overlays** (`config/env/*.local.env`) — an original on one
  disk, invisible to rotation and review.
- **OIDC machine identity and `Infisical/secrets-action`** — one copy and no
  stored credential, but any dependency could mint its own token and read
  everything the identity can. The identity's role was `Viewer` across the whole
  project, because custom roles are Enterprise-only on this plan, so the Stripe
  live key was one compromised transitive dependency away. Narrowing the
  workflow's `secret-path` bounds only the accidental case.
- **OIDC against a second Infisical project holding only the deploy values** —
  the same blast radius as pushing, with more moving parts and duplicated
  database URLs.
- **Infisical's native GitHub Secret Sync** — needs a standing credential held by
  Infisical with write access to this repository's secrets, and is configured in
  a dashboard nobody reading the repository can see.
- **Each script calling the CLI itself** — ten call sites in nine files had
  implemented four operations five different ways, and the safety lessons had
  not reached all of them.

## What it cost

- The sync is manual. The script verifies afterwards that every name it meant to
  push is listed, and reports names the workflow no longer reads (deleting them
  only with `--delete-stale`), but no API
  returns a secret's value, so it cannot detect a stale one. Re-running it is a
  step in the rotation runbook, which is kept outside this repository.
- Values live in two places, the vault and the derived copy.
- On a failing deploy, masked values print as `***`, including
  `NEON_PROJECT_ID`, in the log being read to find out what happened.

## What it constrains

- **No workflow holds `id-token: write`.** Guarded by `local-gate.test.ts`
  ("no workflow can mint a token for a secret store") and, at the Cloud Run job
  most likely to want an exception, by `production-targets.test.ts`. The same
  reasoning keeps the GCP deploy key's service account from ever holding
  `secretAccessor` (`infra/gcp/README.md`).
- **Push only what the workflow reads.** The script parses `${{ secrets.X }}`
  out of `deploy-production.yml`; it never exports the whole environment. Held by
  [`push-github-secrets.test.ts`](../../apps/web/tests/config/push-github-secrets.test.ts).
- **The path is an exposure decision.** `/` becomes environment variables in the
  running app; `/config` holds build-time values; `/deploy` holds the deploy's
  own credentials (`GCP_DEPLOY_KEY`, `NEON_API_KEY`, `NEON_PROJECT_ID`,
  `LIVEKIT_ORIGIN_IP` and the like). A credential that can deploy the app must
  never sit at `/`, inside the app it deploys.
- **`NEON_PROJECT_ID` is a secret, not a `vars` entry.** Run logs of a public
  repository are world-readable, and the id names the project holding real
  student data ([D-158](./D-158.md)).
- **Each deploy job proves its own set first.** An absent secret interpolates to
  the empty string silently, so the preflight is what stops `prisma migrate`
  running against an empty `DATABASE_URL`.
- **The overlays do not come back.** The laptop reads through
  `infra/infisical/run.sh production …`; `no-private-env-files.test.ts` holds the
  rule. `scripts/env-config.mjs` keeps its three-line single-key override.
- **One wrapper runs the CLI**, with four verbs (`infisical_secrets`,
  `infisical_env`, `infisical_exec`, `infisical_put`). It verifies the project
  rather than inferring it, writes nothing to disk, sends values to stdout and
  progress to stderr, and treats an empty or short fetch as an error. Guarded by
  [`infisical-single-caller.test.ts`](../../apps/web/tests/config/infisical-single-caller.test.ts),
  which matches the CLI in command position only. `infisical secrets set` takes
  no project flag, so it is the one call the project guard cannot fully cover,
  and the wrapper says so. `INFISICAL_SKIP_PROJECT_CHECK=1` bypasses the guard
  when the guard itself is wrong.

## How we got here

- **2026-08-31.** A deploy that fetched `NEON_API_KEY` from Infisical failed
  closed at the checkpoint when the keys were deleted, leaving `production`
  fast-forwarded and the app on the previous release. The laptop switched to
  `neonctl auth`'s stored credential, on the premise that it was the only thing
  that deployed.
- **2026-09-04.** The pre-publication sweep moved six `NEXT_PUBLIC_*` values into
  a gitignored overlay, the pattern `run.sh` exists to abolish. The deploy moved
  to a runner ([D-157](./D-157.md)), ending the laptop-only premise, and the
  `production` environment held **zero** secrets. An OIDC identity shipped the
  same day and was reversed hours later for the per-job token reason above; the
  values were pushed in instead (eleven, later twelve).
- **Early September 2026.** The Infisical calls were consolidated behind one
  wrapper, the day before an Oracle box rebuild. Every verb was exercised against
  a stubbed CLI before any caller moved. The guard's first run flagged a file
  whose only match was the words `infisical init` in an error message, and the
  matcher was tightened rather than the file changed. One of the old readers had
  once leaked `OPENAI_API_KEY` into a terminal by falling through to a bare
  `export`.
- **2026-09-10.** `NEON_PROJECT_ID` became a secret. Both reasons for keeping it a
  variable had expired: the publication sweep removed it from the tree, and under
  the push model Infisical being down no longer removes any value from the
  runner.
- **2026-09-23 onward.** Cloud Run replaced Fly; the runtime push target became
  Secret Manager. On 2026-09-24 the runtime environment carried 73 names, four of
  which nothing in the app reads; names no source reads are now left out.
