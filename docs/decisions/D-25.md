# D-25. Superadmin is hardened: mandatory admin MFA, append-only audit, impersonation discipline

> **Narrowed by [D-40](./D-40.md) (2026-07-04).** Mandatory admin MFA stands.
> What changed underneath it: the WebAuthn/passkey addendum at the foot of this
> record went with Supabase Auth, the AAL2 session mechanism became an
> app-enforced `twoFactorEnabled` gate, and recovery became a documented
> database break-glass rather than a vendor dashboard.

**What changed.** The platform admin tier — and the superadmin at the top of
it, which can read every tenant and sign in as any teacher or student — is now
held to the strictest authentication bar on the platform, not the same bar as a
brand-new student.

- **MFA is mandatory for every admin tier, with no opt-out.** `requireAdmin()`
  (`apps/web/src/lib/admin.ts`) now requires the Supabase session to be AAL2 on
  every `/admin` page and every admin server action. A session with no enrolled
  factor, or one that has not stepped up this window, is redirected to
  `/admin/security` to register a hardware security key (FIDO2/WebAuthn — e.g. a
  YubiKey — or a platform passkey) or set up an authenticator app. This reuses
  the AAL2 primitives in `lib/auth/mfa.ts` (`sessionIsAal2`, `verifyStepUp`);
  unlike the teacher case (§11.2, optional except on a connected payout
  account), admins have no exemption.
- **The admin layout is a shell, the pages are the boundary.** `app/admin/layout.tsx`
  resolves the actor via the new `resolveAdminActor()` (no MFA) so the
  `/admin/security` step-up page it wraps stays reachable — gating it on AAL2
  would be a redirect loop. Every page/action enforces its own `requireAdmin()`.
  `tests/admin/gate-coverage.test.ts` fails the build if a `/admin` page or an
  `admin-*` action ever forgets the gate. The overview page (`app/admin/page.tsx`),
  which previously leaned entirely on the layout, now gates explicitly.
- **The env-allowlist bootstrap is observable and meant to be switched off.**
  `SUPERUSER_EMAILS` grants a synthetic, unattributed superadmin only while
  `admin_users` is empty. Taking that path now logs a warning and sets a Sentry
  tag. Operational rule: seed the first real `admin_users` row from `/admin/staff`,
  then **blank `SUPERUSER_EMAILS` in prod** so the fallback can never re-arm.
- **The audit log is append-only at the database.** Migration
  `20260625700000_overrides_append_only_and_nullable_teacher` adds triggers that
  block `UPDATE`/`DELETE` on `overrides`, so even an admin (or an app bug) cannot
  rewrite or erase history. `writeOverride()` also emits an out-of-band log copy
  so the trail survives a DB-credential holder. `overrides.teacher_id` is now
  nullable so platform-scoped actions (impersonating a standalone student) are
  recorded instead of silently skipped.
- **Impersonation discipline.** "Sign in as" now requires an operator-typed
  reason (kept on the audit row), refuses to target another _active_ admin
  (which would bypass their own MFA + attribution), and always writes the audit
  row.
- **The last superadmin cannot be removed.** Demoting or disabling the final
  active superadmin is refused, so the platform always has a way back in.

**Why it likely changed.** Authentication is passwordless magic-link via Supabase,
so the account's email inbox is effectively its credential and there was no second
factor on the one account that can act on everyone. A phished or intercepted admin
link granted full-platform access with the same strength as any student sign-in.
Mandatory MFA, an unforgeable audit trail, and impersonation that is always
attributed are the minimum bar for an all-access account.

**Unresolved risks.**

- **Account recovery.** A mandatory factor with no in-app bypass means an admin
  who loses their authenticator is locked out of `/admin`; recovery is via the
  Supabase dashboard (remove the factor). Deliberately no env "disable MFA" knob —
  that would just be the new backdoor.
- **Append-only is DB-level.** A holder of the Prisma/service-role DB credential
  could drop the trigger; the out-of-band log copy is the mitigation. A true
  external WORM sink is follow-on work.
- **Per-action freshness.** Every admin action requires session AAL2, but not a
  _fresh_ re-challenge per dangerous action. Shorter impersonation-link TTL and a
  shorter AAL2 window are Supabase Auth config changes, noted for later. IP
  allowlist for `/admin` remains §11.11.

**Addendum (security keys / WebAuthn).** MFA is no longer TOTP-only. Hardware
security keys (FIDO2/WebAuthn — e.g. a YubiKey) and platform passkeys are
supported via `supabase.auth.mfa.webauthn` (auth-js ≥ 2.105), wrapped
client-side in `lib/auth/webauthn-client.ts` with shared UI in
`components/auth/security-key-buttons.tsx`. The ceremony runs in the browser (it
needs `navigator.credentials`) against the browser Supabase client, but a
verified WebAuthn factor elevates the session to AAL2 exactly like TOTP — so the
admin gate (`sessionIsAal2`) and the teacher payout step-up are unchanged.
Admins register or step up at `/admin/security`; teachers manage keys at
`/settings/security`. `getMfaStatus()` now reports `totpFactors` and
`webauthnFactors` separately so the step-up UI offers the right ceremony. Two
notes: the relying-party id/origin default to the app's own domain, so a key
registered on the canonical host won't assert on a preview/other domain
(expected WebAuthn binding); and registering **two** keys (a primary plus a
backup) is the recommended hedge against the account-recovery risk above.
