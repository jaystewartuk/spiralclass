# D-129. Every GitHub Actions workflow is deleted; the laptop runs everything, by hand

> **Superseded in part by [D-157](./D-157.md) (2026-09-04).** Three workflows
> came back when the repository went public and the minutes became free — the
> arithmetic below was right and stopped applying to anything. What is kept, and
> is the reason this record still matters: the workflows _call_
> `scripts/ci/gate.mjs` and `scripts/fly-deploy.sh` and restate neither, because
> part of what was deleted here was a second definition of green that agreed
> with the first until the day it did not.

**What changed.** `.github/workflows/` and `.github/actions/` are **deleted** —
all fourteen workflows and all four composite actions. This repo has no
GitHub Actions at all.

- **The three crons are gone**: `nightly-checks.yml`, `synthetic.yml`,
  `backup-prod-db.yml`. [D-120](./D-120.md) kept them deliberately; this
  reverses that, and the reversal is the substance of this decision.
- **The dispatch-only fallbacks are gone**: `main-checks.yml`, `gate.yml`,
  `promote.yml`, `checks.yml`, `integration.yml`, `e2e.yml`, `quality.yml`,
  and `fly-deploy.yml`. D-120 said explicitly not
  to delete these because they cost nothing until dispatched; that is still
  true and is no longer the criterion.
- **The composite actions go with them**: `fly-build-deploy`, `inngest-sync`,
  `neon-checkpoint`, `prisma-migrate`. Every one had a local equivalent
  already, and `neon-checkpoint`'s duplicated retention default is now a
  single number in `infra/database/scripts/neon-checkpoint.sh`.
- **Dependabot loses its `github-actions` ecosystem** and keeps npm. Dependabot
  is not Actions and spends no minutes.
- **`scripts/local/` is new**: the three cron jobs as commands.
  `pnpm local backup`, `pnpm local synthetic`, `pnpm local sweep`,
  `pnpm local:status`. (⚠️ **`backup` was removed the same day** — see the
  addendum at the foot of this file. Neon backs production up.)
- **`pnpm promote` runs the production probes** after the deploy lands.
- **`pnpm gate` prints a maintenance nag** when one of the three has not
  succeeded within its budget.

Nothing about how the gate works changed. `.githooks/pre-push` still runs
`pnpm gate` and still posts the `local-gate` commit status — that is a REST API
call, not a workflow, so it survives having no Actions.

**Why it changed.** The operator's constraint, stated directly: no GitHub
Actions on private repos, and no scheduler on the laptop either. Everything is
run by hand from the one machine.

This is not the cost argument D-120 made, and it should not be read as its
continuation. D-120 measured its way to ~780 billable minutes a month against a
2,000-minute allowance and concluded the scheduled work did not have to move.
That arithmetic was right and is not what changed. What changed is that a
private repo's dependence on a metered third party is itself the thing being
removed — and the failure that made it concrete is on the record: the allowance
emptied mid-month, every private repo's workflows started failing, and the one
that mattered was the backup. **SpiralClass's production Postgres, holding live
payment records, went eleven days without one** while the public repos stayed
green and nothing said otherwise. A backup whose availability depends on how
many minutes the month's merges consumed is not a backup you can reason about.

**What was affected.** The three arguments D-120 used to keep the crons, and
what each one costs now:

- **"A monitor has to live somewhere the thing it watches doesn't."** Correct,
  and unrecoverable locally — a laptop cannot probe production while it is shut.
  What is recovered instead is the moment the probes are worth most:
  `pnpm promote` now runs `scripts/local/synthetic.sh` once production is
  serving the new code, and reports the result in its exit code. The
  regressions synthetic.yml existed for — a route that renders an error, a
  booking page with nothing purchasable, a checkout with no payment rail, all
  of which return 200 — are introduced at deploy time. A 12-hourly cron found
  them within hours of a deploy; this finds them within a minute of one. What
  is genuinely lost is detection of production breaking on its own, between
  deploys, with nobody looking. That is real, it is accepted, and UptimeRobot's
  `/api/health` probe remains the minute-cadence liveness signal underneath it.
- **"A backup that silently didn't run is indistinguishable from one that
  did."** This was the strongest of the three and it is the one this change
  actually engineers against, because the eleven-day gap is precisely that
  failure happening on Actions. Every run of every job now writes a receipt to
  `.gate/local-jobs.json`, keeping the last run and the last _successful_ run
  separately so a fortnight of red does not read as fresh. `pnpm gate` prints
  one line per overdue job — and the pre-push hook runs the gate on every push,
  so the report arrives at a moment the operator is provably at the keyboard,
  rather than in an inbox. The nag is a warning and never part of the verdict:
  a stale backup is not a reason to reject a commit, and a check that blocks
  unrelated work gets bypassed wholesale.
- **"A laptop schedule is one nobody owns."** Agreed, which is why there isn't
  one. No launchd agent, no crontab. These are commands with a nag attached.
  The honest description of the cadence is "weekly, when prompted", and the
  staleness budgets say so: seven days each.

Also affected:

- **There is no fallback for a dead laptop.** D-120 called the dispatch-only
  workflows "the only path that works when this machine doesn't". They were,
  and now there is no such path: no way to get a `local-gate` status onto a PR
  from a cloud session, no way to deploy from anywhere else, no runner-side
  copy of any gate suite. A cloud session's `pnpm gate --allow-dirty` still
  runs the checks and still says what it found; it just cannot post. That is
  the largest single cost here and it is accepted rather than mitigated.
- **The nightly sweep now tests your checkout, not `main`.** A scheduled
  workflow can only run on the default branch. `pnpm local sweep` runs where
  you are, which is a superset in the case that matters — a time bomb lives in
  committed test code — but a local edit can colour the result, so the sweep
  prints the SHA, the branch, whether it matches `origin/main`, and whether the
  tree is dirty before it starts.
- **The backup's five secrets move from repo secrets to Infisical**
  (`production` environment): `PROD_BACKUP_DB_URL`, `R2_BACKUP_BUCKET`,
  `R2_BACKUP_ENDPOINT`, `R2_BACKUP_ACCESS_KEY`, `R2_BACKUP_SECRET`, plus
  `NTFY_URL`/`NTFY_TOPIC` for alerting. `scripts/local/backup-prod-db.sh` reads
  the environment first and falls back to Infisical; it fails closed on any
  missing value, exactly as the workflow did. **Until those five are in
  Infisical, `pnpm local backup` cannot run** — that is an ops step, not a code
  one. (⚠️ Superseded by the addendum: there is no `pnpm local backup`, and the
  secrets were never set up because the job is not a practice.)
- **Failures alert on two channels**: ntfy to the phone (what the workflows
  used) and a macOS notification to the screen (where a hand-run task actually
  fails). Both fail open — alerting must never be what fails the task.
- **The guard tests inverted.** `apps/web/tests/config/local-gate.test.ts` used
  to assert the three schedules survived and that `scripts/local/` did not
  exist. It now asserts `.github/workflows` does not exist, that the three jobs
  do, that each leaves a receipt, and that the gate warns.
  `apps/web/tests/config/checks-path-filter.test.ts` was deleted with the
  `checks.yml` inert-diff skip it locked.
  `apps/web/tests/config/neon-checkpoint-retention.test.ts` were retargeted at
  the scripts they had been asserting through YAML.
- **Branch protection on `main` is unaffected**, and was never enforced
  server-side here: it is a paid feature on private repos on this plan. The
  `local-gate` status still gets posted; the no-direct-push rule is still
  convention.
- **Nothing about Fly's or Neon's own automation changed.** They do not run on
  GitHub-hosted runners.

**Unresolved risks.**

- **A week away from the machine is a week with no probe** (and, per the
  addendum below, no off-Neon dump ever). There
  is no mitigation for this inside the constraint. If it needs one, the shape
  is a small always-on box (the retired dev box was one) or a hosted probe — not a
  workflow.
- **The nag depends on being pushed to.** A fortnight of reading rather than
  writing is a fortnight of no gate runs and therefore no warning.
  `pnpm local:status` is the deliberate check; nothing forces it.
- ~~**`pnpm local backup` has never run on this machine at the time of
  writing.**~~ Superseded by the addendum below: there is no `pnpm local
backup`. The script is still unexercised on macOS, which now matters only if
  someone reaches for it by hand.
- **The probes chained into promote make a promote fail on a red probe**, after
  production is already live. That is intended — the exit code is the only part
  of a long log anyone reliably reads — but it means a flaky probe reads as a
  failed promote.

## Addendum, 2026-08-25 — the backup is Neon's; the hand-run dump is not a practice

**What changed.** The `backup` job is **removed from `scripts/local/jobs.mjs`**.
There is no `pnpm local backup`, and nothing nags about a dump ever again.
`scripts/local/backup-prod-db.sh` is **kept**, unregistered, as an on-demand
tool.

**Why.** The operator's call, hours after this decision merged: **Neon already
backs production up.** The recovery story for production is Neon's
point-in-time restore plus the pre-migration checkpoint branch
`scripts/fly-deploy.sh` takes before every production migration ([D-95](./D-95.md)),
and a hand-run pg_dump to Cloudflare R2 on top of that is not a routine worth
carrying.

**Why it leaves the registry rather than just going un-run.** This decision's
whole mechanism is a warning printed by `pnpm gate` when a job is overdue. That
warning only works while every line in it is a line the operator intends to act
on. A standing "backup last green never" against a decision already made would
train them to skim the banner — and the banner is the _only_ mechanism the
other two jobs have. Removing the job is what keeps the nag worth reading.

**Why the script is kept rather than deleted.** It produces the one thing Neon
cannot: a copy that lives outside Neon entirely. Take it by hand before a
migration risky enough to want that. Deleting it would mean rebuilding it on the
day that case arrives, and the case arrives at the worst possible moment by
construction.

**What this gives up, stated rather than discovered later.** The body of this
decision named two gaps the dump covered, and both are now accepted:

- **A Neon-account-level incident** — billing, suspension, a provider-side data
  loss — takes the backups with the database, because they are the same
  provider. Nothing in this repo produces an off-provider copy on a schedule
  any more.
- **A bad change noticed after the PITR window closes.** PITR is measured in
  hours-to-days on this plan and the checkpoint branches reach back five
  deploys, so "a bad migration shipped Monday, noticed the following week" has
  no restore point. The R2 dump's 14-day retention was what covered that.

Neither is a reason to reverse this; both are the reason it is written down. If
either becomes real, the fix is to run the script by hand — or to decide that a
scheduled off-provider copy needs a machine that is always on, which is the
same conclusion this decision's own unresolved risks reach about the probes.
