# D-26. Staging environment + gated promote-to-production (main no longer auto-deploys to prod)

**What changed.** `main` no longer deploys to production. It now deploys to a
dedicated **staging** environment (`preview.spiralclass.com`) backed by its own
Supabase project. Production is reached only by running the **Promote to
production** workflow (`.github/workflows/promote.yml`), which runs the hermetic
E2E suite once and then fast-forwards a `production` branch to the approved
commit; Vercel builds production from `production` (prod env + `prisma migrate
deploy`). This supersedes "every merge ships to prod" now that real students use
the system. It also retires the dormant Supabase-Branching preview path
(`preview-env.sh`, `PREVIEW_DEPLOYMENTS.md`, the `PREVIEW_DB_ENABLED` idea) in
favour of a real always-on staging environment.

**Why it likely changed.** With live students a bad merge can break booking or
payment instantly. Decoupling _merge_ from _deploy_ keeps trunk velocity (merge
freely to `main`/staging) while making each production change deliberate, tested
as a batch, and scheduled outside lesson hours. It also cuts cost: the full E2E
moved from per-PR to the promote gate (one run per release covers many merges);
PRs keep the fast `ci.yml` + `integration.yml` checks.

**Promote vs rebuild (the reconciliation).** Production is a **rebuild** on the
`production` branch, not a Vercel artifact-promote of the staging build. Next.js
inlines `NEXT_PUBLIC_*` (the Supabase URL/anon key) at build time, so promoting a
staging-built artifact would serve staging config to production users. Vercel
"promote" is therefore reserved for **rollback** — re-promoting a previous
_production_ deployment, which shares prod's build-time env and is safe.

**What was affected.**

- `apps/web/package.json` `build`: dropped the `preview-env.sh` shim; now runs
  `prisma migrate deploy` when `VERCEL_ENV=production` **or** `VERCEL_GIT_COMMIT_REF=main`
  (so staging migrates too). `turbo.json` build env: `POSTGRES_*` removed,
  `VERCEL_GIT_COMMIT_REF` added.
- `.github/workflows/e2e.yml`: now `workflow_call` + `workflow_dispatch` (the
  `pull_request` trigger is gone); `promote.yml` calls it as the release gate.
- New `apps/web/src/lib/flags.ts`: an env-based `flagEnabled("FLAG_…")` seam for
  dark-launching — merge to staging with a flag on, keep it off in Production.
- Deleted `apps/web/scripts/preview-env.sh` and `docs/ops/PREVIEW_DEPLOYMENTS.md`.
- Runbook: `docs/deployment/RELEASE_AND_STAGING.md`. Narrative: orientation 09.
- Builds on **D-18** (prod build still runs `migrate deploy`); does not revert it.

**Unresolved risks.** The Vercel Production-Branch switch and the staging Supabase
project are manual dashboard steps (see the runbook), done off lesson-hours; until
they're in place the promote workflow's fast-forward has no effect on a real prod.
The `production` branch must not have branch protection that blocks the Action's
fast-forward push (or a `PROMOTE_TOKEN` PAT is needed). Migrations remain
expand/contract — the promote E2E applies migrations to a fresh DB and so catches
a broken migration before it reaches prod, but destructive changes still need the
deliberate two-step.
