# D-170. The Codespaces path is deleted, not repaired

**Status.** Active. Reverses one sentence of [D-169](./D-169.md) and removes a
consumer [D-85](./D-85.md) named; both records stand as written.

**What changed.** `.devcontainer/` is deleted — the container definition, its
README, `post-create.sh` and `dev.sh` — along with `pnpm dev:cloud`, the
`allowedOrigins` branch in `next.config.ts` that existed only to satisfy
Codespaces' forwarded origin, and the four prose references that pointed at any
of it. There is one supported way to run this locally now: `pnpm setup` and
`pnpm dev`.

**Why.** The maintainer used it once and will not use it again. That is the
whole reason and it is sufficient: a development path with no users is not a
feature, it is four files and a code branch that every future reader has to
work out the status of.

It was also broken, which is how the question came up. The image was
`typescript-node:1-22-bookworm`, and `engines.node` has been `>=24.15.0` since
the Dockerfile moved to Node 24 — so `pnpm install`, the first command a
Codespace runs, could not have succeeded. The comment above the image said "Node
22 to match every CI job (checks/integration/e2e all pin node 22)", which no job
had done since. Nothing failed, because nothing ran it.

Two things could have been done with that. Repair it — retag the image, retest
the secrets prompts, keep it working — or delete it. Repair costs the work plus
the standing obligation to keep a path green that nobody walks — the expensive
kind: dead machinery that reads as load-bearing because a guard or a comment
still vouches for it.

**What was considered and rejected.**

- **Keep it and fix the image tag.** Rejected on use: one session, ended, not
  returning. A working path nobody takes is indistinguishable from a broken one
  until somebody takes it, and then it is worse, because it was advertised.
- **Keep it, unrepaired, with a note saying it is unsupported.** This is the
  shape [D-164](./D-164.md) already rejected for runbooks — dead documentation
  is deleted rather than banner-ed, because a banner is a thing a reader must
  find before the content misleads them.
- **Keep only `next.config.ts`'s `allowedOrigins` branch**, on the argument that
  it is five lines and might serve a future tunnelled origin. Rejected: it reads
  `CODESPACES`, `CODESPACE_NAME` and `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN`,
  three variables nothing in this repository sets. A future tunnel would need
  its own origin anyway, and would be a change of one line either way.

**What it constrains.** Nothing forbids a cloud development path later. What it
forbids is a _dormant_ one: if this comes back it comes back working, verified
against the Node major in the Dockerfile, and named in
`docs/development/setup.md` — or it does not come back.

⚠️ **There is deliberately no guard asserting `.devcontainer/` stays gone.**
There is a worked example in this tree: a guard written to hold a decommission
in place outlived the premise it was written for and made 220 unreachable
routes look load-bearing for a month. Nobody is going to recreate this by habit; the
one thing that would recreate it is somebody deciding to, which is allowed.

**What was affected.** `.devcontainer/**` (deleted), `package.json`
(`dev:cloud`), `apps/web/next.config.ts` (`experimental.serverActions
.allowedOrigins`), `docs/development/setup.md` ("Cloud development"),
`config/env/README.md` (two references), `apps/web/.env.example`,
`apps/web/tests/scripts/env-config.test.ts`, `infra/infisical/README.md`,
`.gitignore`. D-85 and D-169 name `.devcontainer/dev.sh` and are **not** edited
— they describe a tree that existed when they were written, which is what a
decision log is for.

**Trade-offs accepted, and unresolved risks.**

- **The zero-install path is gone.** Anyone evaluating this repository now needs
  Node, pnpm and Docker locally. That is a real cost and it is accepted: the
  path that was there did not work, so nothing was lost that anybody had.
- **`.nvmrc` moved from 24 to 26 in the same change**, which is a separate
  correction that happened to be found by the same question. If `nvm use` now
  asks you to install a major you do not have, that is why; `engines.node` is
  still a floor at 24.15.0 and a 24 shell still works.
- **Nothing checks that the deleted references stayed deleted.** The doc-path
  and doc-link guards would catch a `docs/…` pointer at a missing file, but
  `.devcontainer/dev.sh` is not under `docs/`, so the two decision records that
  name it are unguarded by construction — correctly, since they are history.
