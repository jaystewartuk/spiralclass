# D-89. Production cutover executed — production now runs on Fly + Neon; Vercel/Supabase kept dormant as rollback

**What changed.** The production cutover planned in D-70 and sequenced in
`docs/ops/PRODUCTION_CUTOVER.md` has been **executed**. Production no longer
runs on Vercel + Supabase — it runs on the same **Fly + Neon** stack preview
already used:

|                               | Before (D-26 era)            | Now (this decision)                                                                               |
| ----------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------- |
| **Production app**            | Vercel (`production` branch) | Fly app `agendaprofe`                                                                             |
| **Production DB**             | Supabase Postgres            | Neon (production project)                                                                         |
| **Preview app**               | Fly `agendaprofe`            | Fly `agendaprofe-preview`                                                                         |
| **Preview DB**                | —                            | Neon (preview project, disposable/reseeded)                                                       |
| **`spiralclass.com`**         | Vercel                       | Fly `agendaprofe`                                                                                 |
| **`preview.spiralclass.com`** | Fly `agendaprofe`            | Fly `agendaprofe-preview`                                                                         |
| **Vercel / Supabase**         | Serve production             | **Dormant** — kept configured as the rollback path through the soak period, not deleted (Phase 5) |

Deploys are now entirely GitHub-Actions-driven via `fly-deploy.yml` (no Vercel
native git integration, no Fly native GitHub integration): `production` is
fast-forwarded by `promote.yml` after the full gate, and the push auto-deploys
the `agendaprofe` app; preview is a manual dispatch after a `main` change.
Both the preview and production deploy jobs now apply their Neon migrations
through the **one** `./.github/actions/prisma-migrate` composite action before
the deploy — production's inline copy of that logic was folded into the shared
action as part of this decision, closing the D-72 loose end where "does this
environment get its migrations?" depended on hand-keeping two copies in step.

**Why it likely changed.** D-70 committed the direction and built/tested the
hard parts in isolation (the Supabase-free schema squash, the Realtime→polling
move, the runbook) but explicitly left the live cutover — Neon prod provisioning,
the real data clone, the DNS flip — ahead of it, gated on the runbook's
checkpoints and the D-58 Stripe-live-keys prerequisite. Those steps have since
been carried out against the real infrastructure, so the repo's "current policy"
(D-26's promote-gated **Vercel** model, and the preview-only Fly experiment's
"production is untouched — still Vercel") was stale and actively misleading for anyone touching deploys. This
decision records the executed reality so the docs match production.

**What was affected.**

- `.github/workflows/fly-deploy.yml` — production `migrate` step unified onto
  `./.github/actions/prisma-migrate` (identical behavior: `migrate-regions.ts`,
  fail-closed on missing `PROD_DATABASE_URL`/`PROD_DIRECT_URL`); the job-level
  `pnpm`/`setup-node` + inline install/migrate it duplicated are gone. Production
  now mirrors preview structurally.
- `.github/actions/prisma-migrate/action.yml` — header updated: both environments
  call it now; the loose end is closed.
- `CLAUDE.md` — the development-workflow bullet ("Production is untouched —
  still Vercel") and the rollback line ("promote the last good Vercel deployment")
  corrected to the Fly + Neon reality.
- `docs/ops/PRODUCTION_CUTOVER.md`, `docs/decisions/D-70.md` —
  status moved from "reviewable plan / not yet executed" to "executed; see D-89."
- No application code or `SUPABASE_*` env handling was removed — `env.ts` already
  treats those as optional (the deliberate Supabase-Storage rollback path). That
  removal is Phase 5 decommission work, gated on the items below.

## Phase 5 — decommission (EXECUTED after the soak)

Vercel and Supabase are now fully decommissioned — the Vercel project and
Supabase project are torn down, and the dead code coupling was removed:

- **Supabase code gone.** The `@supabase/supabase-js` dependency, the
  `lib/supabase/service.ts` service-role client, the `createSupabaseProvider`
  Storage rollback path (`getStorageProvider()` was already R2-only), and both
  the `SUPABASE_*` server-schema and `NEXT_PUBLIC_SUPABASE_*` client-schema env
  vars are removed — plus the `NEXT_PUBLIC_SUPABASE_*` build args from
  `preview.build.env` and the Dockerfile. Storage is unconditionally R2.
- **Vercel-runtime code gone.** No more `VERCEL_ENV` branches — prod-vs-preview
  is decided by `APP_URL` in `isProductionDeployment()` / `sentryEnvironment()` /
  the CSP; the Vercel Live toolbar CSP hosts and `VERCEL_GIT_COMMIT_SHA`
  fallbacks are removed. Two live regressions the cutover had silently
  introduced (both keyed off the never-set-on-Fly `VERCEL_ENV`) are fixed: the
  preview `X-Robots-Tag: noindex` header now keys off a new
  `NEXT_PUBLIC_DEPLOY_ENV` build arg, and the redundant build-time region
  migration was dropped (migrations run in `fly-deploy.yml`).
- **Seed prod-safety guard is env-driven.** `assertNotProductionTarget` keyed
  off the old hardcoded Supabase project ref (which matched nothing on Neon);
  it now refuses when `DATABASE_URL`/`DIRECT_URL` resolve to a host in
  `PROD_DB_HOSTS` (set in the prod/CI env), a no-op when that's unset.
- **One-off scripts removed** — `scripts/migrate-storage-to-r2.ts` and
  `scripts/sync-preview/` (both dead post-cutover).

**Still open (follow-up, not a blocker).**

- **Vercel Skew Protection has no Fly equivalent** — only the client-side
  `lib/server-action-recovery.ts` fallback exists, so a user active across a
  production deploy is likelier to hit a stale server-action bounce. Known,
  accepted behavior change (D-70).
- **The Vercel-era ops docs still need a sweep** — `RELEASE_AND_STAGING.md`,
  `docs/orientation/09-infrastructure-and-deployment.md`, `FLY_SPIKE.md`, and the
  older decision docs describe the pre-cutover topology in places. They are
  historical context or lower-traffic runbooks; correcting them is a follow-up,
  not a blocker, and the current-policy surfaces (CLAUDE.md, this decision, the
  runbook status) are corrected.
