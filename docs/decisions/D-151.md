# D-151. A testimonial the teacher cannot write: verified student submissions

**What changed.** `testimonials` grows three columns — `source`
(`teacher_curated` | `student_submitted`), `student_id` and `verified_at` —
and the public booking page badges the second kind with **"Verified student ·
N classes with her"**, a count read from completed bookings at render time.
A signed-in student with at least one completed class writes one from
`/my-classes/teachers/<id>`; the teacher can hide or delete it and **cannot
write or edit one**. Every existing row becomes `teacher_curated`, which is
what it already was, and renders exactly as before.

The guarantee is enforced twice. Every teacher-side write in
`lib/testimonials/store.ts` filters on `source: "teacher_curated"`, so an edit
aimed at a verified row matches nothing and returns not-found — on the web
form and on every other write path alike. Underneath that, a CHECK constraint ties
the three columns together:

```sql
("source" = 'teacher_curated' AND "student_id" IS NULL AND "verified_at" IS NULL)
OR
("source" = 'student_submitted' AND "student_id" IS NOT NULL AND "verified_at" IS NOT NULL)
```

`verified_at` is therefore not a flag the app sets when it believes a row is
genuine; it is unwritable without the student row the claim is about. One
missed filter — a future bulk import, a route that forgets a column —
cannot mint a badge.

**Why it likely changed.** The table's own schema comment said the omission was
deliberate: student reviews _"need volume + moderation to be credible"_,
deferred for the same reason as the referral engine. That is a sound argument
against **ratings** and it was applied to the wrong thing. One testimonial the
platform can vouch for beats one it cannot at any n, and the moderation burden
**inverts** rather than growing with scale: a curated quote asks the reader to
trust the teacher, a student-submitted one is written by the student and can
only be hidden by her.

What made it urgent is that these quotes do not sit still. [D-125](./D-125.md)'s
acquisition planner both nags for them — `page-readiness.ts` raises
`no_testimonials` and points at `/dashboard/testimonials` — and schedules a
`testimonial` content kind that republishes them into Facebook groups and
Reddit. `content-kinds.ts` already carries the sentence that gives the game
away:

> "Testimonial post" with no published testimonial produces a fabrication.

The planner is careful that a quote **exists** and has no way to care whether
it is **true**. So the failure mode was never a quiet exaggeration on one page;
it was the platform amplifying an unverifiable claim into public communities
with its own scheduling behind it.

There is a regulatory edge, stated as a factor and not as advice: the platform
entity is UK-established ([D-58](./D-58.md)) with UK-governed terms, and the
DMCC Act 2024's fake-review provisions ban publishing fake consumer reviews
**and facilitating them**. Nobody is accused of anything — the point is that
until now the product had no way to tell, while offering a name field, a photo
upload and a syndication path. Neither this paragraph nor
`packages/shared/src/legal/privacy-policy.ts` was written by a solicitor.

**What was affected.** The migration is additive and non-destructive. The
public page (`b/[slug]/page.tsx`) gains the badge, an explainer line shown only
when there is a badge on the page to explain, and one grouped
`completedClassCounts` query. The teacher's editor renders a verified row
read-only beside her own editable ones — deliberately in the same list, since
the comparison is how she learns what the page is claiming. The student portal
gains the form. `lib/testimonials/eligibility.ts` is the single place both
sides read standing from, so the write path and the public page cannot disagree
about it.

Three smaller calls worth recording:

- **Counts are derived, never stored.** A number copied onto the row at
  submission time starts drifting the next lesson, and a badge reading "12
  classes" against a database saying 40 is a small lie in the one place the
  feature is asking to be believed.
- **`no_show` does not count.** The class was consumed against the package and
  the teacher was owed for it, but the student was not taught.
- **A verified row publishes on arrival.** Holding it for teacher approval
  would quietly rebuild the thing being fixed — a page showing only the
  verified quotes its owner liked is curated again, with extra steps. She can
  still hide any single one, which is a visible act on a row she can see.

`lib/seo/jsonld.ts` is deliberately **untouched**. It emits no
`Review`/`AggregateRating` markup because unrated curated quotes would violate
Google's review-snippet policy, and a verified testimonial still carries no
rating, so the rule is unchanged and the file should stay that way.

The student-row FK cascades on delete: once the row is erased the claim is no
longer provable, and an orphan still saying "verified student" is the exact
failure this exists to prevent.

**Unresolved risks.** **Discovery is the real limit.** A student only finds the
form by visiting their teacher's page in the portal, because the obvious
prompt — the platform emailing her students to ask — is an outbound message to
her customers on her behalf, and that needs a per-teacher opt-in, a rate limit
and the existing notification-preference and opt-out paths. It was scoped out
here rather than half-built; the HMAC pattern in
`lib/notifications/settings-link-token.ts` is the shape it should take
(`k: "testimonial-request"`), through the existing `enqueue` and dispatcher
pipeline. Until then, uptake is likely to be low, and low uptake on a
one-teacher platform means the badge may not appear on any page for a while.

**Verification is not endorsement of the sentiment.** A teacher can still ask a
happy student to write one, and coach what it says. The badge claims what the
database can prove — a real, paying, taught student wrote this — and never that
the opinion was unprompted. The copy is written to claim exactly that and no
more.

**Not exercised end to end.** The eligibility resolution, the store rules and
the count derivation are unit-tested; the CHECK constraint and the partial
unique index are not — they are exercised only by a real migration against a
real database, which is the `full` tier's integration step, and no browser test
covers the student writing one.

**Nothing existing was re-labelled.** A curated quote renders today exactly as
it did yesterday, with no "unverified" mark. That is deliberate — marking every
existing testimonial as suspect on the strength of a feature nobody has used
yet would punish the teacher for the platform's previous design — but it does
mean the contrast only does its work once at least one verified quote exists on
a page.
