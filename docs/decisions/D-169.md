# D-169. One wrapper owns every Infisical call, and deployment does not make one

**What changed.** Every invocation of the Infisical CLI moves behind a single
file, `infra/infisical/infisical.sh`, exposing four verbs. Nothing else in the
repository shells out to `infisical`. `scripts/fly-deploy.sh` loses its own
Infisical branch, because [D-163](./D-163.md) already said what replaces it and
the branch outlived the decision.

This is a consolidation, not a new position. Every rule it enforces is already
written down somewhere in this repository; the problem is that it is written
down in five places and implemented in five different ways.

## What forced it

Ten call sites, in nine files, implementing four operations five different ways:

| Operation                    | Implementations today                                                                                                            |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Read named secrets           | `with-secret.sh` (sourced, exports into the caller), `fly-deploy.sh` (inline), `oracle-render-livekit.sh` (inline)               |
| Read a whole environment     | `oracle-deploy.sh` (inline, two paths), `push-fly-secrets.sh` (inline, one path), `push-github-secrets.sh` (inline, three paths) |
| Run a command with injection | `run.sh`, `.devcontainer/dev.sh`                                                                                                 |
| Write                        | `infra/aws-ses/push-infisical-secrets.sh`                                                                                        |

⚠️ **Each of the five learned the same lessons separately, and not all of them
learned all of them.** `with-secret.sh` refuses an empty fetch, because falling
through to a bare `export` once leaked `OPENAI_API_KEY` into a terminal and a
chat transcript. `oracle-deploy.sh` proves the whole expected key set before it
touches anything, because a fetch that quietly returns fewer secrets than asked
for looks exactly like one that worked. **Neither guard exists in the other
three readers.** A wrapper is how a lesson learned once applies everywhere.

## What deployment needs from Infisical: nothing

**Both deploy workflows already run without it.** `deploy-preview.yml` and
`deploy-production.yml` run on `ubuntu-latest`, take every value from a GitHub
**environment** secret, and call `scripts/fly-deploy.sh`. Neither has the CLI,
a token, or a network path to the vault.

⚠️ **That is a security property, not an accident, and this record does not
touch it.** [D-163](./D-163.md)'s addendum reversed an OIDC machine identity
for a specific reason: `id-token: write` is granted per **job**, so the
token-minting variables land in the environment of every step — `pnpm install`
running the lifecycle scripts of the whole dependency tree included. A pushed
copy of eleven values has no way to ask for a twelfth.

**So Infisical's entire role in deployment is populating the two push targets**
— `push-github-secrets.sh` into GitHub environments, `push-fly-secrets.sh` into
Fly. One vault, two push targets, one mental model.

## Where it is genuinely needed, after that

**Only the laptop, and only for operations — never for a deploy.**

| Consumer                                       | Why it cannot be a workflow                                                                  |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `run.sh` → **7** `apps/web` package scripts    | `migrate:prod`, `db-push:preview`, `uat:verify` — operator judgement against a live database |
| `with-secret.sh` → **7** scripts               | seed and reset preview, `backup-prod-db`, the two LiveKit activity probes                    |
| `oracle-deploy.sh`, `oracle-render-livekit.sh` | rebuild a box that holds its own OCI credentials                                             |
| the two push scripts                           | they are what _fills_ CI; they cannot run inside it                                          |
| `push-infisical-secrets.sh`                    | writes SES keys back after Tofu creates them                                                 |

## What gets deleted

⚠️ **`scripts/fly-deploy.sh`'s Infisical branch, which a merged decision already
replaced.** D-163's own text in `deploy-production.yml` says the laptop reads
these values _"through `infra/infisical/run.sh production ./scripts/fly-deploy.sh …`
rather than from a file that is the copy nobody rotates."_ The composition is
the supported path; the branch is a second one nobody removed.

`fly-deploy.sh` becomes environment-only, exactly as CI already invokes it. **No
capability is lost** — the laptop path is one wrapper call in front of it — and
one of the five reader implementations disappears with it.

## The shape

```
infisical.sh — the ONLY file that runs the CLI

  infisical_secrets <env> KEY...       named secrets  → dotenv on stdout
  infisical_env     <env> [path...]    whole env      → dotenv on stdout
  infisical_exec    <env> -- cmd...    inject and exec
  infisical_put     <env> KEY=VALUE... write
```

Four properties, held in one place instead of five:

- **The project is verified, never inferred** — `project-id.sh`, already merged.
  The link lives in `$HOME`, so _which_ project is a live question.
- **Nothing reaches the disk.** Values go to stdout or into a process
  environment. No temp file survives a call.
- ⚠️ **An empty or short fetch is an error, never an empty export.** Both
  existing guards generalise: refuse an empty result, and when the caller names
  the keys it expects, prove the whole set arrived before returning any of it.
- **`stderr` for progress, `stdout` for values only**, so a caller can always
  pipe safely.

## What is deliberately NOT done

- **No machine identity, and no OIDC.** D-163's addendum settled that and its
  reasoning is unchanged.
- **`oracle-deploy.sh` does not move into a workflow.** It destroys and rebuilds
  a box; the operator watching it is a feature.
- **`.devcontainer/dev.sh` is left alone.** Codespaces authenticates with
  `INFISICAL_TOKEN` rather than a user login — a different mechanism, and
  folding it in would put a token path into a wrapper that otherwise has none.
- **`infisical secrets set` keeps its `cd`.** The subcommand takes no project
  flag, so `push-infisical-secrets.sh` cannot pass one. ⚠️ **It is therefore the
  one call the project guard cannot cover**, and the wrapper says so out loud
  rather than pretending otherwise.

## What holds it in place

`apps/web/tests/config/infisical-single-caller.test.ts` walks every `.sh` file
and fails if any but the wrapper invokes the CLI in command position. **Nothing
stopped a sixth implementation appearing except somebody noticing**, and this is
what notices.

⚠️ **It found a real miss on its first run** — `oracle-deploy.sh`, whose only
match turned out to be the words `infisical init` inside a `fail` message. The
matcher was tightened to command position rather than the file being changed,
because **a guard that cries wolf gets deleted.**

## ⚠️ What this cost, stated plainly

**It landed the day before the Oracle rebuild and two days before publication,
which is not when this would have been scheduled.** It touches
`scripts/oracle-deploy.sh`, whose terminate cannot be undone if A1 capacity is
gone. Two things make that survivable rather than reckless: **every verb was
exercised against a stubbed CLI before any caller moved** — including the
partial-fetch refusal, the closed environment list and the path ordering — and
**`INFISICAL_SKIP_PROJECT_CHECK=1` still bypasses the project guard** if the
guard itself is what is wrong at 02:00.
