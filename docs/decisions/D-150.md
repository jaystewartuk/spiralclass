# D-150. The web app moves to Oracle Always Free; Fly is preserved, not replaced

> [!IMPORTANT]
> ⚠️ **Two things below have been overtaken. First, the title is half wrong:
> the web app does NOT move** — see the
> 2026-09-04 addendum at the foot of this file: production stays on Fly,
> production's database stays on Neon, and Oracle takes LiveKit, preview and
> preview's database. Everything above that addendum is the reasoning as it
> stood, and the measurements in it are still the best ones taken.
>
> ⚠️ **Second, the "no OpenTofu is committed before it is applied" condition
> has been waived once** — see addendum 3. The module is on `main`, unapplied,
> behind a banner in its own README that says so.

**Status: Decided, not executed.** No code changed and nothing has moved. What
this record buys is that the hosting question has been answered against
measurements rather than against the shape of a bill, and that the two
surprising answers — the free box is in the wrong country for the database,
and the database must not follow it there — are written down before anyone
rediscovers them halfway through a migration.

Prompted by a Fly invoice of roughly ten dollars for the month, against a
product with no paying teachers that is deliberately not chasing any yet.

## What was decided

**One. The self-hosted LiveKit box gets an OpenTofu definition again, and it
gets applied.** This reverses the cost [D-139](./D-139.md) knowingly accepted
— see the condition attached below, which is the whole of why the reversal is
allowed.

**Two. The Next.js app moves onto Oracle Always Free, and Fly stays a
first-class deployment target rather than being deleted.** The application is
already provider-neutral; what is Fly-specific is small and stays isolated so
that returning is a command, not a project.

**Three. Postgres stays on Neon and is NOT colocated onto the box.** This is
the recommendation that runs against the technically fastest architecture, and
the reasoning is in "Why not put Postgres on the box" below.

## The measurement that decided it

The Oracle Always Free instance is in **`mx-queretaro-1`** — Querétaro,
Mexico. Neon production is in **`aws-us-east-2`** — Ohio. Measured on
2026-09-02 from the running machines themselves, not estimated:

| Hop                                        | Round trip |
| ------------------------------------------ | ---------- |
| Fly `ord` machine to `aws-us-east-2`       | 12 ms      |
| Oracle `mx-queretaro-1` to `aws-us-east-2` | 58 ms      |
| Oracle `mx-queretaro-1` to `aws-us-east-1` | 55 ms      |
| Oracle `mx-queretaro-1` to `aws-us-west-2` | 78 ms      |

Method, stated so the numbers can be re-taken: ICMP to
`s3.us-east-2.amazonaws.com` from the Oracle box, TCP connect on port 443 to
the same host from inside the Fly machine via `flyctl ssh console`. **The
Neon endpoint itself was not measured** — the credential was unavailable in
session — so an AWS host in the same region stands in for it. Both figures
were stable across repeated samples, at a standard deviation under a tenth of
a millisecond.

**Nothing available fixes this.** Oracle Always Free resources can only exist
in the tenancy's home region, and the home region is Querétaro. No Neon region
is meaningfully closer than the one already in use. So the distance is a
property of the free box, not a configuration mistake.

### Why 46 milliseconds is worth a decision record

`fly.production.toml` already carries the answer, from the last time this was
measured rather than assumed. Prisma spends **four round trips on every single
query** — BEGIN, the query, COMMIT, DEALLOCATE ALL — and a class-detail
request issues about **seven queries**. From `dfw`, Sentry measured `BEGIN`,
a statement that does no work whatsoever, at 27.5 ms average, which is round
trip time and nothing else. That put roughly 800 ms of a 1.7 second response
into network latency, and it is why the machine sits in `ord` today:
colocation with the database was deliberately chosen over colocation with the
users.

Twenty-eight round trips at 12 ms is about 336 ms. The same twenty-eight at
58 ms is about **1,624 ms**. The move therefore costs an estimated **1.3
seconds on database-heavy pages** — call it a doubling of a dashboard page
load. That estimate is arithmetic over a measured round trip and a documented
query pattern; it is not itself a measurement, and closing that gap is the
first unresolved risk below.

Users being in Mexico claws back a little of it — Querétaro is far closer to
them than Chicago is — but that saving is paid once per request while the
database penalty is paid twenty-eight times. It does not change the sign.

## Why Oracle wins anyway

Because the honest comparison is not against production as it runs today. It
is against **what Fly costs when it is also free**, and Fly has no free tier.

The bill is one always-on `shared-cpu-1x` machine with 1024 MB in `ord`,
roughly 5.70 dollars a month. There are no volumes and no dedicated IPv4 on
either app, so essentially the whole SpiralClass line is that one machine.
Fly's floor is `min_machines_running = 0`, which costs pennies of rootfs
storage and buys a cold start — the health check's own grace period puts the
boot at about eight seconds, and preview already runs this way.

So the three real options are:

- **Fly at `min = 1`** — fast database, always warm, about 5.70 dollars a month.
- **Fly at `min = 0`** — fast database, roughly 30 cents a month, and an
  eight to ten second cold start on nearly every visit, because the traffic is
  sparse enough that almost no request finds a warm machine.
- **Oracle** — always warm, zero, and 1.3 seconds of database latency.

**Oracle beats Fly-at-zero decisively**, which is the comparison that matters
if the objective is zero. A permanent 1.3 seconds is better than an
intermittent ten. The genuine trade is therefore not "Oracle versus Fly" but
**"is 5.70 dollars a month worth buying back 1.3 seconds"**, and at a stage
whose stated primary objective is near-zero infrastructure cost, it is not.

What makes this safe to decide now rather than agonise over is that the answer
is **reversible for the price of a DNS record**. Fly stays configured, the
image stays buildable for it, and the day a paying teacher makes 5.70 dollars
obviously worth spending, going back is one deploy.

There is also a real and unrelated gain hiding in the move. Oracle's A1 shape
is arm64, and so is the development machine, so the deploy stops needing the
amd64 cross-build under QEMU that this repository complains about in four
separate places and that costs twenty to thirty minutes per production deploy.

## Why not put Postgres on the box

This is the option that is technically best and is still being rejected, so it
is worth being explicit.

Colocating Postgres would put the application, the users and the database all
in Mexico. Query round trips collapse from 58 ms to loopback, which is not
merely better than the Oracle-plus-Neon option — it is **dramatically better
than production is today**, since it removes the 336 ms that `ord` currently
pays as well. It would also be free. On latency and cost alone it wins
outright.

It is rejected on the operator's own measured history. The
[D-129](./D-129.md) addendum removed the hand-run database backup from the job
registry specifically because **Neon backs production up** and a hand-run
`pg_dump` is therefore not a routine anyone should be nagged about. That
addendum exists because of what happened when backups did depend on something
other than a managed service: production's Postgres went **eleven days with no
backup** while nobody noticed. Moving payment and teacher records onto a
free-tier virtual machine that Oracle reserves the right to reclaim, behind a
backup routine that a human has to remember to run, re-opens exactly that
hole — and it does so for the one dataset in the product that cannot be
regenerated.

The managed database is also the thing that keeps this whole decision cheap to
unwind. With Neon in place, moving the application back to Fly is a deploy.
With Postgres on the box, it is a data migration.

Neon's free tier is unaffected by any of this and remains within its limits.

## What this reverses in D-139, and the condition attached

[D-139](./D-139.md) deleted `infra/oracle-runner` and `infra/cloudflare`, and
accepted, in as many words, that "a rebuild of the Oracle box is now a hand
operation with no machine-checkable definition."

**D-139 was not wrong about infrastructure-as-code.** Its objection was
precise and it still binds: a module that has never been applied does not
describe infrastructure, it asserts a state nobody has reconciled, and the
assertion is confidently wrong in a file that reads as authoritative. That
cost was not hypothetical — a session read `infra/oracle-runner`'s claim that
a `tofu apply` "reproduces the box as-is" and twice proposed applying it to
fix a missing TLS certificate, which would have edited a template while
production stayed broken.

What changes is that the module now gets **applied**, which is the one thing
that was never true before. D-139 itself named the path it was closing: "what
is genuinely lost is the possibility of making it true later by importing
existing infrastructure into state — that path is now a rewrite rather than an
import." This decision accepts that rewrite as the price and pays it.

> [!IMPORTANT]
> **The condition, and it is not negotiable: no OpenTofu for this box is
> committed to this repository until it has been applied and a state file
> exists.** Writing it is not the deliverable; applying it is. Committing an
> unapplied module — however good — recreates D-139's fault exactly, and the
> next reader has no way to tell this module from the one that lied to them.

The reversal is also narrow. It reverses D-139's **accepted cost**, not its
reasoning, and it says nothing about `infra/cloudflare`, whose deletion stands
for the separate and stronger reason D-139 gave: its Access application was
made by hand, so a first apply would have created a second application on the
same hostname rather than adopting the existing one.

The existing module is recoverable from `db1af711^` and was read while writing
this. It is high quality and is the right starting point rather than a blank
file: the security-list rules, the `for_each` blue-green key, the
`ignore_changes = [metadata]` guard on a call-serving box, and the reasoning
about why the Cloudflare record must stay proxied are all correct and all
still apply. What it needs is to be reconciled against the machine as
[`ORACLE_BOX_REBUILD.md`](../deployment/ORACLE_BOX_REBUILD.md) transcribed it
on 2026-08-29, extended to carry the web application, and then actually run.

## Why the box deserves this regardless of where the web app runs

The LiveKit half of this decision would be worth doing at any hosting cost,
and it is the strongest part of the change.

Today that machine carries every live class, and losing it stops classes.
Rebuilding it is a hand operation the runbook estimates at two to four hours.
Its only change history is a set of `.bak` files sitting next to the live
configuration. Two of the values on it name the application and are rewritten
by nothing, which is how the 2026-08-30 outage happened: the
[D-138](./D-138.md) rename swept 934 files in this repository and could not
touch the box, so the captions agent posted into a 301 and published no
captions at all through a real class, and livekit-server's webhooks silently
stopped arriving while its own log went on saying `sent webhook`.

The certificate renewal path is the sharper version of the same exposure. It
depends on "Always Use HTTPS" staying off on two Cloudflare zones, because
http-01 is now the only challenge type that can work through the proxy; if
that setting is ever turned on, renewal fails silently until the certificate
expires and every class stops. The next renewal is due around 2026-10-28.
None of that is visible from outside the box, and none of it is asserted by
anything in this repository.

## Unresolved risks

**The 1.3 seconds is arithmetic, not a measurement.** It multiplies a measured
round trip by a query pattern documented in `fly.production.toml` from an
earlier incident. The pattern may have changed; Prisma's four-round-trip
behaviour depends on connection and transaction settings that were not
re-verified here. **The migration must not cut DNS before the real number is
taken from a deployed instance**, and if it comes back far worse than 1.3
seconds this decision should be re-opened rather than absorbed.

**The invoice was not itemised.** The Fly organisation also holds two
applications unrelated to SpiralClass. The 5.70 dollars a month above is
derived from the machine that is actually running, not read off a bill, so
SpiralClass's true share of the organisation-wide total is unconfirmed. If most
of that bill is the other two applications, this decision is trading 1.3
seconds for less money than it thinks.

**Oracle Always Free is a weaker promise than a paid machine.** Oracle
reserves the right to reclaim idle Always Free compute, capacity for new A1
instances in a small region is frequently unavailable, and there is no support
relationship. Putting the web application beside LiveKit also concentrates
risk: today an Oracle outage stops video and leaves the site up, and
afterwards it stops everything. Provisioning the application onto a **second**
Always Free instance rather than the existing one is the mitigation, and the
tenancy has exactly the two OCPUs and twelve gigabytes left to do it — but it
is a mitigation for the blast radius, not for the provider.

**The application-side portability is asserted, not proven.** It looks strong:
the Dockerfile is provider-neutral, non-secret configuration already lives in
`config/env/<APP_ENV>.{build,runtime}.env`, secrets already arrive as plain
container environment, and `scripts/docker-entrypoint.sh` knows nothing about
Fly. But the image has only ever been built for amd64 and run by
`flyctl deploy`, so "it will run under plain Docker Compose on arm64" is a
reading of the code, not an observation.

**Nothing here has been applied, and one dependency is missing.** There are no
OCI credentials on the development machine — no `~/.oci`, no `oci` CLI — so
the module cannot be applied, which by the condition above means it cannot be
committed either. Until those exist, this decision is a plan and the
`ORACLE_BOX_REBUILD.md` runbook remains the only description of the box.

## Addendum, 2026-09-04 — the web app does NOT move; Oracle carries everything else

**What changed.** The operator's decision, taken while the rebuild was staged
and unapplied: **the production web app stays on Fly, production's database
stays on Neon, and Oracle carries everything else** — the self-hosted LiveKit
stack, the preview web app and preview's Postgres. **Every deploy runs through
GitHub Actions.**

This reverses **decision two** above and nothing else. Decision one — the box
gets an OpenTofu definition and it gets applied — stands, and was always the
strongest part of this record. Decision three — Postgres stays on Neon —
stands and is now settled rather than merely recommended.

**What it costs.** Roughly **5.70 dollars a month**: the always-on
`shared-cpu-1x` machine in `ord` that this record set out to remove. That is
the whole of the saving decision two was chasing, and it is being spent
deliberately.

**What it buys, in the order that decided it.**

- **The 1.3 seconds never gets charged.** The measurement above stands: 58 ms
  from Querétaro to Neon in Ohio against 12 ms from `ord`, times twenty-eight
  round trips on a database-heavy page. Keeping the app in `ord` keeps the
  fast hop and makes that estimate moot rather than something to re-measure
  after a migration.
- **Production stops sharing two OCPUs with live video.** Oracle halved the
  Always Free A1 allowance, so this is one box, and everything on it competes
  with `livekit-server` and an egress that reserves both OCPUs for a single
  composite. A runaway request on the box was going to be someone dropped
  mid-lesson.
- **The blast radius stops being everything at once.** This record's own
  unresolved risk said it plainly: "today an Oracle outage stops video and
  leaves the site up, and afterwards it stops everything". That sentence is
  what this addendum acts on.
- **Production's secrets stay in a managed store.** Colocating meant
  `STRIPE_SECRET_KEY`, production's `DATABASE_URL`, `SESSION_SECRET`,
  `BETTER_AUTH_SECRET` and `FIELD_ENCRYPTION_KEY` as mode-600 files on a
  free-tier box Oracle reserves the right to reclaim. The box now holds
  preview's environment plus five LiveKit values.
- **The cutover can no longer take the site down.** `spiralclass.com`'s A
  record is never touched: two hostnames move, `livekit` and `preview`. What
  the rebuild risks is live classes, which was already true before any of this.

**What Oracle is still for.** The LiveKit box, which this record already said
"would be worth doing at any hosting cost" — plus preview, which was on Fly at
`min_machines_running = 0` and paying an eight-to-ten second cold start on
nearly every visit. Preview on an always-warm box is strictly better than that
and free.

**Deploys.** Every deploy runs through GitHub Actions: `deploy-production.yml`
against Fly, which is unsuspended by this decision, and `deploy-preview.yml`
against the box once it is serving. Three things the box's deploy needs and
does not have — a Tailscale OAuth client so a runner can reach a machine whose
`:22` is closed to the internet, an Infisical machine identity so a runner can
render config with no operator session to borrow, and GHCR to replace the
laptop-to-box `docker save | docker load` — are boarded work, not part of the
cutover.

**Unresolved risk this creates, and it is the sharp one.** The captions agent
and `livekit-server`'s webhook call the production app, which is now off the
box and behind Cloudflare. That is the exact path of the 2026-08-30 outage —
but read that outage precisely: the [D-138](./D-138.md) rename left both values
on `agendaprofe.com`, the 301 turned the agent's POST into a GET, it got a 405,
and a class ran with captions silently dead while `livekit-server` logged `sent
webhook`. **The fault was a stale hostname nothing owned, not the fact that the
request left the machine.** So the two defences are that the value is rendered
from one place a rename sweep reaches, and that `scripts/oracle-deploy.sh`
probes it on every deploy and **fails on any 3xx**. Neither is optional, and a
redirect is indistinguishable from success from every other angle.

## Addendum 3, 2026-09-05 — the no-commit-before-apply condition is waived, once

**What changed.** `#1061`
merges **before** the module has been applied. That is a direct waiver of the
condition written above, which called itself non-negotiable.

**Why, and it is a sequencing fact rather than a change of mind.** The
repository's history is being rewritten into a **new, public repository**. What
the new repository inherits is `main`'s history — so a branch that is not on
`main` at that moment does not travel. It stays on the private archive, and
recovering it afterwards means moving commits between two repositories that
share no history, by hand, during the same week as a rebuild with no rollback.

The condition existed to stop D-139's fault: a module that reads as
authoritative while asserting a state nobody reconciled, which cost real time
when a session read the old `infra/oracle-runner` and twice proposed applying
it to fix a live problem. **That fault is about what a reader believes, not
about which branch a file sits on.** So the condition is replaced by the thing
it was protecting: a `[!CAUTION]` banner at the top of
[`infra/oracle-box/README.md`](../../infra/oracle-box/README.md) saying the
module has never been applied, that no state file exists, that no box matches
it, and — the sentence that would actually have prevented the 2026 incident —
**do not `tofu apply` this to fix a problem with the live box.** It also gives
the reader a test that does not depend on trusting the banner: no state file at
`$HOME/.tofu-state/spiralclass/oracle-box.tfstate`, and a plan that answers
**7 to add**.

⚠️ **The banner is the price, and it must not outlive the apply.** Taking it
off is the closing item in [`CUTOVER.md`](../../infra/oracle-box/CUTOVER.md); a
banner that stays after it stops being true is worse than none, because the
next one is not believed either.

⚠️ **One consequence of merging before the repository is published.** This
module arrived after the pre-publication scour, carrying the old instance
OCID, the old box's public and tailnet addresses, and the Infisical project id
that `oracle-deploy.sh` and `oracle-render-livekit.sh` both defaulted to. None
of them is a credential and the addresses die with the old instance — but a
scour that ran before this merge had not seen any of them. **They are all
placeholders now**; the real values live where D-158 says they live.
