# D-42. Remove the WhatsApp (Meta Cloud API) messaging integration; keep the phone field + wa.me links

**What changed.** The platform no longer sends automated WhatsApp messages. The
whole Meta WhatsApp Cloud API integration is deleted — the send client, the
`/api/wa/webhook` delivery/inbound webhook, HMAC signature verification, the
hourly template-approval sync cron, the `template_approvals` table, the
`whatsapp` value of the `NotificationChannel` enum, and the `meta`/`twilio`
values of `WebhookProvider`. Notifications now ship over **push with an
email (Resend) fallback** — the cascade is `push → email`. Two things were
deliberately KEPT:

1. **The phone number** — `whatsapp_e164` is renamed `phone_e164` (Student /
   Teacher / Lead) and repurposed as a generic contact field. It still powers
   duplicate detection (`same_phone`), roster/lead display, merge, and the
   teacher's manual "message my student/lead" links. No prod phone data is lost.
2. **Plain `wa.me` / `whatsapp://` deep-links** — the "Chat on WhatsApp" support
   button, "share your booking link on WhatsApp", and teacher→student contact
   buttons stay. They just open the WhatsApp app; they use no Meta integration.

Removed alongside the channel: WhatsApp consent (`whatsapp_opt_in[_at]`,
`whatsapp_business_id`, the checkout/account consent checkboxes, the
`/r/uns/[token]` opt-out surface), the
`canUseWhatsApp` Pro entitlement (WhatsApp is no longer a Pro perk), and the
`META_*` env vars + `hasMetaCreds()` + `graph.facebook.com` CSP allowance.
Schema changes ship in migration `20260705000000`-successor
`20260705010000_remove_whatsapp_integration`.

**Why it likely changed.** Meta Business/WhatsApp verification proved a
multi-day, opaque, repeatedly-blocked onboarding with no clear end. It was never
launch-critical (the product runs fine on push + email), so it was sitting on the
critical path for no proportionate value. In this market WhatsApp _reminders_ do
beat email for no-shows, but that upside is recoverable later (ideally via a BSP
that eats the verification burden) and wasn't worth continuing to fight Meta
solo. The phone field and manual wa.me links are cheap to keep and remain
genuinely useful, so only the _automated platform messaging_ was cut.

**What was affected.** `apps/web/src/lib/whatsapp/**` (deleted; template types
re-homed to `src/lib/notifications/templates.ts`), the notification dispatcher /
resolve-channel / enqueue / preferences, `packages/shared` (`api.ts` DTOs,
`validators.ts` field keys `whatsapp`→`phone` / `studentWhatsapp`→`studentPhone`,
`notifications.ts` channel set, `subscriptions-entitlements.ts`), ~25 web routes
/ actions / pages / forms, field
encryption / Sentry scrub keys, seed/import/anonymize scripts + the import CSV
header, and marketing/PRD copy. `docs/engineering/integrations/whatsapp.md` is
kept as a tombstone.

**Unresolved risks.**

- **This breaks the expand/contract discipline for the API.** The removal drops
  response fields old installed clients read (`whatsappOptIn`, `hasWhatsapp`,
  the notifications-admin `templates`/`meta`) and stops honoring the checkout
  `whatsappOptIn` request field, all in one contract step rather than
  additive-first. Request-side is partly tolerant (the create-student route
  still accepts a legacy `whatsapp` alias for the phone), but a pre-cutover
  build will see missing fields. **Mitigate before prod cutover** with the
  min-version force-update gate (same lever the D-40 cutover needs), or ship a
  short additive-compat window.
- **No-show reduction may dip** where WhatsApp reminders previously reached
  one-off bookers who never turn on push (email under-performs in-market).
  Revisit later with data — a BSP re-entry is the likely path, not fighting Meta
  Business Manager again.
- The migration **recreates the `NotificationChannel` and `WebhookProvider` enum
  types** and **deletes `webhook_events` rows with `provider IN ('meta','twilio')`**
  (processed-webhook idempotency guards; safe to drop, but it is a data
  deletion). Enum recreation is irreversible on prod — verify on staging first.
