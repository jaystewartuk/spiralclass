# D-146. One heavy job at a time: the laptop becomes a queue, not a free-for-all

> **Superseded in part by [D-157](./D-157.md) and [D-161](./D-161.md).** The
> machine lock stands and is still what stops several concurrent sessions
> corrupting one shared test database. The batching does not: the heavy suites
> run on GitHub-hosted runners now, on every pull request and every push to
> `main`, so the arithmetic that made batching worth its delay is gone.

**Date:** 2026-08-31

**What changed.** Three things, which together make several concurrent Claude
Code sessions a supported way to work this repo rather than a way to thrash the
machine.

- **A machine-wide lock.** `scripts/ci/lock.mjs` lets exactly one heavy job run
  on this laptop at a time. Everything else queues, in arrival order, and says
  what it is waiting for. The gate takes it, and so do `integration.sh` and
  `e2e.sh` on their own account, so a hand-run is serialized too.
- **The pre-push hook always runs the FAST tier.** The escalation to the full
  tier on production-risk paths is removed, from the hook and from
  `scripts/ship-pr.sh` alike. The heavy suites now run once per batch, against
  merged `main`, inside `pnpm ship-pr`.
- **One turbo cache for every checkout.** `scripts/turbo.mjs` points
  `TURBO_CACHE_DIR` at a single directory under the home cache, so work done in
  one worktree is a cache hit in all the others.

**Why it changed.** [D-119](./D-119.md) moved CI onto the dev machine and
[D-129](./D-129.md) removed every alternative, so this laptop is the only
runner there is. Neither decision anticipated the working style that arrived
afterwards: several Claude Code sessions at once, each in its own git worktree,
each with its own `.gate` receipt and its own copy of the pre-push hook.
Nothing connected them. Seven sessions pushing meant seven simultaneous gates,
and the machine has ten cores, 16GB of memory and about 22GB of free disk.

Measured on this machine while writing this decision: **8.1GB of the 9.2GB
swap file in use**, with a Playwright fleet, a `next-server`, a Docker VM and
seven `claude` processes resident. That is the failure the operator reported,
observable at the moment it was reported.

**Contention was the smaller half of the problem. Two of the three shared
resources corrupt rather than queue:**

- **The test database is a singleton, machine-wide.**
  `apps/web/docker-compose.test.yml` pins `container_name: spiralclass-test-db`
  on port 5433. Whichever worktree boots it, every other worktree gets that
  same container. Two integration runs therefore share one database, while
  `integration.sh` drops and recreates `spiralclass_drift` **with force**
  partway through, and `GATE_FRESH_DB=1` removes the volume outright. A
  concurrent pair corrupts each other's run, and the symptom arrives days later
  looking like flakiness.
- **Port 3000 is a singleton too.** `e2e.sh` serves the production build there
  and already guards the port, because a stray server on it silently
  contaminates a run. That guard was written after a two-hour-old stray
  `next start` caused eleven spec failures. A second concurrent E2E either
  trips that guard or, with `E2E_KILL_PORT_HOG=1`, kills the first run's
  server.
- **Memory is merely contended, but contended badly.** Both suites build with
  `--max-old-space-size=6144`. Two at once is a 12GB ceiling on a 16GB machine
  that is also hosting the editors and agent sessions that started them.

**Namespacing the container and the port per worktree was considered and
rejected.** It would fix the two corruption modes and make the memory one
worse, which is the wrong direction on a 16GB box: N Postgres containers and N
concurrent Next builds is the opposite of what this machine wants. Keeping
exactly one of each and serializing access to it gets the same correctness for
less memory, and it is the only option that also makes the queue visible.

**Why the full tier left the push path.** The hook escalated on Tier 2 paths
for a good reason, stated in its own comment: integration and E2E are the only
checks that catch a route conflict, a schema drift or a broken checkout, and
they otherwise run once, at promote, when the change is already on `main`. For
money, auth and schema that is too late to be comfortable.

The reasoning was right and the placement was wrong, for a reason that has
nothing to do with risk. A Tier 2 push fired a 20 to 40 minute run at an
arbitrary moment, in an arbitrary checkout, with no idea what the other six
sessions were doing. With the lock in place that no longer thrashes; it just
holds the machine for forty minutes while every other session waits.

So the heavy suites moved to where the batching already lived.
`scripts/ship-pr.sh` gates each PR fast, merges them, and then runs the full
tier **once** against `main` with every merge in it, before anything is
deployed. That is not a weaker signal than gating each branch, it is a stronger
one: gating a branch in isolation cannot catch the combination that is broken
though each half was green alone, and that combination is the specific risk a
batch introduces. The arithmetic matters too. A batch of five Tier 2 PRs used
to mean five full tiers, which is five Postgres boots, ten production builds
and five Playwright fleets, about three hours, to answer five times a question
one run answers once.

**Why one turbo cache.** Turbo's filesystem cache defaults to `.turbo/cache`
inside the repo, which with one checkout is right and with seven means seven
caches that never see each other. Turbo keys on a content hash rather than a
path, so the same inputs in a different directory are the same entry. Measured
on 2026-08-31: a cold `typecheck` of `@spiralclass/shared` took 1.5 seconds in
one worktree and 302ms as FULL TURBO in a **different checkout at a different
commit**, from the cache the first one wrote. Across the whole monorepo the
same run went from 16.5 seconds to 88ms, five tasks of five cached. Most
branches differ from `main` in a handful of files, so most packages are a hit
in every other worktree the moment one of them builds.

A `cacheDir` in `turbo.json` would not do it, because that field resolves
relative to the repo root and the repo root is a different directory in each
worktree, which is the one thing the shared cache must not depend on. An
exported variable in a shell profile would work only for shells that sourced
it, which excludes hooks and agent sessions. Hence the wrapper.

**What was affected.**

- `scripts/ci/lock.mjs` is new. `scripts/turbo.mjs` is new.
- `scripts/ci/gate.mjs` takes the lock around the whole run, names the running
  step so a waiter can see it, passes a token to child processes so they pass
  through instead of deadlocking, and releases before the receipt, the status
  post and the staleness nag. `--no-lock` opts out.
- `scripts/ci/integration.sh` and `scripts/ci/e2e.sh` re-exec themselves under
  the lock unless they already hold it.
- `.githooks/pre-push` always runs the fast tier. `GATE_TIER=full` still opts
  in.
- `scripts/ship-pr.sh` loses its copy of the Tier 2 regex and gates each PR
  fast.
- Root `build`, `lint`, `typecheck` and `test` route through the turbo wrapper.
  `pnpm gate:lock` prints who holds the machine.
- `apps/web/tests/config/machine-lock.test.ts` is new and behavioural: it races
  three real processes and asserts none of their intervals overlap, and it
  SIGKILLs a holder and asserts the next acquirer proceeds. Source-reading
  guards cannot tell a working lock from one that never excludes or one that
  deadlocks, and both of those are silent.
- `apps/web/tests/config/local-gate.test.ts` swaps its Tier 2 escalation guards
  for the lock and shared-cache invariants, and keeps a guard that the Tier 2
  list still exists in prose.

**Unresolved risks.**

- **A Tier 2 commit can sit on `main` having had only the fast tier.** Merging
  to `main` deploys nothing ([D-120](./D-120.md)), so the exposure is a red
  commit on an undeployed branch, caught minutes later by the full run and
  fixed forward before preview. It is a real narrowing of when the signal
  arrives, accepted deliberately, and `GATE_TIER=full git push` is the escape
  hatch when you would rather know now.
- **The lock is advisory, not enforced by the operating system.** Anything that
  boots the test container or binds port 3000 without going through the gate or
  the two suites is still invisible to it. `pnpm dev` on port 3000 is the
  obvious one, and it is a pre-existing hazard rather than a new one.
- **A queued push looks like a hung push** to anyone who does not read the
  output. The wait prints who holds the machine and reprints every thirty
  seconds, which is the mitigation, but a session that scrolls past it will
  still wonder.
- **The timeout is one hour**, chosen to sit above a slow full tier. A job that
  genuinely takes longer fails its waiters rather than queueing them, and
  nothing yet distinguishes that from a wedged holder whose process is somehow
  still alive.
- **Nothing caps how many worktrees exist.** Seven checkouts were using 18GB
  against 22GB of free disk while this was written. The lock stops them
  competing for CPU and memory; it does nothing about disk, and a full disk
  fails in more confusing ways than a slow gate.
- **The shared cache is a single point of corruption.** Turbo's entries are
  content-addressed and it repopulates on a miss, so the failure mode is a slow
  run rather than a wrong one, but no evidence was gathered on what a truncated
  entry does.
