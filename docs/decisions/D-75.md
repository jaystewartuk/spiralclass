# D-75. In-class "waiting room" presence + on-demand nudge (don't auto-ring)

> **Its transport was replaced (2026-09-06).** The presence model and the
> argument against auto-ringing a scheduled appointment both stand. The nudge
> itself fanned out over a transport that was later removed, so it silently
> delivered nothing for a month while still reporting "Sent"; it rides Web Push
> now and returns a real delivered count.

**What changed.** The in-class video call (D-16) gained a **waiting-room**
experience and an **on-demand nudge**: when one party is connected to the
LiveKit room and the other isn't there yet, the present party sees a
_"Waiting for the other person to join…"_ state with a **Nudge** button. Tapping
it fires a high-priority push to the counterparty's devices
(_"{name} is already in the video call. Tap to join."_) that deep-links straight
to the class screen. It works for **both** roles (either the teacher or the
student can nudge the other).

We deliberately did **not** build an automatic phone-style "ring both devices at
start time" flow. For a _scheduled_ appointment both parties already opted into
a time and receive the reminder ladder (5d/24h/1h/5m — `schedule-reminders.ts`);
an auto-ring is jarring, fires even when both are already present, and — because
there is no web push (D-44/D-49: no realtime infra, foreground polling only) —
can't reach a web user in the background anyway. The real failure mode isn't
"they forgot the time", it's "one person is here and the other hasn't shown up
yet" — a _presence + nudge_ problem, which is what this solves.

**Why it likely changed.** "Presume both join on time" leaves the present party
staring at an empty room with no recourse when the other is late or distracted.
An instant ring — a spontaneous, ephemeral "someone wants to talk now" signal
— is the opposite of what a scheduled lesson needs: the time is agreed and the
reminder ladder has already run, so ringing wholesale would over-notify. A
contextual nudge — sent only when someone is _actually waiting_, only to the
party who is _actually missing_ — is the minimal, non-annoying lever, and it
rides on direct-push machinery that already exists.

**What was affected.**

- **Presence** is read from LiveKit itself — no new realtime infra (consistent
  with D-44/D-49). The clients already detect "I'm alone in the room"
  (`remoteParticipants.size === 0`); the waiting state now hangs the Nudge
  button off that. Server-side, the nudge
  core cross-checks the room's participant list
  (`listRoomParticipantIdentities()` in `lib/video/room.ts`) and **skips** the
  push if anyone other than the caller is already in the room (race guard).
- **Shared nudge core** — `apps/web/src/lib/video/nudge.ts`
  (`nudgeCounterparty()`): one place that resolves the counterparty's locale,
  fans a direct localized push across their device tokens, and enforces a
  per-(booking, recipient) cooldown via the existing `rate-limit.ts` limiter
  (45 s window). Deliberately a **direct push**, not the templated
  Notification → dispatcher pipeline: the signal is real-time and ephemeral, so
  an email/inbox copy would land after the moment passed. It carries `{ type: "class_nudge", deepLink }` where the
  deep-link suffix is role-appropriate (`dashboard/classes/<id>` for a teacher
  recipient, `s/class/<id>` for a student) and is already handled by the
  push-tap router — so no new deep-link plumbing.
- **Web** — a `nudgeFromTeacher` / `nudgeFromStudent` server-action pair
  (`app/actions/call-nudge.ts`, auth-scoped exactly like the call-token routes),
  bound into `<ClassCall>` via an `onNudge` prop; the button renders inside the
  existing `waitingForOther` block.
- **A second client** mirrored the same pair of endpoints and rendered the
  button in
  the "no remote track yet" block.
- **i18n** — nudge copy added to the shared catalog (`call.nudge*`, es/en); the
  push body itself is inlined es/en in the core rather than routed through the
  notification templates.

**Unresolved risks.**

- **A browser can't be nudged in the background.** With no web push at the
  time, a nudge reached a counterparty only if their tab was open. That
  asymmetry was intended, not a bug — but it meant "Nudge sent" was
  best-effort.
- **Student identity sets.** A booking's `studentId` is one roster row; a
  multi-teacher student may join under a sibling identity row
  (`studentIdentityIds`). The presence race-guard sidesteps this by checking
  "is anyone _other than the caller_ in the room" rather than matching the
  counterparty's exact id, so it's robust; the device-token fan-out targets the
  booking's `studentId` row, which is where that student's tokens are
  registered.
- **No auto-nudge yet.** If nobody taps, nobody is pinged. See follow-ups.

**Planned follow-ups (spec, not yet built).**

1. **T-0 "Join now" reminder leg.** Extend `schedule-reminders.ts` with a leg at
   `scheduledStart` ("Your class is starting — join now", booking channel,
   deep-linked to the call). Pure extension of the existing reminder ladder;
   deferred here only to keep this change off the heavy notification-template
   surface (new `TemplateName`s ripple through `templates.ts` / `enqueue.ts` /
   `resolve-channel.ts` / the email + push renderers) and give it its own review.
2. **One automatic nudge at ~T+2min.** A short Inngest job (or a client-side
   timer on the present party) that fires a single nudge if exactly one side is
   present shortly after start — so the waiting person doesn't have to think to
   tap. Best done after (1) so it shares the "join now" copy.
3. **Web incoming-nudge banner.** A foreground poll + global banner so an open
   web tab surfaces an incoming nudge, closing the web receive-side gap.
4. **No-show tie-in.** A defined waiting/grace window could feed the existing
   `cancellation/classify.ts` no-show path instead of a silent forfeit.
