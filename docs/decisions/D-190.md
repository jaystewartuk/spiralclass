# D-190. A Cloud Run instance that stops answering is restarted by a liveness probe, not by a second instance

**Status.** Active · closes the single-point-of-failure half of #94 for the
target [D-184](./D-184.md) and [D-186](./D-186.md) made the only one.

**What changed.** Every production deploy now passes
`--liveness-probe` to Cloud Run, with its value in
`config/cloudrun/production.env` (`LIVENESS_PROBE`): an HTTP GET of
`/api/health/live` on port 3000 every 15 seconds, a 5-second timeout, and a
restart after four failures in a row, about a minute. The route queries
nothing. `apps/web/tests/config/cloudrun-deploy.test.ts` pins the flag, the
path and the bounds on the timing.

**Why.** Production went down on 2026-08-26 and again on 2026-09-21, both
times with the process alive, its port open and its event loop not answering.
On Fly the health check could remove the only machine from the proxy but never
replace it, because Fly restarts on exit, not on a failing check. #94 was filed
about that, with a second Fly machine as its cheapest fix.

Fly is gone, and the premise changed shape rather than disappearing. Read from
the live service on 2026-09-29, Cloud Run `web` carried **no liveness probe**:
its only check was the default TCP startup probe, which a wedged process
passes, because it still holds the port. Cloud Run would scale out beside a
wedged instance once its concurrency slots filled, but nothing would ever
restart it, and until it filled it would keep taking requests it could not
answer.

A liveness probe is the mechanism Cloud Run documents for exactly this: a
failed probe restarts the container. It costs nothing, needs no operator, and
unlike a second instance it fixes the wedged instance rather than routing
around it.

**What was considered and rejected.**

- **`MIN_INSTANCES=2`**, the Cloud Run form of #94's option 1. Two
  always-on instances are outside the free grant D-184 was chosen for, and a
  wedged instance would still hold half the requests until it was replaced,
  which nothing would do.
- **Probing `/api/health`**, which queries Postgres. Every instance would
  restart during a Neon outage, which fixes nothing, and a query every 15
  seconds keeps Neon's compute from suspending, the cause of the 2026-08-07
  bill (see the route's own comment).
- **A tighter probe**, ten or twenty seconds to restart. A restart drops the
  requests in flight, and one slow server render is not a wedge. The
  2026-09-21 wedge answered one check in 15 seconds and then nothing, so a
  5-second timeout still counts that as a failure.

**What it constrains.** `/api/health/live` must stay cheap and must never
query the database: it now decides whether an instance lives. The probe is
passed on every deploy, like the rest of the shape, so a probe edited in the
console is reverted by the next release rather than surviving it silently.

**Trade-offs accepted, and unresolved risks.**

- **Not yet seen working.** Nothing here has watched a wedged instance get
  restarted; the claim rests on Cloud Run's documented behaviour. After the
  next promote, a read of the service should show a `livenessProbe` block, and
  the next wedge, if there is one, should show a restart in the revision's
  logs rather than an outage.
- **It does not remove the wedge.** The 2026-09-21 cause, most likely a
  saturated Prisma pool starving the event loop, is inferred and unfixed. The
  probe bounds the outage to about a minute per wedge; it does not stop one.
- **Probe CPU.** The service bills CPU per request, and whether probe traffic
  is billed at this rate is unmeasured. Four probes a minute on at most one
  warm instance is small against the grant.
