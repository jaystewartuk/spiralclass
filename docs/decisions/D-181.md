# D-181. A security fix lands as a public pull request with a neutral title, pushed only when it can ship

**Status.** Active.

**What changed.** A fix for a vulnerability lands through an ordinary pull
request on this repository, never through a GitHub security advisory's
temporary private fork. Its title, body and commit subject are neutral: they
name the area and the testing, not how the flaw could be used. Its branch is
not pushed until the maintainer can merge and promote in the same sitting, so a
session writing one commits it and stops short of `pnpm pr`.
[SECURITY.md](../../SECURITY.md#how-a-security-fix-lands) states the rule, and
CLAUDE.md's title convention points at it as the one exception.

**Why.** Two rules in the tree disagreed. SECURITY.md tells a reporter never to
open a pull request for a security problem, because an unfixed vulnerability
described in one is a roadmap for abuse. CLAUDE.md says every change lands
through a pull request. A fix for a privately held finding had to break one of
them, and the window that matters is the time between the fix becoming readable
in public and production carrying it — the flaw is documented and live at once.

The private fork looks like the way to honour SECURITY.md, and GitHub's own
documentation rules it out here: "status checks do not run on pull requests in
temporary private forks", and on merge "GitHub won't enforce any of the
protection rules that you may have set up for the branch you're trying to merge
the changes in to." The pre-push hook would still run the fast tier on the
laptop, but the heavy suites — the only checks that see a real database or a
browser — would first run after the fix was already on `main`. CLAUDE.md's
second rule forbids bypassing the gate; a private-fork merge bypasses it by
construction, and does so on the auth and payment paths where a broken fix
costs the most.

**What was considered and rejected.**

- **The temporary private fork.** It merges past every protection rule and
  every runner check, above.
- **A public pull request under the normal title convention.** The title and
  body narrate the flaw to anyone watching the repository, and the branch is
  public from its first push, however long review takes.
- **A private mirror repository for security work.** It doubles the protection
  rules, secrets and runner configuration that must stay identical to this
  one's, and a divergence would surface at merge time, which is the worst time.

**What it constrains.**

- Never merge a fix from a temporary private fork.
- Never push a security fix's branch early to get a runner's answer. Run
  `pnpm gate --allow-dirty`, and `pnpm gate:heavy` locally when the heavy
  answer is needed before the push.
- The neutral title is for security fixes only. Every other change keeps the
  rule that a title names the problem it fixed.

**What was affected.** `SECURITY.md`, the title convention in `CLAUDE.md`, and
this log's index.

**Trade-offs accepted, and unresolved risks.**

- A neutral title hides nothing from someone reading the diff. The window is
  shortened, not closed.
- "The same sitting" still spans the pull request's heavy run, the merged
  commit's runs and the production deploy, and a Tier 2 change is not promoted
  during lesson hours. At best the window is tens of minutes; a red run
  lengthens it.
- An unpushed fix exists on one machine until it ships.
- Nothing checks that a title is neutral or that a branch was held back. Both
  rest on whoever writes the fix.
