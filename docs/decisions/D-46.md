# D-46. A teacher's lesson template drives AI class-content compose — teacher-owned structure, not a platform curriculum (2026-07-07)

**Status: Active (built, option A — 2026-07-08).** Shipped behind the existing
`class_content` Pro gate, **no migration** (the sub-decision below
resolved to A). Builds directly on [D-17](./D-17.md) (in-house AI class-content compose) and
[D-20](./D-20.md) (class-content inputs are teacher-owned seedable data, **not** a
platform curriculum library). Grew out of an early teacher's method proposal —
see § Origin.

## The question

Alicia Moreno designed a full pedagogical method for her Spanish school with a fixed
internal **module structure** — every lesson follows the same skeleton
(bienvenida → objetivo → situación real → gramática → vocabulario → … → palabras
con intención → reflexión → proyecto → evaluación). Today AI compose (D-17)
generates lessons in a **generic** shape hard-coded in
`lib/class-content/prompt.ts` ("a clear objective, material, worked examples,
practice"). So a generated lesson doesn't come out in _her_ structure, and she'd
have to reshape every one by hand — the exact friction D-17 set out to remove.

The question this decides: how does a teacher's own lesson structure become part
of what AI compose produces, **without** the platform authoring or owning a
curriculum (the D-20 trap)?

## What was decided

1. **A teacher's own lesson template becomes an input to AI compose.** The
   teacher-authored `ClassContentTemplate` (a named Markdown skeleton she already
   creates today) is passed into the compose prompt as the **section structure**
   the model must follow, adapted to the student's level/goals/covered — instead
   of the generic hard-coded shape. This is the whole feature.

2. **Reuse the existing primitive — no new model, no curriculum store.** The
   `ClassContentTemplate` model, its actions, and the template picker on the
   class-content panel already exist (D-17 "task 3",
   manual editor prefill). The only missing wire is _template → AI prompt_. We
   add that wire and nothing structural.

3. **The template is teacher-owned data, never platform content.** We do **not**
   ship "Gramática en Contexto" (or any method) as platform-baked content. Alicia Moreno
   authors her template once in the existing template editor; it lives in _her_
   rows like her focus tags and levels. This holds the D-20 line exactly: the
   platform owns the machinery, the teacher owns the method. A music or math
   teacher uses the same feature with their own template.

4. **Gating unchanged; structure is optional.** Generating with a template rides
   the same `gateProFeature("class_content")` Pro gate and the monthly AI cap as
   D-17; student **viewing stays free**. Picking **no** template is always
   allowed and falls back to today's generic shape — so nothing regresses for a
   teacher who never makes a template.

## Why

- The template already models exactly the thing Alicia Moreno's method needs (an
  ordered, reusable lesson skeleton). It was just disconnected from the AI path.
  Wiring it is the smallest change that delivers her method's structure.
- It keeps the D-20 discipline intact: her structure is a few rows of _her_ data,
  not a curriculum the platform authors and maintains. The moat stays the student
  context the platform already holds (level + goals + interests + covered), now
  poured into _her_ shape.
- It amplifies the shipped D-17 feature rather than adding a parallel system:
  same panel, same gate, same cap, same review-before-save flow.

## Scope (v1)

**Prompt.** Extend `ClassContentPromptInput` with an optional
`templateBody?: string` (the chosen template's Markdown). When present,
`buildClassContentPrompt` instructs the model to follow that section structure in
order, filling each section for the student's level/goals/interests/covered, and
to keep the teacher's section headings. When absent, output is unchanged from
today.

**Compose handler.** `generateClassContentForBooking` takes an optional
`templateId`; it resolves the template body **tenant-scoped** (only the teacher's
own rows — never trust a posted id, mirroring `resolveFocusTagLabels`) and passes
`templateBody` through. An unknown/foreign id resolves to "no template" (silent
fallback, never an error). Bound the injected body length the same way `topic`
and focus tags are bounded, so a large template can't blow the prompt budget.

**Entry point.** Thread the optional `templateId` through
`generateClassContentAction`. It already loads the teacher's templates for the
manual-prefill picker, so the generate control reuses that same list.

**UI.** On the class-content panel (`class-content-panel.tsx`), the AI-generate
control gets a "structure"
selector populated from the teacher's templates, defaulting to her first
template (position 0) if she has any, with an explicit "no structure" option.
This reuses the existing template list already fetched for manual prefill — it's
a second consumer of the same data, not a new fetch.

**Analytics.** Add `usedTemplate: boolean` to the existing
`class_content_generated` PostHog event so we can see method-driven adoption. No
new event.

## What it constrains

- **No platform curriculum.** Do not add seed packs of lesson _templates_ the way
  disciplines seed focus tags — a template is a full authored lesson skeleton
  (her brand/voice), not a neutral taxonomy row. Templates stay teacher-authored.
  (A single optional one-tap "starter structure" suggestion in the editor is
  acceptable as a convenience, but it inserts editable text she owns — it is not
  a maintained platform curriculum.)
- **Optional, never a gate.** No-template must always work and equal today's
  behavior. The template shapes output; it never blocks generation.
- **Tenant scoping is non-negotiable.** The template body is teacher-private and
  resolved only from the teacher's own rows; a foreign id is treated as none.
- Viewing stays free; only authoring/generate sits behind `gateProFeature`
  (unchanged from D-17/D-20).

## Resolved sub-decision (2026-07-08): option A

**How the default template is chosen — resolved to A (explicit pick, defaulting
to position 0, zero migration).** Shipped Tier-1 to `main`. Option B (a sticky
`isDefault` column) stays an additive follow-up if sticky defaults are wanted.
The original options, for the record:

- **A (recommended, zero migration): explicit pick, defaulting to position 0.**
  The generate control defaults to her first template; she can switch or choose
  none per generation. No schema change → this stays a **Tier-1** change (docs +
  UI + prompt), shippable straight to `main`.
- **B: a sticky `isDefault` flag on `ClassContentTemplate`.** One template marked
  the default is auto-applied every generation. Nicer for a teacher with one
  method, but adds a boolean column + migration → touches `prisma/**` → the
  schema-change discipline (`pnpm verify:local` + the migration rules).

Lean **A** for v1: it delivers Alicia Moreno's outcome (she'll have one template, and
it's the default) with no migration, and B is a purely additive follow-up if
sticky defaults are wanted later.

## What it affects

- `lib/class-content/prompt.ts` (new optional input + prompt lines),
  `lib/class-content/handlers.ts` (resolve template, thread it),
  `app/actions/class-content.ts` (new param), and `class-content-panel.tsx`
  (structure selector).
- **No migration under option A.** No payment / auth / booking-state logic →
  **not a Tier-2 path**. Under A it's Tier-1 (straight to `main`); under B it
  touches `prisma/**` and follows the schema discipline.
- **Tests:** prompt builder emits the template structure when a body is present
  and is unchanged when absent; the compose handler threads a valid `templateId`
  and **ignores a foreign/unknown one**; the injected body is length-bounded;
  cross-tenant isolation (a teacher never composes with another teacher's
  template).
- **Orientation:** update `docs/orientation/04-levels-and-materials.md` in
  read-aloud prose when it ships (the standing CLAUDE.md rule).

## Effort

~1–1.5 days under option A (prompt wiring + two entry-point params + the selector
on both panels + tests). The heavy lifting — the template model, its CRUD, the
picker, the Pro gate, the AI pipeline — already shipped with D-17/D-20.

## Origin

Alicia Moreno (first teacher) proposed designing the full "Gramática en Contexto" method
as the content backbone for her school. Analysis (2026-07-07): the _method_ is
hers to author and is high-value as a document, but baking it into the platform
as canned content is the D-20 trap. The one genuinely useful, on-strategy new
capability was letting her method's **structure** drive AI compose — which turned
out to need only wiring the template that already exists. Everything else in her
proposal maps onto shipped primitives (levels, focus tags, student profile,
notebook) or was deferred (automated module unlocking / competency-gated
progression contradicts the teacher-accompanied model in
`LEVEL_MATERIALS_PLAN.md`; new interactive resource types are each a separate
build).

## Unresolved risks

- **One template, many levels.** A single skeleton is applied across A1–C1; the
  model adapts the _fill_ to level, but the _sections_ are constant. If Alicia Moreno
  wants materially different structures per level she authors more than one
  template and picks per class — acceptable for v1, revisit only if it bites.
- **Template quality is the teacher's.** A vague skeleton yields vague structure;
  this is authoring guidance (onboarding/GTM), not an engineering guard.
- **Seeding pressure.** There will be a temptation to "just seed the Spanish
  method template for everyone." Resist it — that's the D-20 line. A per-teacher
  one-tap starter she can edit is the sanctioned convenience if we want one.
