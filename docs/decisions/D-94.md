# D-94. Production cuts over to self-hosted LiveKit; the gated video flags are turned on

> **Narrowed, then reversed, then narrowed again.** The LiveKit half stood
> for production until 2026-09-19, when [D-182](./D-182.md) took production
> back to LiveKit Cloud: the box was terminated for its rebuild and Oracle
> refused every relaunch for capacity. D-182 states what must be true before
> production returns to a box. Preview has held no LiveKit key pair since the 2026-09-16
> addendum at the foot of this file, so preview has no video. The flag half did not:
> [D-114](./D-114.md) turned recording and transcription back off before first
> promotion, [D-131](./D-131.md) turned them back on, and
> [D-135](./D-135.md) made the recording audio-only after the first real class
> produced an 846 MB file.

**What changed.** Two related, explicitly-approved risk acceptances
(2026-07-21), bundled because they land in the same
`config/env/production.runtime.env` change:

1. **Production LiveKit moves off LiveKit Cloud onto the same self-hosted
   Oracle-box deployment preview already uses**
   (`docs/deployment/ORACLE_LIVEKIT_PRODUCTION.md`). `b8a405ba` scoped that
   deployment to preview only, explicitly: "production stays on LiveKit
   Cloud, untouched." That scoping is now reversed — production's
   `LIVEKIT_URL`/`LIVEKIT_API_KEY` point at `wss://livekit.spiralclass.com`,
   the same physical server preview uses. Zero app code changed (the whole
   point of D-16's `VideoProvider` seam and its Phase 1 extension in
   `VIDEO_ARCHITECTURE_AUDIT.md` §21-22). Accepted, not mitigated: the box's
   measured ceiling (~15-20 concurrent 2-participant rooms before packet
   loss, `ORACLE_LIVEKIT_SPIKE.md`) now has to absorb BOTH environments'
   traffic, and the box carries no SLA and a documented Oracle
   free-tier-suspension risk ([D-49](./D-49.md), which had ruled it out for
   anything prod-critical). Accepted at current scale (single teacher,
   preview already proved the box handles real call/recording traffic).
   **Graduation trigger, unchanged from the preview decision:** a second or
   third teacher generating real concurrent load, or the box becoming
   unavailable, is the signal to actually provision the previously-scoped
   dedicated box (Hetzner CX22 or similar) instead of waiting for a bigger
   incident to force it.
2. **`CLASS_RECORDING_ENABLED`, `LIVE_CAPTIONS_ENABLED` and
   `LESSON_INSIGHTS_TRANSCRIPTION_ENABLED` turned on
   in production**, reversing the 2026-07-14 setting that left them off. The
   reasoning behind that reversal is not published here; see
   [D-159](./D-159.md). **What it does NOT change:** the per-student D-22
   insights-consent check (`lib/lesson-notes/consent.ts`) still gates who
   actually gets voice captured for the insights pipeline — a flag flip turns
   the capability on, consent still decides per pair. Captions additionally
   require `DEEPGRAM_API_KEY`/`ANTHROPIC_API_KEY` present in production
   Infisical to do anything (verify against the deployed app's secrets, not by
   grepping this repo) — the flag alone doesn't activate the feature.

**Why it likely changed.** Found while auditing the video/LiveKit stack for
further self-hosted opportunities: the premise that production was "already
self-hosted" was wrong (only preview was), and the premise that
recording/captions/transcription were off for LiveKit Cloud _cost_ reasons was
also wrong — no code in this repo disables a feature specifically for LiveKit
Cloud pricing. With that corrected, both changes were made rather than
narrowing scope.

**What was affected.** `config/env/production.runtime.env` (LiveKit host +
four flags), alongside a bug fix (recording/lesson-audio-capture coupling,
see `lib/video/call-recording.ts`'s `maybeStartLessonAudioCapture`) that
makes the insights-capture path work correctly once
`CLASS_RECORDING_ENABLED` is genuinely toggle-able in production rather than
permanently off. `docs/deployment/ORACLE_LIVEKIT_PRODUCTION.md`'s status section
needs updating to describe both environments sharing the box (tracked
alongside this doc, not restated here to avoid the two going stale relative
to each other).

**Unresolved risks.**

- The Infisical `LIVEKIT_API_SECRET` for production has NOT been updated by
  this change (no credentials access) — production will mint tokens the
  self-hosted box rejects until that secret is set to match the preview
  value. This is a manual step, called out inline in
  `production.runtime.env`.
- No monitoring beyond `docker stats` exists on the box (unchanged from the
  preview deployment) — a real outage on the shared box now affects
  production, not just preview, with no automated alert. `synthetic.yml`'s
  nightly prod-route-render probe is being extended to also hit
  `livekit.spiralclass.com` as a cheap black-box signal, but this is not
  equivalent to real infra monitoring.
- The privacy and consent questions D-21/D-22 raise are not resolved by
  this decision. What gates capture is the per-student D-22 consent record, not
  these flags.

## Addendum, 2026-09-16 — preview holds no LiveKit key pair

**What changed.** Preview holds no LiveKit key pair at all. There is no
`LIVEKIT_API_KEY` in `config/env/preview.runtime.env`, and no
`LIVEKIT_API_SECRET` or `LIVEKIT_API_KEY` in Infisical's `preview` environment.
Production's pair is rotated and is set only in production's scope. Video on
preview shows [D-16](./D-16.md)'s "isn't switched on yet" fallback until
preview's own LiveKit server is decided. This narrows item 1 above: production
keeps the box, and preview stops holding credentials for it.

**Why.** A LiveKit key pair is valid for the whole server it is configured on.
LiveKit cannot scope one to a single environment's rooms, so two environments
sharing one server cannot be kept apart by giving each its own key.

**What was considered and rejected.**

- **A second key pair for preview on the same server.** Preview's pair could
  then be rotated and revoked on its own. It would change nothing about what
  that pair can reach, for the reason above.
- **Preview's own LiveKit server now.** Not rejected, only not decided. It is a
  second box to run, and nothing on preview needs live video before that
  decision is taken.

**What it constrains.**

- Never set a LiveKit key or secret in Infisical's `preview` environment, or a
  `LIVEKIT_API_KEY` in `config/env/preview.runtime.env`, while the only LiveKit
  server is production's. `apps/web/tests/scripts/env-config.test.ts` fails on
  the file. Nothing can check Infisical from the tree, so
  `infra/oracle-box/CUTOVER.md` step 9 carries that half.
- Tooling that needs a LiveKit pair uses production's, read from production's
  scope (`docs/deployment/livekit-activity.sh`).
- Preview gets video back through a server of its own, recorded as a new
  decision. Borrowing production's pair to get it back sooner is not an option.

**Trade-offs accepted.**

- Preview cannot rehearse a call, live captions, recording or transcription.
  The first place a change to any of them meets a real LiveKit server is
  production. No automated suite ran a call on preview before this: the E2E
  suite has no call test, and the visual sweep skips both call routes.
- The rotation restarts livekit-server, which drops any call in progress. It
  is done outside lesson hours.
- This record and the env-file test can only state the Infisical half, not
  verify it. It holds only as long as nobody adds a pair to `preview` by hand.
