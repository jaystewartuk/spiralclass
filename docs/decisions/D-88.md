# D-88. AI-generated materials always assume a one-to-one lesson — a single always-on directive in the shared prompt builders, not a per-form option

**Status: Active.**

**What changed.** A teacher reported that AI-generated materials sometimes
contained group work, pair work, team activities, classroom-management
instructions ("divide students into groups," "walk around the room"), or
plural "the class"/"students" phrasing — all wrong for SpiralClass, which is
one-to-one only end to end (a `Booking` has exactly one `studentId`; there is
no multi-student booking concept anywhere in the schema). Every AI
material-generation call now carries an explicit, unconditional constraint:
exactly one teacher and one student, no group/pair/team activities, and any
activity that would naturally be a group activity gets rewritten into a
one-to-one equivalent instead of just dropped (a group debate → the teacher
and student argue opposite sides and switch; a multi-character role-play →
teacher and student each voice one role; a team quiz → teacher-vs-student or
turn-based).

**Why this shape, not the alternatives considered.**

The task brief for this fix (a teacher-reported bug) listed several
architectural options: a platform-wide default, a teacher-settings field, a
per-generation form option, or a shared prompt-building abstraction. The
codebase already answered most of this:

- **A form option or teacher setting was rejected as unnecessary today.**
  There is nowhere in the product for a class to be anything other than
  one-to-one — the `Booking` model itself only ever has one student. A
  toggle or settings field with a single possible value is UI for a choice
  nobody can make; it would be speculative surface area for a "group mode"
  that doesn't exist yet, which CLAUDE.md's engineering guidance explicitly
  warns against ("don't design for hypothetical future requirements").
- **A shared prompt-building abstraction already existed and was the right
  lever.** All AI material-generation call sites — `generateMaterial`,
  `refineMaterial`, `generateMaterialStream` (class content, library
  material, and the streamed "watch it write" variant) — already route
  through exactly two pure functions, `buildMaterialPrompt` and
  `buildMaterialRefinePrompt`, in `apps/web/src/lib/materials/prompt.ts`
  ("one AI plumbing, two outputs," D-69). The podcast-script builder,
  `buildPodcastScriptPrompt` in `podcast-prompt.ts`, is a deliberate sibling
  (a different job: spoken prose, not Markdown) rather than a caller of the
  other two, so it needed the same directive added separately — but still
  just one function, reused rather than re-derived.
- **So the fix is one new directive function, called from three places.**
  `lessonFormatDirective()` in `prompt.ts` is exported and imported by
  `podcast-prompt.ts` so the wording — and the constraint itself — has
  exactly one source of truth across all four Anthropic call sites in
  `apps/web/src/lib/ai/anthropic.ts`. No API route, UI form, or `handlers.ts`
  orchestration code changed; the constraint applies to every current and
  future caller of those three builders automatically.
- **Always-on, not opt-in.** Unlike the D-78 style directives (tone/learner
  age/variety/custom instructions), which return `""` when unset and are
  genuinely optional teacher preferences, this directive follows the D-80
  vocabulary-difficulty pattern instead: it is **always emitted**, defaulting
  internally to `DEFAULT_LESSON_FORMAT` ("one_to_one") via a switch, because
  there is no "off" state that makes sense for a platform that has no group
  lessons.
- **Placed early in the system prompt, right after the opening framing.**
  Ahead of the subject/target-language rules (D-72) and the format-shape
  rules, on the same reasoning as those: a constraint stated early and
  concretely is more reliably followed than one appended as an afterthought,
  and it should govern every activity description the model writes below it,
  not read as a late caveat.

**What was affected.**

- `packages/shared/src/validators.ts` — new `LESSON_FORMATS` (currently just
  `["one_to_one"]`), `LessonFormat` type, and `DEFAULT_LESSON_FORMAT` constant,
  next to the existing `MaterialTone`/`MaterialVocabulary` enums they're
  patterned after.
- `apps/web/src/lib/materials/prompt.ts` — `lessonFormatDirective()` (new,
  exported), wired into `buildMaterialPrompt`'s and
  `buildMaterialRefinePrompt`'s system arrays; both `MaterialPromptInput` and
  `MaterialRefinePromptInput` gain an optional `lessonFormat` field.
- `apps/web/src/lib/materials/podcast-prompt.ts` — imports and calls the same
  `lessonFormatDirective()`; `PodcastPromptInput` gains the same optional
  field.
- No changes to `apps/web/src/lib/materials/handlers.ts`, the API routes
  (`app/api/materials/generate/stream`) or `app/actions/library.ts` — every one
  of them already calls into the updated builders and inherits the constraint
  with zero code change.
- Tests: `apps/web/tests/materials/prompt.test.ts` (new `describe` blocks for
  `buildMaterialPrompt`/`buildMaterialRefinePrompt`, covering both `forClass`
  branches, the default-when-unset case, and prompt ordering) and
  `apps/web/tests/materials/podcast-prompt.test.ts` (one assertion the
  constraint is always present).
- Docs: this file, and a cross-reference added to
  `docs/product/MATERIALS_TAXONOMY.md`'s "one AI plumbing, two outputs"
  principle.

**Extension point for group classes (future).** If the platform ever supports
group lessons, the blast radius is additive, by design:

1. Add a `"group"` (or similarly named) value to `LESSON_FORMATS` in
   `packages/shared/src/validators.ts`.
2. Add a matching `case` to `lessonFormatDirective()` in `prompt.ts` with
   group-appropriate wording (pair/group work becomes allowed; the
   one-to-one language is dropped for that branch only).
3. Resolve the actual value somewhere real — most likely mirroring the D-80
   vocabulary precedent (`resolveVocabulary`, a `bookings.vocabulary_override`
   per-class field beating a `teachers.material_vocabulary` default): a new
   `Booking`/`Teacher` field, read once in `handlers.ts#resolveSubject` (or a
   booking-scoped equivalent) and passed as `lessonFormat` into the prompt
   input. That also requires the `Booking` model itself to grow a real
   multi-student concept first, which is the actual precondition group
   lessons need — this decision only closes the prompt-side gap, not the
   product's single-student data model.
4. No other call site changes: `generateMaterial`, `refineMaterial`,
   `generateMaterialStream`, `generatePodcastScript`, every API route, and
   every UI form remain untouched, because they never reference
   `lessonFormat` directly — they pass through whatever `resolveSubject` (or
   its future equivalent) resolves.

**Unresolved risks.**

- **This is a prompt-level guardrail, not a hard content filter.** Like every
  other directive in these builders (D-72's language axis, D-78's tone), it
  relies on the model following instructions — there is no post-generation
  validation that scans the returned Markdown for group-work phrasing. A
  determined adversarial custom instruction (D-78's free-text escape hatch)
  could in principle try to override it, same class of risk the language-axis
  and student-name safeguards already carry and mitigate the same way:
  ordering the constraint early and unconditionally, ahead of
  `customInstructionsDirective`, which is explicitly worded to defer to the
  rules stated before it.
- **No eval set.** As with D-87's models and D-78's tone presets, there is no
  golden-output corpus or automated check that generated content actually
  stays one-to-one in practice — only that the instruction is present in the
  prompt (unit-tested) and that it reads correctly to a human. Regressions
  would surface as a teacher report, same as the one that motivated this
  decision.
