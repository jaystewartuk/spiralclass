# D-145. The manual bank-transfer rail is removed; Wise stays

**What changed.** The `bank_account` payout instrument is deleted — the kind,
the 15-scheme per-country registry behind it ([D-124](./D-124.md)), its
checksum validators, the settings form, and the three columns that stored it. A teacher's payee options are now **Stripe** and
**Wise**.

Wise is untouched and stays for three reasons that are properties of Wise, not
of the manual rail in general:

- it **auto-reconciles** through the teacher's own Wise API credentials, so it
  never depended on her confirming a payment by hand;
- it is the fallback in the five countries Stripe refuses a merchant account
  (IN, ZA, NG, ID, IS) and everywhere outside the 44 measured Connect
  countries;
- it still works if her Stripe account goes restricted.

**Why.** [D-143](./D-143.md) made the teacher merchant of record on her own
Stripe account, and on 2026-08-31 that account started presenting **SPEI** at
checkout — `payment_method_types: ["card", "oxxo", "customer_balance", "link"]`
on a live session, verified end to end.

Mexico's bank transfer was therefore being offered **twice on the same page**:
once by Stripe, confirming automatically, and once as a `bank_account`
instrument the student self-attested and the teacher confirmed by hand. Same
rail, two flows, different reliability, and no way for a buyer to tell which
one was "right". The worse copy is the one that goes.

`bank_account` was never merely slower. It was **permanently** teacher-confirmed
— no retail bank exposes a per-teacher statement API to reconcile against,
which D-124 recorded as a property of the instrument rather than a gap that
would close. Stripe closed it from the other side.

**Why not keep it dormant.** Because carrying an unused rail is a parity tax
already diagnosed and priced. The surface is not small: ~55 files,
a 1,000-line registry with its 491-line test, a Postgres enum, three columns,
four CHECK constraints, per-country payee forms on two clients, and 120 i18n
keys across three catalogs. Every one of those is read, maintained and reasoned
around by anyone touching payments — and this session alone produced three real
bugs that came from payments having two of everything.

**What was NOT removed, deliberately.**

- **`PaymentRail.bank_transfer`** stays in the enum. Nothing writes it; rows
  written before today carry it and must not be reinterpreted.
- **`TeacherPayoutInstrument`** stays, with `kind` a one-member enum. The union
  is what a second kind would return through, and dropping it would make
  `kind` a column that says nothing.
- **The legacy wire keys** — `schemeId`, `schemeName`, `bankName`, `clabe`,
  `clabeFormatted`, `schemeOptions`, `details` — are held at constant nulls and
  empties rather than deleted, because a key that vanishes is a wire-contract
  change no surface baseline catches.
- **The rule that a payee value is validated in shared code every caller runs.**
  That outlived the registry it was written for. If a kind is added back it
  comes with a validator, never a free-form text box: an unvalidated payee
  field on a page someone pays from is the one place this rail loses real money
  with no way back.

**The migration asserts its precondition rather than assuming it.** Dropping
the enum value means deleting every row that holds it, and a `payments` row
must name an instrument (`payments_instrument_required_for_manual_transfer`),
so a payment attached to a `bank_account` cannot survive the drop. The
migration therefore `RAISE EXCEPTION`s if one exists rather than deleting it —
the deploy stops with the money history intact and someone decides
deliberately.

⚠️ **The guard fires on both preview AND production, and the second was a
wrong call in the first version of this document.**

Preview tripped it on the first deploy attempt, exactly as expected: #954,
merged the same morning, added a `sofia-spei` hero and a multi-rail hero whose
students' seeded manual-transfer payments reference a `bank_account`. Those
fixtures are removed here; an existing preview database still holds the rows
and must be re-seeded first.

**This document originally said "Production is unaffected (measured: zero)".
That was wrong.** Production holds payments attached to an `mx_clabe`
instrument — abandoned internal test checkouts, each `pending` with a null
`paid_at` and no bookings.

The error is worth more than the fix. "Measured: zero" came from PostHog's
`payment_received`, **which only fires on a PAID payment** — a manual transfer
that a student starts and never completes emits nothing at all. So the event
stream said zero while the database held two, and the two the guard cares about
are precisely the kind the event stream cannot see. An event stream is a record
of what happened; a foreign key is a record of what EXISTS, and a migration
guard asks the second question. Check the table.

Neither row carries money, so the cleanup is a deliberate delete of two
abandoned checkouts before the promote — not a data migration.

**Costs, stated.**

- **A teacher in IN, ZA, NG, ID or IS now has exactly one rail**, Wise, where
  she previously had two. If she cannot or will not use Wise, she cannot be
  paid at all.
- **Re-adding a country's bank account is no longer a registry row.** D-124's
  central achievement was making that a shared-package edit rather than a
  migration; restoring it would mean restoring the migration too.
- **Stripe becomes a single point of failure for a teacher with no Wise
  instrument.** Recoverable — she can add one — but nothing prompts her.
- **Nobody has taken the reverse measurement.** No student has ever been
  offered a choice between Stripe's SPEI and a manual one, so "the duplicate
  was costing conversion" is an argument from the shape of the page, not from
  a funnel.
