# D-16. Own the in-class video call behind a provider seam (LiveKit), so the live-notes panel can overlay it

**Status: Active** (web; step 3 of the in-class co-pilot — see
`live-notes-panel.md`).

**What changed.** SpiralClass now owns an in-class video call, reversing the
launch-era stance that classes happen on WhatsApp with "no meeting link to
surface". The differentiated reason to own video is the one the live-notes design
named: on a single screen you can't comfortably show the WhatsApp call _and_ the
panel, so owning the call lets the panel **overlay** it. That overlay — the
teacher's private cues, or the student's instructions, sitting on top of the
video — is the whole point; the media transport is commodity.

**What was decided.**

1. **Media transport sits behind a `VideoProvider` seam** (`lib/video/provider.ts`),
   not called directly from the UI. The call page is handed a `{ url, token }`
   grant and knows nothing about who issued it.
2. **LiveKit is the provider**, chosen because it is the only option that is
   optimal _long-term_: start on **LiveKit Cloud** (managed TURN, recording,
   scaling), and self-host the **same** open-source server later — behind the
   same interface, with the same client SDK and app code, no media-layer rewrite.
   Pure peer-to-peer would be cheaper today but caps at 1:1 and makes recording
   and group classes painful; a self-hosted SFU+TURN is right only at scale.
3. **The call is a Pro live surface**, gated exactly like present mode and the
   realtime panel via `gateProFeature(teacher.id, "lesson_notes")` (D-15). For a
   student, the call rides the _teacher's_ plan: a student of a Free teacher is
   told it isn't enabled, never shown an upgrade prompt (not their purchase).
4. **The room is keyed by booking id** (`class-<bookingId>`); tokens are minted
   per page visit, short-lived. No new table — the booking _is_ the room.
5. **Student call access mirrors the teacher's** — gated only by the teacher's
   Pro plan + LiveKit being configured, _not_ by a time window. Either party can
   join whenever the class is on the calendar (e.g. a few minutes early), so the
   surfaces are symmetric. The student's _written instructions_ are still only
   revealed inside the class window (D-15) — joining early shows the call without
   leaking notes the teacher prepped ahead. (Originally the student call was also
   window-gated. That was lifted: a button leading to an "opens shortly before"
   wall was poor UX with no real benefit — the room is per-booking and simply
   empty until the other party joins. The student class page renders the join
   button when the call is genuinely available for the booking — the class is
   scheduled, the teacher is on Pro, and LiveKit is configured — so a Free
   teacher's student sees the live-notes card without a dead button, the same two
   checks the call page itself enforces.)

**Why.**

- _Seam over direct calls:_ the differentiated work (panel overlay, gating, room
  lifecycle) is ours and stable; the transport is swappable. Keeping it behind an
  interface means the expensive, hard-to-reverse infra choice (cloud → self-host,
  or a different provider entirely) never touches the product code.
- _Graceful degradation:_ with no LiveKit keys configured the call page shows a
  friendly "video isn't switched on yet" message instead of erroring — the same
  pattern as the AI summary without an Anthropic key. So dev, tests, and a
  not-yet-provisioned prod all behave.

**What it constrains.**

- Don't call a media SDK directly from a page or component — add an implementation
  of `VideoProvider` instead. The call UI must stay provider-agnostic.
- The websocket URL travels in the per-call grant, **not** a `NEXT_PUBLIC_` env —
  it's paired with the short-lived token and never a build-time constant.
- `livekit-client` is browser-only; the call UI loads with `ssr: false` (via
  `class-call-client.tsx`). Don't import it into a server component.

**Unresolved risks.**

- **TURN for hard NATs.** LiveKit Cloud provides TURN; a future self-host must
  stand up its own TURN, or a minority of participants behind symmetric NATs
  won't connect. Not a problem on Cloud; flagged for the self-host migration.
- ~~**Notifications still say "no meeting link".**~~ Resolved (follow-up): the
  confirmation + reminder **emails** now swap the "we meet on WhatsApp" line for a
  "Join video call" button when the call is available for that booking (LiveKit
  configured + teacher on Pro), decided in the dispatcher via `callJoinSuffix`.
  WhatsApp templates stay unchanged — Meta's approved structure is locked — so the
  join link is email-only for now.
- **Recording, waiting rooms, and group (multi-party) calls** are unbuilt. The
  1:1 path is the slice; LiveKit supports the rest when there's evidence to build
  it.
- **Media is unverified in CI.** The connection logic follows the livekit-client
  API and passes typecheck + a production build, but real audio/video needs
  on-device QA with LiveKit keys set.
