# D-95. Production DB safety net moves from a pg_dump-to-R2 deploy gate to Neon-native PITR + pre-migration checkpoint branches

**Status: Active (built).**

**What changed.** The pre-deploy production database safety net stops being a
`pg_dump -Fc` → verify → upload-to-Cloudflare-R2 step that blocked every
promote and every production deploy (`backup-prod-db.yml`, previously a
required dependency of both `promote.yml` and `fly-deploy.yml`'s `production`
job). It's replaced by two Neon-native mechanisms:

1. **Point-in-time restore (PITR)** — always-on, no workflow step required.
   Neon retains WAL history continuously for every branch; any point within
   the project's plan-dependent retention window is recoverable via instant
   branch restore.
2. **A named pre-migration checkpoint branch** — `fly-deploy.yml`'s
   `production` job now runs `infra/database/scripts/neon-checkpoint.sh`
   (wrapped as `.github/actions/neon-checkpoint`) immediately before `Apply
database migrations`, creating a copy-on-write Neon branch
   (`pre-deploy-<timestamp>-<sha>`) off `production`. Old checkpoints beyond
   the most recent 5 are pruned in the same step. This is the fast,
   reliable, _discoverable_ restore point PITR alone doesn't give you — no
   need to hunt an exact timestamp during an incident.

   > **Amended 2026-08-09.** Retention shipped at 20, above the production
   > Neon project's per-project branch ceiling of 10 — checkpoints would have
   > accumulated until `branches create` failed with "branches limit
   > exceeded", and because this step fails closed and runs first, that would
   > have blocked production deploys outright. Retention is now **5**
   > (defined identically in the script and the composite action, pinned by
   > `apps/web/tests/config/neon-checkpoint-retention.test.ts`), the script
   > reads the project's real branch limit and refuses up front if retention
   > no longer fits, and checkpoints are created with `--no-compute`, since a
   > restore point needs no endpoint until someone restores from it.

`backup-prod-db.yml` is **not deleted** — it's demoted to
`workflow_dispatch`-only, decoupled from every deploy path, kept as an
optional off-Neon-platform DR copy for the cases PITR genuinely doesn't cover
(a Neon-account-level incident, or recovery past the plan's retention
window). Restoring is now `infra/database/scripts/neon-rollback.sh` — lists
checkpoint branches or accepts an arbitrary timestamp, restores via Neon's
`branches restore` (seconds, auto-preserving the pre-restore state as its own
backup branch) — rather than a `pg_restore` cycle.

**Why it likely changed.** The R2 pg_dump step was designed for Supabase,
which (per the original comment in `backup-prod-db.yml`) had no native
backup/PITR product wired into this project. The D-70 Fly + Neon cutover
changed that — but the deploy-gating dump step was never revisited after the
cutover actually happened, so production kept paying a slow, disk-bound
dump/upload on every deploy for protection Neon's own PITR + branching now
give faster and more reliably, with a smaller failure surface: pg_dump
requires its client major version to be ≥ the server's, which already broke
this exact workflow once, silently, at the worst possible moment — the day
of the Neon cutover itself (2026-07-20), when the server jumped to PG 18. A
Neon branch has no such constraint. Also fixed in the same pass: the R2
backup ran _twice_ per promote (once in `promote.yml`, again when the
resulting push triggered `fly-deploy.yml`) even though `promote.yml` itself
never touches the database — `promote.yml` only fast-forwards a branch
pointer; the migration only ever runs in `fly-deploy.yml`'s `production`
job. That redundant dependency is removed; `promote.yml` no longer has any
database-safety step of its own.

**What was affected.**

- `.github/workflows/backup-prod-db.yml` — trigger narrowed to
  `workflow_dispatch` (dropped `workflow_call`); header comment rewritten to
  describe the new secondary/optional role.
- `.github/workflows/fly-deploy.yml` — `backup-prod-db` job removed; its
  `production` job gains a "Checkpoint production on Neon" step before
  migrations, via the new `.github/actions/neon-checkpoint` composite action.
- `.github/workflows/promote.yml` — `backup-prod-db` job and its `needs`
  dependency removed entirely (redundant, as above); header comments rewritten
  to point at the new mechanism.
- `.github/actions/neon-checkpoint/action.yml` — new composite action, thin
  wrapper around the script below so CI and a human running it by hand share
  one implementation.
- `infra/database/scripts/neon-checkpoint.sh` — new; creates + prunes
  checkpoint branches via `neonctl`.
- `infra/database/scripts/neon-rollback.sh` — new; lists checkpoints and
  restores a target branch via Neon's instant restore.
- `docs/deployment/DB_BACKUP_RESTORE.md` — rewritten: Neon PITR + checkpoint as
  primary, R2 dump as secondary/fallback, updated rollback procedure.
- `docs/ops/PRODUCTION_CUTOVER.md`, `D-70.md` — status notes added
  confirming the Fly+Neon cutover is in fact executed (it was, but neither
  doc had been updated to say so — see the evidence trail in
  `DB_BACKUP_RESTORE.md`).

**Unresolved risks.**

- **New repo secrets required, not yet provisioned by this change:**
  `NEON_API_KEY` and `NEON_PROJECT_ID` (production). The checkpoint step
  fails closed without them — the very next production deploy after this
  merges will block on `Checkpoint production on Neon` until an operator sets
  both. This is deliberate (silently skipping the safety net is the failure
  this whole redesign exists to prevent), but it is a real, immediate
  operational dependency, not a someday cleanup item.
- **The production Neon project's plan/PITR retention window is unconfirmed
  in these docs.** Whether production has 6h (Free), 7d (Launch), or 30d
  (Scale+) of continuous PITR coverage materially affects how much the
  checkpoint-branch pruning window and the R2 fallback actually matter.
  Confirm and record it in `DB_BACKUP_RESTORE.md`.
- **Neither `neon-checkpoint.sh` nor `neon-rollback.sh` has been exercised
  against a real Neon project yet** — written and syntax-checked, not run
  end-to-end. Do a real dry run (checkpoint a scratch branch, restore it,
  verify) before trusting this under incident pressure, same caveat the
  previous R2-based runbook carried and never closed.
- **`backup-prod-db.yml`'s standalone dispatch still needs `PROD_BACKUP_DB_URL`
  pointed at Neon** (it may still point at the pre-cutover Supabase
  connection string, per the ambiguity this decision also resolves in
  `PRODUCTION_CUTOVER.md`) — no deploy depends on it anymore, but a stale
  target would make an operator's manual DR dispatch quietly useless.
