# D-136. Closing an account destroys its recordings

**What changed.** `anonymizeTeacher` now calls `purgeTeacherRecordings`, which
deletes the R2 objects and rows for a closing teacher's `CallRecording` and
`LessonAudio`, plus her `LessonTranscript` and `LessonSummary` rows. The
retention table in `packages/shared/src/legal/privacy-policy.ts` gains the two
words that make it true — "then deleted with it" — and its "live class audio and
video" row now says a recording is audio only ([D-135](./D-135.md)).

**Why it likely changed.** The policy already promised this and the code did not
do it. Since [D-131](./D-131.md) the published retention table has said a class
recording and its transcript are kept "while the teacher's account is open", and
D-131's own unresolved risks named the gap in plain words: _"nothing purges
recordings from R2 on account closure."_ It shipped anyway, correctly — the
capability mattered more than the cleanup, and there were no recordings yet.
There are now. `anonymizeTeacher` touched the teacher row, device tokens and
notifications and nothing else, so every recording, every per-speaker audio file
and every transcript outlived the account indefinitely.

That is the whole reason. It is a promise-keeping change, not a new policy: no
retention _period_ is introduced here, because the policy does not state one and
inventing a number is the operator's call, not a refactor's.

**What was affected.** A new
`apps/web/src/lib/account-deletion/purge-recordings.ts`, wired into
`anonymizeTeacher` after its transaction, plus the two retention rows. No schema
change and no migration — every one of the four models already carries a
denormalized `teacherId`, so the purge is four `where: { teacherId }` queries.

Two properties are load-bearing and are asserted directly in tests rather than
left to review:

- **Storage first, row second, one object at a time.** The row is the only
  pointer to the object. Deleting it while the object survives would strand a
  recording in R2 with nothing left to find it by — the exact opposite of what
  this function is for. A row whose object could not be deleted is deliberately
  left in place. And the objects go one call at a time because the storage
  provider's `remove` aborts a batch on its first failure, which would strand
  every key after the failing one.
- **The purge cannot block a deletion.** It runs outside the transaction and
  inside a `try`/`catch`. A user who has waited out the 30-day grace window
  should not have their deletion fail because R2 was unreachable, and throwing
  would also skip the session revoke that follows it.

**Unresolved risks.**

- **Nothing retries a partial purge.** The request is marked complete either
  way, so an object R2 refused to delete stays in the bucket until a human reads
  the `recording purge left objects behind` error line. A retry queue was
  rejected as machinery nobody would watch — the same reasoning
  [D-129](./D-129.md) applied to schedulers — but this is a real hole and it is
  logged at error level for that reason.
- **Student deletion purges nothing.** The recordings belong to the teacher's
  account and the policy row is teacher-scoped, so this is consistent with what
  is published — but a student who leaves the platform leaves her voice in her
  ex-teacher's recordings, and no one has decided whether that is right. It is
  named here rather than settled.
- **Still no retention period.** A recording on an OPEN account is kept forever
  by policy and by code. That is what the policy says today; whether it should
  say ninety days, or a year, is a question for the operator, and it is the
  obvious next decision after this one.
- **The better-auth `user` row is still a manual operator step**, unchanged by
  this and noted in `anonymize.ts`'s own header.
