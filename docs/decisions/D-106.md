# D-106. Live class captions move to a server-side LiveKit Agent

**What changed.** Ordinary scheduled classes' live captions move off the fully
client-driven design (each participant's browser/phone opens its own
Deepgram WebSocket, calls Anthropic, publishes over a hand-rolled data
channel) onto a new server-side worker, `packages/livekit-captions-agent`,
deployed on the self-hosted LiveKit box (`infra/oracle-runner`, co-located
per the audit's Oracle-ceiling addendum — confirmed 2 OCPU/12GB, one live
teacher today leaves headroom). This supersedes D-27's "serverless can't
host a long-lived worker" constraint, which stopped being true once the
Oracle box existed (D-94).

- **Runtime**: Node.js/TypeScript built directly on `livekit-server-sdk` +
  `@livekit/rtc-node` (not the full `@livekit/agents` framework, which pulls
  `fluent-ffmpeg`/OpenTelemetry/`openai` this job never needed) — confirmed
  `@livekit/rtc-ffi-bindings-linux-arm64-gnu` exists on npm, so the box's
  arm64 arch is fully supported. The Agent polls
  `RoomServiceClient.listRooms()` every ~3s for new `class-*` rooms (same
  pattern `packages/livekit-activity-cli` already uses), joins with its own
  identity (`captions-agent`), and per room: subscribes to each
  participant's mic track, runs one reconnecting Deepgram stream per
  participant, calls the app's new internal API for consent/language config
  and translation, and publishes the translated line addressed to the
  listener only.
- **Business logic stays server-side in the Next.js app**, not duplicated:
  two new shared-secret-authenticated routes,
  `apps/web/src/app/api/internal/captions/{room-config,translate}`, reuse
  the exact existing `directionForBooking`/`captionsPublishConsentOk`/
  `liveCaptionsEnabled`/`gateProFeature`/`translateCaption` functions. The
  Agent polls `room-config` every ~60s per room, closing a real gap the old
  design had (consent was only ever checked once, at token-mint time).
- **Toggle-gated processing, not continuous** (a real fork surfaced and
  confirmed mid-build, not an incidental default): a naive Agent design
  would transcribe both parties for a room's entire duration once
  consent+entitlement allow it — a real expansion of when audio leaves the
  box, beyond what the existing consent language (PR #702) describes.
  Instead, the client sets a LiveKit participant attribute (`captionsOn`) on
  toggle; the Agent only opens a Deepgram session for a participant while
  that attribute is `"true"` AND consent/entitlement hold — audio frames are
  still always read off a subscribed track (the API requires a continuous
  consumer) but nothing is forwarded to Deepgram unless every gate is open,
  preserving today's exact processing scope.
- **Wire protocol bump** (`packages/shared/src/captions.ts`): every
  `CaptionMessage` now carries a required `for` field (the recipient's
  LiveKit identity). Before the Agent, a room always had exactly 2 human
  participants and LiveKit never echoes a publisher's own data back to
  itself, so "whatever arrives on this topic must be the other side's line"
  held by construction. The Agent is a third room participant, breaking that
  assumption — receivers on both platforms now filter on
  `msg.for === myOwnIdentity`.
- **Straight cutover, no dual-path fallback shim**: `class-call.tsx` no
  longer calls `useCaptionPublisher`; the class-specific token/translate
  routes are deleted outright (`/api/captions/{token,translate}`), along with
  the now-dead `resolveClassCallViewer` export.
  Given only one teacher is live today, the accepted risk is a brief window
  where captions simply don't appear if the Agent isn't yet running in a
  room (no error — the receiver just never gets a message) — not a
  permanent fallback path to maintain. **The other two-way call surface is
  explicitly out of scope and stays client-driven** — `useCaptionPublisher`
  stays alive for that flow, updated only for the new `for` field (addressed to "whichever other participant is in
  the room," since that flow is always exactly 2 people).

**Why it likely changed.** The audit found the client-driven design was the
slowest and least reliable option LiveKit supports (~1-2s latency, no
Deepgram-socket reconnect logic, a real dual-mic-capture risk), all
consequences of a 2026 constraint (no long-lived worker host) that no longer
holds. the operator confirmed high appetite for the migration conditional on staying
free/self-hosted, then confirmed the Oracle box has headroom to co-locate
the Agent rather than needing new infra spend.

**What was affected.**

- New package `packages/livekit-captions-agent` (Node/TS, own `package.json`/
  `Dockerfile`/tests).
- `packages/shared/src/captions.ts` — `for` field added to the wire protocol
  (breaking change, coordinated with both clients in the same effort).
- `apps/web/src/lib/captions/{class-access,internal-auth}.ts` (new/changed),
  new `apps/web/src/app/api/internal/captions/*` routes, new
  `CAPTIONS_AGENT_SHARED_SECRET` env var (`apps/web/src/lib/env.ts`).
- `apps/web/src/lib/captions/use-live-captions.ts` (publisher narrowed to
  the one remaining client-driven flow) + `apps/web/src/components/video/class-call.tsx` (publisher
  call removed, attribute-set added to the toggle).
- The dual-mic-capture risk is **reduced, not eliminated** — it no longer fires
  for ordinary classes (the common case) but still exists for the smaller,
  bounded surface that keeps
  the client-side publisher.
- `infra/oracle-runner`: `docker-compose.livekit.yml` became
  `docker-compose.livekit.yml.tftpl` (new `captions-agent` service) with two
  new Tofu variables (`deepgram_api_key`, `captions_agent_shared_secret`),
  both sourced from Infisical's `infra` environment like the existing
  `livekit_api_key`/`livekit_api_secret`.

**Unresolved risks.**

- **No real deploy has happened.** Same blocker as the box's own OpenTofu
  module: this session had
  no Tailscale/SSH/OCI credentials. Code, infra config, and a Dockerfile are
  ready; the actual `docker compose pull && up -d` on the live box, and a
  real two-device test, are still outstanding.
- **The Dockerfile is unverified** — no Docker daemon was available in this
  sandbox to actually build it. It mirrors the proven root `Dockerfile`'s
  pnpm-monorepo pattern closely but hasn't been built for real, let alone for
  `linux/arm64`.
- **New Infisical secrets were prepared but not written** — the auto-mode
  classifier blocked the `infisical secrets set` calls for
  `TF_VAR_deepgram_api_key` / `TF_VAR_captions_agent_shared_secret`
  (production-secrets write, correctly requires explicit human approval).
  The values are known (production's existing `DEEPGRAM_API_KEY`; a freshly
  generated shared secret) but need to be added by the operator, along with
  `CAPTIONS_AGENT_SHARED_SECRET` on the app side (production environment).
- **A pre-existing gap, discovered while checking Infisical for this work**:
  `TF_VAR_livekit_api_key`/`TF_VAR_livekit_api_secret` — which the box's
  OpenTofu module already expects — are **not actually present** in Infisical's `infra`
  environment either. This blocks `tofu apply` regardless of anything in
  this change; it isn't something this PR introduced, but it needs fixing
  before _any_ re-apply of this module succeeds.
- **The Agent only correctly serves PRODUCTION class calls.** Preview and
  production share this one physical box (same `LIVEKIT_API_SECRET` in
  both Infisical environments) but have separate Neon databases: the Agent's
  `APP_INTERNAL_BASE_URL` is hardcoded to `https://spiralclass.com`
  (production), so a preview booking's room-config lookup would 404 against
  production's database. Given only one teacher is live in production today,
  this is an accepted v1 scoping gap, not a silent bug — but it means
  captions can't currently be manually QA'd against preview traffic the way
  most other features are.
- **P6 (admin-visible health check for a misconfigured Deepgram key on the
  box) remains deliberately deferred**, per the audit's own sequencing —
  no existing admin-portal hook for box-side service health exists yet.
- Phase B (native `lk.transcription`, dual-language, timestamped display) is
  intentionally not part of this change — sequenced as an immediate
  follow-on once this Agent is confirmed stable in a few real classes.

**Addendum (2026-07-26): confirmed live end-to-end on preview, translate
route removed for latency.** The Agent shipped, and a real two-device
preview test (teacher + student, LiveKit grant + secrets fixes below)
confirmed captions work end-to-end. Two real bugs surfaced only through that
live test, neither catchable by unit tests against fakes:

- `localParticipant.setAttributes({ captionsOn })` was being rejected by the
  LiveKit server (`SignalRequestError: does not have permission to update
own metadata`) because the minted token grant (`LiveKitProvider.mintToken`,
  shared by every call surface) never included `canUpdateOwnMetadata`.
  The toggle updated client-side state but never reached the server, so the
  Agent could never see it. Fixed by adding the grant.
- The Agent reconnecting into an **already-active** room (its own restart,
  not a fresh room) could miss `RoomEvent.TrackSubscribed` for tracks
  published before it connected. `RoomWorker.start()` now also sweeps
  `room.remoteParticipants`/`trackPublications` directly after `connect()`
  for anything already subscribed, deduped against the event-driven path.

New per-utterance timing logs (`utterance_timing`, `final->translatedMs`)
showed the Anthropic translate call was ~100% of total latency (avg ~890ms,
up to 1.7s) — Deepgram finalization and the LiveKit publish itself were both
negligible by comparison. Since translation (unlike `room-config`) has no
DB/consent/entitlement dependency, routing it through
`/api/internal/captions/translate` was a second network hop (box → Fly →
Anthropic) for no reason. That route is now **removed**; the Agent calls
Anthropic directly (`packages/livekit-captions-agent/src/translate.ts`,
mirroring the app's prompt/model/fallback-latch logic, duplicated rather
than shared since this package doesn't depend on `apps/web`). The Agent
needs its own `ANTHROPIC_API_KEY` (+ optional `ANTHROPIC_MODEL`/
`CAPTION_TRANSLATION_MODEL` overrides) — a new box-side secret, same
two-copy-no-automated-sync pattern as `DEEPGRAM_API_KEY`. `room-config`
stays app-routed — it's genuinely DB-backed business logic, not just an
API passthrough.

An on-box/local translation model (no third-party call at all) was
considered and rejected for now: the box is a 2 OCPU/12GB Oracle Always-Free
instance already shared with `livekit-server`/Egress/Redis at a stated
"headroom is fine for one teacher, revisit if concurrency grows" ceiling: a
local MT runtime (e.g. quantized NLLB-200 or per-pair OPUS-MT via
CTranslate2/ONNX) would add real CPU/RAM contention risk and a new
model-asset/quality-testing surface, for a product that already supports
many language pairs. Worth revisiting if concurrent-room volume ever
justifies dedicated capacity for it.
